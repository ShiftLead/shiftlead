# TD-2077: Comparing flows needs its metrics recorded from the start

## What it does
Each entry's stage record, the file the home keeps per entry on the repo's state branch, also keeps what a
later comparison of one flow against another needs. Every time a session's part in an entry ends, however it
ends, the record notes which model, tool, tool version and login that session ran on, what it spent, how many
questions it put to you, and which version of the flow it ran under. Lost sessions, every question the home
asks you (the merge gate's among them), limits reached and a review's count of findings each leave a mark. A
closed record is moved to a kept copy after thirty days instead of being deleted. A table in the design says
where each reading is.

## The key choices, and why
- One store: the readings live on the entry's own record, which no rule acts on, so nothing new is kept
  elsewhere and nothing about how entries move changes.
- A flow's version is a fingerprint of its definition and of each stage's instructions exactly as its session
  receives them, and the text behind each fingerprint is kept, so runs before and after an edit can be told
  apart.
- A stage's session reads its tool's version when it starts, as a seat does, where its tool can report one.
- The spend written when a stage ends is a floor; the comparison reads it again from the home's spend file,
  kept thirteen months, which has the session's last turns.
- Each session's spend is counted once: a session that leaves two marks at one ending puts its spend on one,
  and a stage entered again under a reused session name counts only what it spent since.
- A review stage gives two counts, every finding and those it would not ship with, which stand in for the
  finding classes a design's review rounds have. The build that adds them lands after the one that adds the
  rest, since both change the same mark.
- Closed records are copied, not read from the branch's history, so a comparison reads plain files.
- All three builds land before the switch-over window, since it waits on this design.

## What it rules out
- Audits and the jobs of the seats for pull requests and board answers record none of this: a comparison
  reads entries alone. A review of a job's pull request is still to be built, and records none either.
- Defects a build or a review let through are not counted: the ledger marks only a design's misses.
- A follow-up entry is not linked to what it follows.
- Per-stage cost, time, questions and losses have no baseline from before the switch-over; cost per entry
  and review comments do.
- Which login a session ran on reads empty until sessions start on logins (TD-2068, TD-2069).
- The comparison itself is later work (TD-2078).

## What you will see
Nothing changes on any page. A review stage's session is told to give its two counts when it ends, and the
review comment it leaves carries the real count. A session that repeats its last step is told where the
entry is now.
