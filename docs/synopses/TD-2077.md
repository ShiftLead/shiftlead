# TD-2077: Comparing flows needs its metrics recorded from the start

## What it does
Each entry's stage record, the file the home keeps per entry on the repo's state branch, also keeps what a
later comparison of one flow against another needs. Every time a session's part in an entry ends, however it
ends, the record notes which model, tool, tool version and login that session ran on, what it spent, how many
questions it put to you, and which version of the flow it ran under. Lost sessions, every question the home
asks you (the merge gate's among them), limits reached and a review's count of findings each leave a mark. A
closed record is moved to a kept copy after thirty days instead of being deleted. A table in the design says
where each reading is.

## The key choices, and why
- One store: the readings live on the entry's own record, which no rule acts on, so nothing about how entries
  move changes.
- A flow's version is a fingerprint of its definition and of each stage's instructions, and the text behind
  each fingerprint is kept, so runs before and after an edit can be told apart. A release that changes a
  standard stage instruction is a new version of every flow using it; where an instruction cannot be read,
  the version is unknown. A stage's session reads its tool's version when it starts, as a seat does.
- Each session's spend is counted once, from the home's one spend reader: a name can come back, so each start
  notes what the name had spent and a run counts what it added. Where that cannot be read, or comes out below
  zero, it is unknown; a refused start's spend is on no run. Money is kept apart by kind, day by day, so a
  subscription's estimate and a metered bill are never added together.
- The spend written when a part ends is a floor that can miss about its last minute. Reading it again later
  is left to the comparison work (TD-2078), whose rule kept reopening here; each row keeps what that needs.
- A stage's name is at most 20 characters when a flow is saved, so each stage's session keeps a name of its
  own; a flow saved before that rule keeps running.
- A review stage gives two counts, every finding and those it would not ship with. All three builds land
  before the switch-over window, and closed records are copied, so a comparison reads plain files.

## What it rules out
- Audits and the seats' jobs for pull requests and board answers record none of this; a job's review comment
  carries its real count of findings.
- Defects a build or a review let through are not counted, and a follow-up is not linked to what it follows.
- Per-stage cost, time, questions and losses have no baseline from before the switch-over.
- Which login a session ran on reads empty until sessions start on logins (TD-2068, TD-2069).
- The comparison itself, and any second reading of a run's spend, is later work (TD-2078).

## What you will see
Nothing changes on any page, except that a flow with a stage name over 20 characters is refused when saved.
A review stage's session is told to give its two counts when it ends, and its review comment carries the
real count. A session that repeats its last step is told where the entry is now.
