# TD-1720: What a design's author prepares before a review: the checklist, the prep file and the gate

## What it does

Before any reviewer reads a design here, its author has done three things. They drafted against a short checklist
of the situations designs here miss. They declared, in a prep file beside the review record, what the design claims
about existing code, the rules it states in more than one place, the files its builds will create, and any false
alarms. And they ran a script that checks the design against that file at the exact commit a reviewer will read.
Every reviewer runs the same script first and stops unread if it fails. This is part of the cheaper way to design
(TD-1711), for the trial TD-1722 runs; it lives in this repo's designer brief and one script.

## The key choices, and why

- The checklist is fifteen questions drawn from past review findings, placed by how often each situation needed a
  design review to catch it, so eleven go to the hard ones: interactions, two things at once, timing, endings, who
  acts, failures and restarts.
- It leaves out the findings of the three designs the trial replays, so a replay never meets its own answers. You
  picked them: TD-1557, TD-1569 and TD-1470; only TD-1470's findings are in the analysis the checklist draws on,
  so those are the ones left out.
- The author names the terms of each repeated rule (your lean); nothing is inferred. When a fix changes a term, the
  script names every place still saying the old one.
- Of 510 past findings a script could catch, two judges reckon at most 225 would have been, and all but 9 only
  because the author declared the rule or claim. That is hindsight, so the trial measures the real rate.
- Reviewers run the script themselves, so the gate does not rest on the author's word. A false alarm is waived in
  the file, where the fact-check sees it; a waiver on a rule names that rule and one paragraph.
- The gate is decided once per design and noted on its entry; designs already in their rounds are left as they are.

## What it rules out

- No reviewer reads a design that fails the script, except when the script itself cannot run.
- The script runs no command the author wrote; counts are plain file and line counts.
- No wider checks of ledger fields or PR numbers: they would have caught three findings in all.

## What you will see

- One decision: whether the builds go ahead after four rounds that ended at the cap.
- Then three builds: the script, the designer brief's steps, and the checklist.
