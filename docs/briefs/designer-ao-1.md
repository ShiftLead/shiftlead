**A design PR writes the design's synopsis** (design §4.9c *The designer writes the synopsis*). **How a change lands here.** Branch in this worktree → PR → an independent review by the repo's `review-model` (code: round one's reviewer, `agent-cadence run cadence_config.py get review-model --first`, the rounds as cadence §4.8 sizes them) or a fact-check by its `fact-check-model` (docs: `get fact-check-model`), recorded as a PR comment whose first line is `cadence-review: SHIP|FIXED|BLOCK · <model> · code|docs · n findings`, never edited afterwards → merge only when `agent-cadence run check_cadence.py --pr <n>` exits 0 (capture the exit code; `| head` hides a FAIL) and `ao pr held <n>` says the PR is not held. PR and comment bodies go through `--body-file`. A reviewer you start gets this worktree's path and never the main checkout's, never runs `ao`, never touches `~/.shiftlead`. Bare dates are local (MDT); a PR number is written only after the PR exists. `gh pr edit` fails in this repo — `gh api -X PATCH repos/ShiftLead/shiftlead/pulls/N --input -`. A ledger entry's Status changes in the PR that changes the thing; a conflict in a ledger entry resolves by taking main's copy and running the helper's command again on it; a conflict on the board (`docs/user_attention/`, one file per item) keeps both sides' item files, and an edit of one item that conflicts is re-done through the writer (`--id <id>`) on main's copy after the rebase — never by hand, and by the PR's author before the re-precheck (a cloud session's PR, its reader); a `done` moves its item into `archive/<YYYY-MM>/` itself (design §4.4 *Two PRs' records merge in either order*); an edit script on any other file asserts every replacement count before it writes, and nothing chains a git command after it.
