**A design PR is recorded on its design** (design §4.9c *The designer records its PR*). **A design PR writes the design's synopsis** (design §4.9c *The designer writes the synopsis*). Every design PR writes `docs/synopses/TD-<design>.md`, the design in plain words for the person: the first round's PR makes it, and each later round's PR — a bought round's or a `Hold` revision's among them — rewrites it whole, in the present tense, so it says what the design says at that PR's head. Write it last, after the round's fixes, so the closing fact-check reads it with the diff and checks that it says nothing the design does not and leaves out none of the choices the person would weigh. Its shape and its writing rule are `docs/synopses/README.md`'s; `tests/test_synopses.py` holds every synopsis to them.

**How a design is reviewed here, before its PR merges**: cadence §4.8 *Design review rounds* (`agent-cadence path cadence.md`), with what this repo adds. The build entries a design PR files are in the grinders' lanes the moment it merges (a `build` settles 0 minutes, design §4.4 *A new entry settles before it is pickable*), so **the design PR stays unmerged while its rounds run**.
- **The class and the cap.** Before round 1 the design entry's Status states its class (in-repo or wide) and why; the cap is `agent-cadence run cadence_config.py get design-rounds` for in-repo, `get design-rounds-wide` for wide.
- **Fact-checks** by the repo's fact-checker (`get fact-check-model`): one of the whole design opens round 1, one of what changed since opens each later round.
- **The gate holds once, from round 1** (design §4.9c *What a design's author prepares before a review*, from *The prep file* through *The gate*). Whether a design is gated is decided by the brief its round 1 starts under, and recorded: before round 1's first run of the pre-review script, you write `gated (TD-1720)` on the design entry's Log (`agent-cadence run ledger.py note TD-<design> "gated (TD-1720)"`) and commit it, so the note is in the commit that passes; a later round's sender reads it, and no note means ungated. A design whose round 1 starts under this brief is gated in every later round, its bought rounds and `Hold` revisions included. One whose round 1 began earlier is not, in any round: its prep file is optional, the script runs on it with `--advisory` where the file exists, and its reviewers' prompts carry no script step.
- **The prep file.** With the draft, before the first review, write `docs/reviews/TD-<design>.prep.yml` (§4.9c gives its four keys, `claims`, `rules`, `new` and `waive`): every claim the design makes about what existing code, a doc or another section does, each with its `at` or `count`; every rule it states in two or more places (its sections, the briefs, the builds' Fix and Done when, the synopsis), with `terms` you choose, never inferred; and every `new` path a build will create, with the build that creates it. Whoever applies a round's fixes keeps it true at every fix: a fix that writes a claim declares it, one that changes a rule's terms changes them in the file first, and one that states a rule in a second place declares it. Read *The author's checklist* (below) before drafting and again before the first review.
- **No review is sent without a pass.** Whoever sends a review — each round's fact-check and design reviews and the closing fact-check, but not the fact-check trial's ask to `fact-check-ao-1`, which is outside the gate, with no row and no line — runs `pdm run python scripts/design_prep.py --entry TD-<design>` from its own worktree on the commit the review will read, and sends the review only on a PASS, or on the script's own CANNOT RUN, which it files with `ao finding` and sends in the pass line's place. A FAIL (exit 1) or a NOT PREPARED (exit 2) is mended first.
- **Every reviewer's prompt meets the gate first.** Each reviewer's prompt, fact-checks and design reviews alike, makes its first step `git fetch origin` and `pdm run python scripts/design_prep.py --entry TD-<design> --rev <the commit it reads> --base <the base the sender's pass line names>`, run from its own worktree, never the main checkout (with the main checkout's `.venv` interpreter where that worktree has no environment of its own); it is the one command a reviewer runs that is not a read. On exit 1 or 2 its whole reply is `NOT PREPARED` and the script's lines, and the review gets no row in the record. On exit 3, or any output whose first line is not `design-prep:`, it goes on if it can read the commit, its reply leading with the CANNOT RUN line, else its whole reply is that line and the review gets no row; either way you file it (`ao finding`). A NOT PREPARED where your own run passed is the script's fault: run it again with the same `--rev` and `--base`, and if it still passes, file the difference and send the review again, telling the reviewer to go on as on a CANNOT RUN.
- **The rounds list.** The design PR's body holds a `**Rounds**` list, one line for each review, written when its row is: `R<n> · <round> · <role> · <the pass line it ran on, or your filed CANNOT RUN line>`, `R<n>` the record's id and `<round>` cadence §4.8's round. A review that ended NOT PREPARED, or that your run kept from being sent, has no line; one sent again after a reviewer's NOT PREPARED has the one line of the review that ran. Its last line is `final · <pass line>`, run on the commit that merges — the head once the closing fact-check's fixes and the bookkeeping after them are in (the end-of-rounds item, the builds' blocks, Asks and Fix, the Status) — and again whenever the head moves before the merge. A FAIL there is mended with no new review, and a mend that changes what the design says, or a waiver added or widened, is listed as a fix no review has read; a CANNOT RUN there is filed and written in the line.
- **What each fact-check reads of it.** Each round's fact-check checks every claim added or changed since the last (round 1's, every claim) at its `at`, reads every waiver, and raises a claim about code in the changed text that the file does not declare (`minor`) or a waiver that hides a real fault (`build-changing` when what it hides is). The closing fact-check also reads the rounds list against the record's rows (a mismatch is a `minor` finding), raises a round 1 whose lines carry pass lines on an entry with no `gated (TD-1720)` note, and reads the end-of-rounds item and the PR body, which the script cannot see, for restated rules.
- **The ways out when it cannot pass**: a path that rightly does not exist yet is a `new` path its build names; a false alarm is a `waive`, which the fact-check weighs; a NOT PREPARED is mended. Nothing else passes the gate. Before a later round's first run, in a PR of its own (a bought round's or a `Hold` revision's), drop the waivers that PR's text no longer needs: a waiver that hides nothing is itself a flag.

**The author's checklist** (design §4.9c *The checklist: fifteen questions, weighted to the hard situations*, TD-1757). Read it before drafting a design and again before its first review, and answer each question in the design itself wherever the design meets its situation: there is no answers block, since an answer worth writing is a rule a reviewer reads. The questions come from the findings only a design review or the live system caught, the places weighted by situation and no row of a design TD-1722 replays drawn from; `docs/decisions/2026-11-11-design-review-findings/checklist.csv` names each question's situation and the findings behind it. The list changes only by a design PR, and until TD-1722's trial ends never takes a row from a replayed design.

1. Does every reader, section and site treat this the same way? *(interaction)*
2. Does the new rule contradict any existing rule, text, or test? *(interaction)*
3. What existing behaviour or guarantee does this lose or undermine? *(interaction)*
4. What does a background pass or read see mid-action? *(concurrency)*
5. Which steps must be atomic, and what lock serialises them? *(concurrency)*
6. What clears this marker or stale state, and when? *(when)*
7. What bounds each wait, timer or retry, and when does it restart? *(when)*
8. Exactly which kinds, members or records does the rule include? *(scope)*
9. Does the description cover every rule, risk, and exception? *(scope)*
10. What happens to a record that is replaced, redone or archived? *(ends)*
11. Who performs each step, and who picks up the hand-off? *(who)*
12. What state remains if an operation fails partway? *(failure)*
13. Does stored state or a counter survive a restart or replay? *(restart)*
14. When several candidates apply, which wins and in what order? *(which)*
15. Which identity does each stored or printed value refer to? *(shape)*

**How a change lands here.** Branch in this worktree → PR → an independent review by the repo's `review-model` (code: round one's reviewer, `agent-cadence run cadence_config.py get review-model --first`, the rounds as cadence §4.8 sizes them) or a fact-check by its `fact-check-model` (docs: `get fact-check-model`), recorded as a PR comment whose first line is `cadence-review: SHIP|FIXED|BLOCK · <model> · code|docs · n findings`, never edited afterwards → merge only when `agent-cadence run check_cadence.py --pr <n>` exits 0 (capture the exit code; `| head` hides a FAIL) and `ao pr held <n>` says the PR is not held. PR and comment bodies go through `--body-file`. A reviewer you start gets this worktree's path and never the main checkout's, never runs `ao`, never touches `~/.shiftlead`. Bare dates are local (MDT); a PR number is written only after the PR exists. `gh pr edit` fails in this repo — `gh api -X PATCH repos/ShiftLead/shiftlead/pulls/N --input -`. A ledger entry's Status changes in the PR that changes the thing; a conflict in a ledger entry resolves by taking main's copy and running the helper's command again on it; a conflict on the board (`docs/user_attention.md`, its archive with it) resolves by `agent-cadence run board_edit.py replay --board docs/user_attention.md` at the stop, which makes your side's board writes again on the other side's board and stages them, then `git rebase --continue` — never by hand, and run by the PR's author before the re-precheck (a cloud session's PR, its reader); a `done` that archives (the board already holds `ARCHIVE_AT` less one, nine, closed items) runs without `--no-commit`, the board committed first, so its archive is the helper's own commit (design §4.4 *Two PRs' records merge in either order*); an edit script on any other file asserts every replacement count before it writes, and nothing chains a git command after it.

**How a run ends here:** `ao progress none --why` with counts, not a sentence per entry.
