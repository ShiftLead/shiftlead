**A design PR is recorded on its design** (design §4.9c *The designer records its PR*). Title a design PR with the entry's id and the word *design* — *TD-<n> design: …* — so an item about the design links it while it is open. Once it is open, its number being the forge's, and before the first `ask` or `steer` about the design, append it to the design entry's `Design PR:` section — `agent-cadence run ledger.py edit TD-<design> --section "Design PR" --from <file>`, the file the old list with `, #<n>` after it (`#<n>` alone for the first) — committed in that PR: it lands with the merge, and from then on the section is what an item about the design links (design §4.5 screen 6 *An item about a design links the design's PR*). **A design PR writes the design's synopsis** (design §4.9c *The designer writes the synopsis*). Every design PR writes `docs/synopses/TD-<design>.md`, the design in plain words for the person: the first round's PR makes it, and each later round's PR — a bought round's or a `Hold` revision's among them — rewrites it whole, in the present tense, so it says what the design says at that PR's head. Write it last, after the round's fixes, so the closing fact-check reads it with the diff and checks that it says nothing the design does not and leaves out none of the choices the person would weigh. Its shape and its writing rule are `docs/synopses/README.md`'s; `tests/test_synopses.py` holds every synopsis to them.

**How a design is reviewed here, before its PR merges**: cadence §4.8 *Design review rounds* (`agent-cadence path cadence.md`), with what this repo adds. The build entries a design PR files are in the grinders' lanes the moment it merges (a `build` settles 0 minutes, design §4.4 *A new entry settles before it is pickable*), so **the design PR stays unmerged while its rounds run**.
- **The class and the cap.** Before round 1 the design entry's Status states its class (in-repo or wide) and why; the cap is `agent-cadence run cadence_config.py get design-rounds` for in-repo, `get design-rounds-wide` for wide.
- **Fact-checks** by the repo's fact-checker (`get fact-check-model`): one of the whole design opens round 1, one of what changed since opens each later round.
- **A round is a Fable review of the written design, then a Sonnet review** (Paul, 2026-11-03). The round's reviewers are this repo's own, Fable then Sonnet, never `review-model`'s list, which stays `sonnet` for PR reviews; Fable reviewing a design the designer wrote on Fable is Paul's exception to the cadence's *never the same*, whatever model the designer runs. Each is a fresh agent given this worktree's path, the design's sections and entries, and the findings table; it reviews for gaps, contradictions with the rest of the design and anything a builder would guess, names a finding it reopens by id, and labels each finding `build-changing` or `minor`.
- **Adopt each finding by the template's three tiers**: one that follows from what is written is yours to write in; a choice Paul might care about is a `steer` with your adoption as its `--default`; taste or scope is an `ask`, the entry's Status saying it waits on it. A finding out to a `steer` or an `ask` is `open` in the table until the answer makes it `applied` or `rejected: <why>`.
- **The rounds end as §4.8 says**: its stop rule (a round with nothing build-changing), the cap, or the one round a `One more round` answer bought; a recurring topic never ends them.
- **A fix no review has read recommends One more round** (agent-cadence#TD-243, until a pinned §4.8 says it, when this line goes): while any build-changing fix is unread by a review — a fix to the cap's last round, to a bought round, or to a closing fact-check's finding — the end-of-rounds item recommends `One more round`, never `Go`, and its first answer is `One more round (default)`; the item names each unread finding by its id, by build. `Go` is recommended only when every build-changing fix has been read by a review.
- **The PR's docs fact-check is the closing fact-check**: run over the whole diff after the last round's fixes, fixed and re-run until it raises nothing. Its first run is the PR's `cadence-review:` evidence comment (`SHIP` when it raises nothing, `BLOCK` when it raises a finding, cadence §4.9), the re-run that raises nothing its `FIXED` follow-up, each run a row (`R<n>`, role `fact-check`) under the last round; a closing finding that changes the design makes you recommend `One more round`. There is one closing fact-check, never a second beside the PR's.
- **The fact-check trial** (design §4.9b *The fact-check*, TD-1213): every doc-only PR of yours, a design PR among them, also asks ao-grind's seat `fact-check-ao-1` once its head is pushed, beside the closing fact-check and never in place of it, and you post its one `fact-check-trial:` comment — the rule as the paragraph *The fact-check trial* in `docs/briefs/grinder-ao-1.md` writes it: read it and follow it.

Parts: TD-a, TD-b.` — its detail block listing by build the fixes no review has read, written by `agent-cadence run board_edit.py add --board docs/user_attention.md --kind decide --answer … --context "TD-<design> decision (paul)" --parts TD-a,TD-b --detail … --due … --no-commit` (`add --help` lists the rest) and committed in the design PR. With the item the PR merges with the design entry and every build it files carrying `**Blocked by:** decision (paul)` and an `**Ask:**` line: a part inherits nothing from its parent, so each build carries its own. **How a change lands here.** Branch in this worktree → PR → an independent review by the repo's `review-model` (code: round one's reviewer, `agent-cadence run cadence_config.py get review-model --first`, the rounds as cadence §4.8 sizes them) or a fact-check by its `fact-check-model` (docs: `get fact-check-model`), recorded as a PR comment whose first line is `cadence-review: SHIP|FIXED|BLOCK · <model> · code|docs · n findings`, never edited afterwards → merge only when `agent-cadence run check_cadence.py --pr <n>` exits 0 (capture the exit code; `| head` hides a FAIL) and `ao pr held <n>` says the PR is not held. PR and comment bodies go through `--body-file`. A reviewer you start gets this worktree's path and never the main checkout's, never runs `ao`, never touches `~/.shiftlead`. Bare dates are local (MDT); a PR number is written only after the PR exists. `gh pr edit` fails in this repo — `gh api -X PATCH repos/ShiftLead/shiftlead/pulls/N --input -`. A ledger entry's Status changes in the PR that changes the thing; a conflict in a ledger entry resolves by taking main's copy and running the helper's command again on it; a conflict on the board (`docs/user_attention.md`, its archive with it) resolves by `agent-cadence run board_edit.py replay --board docs/user_attention.md` at the stop, which makes your side's board writes again on the other side's board and stages them, then `git rebase --continue` — never by hand, and run by the PR's author before the re-precheck (a cloud session's PR, its reader); a `done` that archives (the board already holds `ARCHIVE_AT` less one, nine, closed items) runs without `--no-commit`, the board committed first, so its archive is the helper's own commit (design §4.4 *Two PRs' records merge in either order*); an edit script on any other file asserts every replacement count before it writes, and nothing chains a git command after it.
