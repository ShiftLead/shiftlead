**A change to a page is verified by you, before its PR (design §4.9b, TD-291).** A PR that changes anything under `src/shiftlead/ui/` is run first on a scratch home: `pdm run python scripts/look_home.py` in your worktree stands up a host agent and the UI from it, on a home under `/tmp`, a tmux server and a port of their own, with fixture sessions and a fixture board; it prints the URL, and SIGTERM or Ctrl+C tears it all down. Drive the page in headless Chromium under Playwright, installed at `~/ao-shots/pwlib` (`PYTHONPATH=~/ao-shots/pwlib ~/.local/share/shiftlead-venv/bin/python <your script>`): load, wait for the scripts and the terminal, read values, press, screenshot. The PR's body carries a **UI check** heading, one line per check (what the change says, what was read), and its screenshots are committed as `docs/mockups/reviews/<date>-td<n>-<what>.png`, cropped to the change, at most four; a page PR with no UI check is not ready to merge. What a browser cannot settle — whether a layout or a wording is what the design means — is an `ask` to `{techlead}` before the merge (`ao msg --kind ask --about TD-NNN {techlead} "…"`) naming the screenshots and the §4.5 / §4.5a section and mockup; a *does not match* is fixed before the merge. What only the live copy shows is a `watch` line on `docs/user_attention.md` naming what to read (`agent-cadence run board_edit.py add --board docs/user_attention.md --kind watch --text … --due … --no-commit`; closed with `ao board edit done`, never typed): the member that next reads the board with the change's commit live (`ao promote status`) makes it read-only — a headless GET, no press, no `ao` verb that acts on a session of the live home, nothing under `~/.shiftlead` — and closes it with what it read, or ledgers what is wrong. What is left for Paul is a **look, and a look is mail** (design §4.9b, §4.10 *A look*), sent after the merge — its first paragraph the one thing that is Paul's to judge, then what was checked and by whom, and the screenshots with `ao msg --shot` — in one of three cases: every check held, or the techlead said *matches* — **nothing is sent**, the UI check is the record; the techlead answered *not written* with a lean — `ao msg person --kind steer --default "Works" --bound 43200 --about TD-NNN "…"` naming its reply — the bound in seconds, no shorter than a night — which lapses to *Works* with no press; nobody leaned, or neither the scratch home nor a read of the live copy shows it — `ao msg person --kind ask --answer "Works" --answer "Not right: <what>" --about TD-NNN "…"`. A *Works*, a **Go with it** or a lapse closes it and nothing more is owed; a *Not right: <what>* is ledgered as an entry of its own and its outcome reported. No board line is written for a look.

**The gate here.** `pdm run test` and `pdm run lint` before the PR; before the ask and before `done --pr`, `agent-cadence run precheck.py --pr N` (in the background: it runs the suite in a clean worktree, minutes) records the PR's `cadence/precheck` status — the home refuses both while a required check failed or still runs. GitHub Actions (`ci.yml`) run on a fork's PR and by hand (TD-1035, TD-1285). Merge through cadence step 5's line (`agent-cadence path procedures/cadence.md`, step 5), run whole as one command — `m=$(mktemp -d); agent-cadence run check_cadence.py --pr N --trailers "$m/gate"; agent-cadence run forge.py squash-message N --gate "$m/gate" --out "$m" && gh pr merge N --squash --match-head-commit "$(cat "$m/sha")" --subject "$(cat "$m/subject")" --body-file "$m/body"` — never with `--delete-branch` from a worktree, and never delete a branch another open PR is based on (GitHub closes the stacked PR and its base cannot be changed afterwards). Rebase on the latest main before each merge. A conflict in a ledger entry resolves by taking main's copy and running the helper's command again on it; a conflict on the board (`docs/user_attention.md`, its archive with it) resolves by `agent-cadence run board_edit.py replay --board docs/user_attention.md` at the stop, which makes your side's board writes again on the other side's board and stages them, then `git rebase --continue` — never by hand, and run by the PR's author before the re-precheck (a cloud session's PR, its reader); a `done` that archives (the board already holds `ARCHIVE_AT` less one, nine, closed items) runs without `--no-commit`, the board committed first, so its archive is the helper's own commit (design §4.4 *Two PRs' records merge in either order*).

**The fact-check trial (design §4.9b *The fact-check*, TD-1213).** ao-grind's seat `fact-check-ao-1` (`fact-checker`, a Gemini profile on a free account) is asked beside your own fact-check of every doc-only PR, never in place of it: your fact-checker's `cadence-review:` comment stays the PR's evidence, and the merge never waits on the seat. Once the PR's head is pushed, first read the seat: in `ao status --json`, the record `ao-shiftlead-fact-check-ao-1` — if there is none, or its `seat_unable` is set, the seat cannot answer: ask nothing and post `fact-check-trial: none · <its seat_unable, or no record>` at once (an ask to it would be routed to the techlead or the person, design §4.9b *A seat that cannot answer is routed around*). Otherwise send `ao msg --kind ask --bound 1800 --about '#<n>' fact-check-ao-1 "fact-check PR #<n> at <sha>: <the claims>"` — briefed as cadence §4.8 briefs any reviewer: the load-bearing claims and the figures you have not checked, each to be re-derived — with no `--pr`, since it is no reader's read. If the ask is refused because your last one to the seat is still open, ask nothing for this PR. Each PR gets **one** trial comment, posted by you, merged or not, through `--body-file`:
- **A reply** (`about` names the PR): re-check each of the seat's findings yourself against the asked `<sha>` by refs (`git show <sha>:<path>`), then compare them with your own fact-checker's findings as the evidence comment and its `FIXED` follow-up record them. The comment's first line is `fact-check-trial: SHIP|BLOCK · <adapter>/<model> · caught <c> · missed <m> · false <f> · <minutes> min` — the seat's verdict and model as its reply's first line gives them; *caught* the seat's findings you confirmed, *missed* your fact-checker's confirmed findings the seat did not raise, *false* the seat's findings you found wrong, the minutes from the ask to the reply — then one sentence for each missed or false finding.
- **No reply by the bound**: the ask closes `expired` and nothing tells you; at your own first `ao` reply after the bound, post `fact-check-trial: none · <reason>`, the reason the seat's state then from its record in `ao status --json` (`limited`, `fills exhausted`, `never filled`, or still `working`).
- **Refused as one ask open**: `fact-check-trial: skipped · one ask open`.
- **Routed around** (the send's reply says it went to the techlead or the person, the seat having turned unable since you read it): post `fact-check-trial: none · <the reason the reply names>` at once, and withdraw it if it went to the person (`ao msg --withdraw <its id>`); one at the techlead cannot be withdrawn and lapses at its bound.
A `none` or `skipped` line carries no cells. **The comment carries the string `cadence-review:` nowhere**, not even quoting the seat's reply: the cadence check reads that line from any line of any comment (cadence §4.9). A late reply to an expired ask is read and never posted. If you exit before the reply lands, it waits in your name's mailbox, and the name's next run posts it, when that run keeps the mail (design §4.10 *The name coming back adopts it*) and comes within a day of the close (`CLOSED_KEEP`). The trial runs until there are 20 `SHIP` or `BLOCK` trial lines or 14 days from the first, whichever ends first; the designer's evaluation reads them then.
