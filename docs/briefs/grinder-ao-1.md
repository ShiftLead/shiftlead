This is the shiftlead repo's part of the grinder brief (design §4.8, TD-114): what this repo does differently from the template above and below it, and nothing the template already says. The team is **ao-grind**, started by `ao team start ao-grind`; your manager is **manager-ao-1**, a seat on call that the tick fills when a reading needs it (design §6 rule 3). Paul is around but not driving you.

**Where you work.** Your worktree is `.claude/worktrees/<your name>` on a branch of the same name — a launch artefact, never commit to it. A work branch exists only to carry a PR, never as a save-point, and once `gh pr view <n>` shows MERGED, `git branch -D` the local one.

**First reads, beyond the template's:** docs/design/ §4.5a (a control that is not in that table does not exist) and §9 (the invariants). agent-cadence's scripts and docs are not in this repo: `docs/cadence.toml` pins the commit, `agent-cadence run <script>` runs one and `agent-cadence path <name>` finds a doc (`agent-cadence path cadence.md`); they belong to agent-cadence.

**Never read the design (`docs/design/`, every file) or the ledger whole** (design §4.8 *The bound has two layers*, TD-249). Each is about 200k tokens, which is most of your context bound spent before the first claim, and a run that starts that way restarts after every entry. `agent-cadence run ledger.py --pickable` (or `ao repo`) for the pick order, then the one entry — its own file, `docs/ledger/TD-NNN.md` (`docs/ledger/archive/TD-NNN.md` once archived) — and the design sections it names, each a file of `docs/design/` (`grep -rn` the directory for a phrase, and read a long section as a range). The same goes for `docs/design-history.md`: grep for the id, read the lines. §4.5a and §9 above are read as those files, not as the design.

**You are running inside the thing you are fixing.** Beyond the template's rule: never restart the `shiftlead-agent` / `shiftlead-ui` user units, never create or kill `ao-*` tmux sessions, never edit `~/.claude/settings.json` or `~/.claude.json`. `pdm run test` (private tmux sockets, a temp `SHIFTLEAD_HOME`) and `scripts/look_home.py` are the only ways you exercise the host agent. Only the anchor promotes: a merged fix that needs a live look — a page or not — stays open as `**Kind:** live-check #<n>`, `<n>` the build's last merged PR, its Status saying what to read (*A live check* under the lane, design §4.9b); the one road for what only Paul can judge is a look, below. `sessionorc` never imports `shiftlead`, and tool-specific names stay inside `shiftlead/adapters/<tool>/`.

**A change to a page is verified by you, before its PR (design §4.9b, TD-291).** A PR that changes anything under `src/shiftlead/ui/` is run first on a scratch home: `pdm run python scripts/look_home.py` in your worktree stands up a host agent and the UI from it, on a home under `/tmp`, a tmux server and a port of their own, with fixture sessions and a fixture board; it prints the URL, and SIGTERM or Ctrl+C tears it all down. Drive the page in headless Chromium under Playwright, installed at `~/ao-shots/pwlib` (`PYTHONPATH=~/ao-shots/pwlib ~/.local/share/shiftlead-venv/bin/python <your script>`): load, wait for the scripts and the terminal, read values, press, screenshot. The PR's body carries a **UI check** heading, one line per check (what the change says, what was read), and its screenshots are committed as `docs/mockups/reviews/<date>-td<n>-<what>.png`, cropped to the change, at most four; a page PR with no UI check is not ready to merge. What a browser cannot settle — whether a layout or a wording is what the design means — is an `ask` to `{techlead}` before the merge (`ao msg --kind ask --about TD-NNN {techlead} "…"`) naming the screenshots and the §4.5 / §4.5a section and mockup; a *does not match* is fixed before the merge. What only the live copy shows is a `watch` line on `docs/user_attention.md` naming what to read: the member that next reads the board with the change's commit live (`ao promote status`) makes it read-only — a headless GET, no press, no `ao` verb that acts on a session of the live home, nothing under `~/.shiftlead` — and closes it with what it read, or ledgers what is wrong. What is left for Paul is a **look, and a look is mail** (design §4.9b, §4.10 *A look*), sent after the merge — its first paragraph the one thing that is Paul's to judge, then what was checked and by whom, and the screenshots with `ao msg --shot` — in one of three cases: every check held, or the techlead said *matches* — **nothing is sent**, the UI check is the record; the techlead answered *not written* with a lean — `ao msg person --kind steer --default "Works" --bound 43200 --about TD-NNN "…"` naming its reply — the bound in seconds, no shorter than a night — which lapses to *Works* with no press; nobody leaned, or neither the scratch home nor a read of the live copy shows it — `ao msg person --kind ask --answer "Works" --answer "Not right: <what>" --about TD-NNN "…"`. A *Works*, a **Go with it** or a lapse closes it and nothing more is owed; a *Not right: <what>* is ledgered as an entry of its own and its outcome reported. No board line is written for a look.

**The gate here.** `pdm run test` and `pdm run lint` before the PR; before the ask and before `done --pr`, `agent-cadence run precheck.py --pr N` (in the background: it runs the suite in a clean worktree, minutes) records the PR's `cadence/precheck` status — the home refuses both while a required check failed or still runs. GitHub Actions (`ci.yml`) run on a fork's PR and by hand (TD-1035, TD-1285). A fork's PR is never yours to precheck, fix or merge: its precheck runs a stranger's code here, so it is Paul's; `agent-cadence run check_cadence.py --pr N` exit 0 before the merge (capture the exit code: `| head` hides a FAIL); then `ao pr held N` (the held paths are `.shiftlead.yml`'s `held:`; the path is *The path* above). `org.yml` is not in the repo and never yours to change. `gh pr edit` fails in this repo — use `gh api -X PATCH repos/ShiftLead/shiftlead/pulls/N --input -`. Merge with `gh pr merge N --squash`, never with `--delete-branch` from a worktree, and never delete a branch another open PR is based on (GitHub closes the stacked PR and its base cannot be changed afterwards). Rebase on the latest main before each merge.

**One lane for both grinders (TD-749, 2026-10-15).** You and grinder-ao-2 no longer divide the code by package: each picks the highest-ranked pickable entry nobody holds (`ao repo`'s order, design §4.8 *Choosing in a free-pick lane*), whatever it touches — `src/sessionorc/`, `src/shiftlead/` or both. A claim names the files it touches that a live sibling's claim also touches, and the sibling is told with `ao msg`; whichever of you merges second rebases right before its review.

**The lane.** On `free-pick`, pick open entries suited to unattended completion: small and medium code fixes, test-coverage gaps, tooling, doc corrections verifiable against the code. Out of your reach: TD-003 and TD-008 (Paul's); TD-005 and TD-006 (need an attended `claude` run); TD-019 (phase 5); TD-004's ssh transport (phase 2); any entry whose status says its design round has not landed; Paul's `aotest` session and any worktree that is not yours.
