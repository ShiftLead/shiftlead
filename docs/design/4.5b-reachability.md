### 4.5b Reachability: the person's own route, and the shape of a hosted service

The question that decides the long-term shape is *how would someone who has never opened a
port use this?* The answer is the one Tailscale and `cloudflared` use: **the home dials out;
nothing on it listens on an address the internet can reach.** So the UI is reached by a route
the person brings — an account of their own with a provider they already trust — and shiftlead
runs nothing in its path. Every route below dials out from the home, so each works behind
carrier-grade NAT (CGNAT), where nothing can dial in to the home's connection at all.

**The routes** (TD-646). One is offered first, one is designed for when it is asked for, one always
works:

| route | what the person sets up | who is in the middle | domain or server | behind CGNAT |
|---|---|---|---|---|
| `tailscale` — **the first offered** | a free Tailscale account (sign-in with Google, GitHub or Microsoft); the client on the home and on the phone; `ao connect tailscale` (§4.7) | for the bytes, nobody: device to device over WireGuard, and when no direct path opens Tailscale's relays carry ciphertext; `tailscale serve` ends HTTPS on the home with a certificate for its `*.ts.net` name whose key stays there. **For identity, Tailscale**: its control plane — and the Google, GitHub or Microsoft account behind it — vouches for the device and the login the route port trusts. Tailnet Lock (the person's own devices sign every new one) stops the control plane adding a node; the account's second factor guards the login; the `*.ts.net` name is public in Certificate Transparency logs | none | works |
| `cloudflare` — **designed, built when asked** (TD-656): for a device that cannot run Tailscale (a locked-down work phone, a borrowed browser) and a person who wants a hostname of their own | a Cloudflare account, a domain on it, a named tunnel from `cloudflared` with its own Access check on (`access: {required: true, teamName, audTag}` in the tunnel's origin settings) and an Access application in front of it, then `ao connect cloudflare` | Cloudflare: it ends TLS at its edge and reads the traffic, which is the trust a person accepts by choosing it | the domain | works |
| `ssh -L 8765:127.0.0.1:8765 <home>` — always, and the default until a route is set | nothing beyond the ssh the person has | nobody | none | needs a way to ssh in: from outside a CGNAT home, that is one of the routes above |

A private network the person runs themselves (WireGuard, ZeroTier) stays possible — the plain
port bound to its address with `--bind` — but `ao connect` neither sets it up nor checks it; the
plain port then answers everyone on that network with no login, which is the person's own call;
and behind CGNAT the network's endpoint must be a machine with a public address. shiftlead adds no
encryption of its own on any route: the route's is the encryption.

**Cutting off a lost device**: the UI has no logout of its own, so the route is where access ends —
for Tailscale, remove the device from the tailnet in the admin console; for Cloudflare, revoke the
person's Access sessions and the device. The guide names the step for each route. Beside
`reach.allow`, a tailnet access rule that lets only the person's login reach the home's ports 443
and 22 is the guide's second lock — 22 too, because a tailnet's rules deny what they do not
grant, and ssh over the tailnet is the person's way into the home from the phone (below).

**Until the route port exists** (dated 2026-10-13, Paul's move to a CGNAT line): a tailnet holding
only the person's own devices, with that access rule, may point `tailscale serve` at the plain port
8765 directly — `tailscale serve --bg --https=443 http://127.0.0.1:8765`, with HTTPS and MagicDNS
turned on in the tailnet's admin console, which `tailscale serve` needs for its certificate. The
tailnet and its access rule are then the only lock: the plain port reads no
`Tailscale-User-Login`. This is taken knowingly: until TD-647, the plain port checks neither `Host`
nor `Origin`, so a hostile page open in the phone's browser can reach the UI through the tailnet.
It ends at the promote of TD-647's first slice: the plain port then refuses the serve's identity
header (below), and the phone gets a page naming the route port and the steps that move to it:
`tailscale serve --https=443 off`, then `ao connect tailscale` (which also recognises this handler
and names the first command in its refusal) — or, until `ao connect` lands (TD-648), by hand:
`tailscale serve --bg --https=443 http://127.0.0.1:8766` and a `reach:` written in `settings.yml`
(`route: tailscale`, `url`, `allow`). The promote that ends it may be the tick's own (§6
*Promote*), with the person on the phone: the shell that runs those steps is an ssh over the
tailnet to the home's name, which the promote does not touch and the access rule grants — so
the person promotes that slice at a keyboard, or with an ssh over the tailnet in hand.

**The route port** (TD-647; an open websocket's following of the setting, below, is its second slice, not built). The UI listens on two loopback ports. The **plain port** (8765) is
what a browser on the home and an `ssh -L` reach; it authenticates nothing (§4.8a). The **route
port** (8766) is the only port a route's proxy is pointed at, and every request and every
websocket upgrade on it is refused `403` — with a page saying which check failed and which command
cures it — unless it carries **the person's identity as the route proves it**:

- **`tailscale`**: the `Tailscale-User-Login` header names a login in `reach.allow`. `tailscale
  serve` removes a client's own copy of that header before it adds its own, and adds none for a
  tagged device or for Funnel traffic, so those are refused; a person using a device shared into
  the tailnet carries their own login, refused unless it is in `reach.allow`. Tailscale encodes a
  header value that is not ASCII (MIME encoded-word); a login is compared as decoded.
- **`cloudflare`** (designed, built when asked, TD-656): the `Cf-Access-Jwt-Assertion` header holds a token whose algorithm is RS256 —
  no other is accepted — signed by the key its `kid` names from
  `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`, whose `iss` is
  `https://<team>.cloudflareaccess.com`, whose `aud` holds `reach.aud`, within its `nbf` and `exp`
  (a minute's leeway), and whose `email` is in `reach.allow`. A token with no `email` — a service
  token's — is refused. The certs are cached for an hour, and fetched again sooner on a `kid` they
  do not hold, at most once a minute; the cache outlives each re-read of `reach:` while `team`
  stays the same; with no certs ever fetched, every token is refused. The tunnel's own Access check
  (`cloudflared`'s `access:` origin setting) stops an unsigned request before it reaches the home's
  port at all; the UI's check stays, since the UI cannot see the tunnel's settings. **A second way
  in is coming and may replace this check**: the passkey the home holds for the relay (below), once
  it exists on the route port, serves every route a provider header cannot — Cloudflare,
  WireGuard, the relay — with no provider-specific verification, so the token check and the passkey
  are decided together, with the relay.

`reach.allow` is compared without case, and an empty one lets nobody in. Which listener a
connection came in on is known from the listener — never from the `Host` header, which the client
writes. **The plain port refuses what a proxy sends**: a request carrying `Tailscale-User-Login`,
`Tailscale-User-Name`, `Cf-Access-Jwt-Assertion`, `Cf-Connecting-Ip`, `X-Forwarded-For` or
`X-Forwarded-Host` is
refused `403` there, its page saying *this is the plain port; point the proxy at the route port*.
This refusal is judged before `Host` and `Origin`, so a proxy aimed at the plain port always gets
the page that names the route port, never a `421`.
A browser on the home and an `ssh -L` send none of them; without the rule, a tunnel aimed at 8765
would skip every check below. Every answer either listener gives, a refusal included, carries
`X-Shiftlead-Listener: plain` or `route`, which is how `ao connect` tells which port a route reaches
(§4.7) — except a refused websocket upgrade, which is a bare `403` (the server's answer to a close
before accept; its reason is in the log).

**Origin and Host, on both ports.** An identity a proxy adds rides on every request the person's
browser makes, including one a hostile page in another tab makes for it: a page can POST to the
route's URL or open its terminal websocket, and the proxy adds the person's login. And a page can
rebind a name of its own to `127.0.0.1` and reach either port. So on both ports a request passes
two checks. `Host` is read case-folded, its port split off (`[::1]` in brackets understood):

- **`Host`** must name the port's own: on the route port the host of `reach.url`, its port not
  compared (`ao connect` pins 443, and `Origin` carries the port check; `ao connect`'s probe proves
  the proxy passes the name through, §4.7); on the plain port `127.0.0.1`, `localhost` or `[::1]`
  at any port (an `ssh -L` may forward from another) and each `--allow-host <name>` the install
  was given, on any bind (repeatable; `ao ui` and `ao service install` carry it; a name the person
  lists is never one a rebinding page controls), and when `--bind` is not loopback also the bind
  address and the machine's own host names (short and full) — else `421`, its page naming
  `--allow-host`. A rebinding page's `Host` is its own name.
- **`Origin`**: a websocket upgrade must carry one, and a request other than `GET` or `HEAD` must
  carry one or `Sec-Fetch-Site: same-origin`; an `Origin` that is present must match, whatever
  else the request carries; else `403`. Matching is scheme, host and port, a default port elided.
  On the route port it must equal `reach.url`'s — the proxy speaks plain `http` to the port while the browser saw
  `https`, so the scheme is `reach.url`'s, never the connection's; on the plain port it is `http`
  and the request's own `Host`.

The UI's own pages, scripts, forms and websockets are same-origin, so none of this is felt by the
person; a Telegram link is a plain `GET`; a script calling the UI over HTTP sends an `Origin`, as the
`403` page says. On the route port an absolute link the server renders (`page_origin`) comes from
`reach.url`; on the plain port from the checked `Host`; the page's script builds the websocket URLs
from the browser's own `location`, and every other link is relative. Neither
listener trusts `X-Forwarded-Proto` or `X-Forwarded-For` (uvicorn's `proxy_headers` off). **Where
the checks live**: in the layer each listener wraps around the app at start, not in the app — so
the app's own tests, which call it directly, are untouched — and before the app sees the
connection, so a refused websocket is refused at its upgrade.

**An open websocket** (`/events`, `/term/<id>`) keeps the identity it was let in with — the login,
or the token's `email` — and the route listener reads `reach:` every five seconds on its own, not
only when a request comes (TD-647's second slice). **It reads `settings.yml` itself**, through the
shared settings reader, never through the host agent: the route outlives the agent, so a phone can
still open the UI, and read its *host agent unreachable* banner, when the agent is what failed. The route port
runs only on the home, since the route is the home's (§4.7: `ao connect` is refused on a node); a
UI is on the home when its `hosts.yml` names no `home:` or names itself (`hosts.is_node()` false),
and a UI started on a node (§4.4a), whose replica of `settings.yml` is read for nothing here, runs
no route listener, as with `--route-port 0`, and logs *no route
listener: not the home*. A socket whose identity the new `reach:` no longer lets in is closed, so
`ao connect off` or a narrowed `--allow` ends the live terminals it no longer lets in. The checks
fail closed: before any `reach:` has been read the route port refuses everything, and when the
file cannot be read or parsed the last good reading holds for a minute, then the route port's
sockets close and it refuses until a read answers. A Cloudflare token's `exp` is read at the upgrade only, as Access's
own session is.

Why a second port rather than an identity check on the one: `tailscale serve` and `cloudflared`
reach the UI from loopback, exactly as a local browser does, so on one port *no identity header*
would have to mean *local*, and a tunnel put up without Access would hand the internet a shell. On
the route port an absent identity is a refusal. **Every refusal is logged** at `warning`, either
port — the listener, the check that failed, `Host`, `Origin`, and the login it carried, decoded,
never a token — so a tailnet member not in `allow`, a tagged device, or a rebinding or cross-site
attempt is shown where it is tried (§4.8a). A route-port refusal whose `Host` is a loopback name
is logged at `info` and not counted: a proxied request carries the route's name, so a loopback
`Host` is a local process — `ao doctor`'s and `ao connect`'s own probes, against which the port is
no wall anyway (§4.8a). Every answer carries `X-Shiftlead-Refused: <n>
<start>`, the count since the UI started, which is how `ao doctor`'s route line reads it when it
asks the port (no answer, no count). The route port binds `127.0.0.1` whatever `--bind`
says (that flag is the plain port's); `--route-port 0` runs no route listener (a scratch home, the
tests); with no `reach:` set it refuses everything, naming `ao connect` (until TD-648, the hand-written `reach:`). A route port that cannot
bind — another process holds it — leaves the plain port serving: the UI logs it, tries again each
minute, and `ao doctor`'s **route** line is *lacking*, naming the holder. **The ports are the
defaults** (8765, 8766) or what `--route-port` names, and `ao connect` and `ao doctor` learn a port's
state by asking it: `GET http://127.0.0.1:<port>/` refused means *the UI is not running*; an answer
with `X-Shiftlead-Listener` is the UI's own; an answer without it is another process, named by `ss
-lptn`. The app learns which listener serves a request from the layer
(the ASGI scope's `shiftlead` key: the listener and the origin its links use). **What it is not**: a wall
against a process on the home. Any process of the person's user reaches the plain port, and can
send the route port a `Tailscale-User-Login` of its choosing; §4.8a's threat model is unchanged
there. The checks close the route to everyone but the person, and both ports to pages the person
merely visits.

Why not a Unix socket for the proxy: `tailscale serve unix:<path>` exists in newer clients and
`cloudflared` has long taken `unix:` targets, but a socket adds nothing against the person's own
user, which already reaches loopback; Tailscale rewrites `Host` to the backend's for a socket and
keeps it for a TCP target, so the `Host` rule would differ by target; and the socket's path would
sit in every provider's configuration.

**The setting**: `reach:` in `settings.yml` (§5) — the route, its URL, who is allowed, and for
Cloudflare the team and the audience tag. From TD-647's first slice, which brings its reader, until
`ao connect` lands, the person may write it by hand in `settings.yml`, the file being its source. `ao connect` (not built; TD-648) writes it through its own `set_reach` RPC,
which checks the shape (a known route, an `https` URL, a non-empty `allow`, `team` and `aud` for
Cloudflare) and is refused to a session; `set_settings` refuses the `reach` key, naming `ao
connect`, so it is set nowhere else (§4.5 screen 8 *Not on the page*: setting a route runs the provider's commands on the
home). `reach.url` is the link a phone opens: the Telegram note's `notify.telegram.link`, absent,
is `reach.url`. Setting up the account is the person's, and the guide (README *Reach it from your
phone*, written by TD-648) walks it — for Tailscale an account with a second factor, the client,
`tailscale up`, HTTPS and MagicDNS on, Tailnet Lock, the access rule and the phone's app; for
Cloudflare (with TD-656) the domain, the tunnel with its `access:` setting and the Access
application. Nobody hands shiftlead a key: an auth
key or a login stays on the person's own machine.

**Transports** — how the UI reaches each host agent, which is a separate question from how the
person reaches the UI:

| transport | who runs the UI | how the host agent is reached | who it is for |
|---|---|---|---|
| `local` | you, on the same host | Unix socket | phase 1, one machine |
| `ssh` | you, on a host you choose | the UI reaches the home host agent; every other host agent is a node that dials the home over ssh (`shiftlead-agent link`, §4.4a). A node in a **container on the home's own machine** dials out the same way, over a per-node link socket at the home whose directory is bind-mounted in; the home brings the container up, installs its own version in it and supervises it (§4.4a *A container node*) | phases 2+, several hosts you own |
| `relay` | the home, as with `local` and `ssh` | as with `ssh`; what changes is the person's route: the home keeps an outbound connection to a relay, and the relay forwards encrypted bytes between it and the person's browser | a person with no Tailscale or Cloudflare account; a hosted convenience |

**The relay, if one is built, carries only ciphertext.** TLS ends on the home; the UI's code is
served by the home; the login is the home's own — a passkey, since nothing a relay says can be
taken as the person's identity. That listener and its login are designed when the relay is: the
route port above, loopback-only and trusting a provider's header, is not it. A passkey is bound to
the hostname it was made on, so moving from a name under the relay's domain to the person's own
re-registers it: the name is chosen at join. The relay routes a connection by the hostname it
opens with and learns that a connection happened, when, and how big it was — with a terminal on
the other end, timing and volume say something of what is typed, and that is the relay's whole
view. **A relay that ends TLS, serves the UI's code or holds the login is ruled out**:
the UI can type into a shell as the person, and whoever serves a page's code can make it do
anything, encrypted connection or not — a technical user would not hand that to a small company's
servers, and should not. One trust stays with whoever controls the DNS of the relay's hostnames: it
could obtain a certificate for a person's name there, which Certificate Transparency logs would
show — and nobody watches those logs for their own name. So **the relay's recommendation is the
person's own domain**, which removes that trust; a name under the relay's domain is the
convenience, said as such at join. With that shape the whole setup is an install, a
join command (not designed), a passkey and a link to open — no port forward, no VPN client, no ssh
keys, no provider account — and every invariant in §9 holds: the host agent is still the only
writer, sessions still live on the host.

Consequences for what is built now: the host agent's RPC is a plain JSON-lines stream over any
byte pipe (`shiftlead-agent rpc` is a stdio bridge); the terminal bridge, which spawns `tmux attach`
locally under `/term/<id>` in phase 1, **must never gain a port of its own** — in phase 2 it reaches
a session's host over the UI's own ssh (§4.4a), and it moves onto the node→home link (§7 phase 2,
*the terminal over the link*); nothing in the UI may assume it can reach a host by address; and the
UI's pages, scripts and websockets all live under the one origin a route serves. `relay` is not
scheduled; it is a phase after 5, and the first hosted version can be a single small VPS
forwarding for a handful of people.
