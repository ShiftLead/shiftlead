### 4.1 Session substrate: tmux, one session per conversation

- Session name `ao-<repo-or-dir>-<name>`; the prefix lets the host agent enumerate its own sessions.
  Both parts are slugified to `[a-z0-9-]` (tmux treats `:`, `.` and whitespace specially).
  **A name identifies one session within its scope** (the repo, or the directory for a
  repo-less session; §10, §9 invariant 12): it is what a person types into `ao focus`, `ao send`
  and the Sessions filter, so two cards called `aotest` is a defect, not a namespace. Every `ao`
  subcommand that takes an id also takes a **bare name**, resolved to the one session of that
  name *here* — this directory, the directory it is under, or a repo it belongs to, which is how
  a name typed in the checkout finds its worktree — with a live session winning over an exited
  one of the same name; two matches are "ambiguous — <ids>" and none is "no session named
  <name> here", never a guess. A full `ao-…` id always means itself. The rules, in the order the
  host agent applies them at create (TD-030):
  - the name is held by a **live** record (any state but `exited` / `closed`) → refused:
    "`aotest` is running — switch to it, or pick another name", with the holder's id, its state
    and the line that switches to it (`ao focus ao-shiftlead-tests-aotest`) as error data rather
    than prose to parse — the CLI prints that as its hint, the form draws a button from it. The
    New session form checks this as you type, like the directory occupancy check (§4.5a), and
    offers **Switch to**.
  - the name is held by an **exited or closed** record → the new session **supersedes** it: it
    takes the id, the old record is **replaced in place** (the card becomes the new session
    rather than going and coming back, and a start that fails leaves the old record standing),
    its run log is kept and linked from the new record as *previous run* (a field on the
    record), and no cadence or hook bookkeeping outlives the session it was about. Resume's
    supersede closes the exited record and keeps it a day; a fresh start under the same name
    forgets it instead, because the name now belongs to the new session. No `-2` card appears.
    **One exception:** a holder a person *suspended* over an identity alarm refuses
    every session's `create` under its name, and only a person lifts it (§4.8a *An alarm's
    answers*). The name check answers `suspended` rather than `supersede`, so the form, `ao new`
    and `ao team start` all refuse without each knowing the rule.
  - the id is taken in tmux by a session the host agent has **no record of** (hand-made, or a
    stale pane the tick has not adopted yet) → the host agent decides on **tmux's own answer**,
    not on whether the tick has adopted it yet: a live pane refuses like a live record (and says
    the card appears within a tick, which is when the tick adopts it); a dead pane nobody has a
    record of is killed and its id reused. The name is checked under a lock on the **scope**,
    not on the directory, because one scope spans a repo's worktrees. The suffix survives only
    for tmux's own "duplicate session" verdict, which the host agent still handles explicitly
    rather than trusting its check — then `-2`, `-3` is shown in the name on the record, so what
    the Sessions page says is what tmux has.
  - `shell` sessions are named by the host agent when the person gives no name (`shell`,
    `shell-2`, …) and follow the same rules under that generated name.
- Every session record carries: `name` (what the person called it), `kind`
  (`interactive` | `command`), `adapter` (`claude-code`, `shell`, …), `profile` (empty for
  `shell`), `dir`, `repo` (optional), `worktree` (optional), `adapter_id` once known (Claude
  Code's session uuid, read from the hook payload; it is what Resumable and the transcript index
  key on), `transcript` with it (the file the tool writes, from the same payload, §4.2), `capabilities` (grants, §4.8 — empty for most sessions), `controllers` (§4.8's
  membership list: which sessions may act on this one; TD-036), `lane`, `progress` and
  `findings` (§4.8's report channels: what the session was handed and what it says it did),
  `role` (the preset it was started from — a badge and nothing more), `team` and `project`
  (badges, §4.9), and `unattended` with its schedule (§6). Grants, report channels, mode and
  schedule are independent fields: a grant says a session may act on others at all and
  `controllers` on the target says on which (§4.8), the channels say what it did, `unattended`
  says whether policies act on it, the schedule says when. Any can be set without the others.
  Resumable shows the name first and the id under it; a session started by hand outside shiftlead
  shows only the id until it is **adopted** (attach to the tmux session, give it a name), which
  is how hand-started sessions enter the Sessions page.
- A live session the adapter can see that has **no tmux at all** (`claude` in a VS Code
  terminal; Claude Code's registry `~/.claude/sessions/<pid>.json`) is **not shown**: the Sessions page is
  what shiftlead started or adopted, and a card for such a session offers nothing to do. The
  registry is read in the one place the anchor rule needs it — `occupancy` (§9 invariant 2): New
  session and `ao new` name a hand-started session that holds the checkout, so nobody starts a
  second agent on top of it.
- A **plain shell is an adapter** (`shell`, scraped, `agent: False` — §4.3 *A record with no agent*: `working` while a foreground process runs,
  `idle` at the prompt — a shell waiting for you is the normal state, not an alert — `exited`
  when the pane is gone). Ad-hoc shells are ordinary `interactive` cards; the profile line reads
  `shell`. Predefined command buttons (§4.5) start `kind: command` sessions, which are hidden
  from the Sessions page unless the filter carries `kind:command` and never rank in the urgency sort.
- Created **only** by the host agent (one writer per shared resource, §9). The UI, the CLI and
  the cron reconcile all call the host agent.
- The **host agent** runs under a user systemd unit with `loginctl enable-linger`, so a reboot
  restarts it. **The installed home's tmux server runs as a system unit, `shiftlead-tmux.service`,
  with `User=` the person** (TD-488): a `systemctl --user exit`, a stop of `user@<uid>.service` or a
  signal that reaches the user manager takes the host agent and the UI down and **no session** —
  the server and every pane live under `system.slice`, outside the user manager's subtree, which is
  the subtree one SIGTERM to `systemd --user` emptied on 2026-10-09, every session on kmaster with
  it, for 4h20m. The unit runs `tmux -D` in the foreground on the default socket (`-D` is no
  daemon, and `exit-empty` off), with `Restart=always`, `KillMode=control-group` (its own stop is
  the one deliberate way to end every session at once, and it is root's), `Delegate=yes` (§4.8a:
  the pane's own cgroup) and none of the user manager's bus or `XDG_RUNTIME_DIR` in its
  environment, so tmux opens no scope under the manager. A system unit is root's to write, so
  `ao service install` writes the user units as before and, when
  `/etc/systemd/system/shiftlead-tmux.service` is absent or differs from the text it would write,
  writes that text to `~/.shiftlead/systemd/shiftlead-tmux.service` and prints the one command the
  person runs once as root, `sudo ao service install --system`, which writes the same text in — made
  again as root for `SUDO_USER`, never copied from the staged file any session can write — and
  `enable --now`s it (refused while a server not the unit's answers on the person's socket; the units under the project's old name, `agentorc-tmux` and `agentorc-watch`, it stops and removes first, refused while their server holds a session — TD-060), with the watch timer beside it (§4.10 *When the home itself is down*, TD-489);
  `ao service status` and `ao doctor`'s tmux check (§4.7) say which the running
  server is — *system unit*, *under the user manager* (a warning) or *none*. Without the system
  unit nothing changes: tmux daemonises away from whatever spawns it, and the host agent starts the
  server idempotently on its own startup and before every create (`start-server`, then `exit-empty
  off` so the server survives its last session closing, §4.6 — against a running server a no-op),
  as it does on a scratch home (`-L <name>`, §4.4), a dev run and a container node (no systemd
  there, §4.4a). The host agent's own units stay user units: a stop of the user manager takes them
  down while the sessions keep working, hooks and `ao` failing to reach the agent until it returns
  and reconciles against the live panes, and TD-489's alarm is what tells the person; moving the
  agent and the UI to system units too was weighed and not taken, since a promote (§6) restarts
  them from the host agent's own tick, which a system unit would put behind root. Default tmux
  socket, so hand-started sessions and "Copy tmux command" just work. tmux, not the host agent,
  **owns the processes**: a host-agent restart, upgrade or crash reconciles against live panes and loses
  no session, where a runtime that holds the ptys itself must kill every session to restart
  ([ADR 2026-09-10](../decisions/2026-09-10-herdr-spike.md)). This is a reason, not an accident.
- The adapter's **argv runs directly** in the tmux session (`new-session -c <dir> -- <argv>`),
  never through the person's interactive shell: rc files change directories, set aliases and
  print banners, and any of those moves or breaks a launch. The `shell` adapter is the one place
  the person's shell is the point. **One exception to *directly*, and it keeps the rule's
  point:** tmux refuses a command line past its message size (*command too long*, about 16 KB).
  Past 8 KB the argv is written to a launch script under
  the home (`launch/<tmux name>.sh`, mode `0700`) that `exec`s it under `/bin/sh` — never the
  person's shell, no rc file — so the pane's first process is still the command itself and the
  limit that applies is the kernel's.
- **No prose in the argv** (TD-336). A session's argv
  names the tool, its flags, its ids and paths — never its brief and never its start context.
  A process's command line is read by everything on the host — `ps`, `pgrep`, `pkill -f` — and
  a `pkill -f` in a script a session runs can match a word in the brief riding in that session's
  own argv and kill the session running it; no rule in a brief can guard against a script the
  session does not read. So the two texts travel
  another way. **The start context is a file**: written under the home beside the launch script
  (`launch/<conversation id>.context.md`, mode `0600` — the tool's id, since the launch is asked for
  before the tmux name is chosen — removed when the last record holding that conversation is
  forgotten, or replaced in place by a create of another conversation) and
  named by the tool's file flag (§4.3), at every launch of the conversation as before. **The brief
  is typed, not passed**: every launch lands at the composer (the no-prompt launch of §4.2, now the
  only kind), and the host agent sends the brief as the session's first prompt the way `ao send`
  does — bracketed paste, the composer must empty, `prompt-stuck` otherwise (TD-027) — once the
  record's first `idle` arrives by hook. The launch record keeps the brief as `first_prompt` until
  it is sent (`first_prompt_sent_at`); a send the composer does not take is tried again on the next
  tick while the session sits idle, `FIRST_PROMPT_TRIES` (3) in all, and then the record carries
  the refusal (`first_prompt_error`) and the card says *brief not sent · <reason>* (§4.5a) —
  the session is live at its composer with nothing to do, which a person or its manager can see
  and cure with a send. What a person sees is unchanged: the brief is still the conversation's
  first turn on Focus and in the transcript, a `create` still returns when the pane exists, and
  the record reads `working` when the brief's turn starts rather than at the launch. The argv
  that is left is a few hundred bytes, so the launch script is for an argv a profile's
  `extra_args` made long, and nothing else. The fields are `LaunchSpec.first_prompt`, the
  record's `first_prompt` (off the pushed view, as a body is), `first_prompt_sent_at`,
  `first_prompt_tries` and `first_prompt_error`; the tick's send runs on the host that holds the
  pane — into an empty composer, or Enter again on one still holding an earlier try's brief, never
  the text twice — the doorbell is held off until the brief is typed, the send is recorded in
  `sends` from `system` as *(the brief)*, and the hook's `prompt` word on `UserPromptSubmit` clears
  the mark. The Claude Code adapter writes the context file (`paths.context_file`) and names it with
  `--append-system-prompt-file`, hands the prompt back as `LaunchSpec.first_prompt` and sets
  `SHIFTLEAD_AT_COMPOSER=1` on every launch but a resume, whose `source: resume` says it; a resume id
  that is not a plain file name is refused.
- **The brief is the person's word, and the tool is told so** (TD-343). A bracketed paste reaches Claude Code's model wrapped as pasted content, with
  the tool's own rule that instructions inside it are followed only where the user's own words ask
  for it — and a brief typed as nothing but a paste is, to a careful model, data: a seat can answer
  its brief that it holds only pasted text and nothing saying what to do with it. So the brief
  travels with two fixed texts around it that no sender chose: the typed line, in the person's
  voice, and the preface. **The typed line**: the first prompt is typed as one line in the person's
  voice — *My brief for this session is pasted below; read it and act on it.* — followed, in the
  same prompt, by the brief as the bracketed paste; the line is literal keys, the brief the paste,
  one Enter, the same submit confirmation (TD-027). The line is the person's words, not a notice
  from shiftlead: it heads the person's own turn on Focus, and it is typed before every first prompt
  — a role's brief, the New session form's Opening prompt, or the opening prompt a Start session
  sends (§4.5a, `briefs/work.md`) — and calls each *my brief*. The opening prompt a Start session
  sends is already written in the person's voice, so a line about the person in the third person
  read as a system message inside it. It is the same line for every starter, a lead or director
  starting a member too: whoever wrote the text, the person sent it deliberately, by pressing the
  button that started the session or its team. **The context file's preface**: the file
  `--append-system-prompt-file` names begins with a fixed paragraph of the
  home's that says the same — that the session was started by a person through shiftlead, that its
  brief arrives as the first prompt, one line in the person's voice, typed, and then the brief,
  pasted, both by the host agent on the person's behalf, and is to be acted on as the person's
  instruction, and that a later `[shiftlead] you have n unread messages` line is the host agent's
  doorbell — and the caller's start context, when there is one, follows it; a launch with no start
  context still has the file, for the preface. The brief itself stays the conversation's first turn,
  on Focus and in
  the transcript, and nothing of TD-336 moves: no prose in the argv, the paste as before, the
  record's `first_prompt` fields as before. Not taken: the brief inside the context file with a
  fixed *begin* as the first prompt — the system prompt is trusted outright, but the conversation
  would then open with no brief in it, a resume would re-give the brief on every launch, and
  *Brief changed* (§6 rule 7) would read a system prompt rather than a turn. The
  line and the preface are `mail.BRIEF_LINE` and `mail.BRIEF_PREFACE`; the tick's first send types
  the line and a space as literal keys, then pastes the brief (`_type`'s `lead`); `create` hands
  every adapter that carries a start context `mail.start_context_file_text` — the preface, then the
  caller's start context after a blank line — so the adapter's file is written at every launch, while
  the record and the launch record keep the caller's text alone. **A brief whose first hook
  is lost** (TD-342): the send waits for the record's first
  `idle` by hook, and a run whose first hook never lands (refused, dropped, a hook config that did
  not load) would make no try and show no mark. So the wait is
  bounded: `FIRST_PROMPT_HOOK_WAIT` (two minutes) after the launch with `first_prompt` unsent and
  no hook event on the record, the tick sends it once when its composer reads
  empty, whatever state the record reads (TD-717, below) (the one send the scraped reading is trusted for, since the pane is the launch's own and
  nothing else has typed into it), and the hook's `UserPromptSubmit` confirms it as any send; if no
  idle is scraped either, or that send does not submit, `FIRST_PROMPT_BOUND` (five minutes) after
  the launch writes `first_prompt_error` *no hook since launch* and the card's *brief not sent* mark
  says it (§4.5a); the send on a scraped idle is marked `scraped` on the record's `sends` entry, and
  a composer holding someone's words is waited past, uncounted, as at a hook's `idle` — the cure as before, a send by a person or its controller. A hook that arrives
  before the bound, the brief still unsent, is the ordinary case: its `idle` sends as before; one
  that arrives after the mark clears nothing by itself — the brief is then sent by a person's hand,
  or by the replay below.

  **A launch whose hook never comes is recovered, not only marked** (TD-717). On 2026-10-15 a
  techlead seat was filled five seconds before an auto promote restarted the host agent. Its
  `SessionStart` hook failed and no hook ever reached it, and it sat at an empty composer for eight
  hours while two held-PR asks lapsed. Four rules close that:
  - **The scraped send reads the composer, not a state.** A Claude Code pane at its empty composer
    matches no screen rule. So a hook-fed record that no hook reaches stays `working` and then reads
    `stalled?`, and a scraped `idle` never comes. The one scraped send therefore waits for no state:
    `FIRST_PROMPT_HOOK_WAIT` after the launch, with no hook ever on the record and no try made, the
    tick sends once when the adapter's `composer` reader reads the composer **empty**. The record may
    read `working`, `stalled?` or a scraped `idle`, but not `needs-you`, `exited` or `closed`. A
    dialog (`None`) or someone's words wait, uncounted, as before. An adapter with no composer reader
    keeps the scraped `idle` road. No screen rule is added for the empty composer, since it would
    read every quiet live session as `idle` by screen, which is a hook's word (§4.2).
  - **"No hook since launch" survives a restart.** The record keeps **`hook_seen_at`**, written by
    the pane's host at the first hook event that reaches it. At load, the agent counts a record as
    freshly hook-fed only when it carries this field, or when its brief is no longer due (sent, or
    never had one): a record that existed before the field, live and hook-fed, then keeps the seeding
    it has today, and a screen rule never outranks its hook state after the promote that brings the
    field. It used to count every `confidence: hook`
    record, and a new Claude Code record is `confidence: hook` from its create. So an agent restarted
    seconds after a launch counted the launch's missing hook as one just heard: it made no scraped
    send, and wrote no mark until a later restart found the record `stalled?` (47 minutes on
    2026-10-15). Both waits count from `created`, across restarts.
  - **The mark acts on an unattended record.** A supervised record, a team member or a seat, marked
    *no hook since launch* is **replayed once** by the tick (§6 rule 1's replay, a seat included,
    since its run never started). The record is live, at an empty composer or reading `stalled?`, so
    the tick first closes it (closer `{by: tick, why: lost-brief}`), as rules 2 and 7 close a live
    record before their replay; the run never started, so nothing is dirty or unpushed and no
    `restart_blocked` is read into it. The replay is then a `create` with `keep_mail` from its launch record,
    and `restarts` gains `{at, why: "lost-brief"}` (counted in `RESTART_CEILING`). The asks and steers
    in its inbox move with the mail. Each sender of one still open is told by a system note, *the
    brief of techlead-ao-1 was lost at its launch; it was relaunched at 08:47 and reads your ask now*.
    The ask's bound is unchanged. A record that came from a `lost-brief` replay and loses its brief
    again is not replayed: it keeps the mark and is the person's (§4.5a *Inbox row: restart*, *brief
    lost twice*, written as `restart_ceiling: {at, count, why: "lost-brief"}`, its words carrying no count), and keeps its *brief
    not sent* mark meanwhile. A seat's replay repeats its fill's context: the fill's *why it came*
    line and `seat_filled`, as rule 3's fill wrote them. It counts in `RESTART_CEILING` and not in
    the fill ceiling, which counts fills alone. A close that fails is the replay's `error`, as
    rule 1's failed replays are. A marked record that is not supervised (a person's own session) is left to its
    cure, a send, as before.
  - **A promote and a launch do not wait for each other.** The rules above recover a launch that a
    restart cut short within `FIRST_PROMPT_BOUND` plus one launch, so neither a fill nor a promote is
    held. **The hook keeps its traceback**: `shiftlead-hook`'s entry point is a module of the
    standard library alone, `shiftlead.hook_entry` (the `shiftlead` package's `__init__` is empty,
    while `shiftlead.adapters.claude_code`'s imports `sessionorc`), which imports the hook inside a
    `try`. An exception there, which is what a half-replaced install would raise, is appended to
    `hook-errors.log` under the home, found from `SHIFTLEAD_HOME` or `~/.shiftlead` without
    `sessionorc.paths` (the last 256 KB kept), with the session and the event. Claude Code still shows its one-line *hook error*.
- `history-limit` is raised at creation; `pipe-pane` streams output to
  `~/.shiftlead/runs/<session>-<created>.log` continuously (a reboot loses nothing that reached
  the pipe).
- Directory is the repo checkout, a worktree, or — with no repo — any directory the person
  names (recent directories remembered per host). The anchor rule (§9) is about directories, not
  checkouts: one *agent* session per directory; a repo's worktrees are just extra directories.
  Shells and `kind: command` runs are exempt — the rule is scoped to `kind: interactive` sessions
  with a non-`shell` adapter — because the person is not what the rule protects against, and a
  shell or a test run next to an agent in the same directory is the common case.
