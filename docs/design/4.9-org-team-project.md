### 4.9 Org, Team, Project: the definitions above a session

The vocabulary is [ADR 2026-09-13](../decisions/2026-09-13-org-teams-projects.md); this section is
what the code does with it (TD-040). A **project** says where repos are, a **team** says which
roles to start in them under which manager, `ao team start` is the one action that launches the
lot with the right `controllers` and checkouts, and the Sessions page shows the result grouped. There
is no second membership list: a team's members at runtime are the sessions whose `controllers`
name its manager (§4.8); the definition only says how to start them.

**Where definitions live.** One org-level file per UI host, `~/.shiftlead/org.yml`, beside
`profiles.yml` and `hosts.yml`, holding `projects:`, `teams:` and an optional org-wide `roles:`;
the org's own flows and defined roles sit beside it as directories, `~/.shiftlead/flows/` and
`~/.shiftlead/roles/` (§4.9c).
A project is a heading over repos (TD-722), so it belongs in no one repo's `.shiftlead.yml`;
that remainder is per install (the ADR of 2026-09-13 says *one org per install*;
TD-210 amends it: a team of one repo is defined in the repo, *The org is an aggregate*, below), so its file is. A repo's `.shiftlead.yml` may also
carry `teams:` — teams whose repo is that repo; on a name collision the org file wins,
and `ao team list` names each definition's source. Both files are read on every use and cached
nowhere (the profiles rule), so editing the file is the whole edit. They are read by the
**clients** — `ao team`, `ao new`, the UI's New session and Sessions page — never by the host agent: a
team start is an ordinary sequence of `create` RPCs, and the host agent stores `team` and
`project` as two plain strings on the record. `sessionorc` stays free of org vocabulary (it never
imports `shiftlead`), and the host agent needs no restart when a definition changes.

**The org is an aggregate of what the repos define** (TD-210; one function, `org.with_repos`,
that `ao team` and the pages both read). A team that works one repo is **defined in that repo**, in
its `.shiftlead.yml` — `teams:`, the `roles:` it uses with their `review:` paths, the briefs
beside them — so it has the repo's history, is changed by PR and is read by whoever clones the
repo. The org a client sees is the union:
- **Every registered checkout's teams.** The clients, `ao` and the pages alike, read `teams:`
  from the `.shiftlead.yml` of each checkout in the host's repos registry (§5 `hosts.yml`
  `repos_registry`, else the home's own roster with dev-cadence's imported — *Repos*; every repo on it is read, and one with no
  `teams:` adds nothing), **as it is checked out**: a branch checked out in a registered
  checkout changes the org while it sits there, as it changes a brief, and `ao org check`
  says which checkouts are off their default branch or hold changes. **The repo is the team's repo**,
  unsaid (TD-722): its name the checkout's directory name, its path on a host that host's registry
  entry, and its project the org file's project that lists it, else none — a heading of its own. A
  `repo:`, a `host:` and a nested `{team: …}` member on a repo's team are each refused by name:
  the repo is the file's own, placing is the org file's, and a team never works a repo other than
  its own; an `anchor:` is refused as retired (*A definition written before TD-722*, below). A brief and a seat's `context:`
  are read from the checkout on the host the team lands on.
- **The org file's**, which is now the remainder: the **project headings** (*Projects*, below), a
  **team kept out of its repo's file** (one whose repo holds no `.shiftlead.yml`, or that the
  person keeps to this install); the org-wide **`roles:`** overlay, which is where a role gets this
  install's profile; and **`place:`**, `{<team>: <host>}`, for a repo-defined team that lands
  on a node. A repo's file names no host. A `profile:` written there is only a name, which the
  install's `profiles.yml` has to hold; the overlay is the better place for it, and `ao org
  check` says when a name is not held.
- **A definition is read at the home, and only there.** A repo that defines a team is
  registered at the home, whichever host the team works on: the home's checkout is what the
  definition is read from, as the repo's ledger, its PRs and its board are (§4.4 *Repo facts*),
  and `place:` puts the work on a node. **A repo registered only on a node defines nothing the
  org sees**: no client reads a `.shiftlead.yml` across the link, since a team whose definition
  sat on a laptop would leave the org each time the laptop slept, taking its card and the
  settings keyed on its name with it. `ao org` lists such a repo under its node — *held only
  on `<node>`: its .shiftlead.yml is not read; register a checkout at `<home>`* — and `ao org
  check` warns in those words (§4.7), from the node's registry, which the
  home's `host_repos {host}` RPC returns through the node's `repos` link method (a read like
  `host_dir`). A node whose registry cannot be read
  is *unknown*, said as a note, never *holds nothing more*.
- **Where a repo's team lands**: `place:` when it names the team; else this host, whose
  registry holds the repo because the definition was read from it (`org.landing`, applied by
  `org.with_repos`: those two clauses and no third). A team `place:`
  puts on another host takes that host as its `host:`, and the repo's path there is the one
  entry of that host's registry with the checkout's name (the CLI asks at each read, the pages
  keep the answer five seconds and wait two for it, a slower host reading as unknown until it
  answers); where the org file has a project of the repo's name, its paths are used and
  nothing is asked, and one with no path on that host is the reason given. A `place:` naming
  a team no registered repo defines is a note. A registry that cannot be read, or that holds the name
  not once, leaves the team listed on its host with the reason as a note, and its start
  refused in those words. `place:` naming a team the org file defines is refused when the file
  is read: that team's own `host:` places it.
- **Names are the org's.** Two repos that define one team name are both refused, each naming
  the other, since a team's name keys its settings (§5 `teams.<team>`) and its badge. The org
  file still wins a name over a repo, which is how an install overrides a repo's team without
  a PR; `ao team list` says *shadowed by org.yml* on the repo's. **`interactive` and `outside` are
  reserved** (§4.4 *Spend per seat*, TD-818): a team named either is refused when the definitions are
  read, by `ao org check` and by every start, naming the reason. **An agent's name is its repo's**
  (Paul, 2026-10-15): a session's id is `ao-<repo>-<name>`, so every session name the teams on one
  repo start — managers, techleads, seats and members — is unique across
  all of them. A name two of a repo's teams both give is refused when the definitions are read,
  by `ao org check` and by every start of either team, naming the two teams and the name; a
  member renamed by its definition is checked as it reads after the change.
- **A repo's held paths are the repo's** (TD-209). `review:` is written whole, `reader` and
  `held` together, on the role in the repo's own `.shiftlead.yml`, the last layer of a preset
  (a layer's `review:` replaces the one under it, and one with no `held:` holds every path),
  so shiftlead's `src/sessionorc/**` is not carried into dev-cadence by an org-wide role. **The
  org file's role carries no `review:`**, only the profile: a role with none takes its team's
  (*A person in the team*, below), which is none where the repo wrote none.
- **On a node** nothing changes: `ao team`, `ao org` and the pages refuse and name the home,
  where the org is read (§4.4a).
- **Members…** (below) edits the org file and nothing else. On a repo-defined team it is
  drawn disabled, *defined in shiftlead's .shiftlead.yml — changed by PR*, with **Open file**,
  and `edit_members` refuses any file but the org's: a
  press that committed to a repo's default branch would go round the repo's review. A team a
  person wants to reshape from the page stays in the org file.

**What is left at the home has a history** (TD-210). `org.yml`, `profiles.yml` and
`settings.yml` stay files under `~/.shiftlead/`, where every reader finds them, and at the home
the directory becomes a git work tree that tracks those three — and the org's `flows/` and `roles/` directories (§4.9c), every file under each, and the person's own preferences, `preferences.md` (§4.9b *The director answers what is passed up to it*, TD-657; a proposal beside it is not tracked until **Accept** moves it over) — and ignores the rest: sessions,
runs and mail are state, and `hosts.yml` is this machine's own name and links, which another
machine must not inherit. **The home's host agent is the one committer**, so two writers never
meet on the index: it commits after its own `set_settings` (*settings: usage_gate.grind.week
30 → 20*; detached from the reply, so a slow git never holds Save), when a client asks with the act's words after **Members…** wrote (*org: ao-grind
+grinder-ao-3*, the `commit_defs` RPC, a person's own), and on the reports' cadence for a hand
edit, as *edited by hand*. It runs `git add` and `git commit` on the three and the two directories and reads none of
them for meaning (it still reads no `org.yml`); a file that does not parse as YAML is left
uncommitted until it does, and a commit that fails is logged and never fails the write. It
commits as *shiftlead*, with the person's git hooks and signing set aside for its own commits
(`sessionorc.defs`), and a home that is not a work tree yet commits nothing until `ao service
install` makes it one. So
`git -C ~/.shiftlead log -p org.yml` is the file's history and the `org.yml.bak-*` copies have
no more work to do. A home made a work tree before the directories were tracked gains their
`.gitignore` lines in its next commit. A node's replica of `settings.yml` is not tracked. **The home never
pushes and adds no remote**: a copy off the machine is the person's own `git remote add` and
push; the daily backup carries the three files, not their history. No secret is in any of the
three (Doppler holds them). The home's work tree is never a checkout a brief is merged into: a
brief kept under `~/.shiftlead` is read from disk, whatever remote the person adds (§6 rule 7). **Standing
the org up on another machine** is then the repos and the remainder: clone the repos and
register them, bring the three files (a clone of the person's remote, or a copy), write that
machine's `hosts.yml` as any new host's is written, and `ao org check` says what the
aggregate finds and what it lacks.

**Projects.** A **heading on repos** (TD-722; Paul, 2026-10-15: *a project heading*, placed *on the
repo*): a named list of one or more repos, each with its checkout path per host, and an optional
`title`, the words the Sessions page draws (the name where there is none):

```yaml
projects:
  contractmatch:
    title: ContractMatch
    repos:
      samscrape:     {kmaster: ~/samscrape}
      contractmatch: {kmaster: ~/contractmatch}
  guardians:
    repos:
      guardians:     {devenv: /workspaces/guardians}
      guardians-api: {devenv: /workspaces/guardians/api}
```

The repo name is the project's word for it; session ids keep using the checkout's directory
name. **A repo sits in at most one project**: a second listing is an error naming both projects
when the org file is read, as an unknown key is (`ao org check` says it too). **A repo in no
project is a heading of its own**, named after the repo, so every repo has exactly one heading. A
team's project is its repo's (*Teams*, below). Nothing acts on a project but the mail gate (§4.10
*across teams, by project*) and the brief's **Project** block (*Home and reach*); the Sessions page draws
it as a heading (*The Sessions page*). A project is a grouping over checkouts that exist, not a place to
register a repo — the roster is (§5 *Repos*: `repos.txt` under the home, dev-cadence's imported) — and `ao team start` refuses with the
missing path rather than cloning anything. A team lands on one host (its `host:`, below, else
the one the start runs on); a repo's entry for any other host is a note inside the Project
block, not a start.

**Teams.** A manager plus members as (role, count), **on one repo** (TD-722; Paul, 2026-10-15: *one
repo per team, declared. We still want to be able to have multiple teams per repo … and those can
be listed together (per repo) but not auto-combined*):

```yaml
teams:
  ao-grind:
    repo: shiftlead
    manager: {role: manager, name: manager-ao-1}
    members:
      - {role: grinder, count: 2, name: grinder-ao, lane: free-pick}
      - {role: hunter, name: hunter-ao, lane: ui}
  guardians-api:
    repo: guardians-api
    host: devenv                      # every session lands on that node (§4.4a "Teams across hosts")
    manager: {role: manager, name: guardians-api-lead}
    members:
      - {role: grinder, brief: docs/briefs/api-grinder.md}
  guardians-ui:
    repo: guardians
    host: devenv
    manager: {role: manager, name: guardians-ui-lead}
    members:
      - {role: grinder}
```

`repo` (on the team): the repo the team works — a name a project lists, or a registered
checkout's directory name (§5 *Repos*) — **required in the org file**, and unsaid in a repo's
`.shiftlead.yml`, where it is that repo. Every session of the team works in it — manager,
techlead, seats and members — so none of them carries a `home`. **A repo has any number of
teams** (a db team and a compliance team on one repo): each is its own team with its own card,
listed together under the repo and never combined (*The Sessions page*). Each team's entries are its
own by the ledger's `Team:` line, declared on its `Fields:` line, and `ao team start` refuses a
team of a repo with two or more teams whose ledger does not declare it (§4.4 *An entry names its
team*, TD-730). What spans repos is a heading
over teams, never one team: a function across repos (docs, audits, dependency bumps) is a role or a
flow stage in each repo's team; a product over several repos is one team per repo under one
project heading, sequenced by cross-repo `Blocked by: <repo>#TD-NNN` (cadence §2.4) and settled by
mail (§4.10 *across teams, by project*). The guardians teams above are that shape: two teams under
the Guardians heading, where they were one team with a nested one.

`host` (on the team): the host every session of the team lands on — a `nodes:`
entry of the home — default the host the start runs on. Checkouts are resolved on it.

`manager`: `role`
(default `manager`; **`person`** means the person manages — no session is started and members
get an empty `controllers` list plus the team badge), `name` (default `<team>-lead`), `profile` (overrides the role's), **`on_call`** (`true` makes the manager a seat filled on §6 rule 3's `team` trigger and closed when it
has acted, §6 *What is left is judgement* — a Start writes its record with no pane (a `create` with
`held`), and the first due reading fills it (§6 rule 3 *A Start writes the seat and never
fills it*); `false`, a standing session that rounds on `ao wait`;
the default is `true` (`org.ON_CALL_DEFAULT`), a team keeping the shape it was started with until its next Start; the default is the `manager` role's alone, whose template has a seat's shape (`repoconfig.ON_CALL_BRIEFS`) — another `manager`-kind role named as manager is a seat only where its definition says `on_call: true`; and a manager is read as a seat from its record's `seat`, never from the definition alone, so a standing manager started before the definition read *on call* is drawn, counted and concluded as the session it is (`teamrun._seat_of`); refused beside `role: person`, which starts nothing to
fill, and refused on a member, where `MEMBER_KEYS` would otherwise inherit it), and the same `lane`, `brief`, `grants` and `unattended` a member may carry — a manager's brief is the one a repo most
often supplements (§4.8: a repo's brief fills the template's `{repo}` slot and never replaces the
template). Unsaid, `grants` means the role's; an explicit `grants: []` on a
manager means *none*, which leaves it unable to act on its own members, and is written only on
purpose. **A key nobody reads is an error naming it**, in a team, a manager or a member: silence
about a typo is how a manager's `brief:` disappears into a file that looks right. A `brief:`
anywhere in a definition names a file that has to be repeatable (§4.8): this command is the
restart, so a brief written for one run strands the next one. The start warns and proceeds when
it finds a clock time or a run number in the text it is about to hand over.

`anchor` (on a team or a repo): **retired** (§4.9b *No anchor seat*, 2026-10-15) — no team starts a seat in a checkout. `anchor: false` is read and passed over — only because no definition writes it today, and it says what is now true; any other value is refused as retired (*A definition written before TD-722*).

`entries` (on the team, TD-180): `{feature: <role>, debt: <role>}`, the role an
interactive session takes when the person opens one from **Add entry…** (*Add an entry to the
ledger*, below); either key may be left out and reads `techlead`; a role nothing resolves — not a
preset, not the org's `roles:`, not a role the repo's own file defines for its own teams, not one
the team's definition starts — is an error naming it when the definition is read, as an unknown key
is. `ao team list --json` carries each team's `entries` with both types said.

`flows` (on the team, TD-307): the flows the team may run,
the first its default; which one it runs now is `teams.<team>.flow` in `settings.yml` (§5), a setting
the person turns, and the current flow gives its members' default lanes, its workers' reader, its
`entries.feature` default, its briefs' `{flow}` and `{stage}` slots, and which members sit out
(§4.9c). Absent, the team has no flow and starts as it does today; every flow it lists must be usable,
or the definition is refused saying why, and followable by its members, or the team's Start is
refused and its card says why (§4.9c).

Each member: `role`, `count` (default 1; a count above one suffixes the name `-1`, `-2`, …),
`name` (the prefix; default the role), `lane`, `brief` (the repo's supplement to the role's template, §4.8),
`profile`, `grants` (default the role's), `unattended` (default **true** — a team is what runs
while the person is elsewhere; an interactive member is the exception and is said so). A member
that is `{team: <name>}` is refused by name: teams that work together are teams on one repo, or on
repos under one heading, and settle things by mail (§4.10), so no team holds another (TD-722).

**A definition written before TD-722** carries `projects:` on a team, `home:` on its manager,
techlead, a seat or a member, or `anchor:` on the team or the repo. Each is **refused by name** when the
definition is read, as any key nobody reads is (*a key nobody reads is an error naming it*,
above), the message saying the fix: *ao-grind: `projects:` is gone — write `repo: shiftlead`*;
*ao-grind: `anchor:` is retired — the anchor seat is gone (§4.9b *No anchor seat*); delete the
key* — except `anchor: false`, which says what is now true and is read and passed over; and, for a team whose old keys named more than
one repo, *guardians spans guardians and guardians-api: a team works one repo — split it into a
team per repo under the guardians heading*. There is no release of warnings: no live definition
carries the old keys, and a warning would leave a second reading of the same team to unlearn. The
team's card says the refusal as any refused definition's does, and `ao org check` lists each. The
person's org file is edited by its backfill (TD-723), not by the build. **The retired seats'
records**: a leftover `<team>-anchor` record is retired by the build's migration — a closed one
forgotten, a live one closed first — and each repo's `Owner: anchor` entries are moved to their
takers (§4.9b *No anchor seat*) before it, so nothing waits on a seat that will not come. **`repo:` resolves to a
path**, on the host the team lands on, in this order: the path the project that lists the repo
gives for that host; else the one entry of that name in that host's registry (`_land`'s rule,
*Where a repo's team lands*, above); else the start is refused in `_land`'s words.

**Home and reach.** Every team session's home is a worktree in its team's repo named after the
session (`<repo>/.claude/worktrees/<name>`, the New session "new worktree" rule in §4.5a), so the
main checkout stays the person's and the anchor rule (§9 invariant 2) holds per member without
anyone counting. The record's `dir` and `repo` are the home, as for every session; `team` and
`project` are badges, like `role` — nothing that acts keys on them but a team's own settings (§5
`teams.<team>`) and the mail gate (§4.10 *across teams, by project*; §9 invariant 9). A team
session's `project` is its repo's project, and the repo's own name where no project lists it, so
two teams on one repo always share one (TD-722). Reach is the ADR's
phase-1 meaning: when the team's project has more than one repo, the session's brief is prefixed with a
**Project** block that names each of the project's repos' checkouts on this host and which one is
the team's. **Reach is reading, not a second home**: a member's reach into the project's other
checkouts is what it was; whether it commits or pushes there is its brief's, and the anchor rule
counts the sessions in a checkout, not the commits that land in it (§9 invariant 2). The
director, the org's and no team's, carries the **Org block** in place of a Project block (§4.9b
*The director seat*). That is the whole of it — no credential, no permission. A hand-started
session in a registered repo carries its repo's `project` badge and gets the same block, both
read from its directory's repo: there is no `ao new --project` and no Project picker (TD-722);
a session in no registered repo carries neither.

**Starting and stopping** (`shiftlead/teams.py` plans a start and `ao team` runs it). `ao team
start <name>` resolves the definition, then checks *everything before launching anything*: every
checkout exists on this host, every role and profile resolves (a profile that runs the shell is
refused, below), and every session name is free under §4.1's rule — a live holder refuses the whole start and names it, so there is never half a
team (a member the team's current flow sits out is not started, and is no half: §4.9c); a holder a person suspended over an identity alarm (§4.8a) refuses it for the same reason;
exited or closed holders are superseded as §4.1 says, which makes `ao team start`
after a night's exit the restart too. Then it creates the manager (its grants, profile and mode —
the role's `control`, the host's profile and unattended, unless the definition overrides any of
them — in a worktree), and each member with `controllers: [lead id]`, its role, lane, brief (the
role's template with `{lane}`, `{techlead}` and `{manager}` filled — `{manager}` the id the manager takes, worked out before anything starts as `{techlead}` is, said by the start should it come up under another, and `none` where a person leads or the session was started by hand — the Project block in front — and a `brief:` in its `{repo}` slot rather than in place of the template),
profile and worktree. Each is created with its profile's own adapter, so no record names a
profile whose tool it is not running; a profile whose adapter is the shell's is refused for any
team session, in the words `ao team start`, Start and `ao org check` share, since a team session
runs a brief and a shell cannot. A person runs it, so no attenuation applies (§4.8 create rule); a manager
running it is subject to it as for any create. It prints one line per session with the id,
`--json` the records. The manager is started with an empty `controllers` list: the definition,
not a repo default, is the authority over a team session, and it is a person who runs the start.
A member the definition starts **interactive** keeps its `controllers: [lead]` but is out of its
manager's reach for as long as it stays interactive (§9 invariant 5), so the
start says so in one line per member rather than leaving a list that silently never fires. The
`project` badge a session carries is its team's repo's project, the repo's own name where no project
lists it (*Home and reach*); a repo sits in one project, so there is no other to name.

`ao team stop <name>` sends the wrap-up prompt (the one the card's Wrap up sends, §4.5a) to each
member, waits for each to go idle or the wrap-up window to pass, then to the manager; `--now`
kills instead of asking. It waits on each member's *state* (idle, exited or closed, or a
`--timeout` window, default 300 s), which is what a client can see — "wrapped up" is not a state
the record carries. `--close` (§4.9a) also closes each member that settled with nothing to lose —
no uncommitted file, no unpushed commit — and names any it left open. *Pushed* needs proof, and
the proof is §4.2's one measure (`git.unpushed` = 0 with a `pushed_against`); a record
whose git state is not known yet is left open, never assumed clean: a wrapped-up Claude Code
session sits `idle` rather than leaving, and `ao team start` refuses while a session holds a
member's name. `ao team status <name>` is the manager's Members view for a terminal: each member
with state, lane and report line; under `--json` each row also carries `unattended`, `seat`,
`out_of_work` and `restart_wanted` as the record has them, and the reply carries `finished`,
the home's reading of the team (§6 rule 9) — `{at, restart, names, why}`, holding when `why` is empty, and none for a team with nothing live — so
a manager's round reads what the tick reads. `ao team list` shows every definition, its source file, and
whether it is live. A team is **live** when any **unattended** session carrying its badge is live (a person's own session in the team keeps nothing
live, *A person in the team* below); there
is no team record — a stopped team is only its definition.

**A person in the team (TD-160).** A person's own session in a team gets the team's reader, is
started from the team, and is left alone by every team act.

- **The reader comes from the team, not from a role a person must choose.** A session started
  with `--team <team>` (the CLI or the form) whose role carries no `review:` of its own takes the
  team's: `reader: techlead` when the team's definition holds a techlead seat, and `held:` the
  union of the `held:` lists of the team's member roles — a person in the team is held to the
  paths its workers are held to, no more. Under a flow (§4.9c item 3) it takes what a member
  stage's role takes: the flow's chain of readers on the repos' top-level `held:`, and no reader
  under a flow with no review stage; its role's own `review:` is set aside there as every role's
  is. Filled at start onto the record's `review`, as a member's is from its role (`ao team
  start`), and read only there (§4.9b: whether a PR is held keys on the record's `review` and the
  PR's paths). In a team with no flow a role's own `review:` wins, so `org.yml` may still say
  `plain: {review: …}`; a team without a techlead seat gives none, and the form
  says so. Nothing new keys on the badge: the badge picks the definition at start, and the
  record's field is what the gate reads (§9 invariant 9).
- **The New session form gains a Team field** (§4.5a *New session* **Team** picker): every team
  of `org.yml` and the repos' `.shiftlead.yml`, or *none*; picking one narrows Host and the
  Directory list to the team's host and its repo, filters Role to the team's roles plus `plain`,
  prefills Controllers with the team's manager when it is live or a seat on call (as `ao new
  --team` does; a seat's id is the fill's, §6 rule 3), leaves Unattended off, and shows the reader the session will get (*held PRs read by techlead-ao-1 on
  src/sessionorc/**, docs/briefs/*** — or *no reader: the team has no techlead seat*).
- **The team's card offers it**: the last card in a
  defined team's grid is the **+ card** (§4.5a *team card: + card*), whose press is this form with
  the Team pick made — a person's session in the team starts from the team, on the Sessions page, not from a
  pick in the top bar's form. Members… stays the definition's: a member added there is a permanent

**Add or remove a member from the team card (TD-163).** Growing or shrinking a running team is
the one change a person makes by watching it. **It is the first control that edits a definition from
the page**, and the settings audit's line holds (ADR 2026-09-25 §5: *a definition says what a team
is and belongs in its file; a setting is a number a person turns*): the control sits on the team's
card, not on the Settings page, and it edits the file as the file is.

- **What is edited.** `teams.<team>.members` in `~/.shiftlead/org.yml`, **as text, in place**: the
  client that serves the page (the UI process, as `ao` would) finds the team's `members:` block
  and edits one line — **add** bumps the `count:` of the member line whose `role` matches and
  carries a `count` above one (the name pattern `<name>-n` gives the next number; a `count: 1`
  names its one session without a number, so bumping it would rename that session), else appends one line
  `- {role: <role>, name: <name>, lane: <lane>}` after the block's last member line, at the
  block's indent; **remove** decrements that `count` (the highest-numbered member goes) or deletes
  the member's one line. Comments, order and spacing stay because nothing is re-serialised
  (`pyyaml` keeps no comments, so the file is never round-tripped). Refused, with the reason, when
  the edit cannot be one line: a member written as a multi-line mapping, a team the file does not hold on one `members:` block, a name the team's definition
  already holds — the manager's, the techlead seat's or a member's, refused before anything is
  written (*dc-grind already has grinder-dc-1*) — and always for a team defined in
  a repo's `.shiftlead.yml`, which is a PR's (*edit it in the repo; this card only reads it*). After
  the write the file is parsed again (`org.load`); a parse that fails restores the bytes and
  refuses, so a definition is never left unreadable. The org file is read per call and never by the
  host agent (§4.4a), so the next `ao team list` and the next page load see the change.
- **When it takes effect.** On a **stopped** team, the definition only: the next Start brings the
  new shape. On a **live** team, **add** plans the team (`teams.plan`) and creates that one member
  under the manager — the same create `ao team start` does for a member, the name check and the
  anchor rule included, `controllers: [manager]` — so the card appears in the group without a
  restart; **remove** of a live member is that one session's wind-down by the home's sit-out form
  (§4.9c *Switching*: the wrap-up prompt and a stop now, as **Wrap up** sends them; a `working` member
  finishes what it holds), never a kill; of a member not live, the definition and the mark. **A
  removed member is marked sat out** (*A member renamed or removed*, below) — the live one once the
  home has closed it, an ended one as it stands — so rule 8 never replays it. Its record **stays a card until Forget**, as any exited
  member's does; the definition no longer names it, so no seat is drawn on call for it, and Forget all
  takes it with the rest.
- **The surface.** **Members…** on the team card's header, beside Start on a stopped team and
  beside Wind down on a live one (§4.5a *team card: Members…*): a dialog listing the definition —
  the manager, the techlead seat when there is one, and each member entry as *role · name · lane ·
  count*, with the session holding it and its state, or *not live* — and two controls: **Add
  member** (a role from the org's roles, the name defaulted to the team's pattern with the first
  number no name of the team holds — `grinder-dc-2` beside `grinder-dc-1`, the next of a counted
  entry's numbers, the role itself for a role the team has none of — never an existing name, save a counted
  entry's next when another entry already holds it, which Add then refuses; the lane from the role's default, editable before the
  press) and **Remove** on each member entry, whose confirm names the consequence: *edits
  `org.yml` (count: 2 → 1) and winds down grinder-ao-2; its card stays until Forget*. A definition
  that already names one session twice (an older add could write one) says so under the
  list, and **Remove** on either line takes the line out and winds nothing down: the other line
  still names the session, which runs on. The manager
  and the techlead seat are listed and not removable here: a team without its manager is a different
  definition, made by hand. Not on the Settings page: its Teams section holds settings (schedule,
  until, reserve), and a member is a definition.
- **The ADR's line, restated.** A definition is edited by a control on the thing it defines, as
  text, preserving the file; a setting by the Settings page through `set_settings`. Nothing here
  writes `settings.yml`, and nothing on the Settings page writes `org.yml`.

**A member renamed or removed in the definition (TD-703).** A definition knows a member by its
name, and a record is the name it was created under, so an edit that renames a member
(`grinder-dc-1` → `dc-grinder`) or drops one leaves records the definition no longer names. The home
reads no definition (§6 *Keeping a team running*): rule 8's start, rule 3's fill and every restart
replay a record under its own name, so a renamed team comes back under the old names, and a person's
Start, which creates under the new ones, would leave the old records beside them for the next rule 8
start to replay — two records for one member. So a rename and a removal are differences the client
finds, as it finds a lane's or a profile's (§4.9c *Switching*), and they reach the records only by a
person's press — **Apply**, or **Start** — never by the home on its own: until one, rule 8 replays the
old names, as a profile edit waits for Apply (TD-619). **After either press no definition name has two
current records, and every current crew record of the team is one the definition names, one marked
sat out, or one whose `relaunch` mark names the newcomer it becomes at its next replay.**

- **What is read as a rename** (`teamrun.renames`, one function the card, `ao team list`, `ao team
  flow`, Apply and Start read). The **orphans** are the team's crew records (`crew`: never a person's
  session, whose name is the person's) that are current (not superseded) and not sat out, whose name
  the definition no longer holds; the **newcomers** are the names the definition holds that no current
  record of the team carries. Within one role — the record's `role` against the launch's; a seat
  against the same seat, the techlead with the techlead, the manager with the manager, a `seats:` entry with the entry of its role — orphans and newcomers are paired in order,
  the orphans by `created` and the newcomers in the definition's order: each pair is a **rename**, an
  orphan left over a **removal**, and a newcomer left over the *starts* a missing member already is.
  The role is the only key; a lane, a reader or a profile that also changed is applied with the rename,
  as Apply applies it to any member. **An orphan already applied is no difference**: one whose
  `relaunch` mark carries a newcomer's `name` is that newcomer's until its replay runs, so a stopped
  team's card stops offering it once Apply has run, and the newcomer reads as held by it. **What was
  paired is shown before anything moves**: Apply's and Start's confirm list each pair, so a pairing the
  person did not mean — two members of one role renamed and reordered — is cancelled there.
- **Where it shows.** On the team card's mark (§4.5a *flow changed — Apply*), whose lines gain
  *grinder-dc-1 → dc-grinder: renamed* and *grinder-dc-2: removed from the definition*, and in `ao team
  list` and `ao team flow <team>`, which print them by member. **A stopped or wound-down team is read for
  renames and removals too** — the one difference read on a team with nothing live, since rule 8
  replays its ended records — and its mark reads **definition changed — Apply** beside Start, its
  title saying *until Apply or Start, a start by the tick brings back the old names*.
- **Apply on a rename** is a relaunch under the new name: `relaunch {id, launch}` whose `launch`
  carries **`name`**, the newcomer's (a key `RELAUNCH_KEYS` gains), with the rest of the launch the
  newcomer composes to. The home writes it as the record's `relaunch` mark, as any relaunch, and the
  record's next replay creates under the new name: rule 7's restart for a live member (an idle one at
  once, a working one on its word), rule 8's start or rule 3's fill for an ended one — so Apply on a
  stopped team starts nothing. That create **succeeds** the old record across names (`create
  {succeeds: <old id>}`, admitted as `keep_mail` is — the person, the home's own replay, or a
  controller of the old record — and refused to any other session): as a resume under
  another id does (§4.4a), the old record's mail moves to the new one (`_move_mail`) and the old one
  records `superseded_by`, so mail still addressed to it is forwarded; its open claims (`progress`
  entries still `claimed`) and its `lane_seen` are copied onto the new record, so the lease and rule 6's
  memory hold across the name; and every record's `controllers`, and every launch record's, that named
  the old address name the new one — a renamed manager or techlead is still each member's controller.
  **A node's own record takes it at its node**: its `controllers` are the node's field, which the
  home's copy takes from the node's next report, so the home rewrites the node member's launch record
  and routes `set_controllers` (the new address added, the old removed) to the node as a person's edit
  is routed — after the rename's create, and on every tick for a record whose launch record names the
  successor of a controller it still holds, so a node whose link is down takes it once it is back. The
  node appends what it adds, so the renamed lead stands last in that record's `controllers` until its
  next create, which takes the launch record's order. The launch record moves to the new id. The old record stays a card until Forget, folded as a
  superseded record is, and every rule passes over it as superseded.
- **Apply on a removal** is the sit-out form, `relaunch {id, sit_out: true, dropped: true}` (§4.9c
  *Switching*; `dropped` is what lets it mark a seat, which a flow's sit-out refuses): a live
  member wound down by the home and marked `closed_for: {why: sit_out}` once closed, an ended one
  marked as it stands; rules 8 and 9 and `wound_down` pass over it, so it is never replayed. A seat
  the definition drops takes the same mark, and rule 3 never fills a sat-out seat. The card reads
  *removed from the definition* where the definition names the record nowhere, and *sits out under
  <flow>* where a flow sits it out; a name put back in the definition reads *starts*, as a sat-out
  member's does. **Members…'s Remove** takes the same form: a live member is wound down by the home
  rather than sent Wrap up's wind-down, and an ended one is marked — so a removed member is never
  brought back by rule 8.
- **Start reads the same pairing** (the Sessions page's Start and `ao team start`, after every check and
  after a concluded team's closes): a newcomer paired with an orphan is created succeeding it
  (`succeeds`, the same carry), and each removal is marked by the sit-out form, before the members
  are created. The result lists them (*grinder-dc-1 → dc-grinder*, *grinder-dc-2 removed*), and the
  confirm says so first. A newcomer an earlier Apply already marked on its orphan is created succeeding
  that orphan too. A live team is offered Apply, never Start: a Start while an orphan still runs (the
  team not concluded) is refused, naming it, and so is a session's `ao team start` of a team with a
  rename or a removal, since both acts are a person's — both refused before anything is marked or created.
- **Not read as a rename**: a person's session; a member a flow sits out (its name is still the
  definition's); a record already superseded. A rename the pairing cannot see — two roles swapped at
  once — reads as two removals and two starts, which Apply's confirm shows before anything moves.

person tells one in its terminal, and it writes the entry on a branch. A thought the person has
while looking at the Sessions page or the Repo page has no way in, and most of what makes an entry good is
work the person should not do — the next number, the header lines, the evidence, the file
locations, the neighbours in the design. The person is needed for the *why* and for a choice
between readings.

  chosen, while the words were written on purpose, so the drafter writes the words' priority and

  the three-line header, the next free number, the Summary row, how it lands — is written once,

  1. **Hand to the techlead.** The words go as an `ask` from the person to the team's techlead

**Roles carry a profile** (`org.yml`'s `roles:` is `resolve_role`'s overlay layer; `ao new`, `ao
roles` and `ao team start` all read it). A preset may name the profile it runs under, so the
pick-list adds an agent by skillset in one choice: `roles.<name>.profile` in `.shiftlead.yml`, in
`org.yml`'s `roles:`, or nowhere (then the host's default profile). Precedence, lowest first:
the package's built-ins, `org.yml`, the repo's `.shiftlead.yml`, a team member's own `profile`,
`--profile` on the command line. The package's built-ins name no profile, because profile names
are the person's (§4.2a).

**Guardians, and any project that lives in a container.** A host is wherever an
`shiftlead-agent` runs beside a tmux server, so a devcontainer that runs the host agent *is* a
host — shape (b) in §10. guardians is not on kmaster and is not to be cloned there; its project
heading lists its repos on the devenv host, each repo's team placed there by `host: devenv`, a machine node, which is not yet in use (§4.4a, TD-057): the host
column fills in, nothing else changes. A container on the *same* machine as the home
(contractmatch's devcontainer) is a container node the home brings up, with the checkout at the
same absolute path inside and a per-node link socket (§4.4a *A container node*).
