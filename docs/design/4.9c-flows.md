### 4.9c Flows: the path an entry takes through a team

**TD-307, TD-314, TD-1954; the first shape built by TD-309, TD-313, TD-315, the repos moved onto it by TD-310; the shape below is TD-1954's, built by the entries that name it in `Part of:`.** The dated record is `scripts/history.py 4.9c`; this section says what is true now.

**Terms used below.** A **flow** is the path a ledger entry takes from filed to done: a list of
**stages** and a list of **audits**. A **stage** does one **kind**
of work (`design`, `build` or `review`) on one model. A session ends its stage by reporting one of
the kind's fixed **outcomes**; the flow says where each outcome sends the entry, its **next**. A
**limit** is how many times an entry may take one move before it comes to the person. The **stage
record** is where an entry is now. The person is in every flow and is no stage.

**A flow is records, not prose.** A flow is one file, `flow.yml`, in a directory with the briefs it
names. It holds no sentence a session must interpret to know where work goes: every stage has a
kind, every kind has fixed outcomes, and every outcome has one destination. A person, or a session
given only the format's description, writes a flow and runs the check (*A flow is usable only when
it flows*, below); three trials on Sonnet and Haiku wrote working flows from the description alone
(`docs/mockups/reviews/td1954-src/trial/`, the description, the check and the requests). A change to
the path is a change to a flow or a switch to another, never an edit to a repo's prose.

```yaml
# shiftlead/flows/build-review/flow.yml
format: 3
name: build-review
max-moves: 25                     # optional; 25 when absent
stages:
  - name: Build                   # free text, unique in the flow
    does: build                   # design, build or review
    model: opus                   # a model family the Tools page lists (§4.2b)
    takes: any                    # which new entries start here
    also: Keep the changelog in the same pull request.   # optional; appended to the stage's brief
    work-pushed: review           # an outcome, and its next
  - name: Review
    does: review
    model: sonnet
    ship: {to: merge, refused: {to: build, limit: 3}}
    changes-wanted: {to: build, limit: 3}
audits:                           # optional
  - {name: Docs audit, model: sonnet, every: 10 merged-pull-requests, brief: docs}
```

A stray key, at the top or in a stage, is refused naming it. A file that writes `format: 3` is read
as this section says. The first shape's files (`stages:` of `role`, `lane`, `brief`) write no
`format:` key: until the cut-over such a file is the first shape and stays usable, and from the
cut-over on it is refused with the words that say so. **The cut-over** is the moment the window
writes its marker (§4.9e), here and wherever this section says *at*, *until* or *after the cut-over*.

**Where flows and roles live: each a directory, whole.** A flow is a directory holding **`flow.yml`**
(its stages) and its stage briefs; a role defined outside the package is a directory holding
**`role.yml`** (its `ROLE_KEYS`, `kind` among them) and **`template.md`** (its mechanics, with the
template slots), which makes it a peer of a preset. They live in three places, resolved as a team's
name is (§4.9 *The org is an aggregate*) — the org's over a repo's over the package's, so an install
overrides a repo's without a PR:

- **the package**: `shiftlead/flows/<name>/` for the built-in flows (until the cut-over these are the
  first shape's, still in use, and the format-3 built-ins ship beside them under `shiftlead/flows3/<name>/`,
  where the first shape's reader does not look; a reader takes a flow by its `format:`, and the
  format-3 ones take the names at the cut-over, a built-in's name being resolved there from then on,
  and the directory when the removal build renames it, §4.9e); the built-in roles are the
  presets (`repoconfig.PRESETS`, `shiftlead/briefs/<role>.md`), each with its `kind`;
- **the org**: `~/.shiftlead/flows/<name>/` and `~/.shiftlead/roles/<name>/`, every team's to use, kept
  in the home's history beside the four files it already tracks (§4.9 *What is left at the home has
  a history*), committed by the home as `org.yml` is;
- **a repo**: `<repo>/.shiftlead/flows/<name>/` and `<repo>/.shiftlead/roles/<name>/`, its own teams'
  only (two repos may each define one name, since neither sees the other's), changed by PR.

A flow's or a role's name is its directory's. **Each is replaced whole, never merged by key**: two
stage lists have no one merge, and a role defined in two places is the org's. **A directory may not
take a preset's name** — refused when read and by `ao org check` — since a preset is the package's
and is redefined by key only (§4.8); nor may a flow directory take a built-in flow's name (`design-wise`,
`build-review`, `build`): a repo or an install that wants other words defines its own flow under its
own name, so a built-in's stage briefs are never a repo's prose by another road. A repo's role
directory the org's shadows is said by `ao org`, as a shadowed team is. What layers by key is unchanged and is not a definition:
`org.yml`'s `roles:` overlay (a role's profile for this install) and a repo's `.shiftlead.yml`
`roles:` (its supplement brief, §4.8), each over the role wherever it is defined. The two orders
differ on purpose — definitions resolve the org's over a repo's, whole; overlays lay the repo's over
the org's, per key (`repoconfig.resolve_role`). **A `roles:` key naming
no preset and no directory is refused** when the file is read (*unknown role*, naming the
directories that would define it): an overlay is not a definition. A repo's `.shiftlead.yml` is
refused as it is read; `org.yml`'s `roles:` may lay over a role a repo defines, which the org file
cannot see, so its key naming nothing is refused where the role is resolved (a start, a flow's
check) and named by `ao org check` against every role directory it can see. A role directory that
is not whole is left out of `ao roles` and the pick-lists, and named by `ao org check`. A role defined in a directory writes its `kind` in `role.yml` (`worker`
where unwritten); an overlay never does. The YAML files keep no `flows:` key: a flow is found by its directory.
**An org flow or role is not usable by a team on a node** (§4.4a): a node team's roles and briefs
are read on the node, and the org's directories are the home's; such a team is told so as *not
followable* (*hunt cannot be followed by cm-grind: an org flow, and cm-grind runs on contractmatch —
define it in the repo*; likewise a repo flow of cm-grind's naming an org role, *security is an org
role*). Whether a node team can follow a flow is read as its start reads the node — the client
asks the node's files (`teams.Files`, `host_files`) for the repo's flow and role directories and the
briefs, so a repo-local flow or role the node's checkout does not hold yet (a branch not merged
there) is *not followable* by name, and a node that does not answer reads *unknown*, never
followable. A package flow rides the wheel and a repo's the checkout, so both reach a
node; the org's directories are not copied to nodes.

**A stage is one kind of work, one model, one fresh session.** An entry is in one stage at a time.
Every time an entry enters a stage, a **fresh session** on the stage's model takes it: it reads the
entry, its pull request and any review on it, does what is still needed, reports an outcome, and
ends its run. No session keeps an entry across stages, and none carries on from one kind of work to
another: one session that designs and then builds, or reviews and then fixes, is what a person's own
interactive session is for. A builder that runs the cadence's independent review on its own work
before it ends (*The gate's review row needs no new input*, below) is no exception: that review is a
fresh subagent's, part of building as it is today, and its findings are the builder's to fix before
`work-pushed`. A stage's keys are `name`, `does`, `model`, `takes`, `only-when`, `brief`,
`also` and its kind's outcomes.

| `does` | What its session does | Outcomes |
|---|---|---|
| `design` | writes the design for the entry and files the builds it needs | `work-pushed`, `no-design-needed` |
| `build` | writes the code, tests or documents, or continues what an earlier stage pushed | `work-pushed`, `design-needs-changing`, `not-needed` |
| `review` | reads whatever is on the entry's pull request and gives a verdict | `ship`, `changes-wanted` |

Every stage also has **`other`**: no listed outcome fits. It needs a reason, goes to the person
unless the flow says otherwise, and the kind's brief names it the last choice.

**All of an entry's work is on one pull request.** The first stage that pushes work opens it and
later build stages push onto it. Running and fixing the tests is `build`'s; a narrower read (a
fact-check, a security review) is a `review` stage with a brief of the person's own, or an `also`. There is no merge stage,
no test stage and no stage of two kinds.

**A stage's key is its name.** The key is the name in lower case with spaces as hyphens (`Second
read` is `second-read`); a destination names a key, and the stage chip reads the name. Renaming a
stage on the Flows page re-keys every destination in the file in the same save, and the stage
records of entries in it (*A switch or a rename re-keys the records*, below). The order of `stages:`
is for reading: only the destinations say where an entry goes.

**An outcome is the session's word, checked.** A session ends its stage with one command,
**`ao stage end <outcome> [--reason "…"]`** (§4.7), run in its worktree. Until it runs the command it
is working: a red check or a failing test is no outcome. **The command is a call to the home**, which
checks the outcome's fact and **refuses an outcome the facts contradict**, saying which fact, so the
session carries on; accepted, the home writes the stage record's move and the session's part is over.
With the home unreachable the command fails and the session tries again: no stage ends without the
home. A session holds one entry, or one audit run, so the command takes no id. **The home takes one
repo's calls one at a time, in the order they arrive**: the host agent serves every RPC on one loop
and runs blocking work in threads (§4.8 *A claim is a lease*; `sessionorc.agent`), so the call holds
a lock of the repo's while it checks and writes. A call whose outcome goes to `merge` records
`merging` and returns; the tick carries out the gate and the merge. A session that gets no answer
in time calls again, which is harmless: the home answers a repeat of an outcome it already took
with where the entry went.

| Outcome | Of | Checked first |
|---|---|---|
| `work-pushed` | design, build | the entry's branch is pushed and its pull request is open; its precheck is green, unless the next is another build stage, which is expected to finish the work (a tests-first stage ends red on purpose); on a build stage whose next is `merge` or a review stage, the pull request archives the entry |
| `ship` | review | the pull request's head is the commit the session read: the head now equals the head its worktree last fetched, else the command refuses and the session reads again |
| `changes-wanted` | review | a reason is given, which is the review |
| `no-design-needed` | design | a reason is given |
| `not-needed`, `design-needs-changing` | build | a reason is given |
| `check-waits` | design, build, on a live check alone (*A live check under a flow*, below) | a reason is given; the entry's `Kind:` is `live-check`; its branch is pushed, its pull request open and its precheck green; the pull request changes only the ledger and the board and does not archive the entry; no review stage has given this pull request a verdict; and the entry's `Blocked by`, read from the forge at the pull request's head, adds to the default branch's copy at least one blocker that holds there: an id whose entry file is at that head and not under `archive/`; an `until` whose UTC day is after today's; an `event (<name>)` whose `**Event (<name>):**` section is in the entry's file at that head; or a `decision (<person>)` with an open `decide` item whose Context names that gate in the board at that head |
| `findings-filed` | an audit | at least one entry filed in this run is named |
| `nothing-found` | an audit | a reason is given |
| `other` | every stage and audit | a reason is given |

When a fact needs the pull request, the home reads the forge itself; the session never states it.
**At the first work pushed the home finds the entry's branch and pull request from the session's worktree**: the
branch checked out there, which must hold the entry's id as a whole token and no other entry's (the match of §4.9e
*Work in flight*), and the one open pull request of this repo whose head is that branch. It writes both on the record,
and from then on reads the pull request the record names.

**A verdict is on the stage record.** `ship` and `changes-wanted` write `{head, stage, outcome}` to the
entry's record, `head` the commit read; that is the whole of a verdict, and nothing is posted to the
forge for the flow to read back. An `only-when` stage that is passed writes `{head, passed}`, which
counts as `ship` at that head.

**One holder ends a stage.** The record names the session that holds the entry, written when the home
offers it. `ao stage end` from any other session is refused (*this entry is not yours*) and changes
nothing; and before the home offers an entry again it ends the old holder's session, so two sessions
never hold one entry and whichever speaks second is refused.

**Where an outcome goes.** A stage writes `<outcome>: <destination>`:

- **a stage's key** — the entry moves there; with `{to: <key>, limit: n}` at most `n` times.
- **`merge`** — of a flow's own moves, allowed on `work-pushed` and `ship` alone. The home runs the merge gate on what is there
  now and merges the pull request (*The merge gate under a flow*, below); no session is started, so no
  model is spent on it. `{to: merge, refused: {to: build, limit: 3}}` says where a merge the gate
  refuses goes, and plain `merge` sends it to the person.
- **`person`** — the entry waits for the person, as the ledger entry's own decision (*A move to the
  person is the entry's decision*, below). `{to: person, answers: {"Try again": build, "Back to
  design": design}}` offers answers that each name a stage; an answer in the person's own words goes
  back to the stage that asked, where a fresh session is given it (at a limit or the cap it takes the
  blocked move instead, *Limits*, below).

**A move to the person is the entry's decision** (Paul, 2026-11-21). It is **one pull request by the
home, holding the ledger change and its board item**, and it uses only what the board and the ledger
do today:

- **On the entry** the home adds `decision (<person>)` to its `Blocked by`, beside whatever that already
  names, and sets the **Ask** and the **Answers**, every one of them a lifting answer, through the ledger's
  writer (`ledger.py set --blocked-by --ask --answers --lifts`). They replace any earlier Ask and Answers,
  which are not put back after the lift: the entry's history keeps them. An entry already waiting on a
  decision is not asked a second time. The Ask is one plain sentence (§4.10 rule 1), from the stage's name and the
  outcome alone (*Build ended as not needed, what next?*), a stage's name that is not a few plain words being said as
  *This stage*; the session's whole reason is the Ask's Context. The Answers are the flow's
  offered answers; *Carry on* where a limit or the cap raised the question; *Archive the entry* and
  *Build it anyway* for a build's `not-needed`; *Try the merge again* for a gate row only a person can
  cure; and always a form, *Something else: <what>*, for the person's own words.
- **On the board** the same pull request files the **covering decide item** the gate sweep would file
  for that gate from the entry's own Ask and Answers (§4.4 *An entry says what it waits for*;
  ledgerboard's `sweep`, which reads the entries it is given, called for this one entry rather than
  waiting for the daily pass). The gate's coverage check wants that item, and the Queue draws its card
  from it, as for every swept gate today.
- **It lands as the home's presses land** (`sessionorc.board._land`): a branch of the host agent's
  own, a pull request it opens and squash-merges at once, the ledger files beside the board's as a
  decide lift's are. That road runs no gate before it merges. The cadence's later reading passes its ledger and
  board rows, the gate being covered by the item it lands with, but its review row knows the board's own
  tool-made edits and the lift, and this pull request is neither, so the weekly read lists it as landed without
  review until agent-cadence has a carve-out for it, which the first build that lands one live waits for.
  The gate keeps the entry from being picked, by the rule every lane reads today.
- **The person's press is the item's decide**, the existing path: an answer on a board item whose
  Context names a gate lifts the gate when the answer lifts, in the same write, with the picked
  label in the entry's Log (ledgerboard's decide lift, `sessionorc.board`). An answer pressed on the
  entry's own Inbox row writes a decided line and lifts nothing (`rpc_ledger_decide`), and **Lift the
  hold** lifts with fixed words; neither carries a label, so the card that matters is the item's.
  **The person's own words** are the form: a Reply whose words begin with a form's head fills it and
  decides (`reply_fills`); a Reply that fits no answer stays a Reply and decides nothing, as today.
- **The tick's *apply the person's answer* act** reads the lifted label and maps it to a move by the
  **answer map stored on the stage record when the question was written**, never the flow's text as
  it reads now; *Something else* takes the default move, back to the stage that asked, or the blocked
  move at a limit or the cap, and its words are kept on the record as `answer` for the next session.

**The order is the record's intent, the pull request, then the record's wait.** `ao stage end` records
on the stage record that the entry is to go to the person, with the answer map and what was
`blocked`, and returns; it does not wait for the pull request. The tick lands it and marks the record
as waiting once it has merged. A crash between leaves an intent, which reconcile lands, the question's mark in the entry's Log keeping it from being asked twice even once answered,
so no session's work is redone. A question costs two forge writes (the pull request and its merge), a
precheck of main of about five minutes (258 to 313 s over the six most recent that passed), and, where the entry has its own
pull request open, that pull request's rebase and a fresh precheck of about the same.

**No stage outcome goes to `done`.** An entry is finished by its pull request merging, or by the person.
A design stage's **`no-design-needed`** says the entry needs no design and goes on to be built: it
goes to the person unless the flow sends it to its build stage, as the built-in `design-wise` does. A build
stage's **`not-needed`** says the entry needs no work at all: it goes to the person, with the answers
*Archive the entry* and *Build it anyway*, the second going back to that build stage. A designer who
thinks the whole entry is pointless says so with `other`. `done` is only how an audit's
`findings-filed` and `nothing-found` end, which no flow writes.

**Who archives the entry.** As today, a build's own pull request archives its entry on the branch
before it merges (`ledger.py archive`, the build brief's step), so a merge leaves nothing to archive;
that holds for a design-first entry whose `no-design-needed` went to a build stage and was built, and a
design entry archives with its last build (below). That archive is today's rule, the build brief's
step (§4.8's `grinder` row: *archive the entry*); the gate's `ledger` row holds only that the pull
request touches the ledger, so `work-pushed` checks the archive itself. Two cases have no such pull request, and in both
**the home archives**, through ledgerboard's writer in a pull request of its own, as it writes a lift
today (§4.4): the person's *Archive the entry* answer, and a design entry with no open part — one
whose own pull request merged and filed no builds, which goes to the person at once with that
answer, and one left open after its last part merged — and any other entry still open after its
pull request merged, which goes to the person with the same answer, a live check's `check-waits` apart (*A live check under a flow*, below). The record closes when the ledger on the
default branch reads the entry archived.

**The merge gate under a flow.** **The home performs the merge itself**, in four steps: the call marks
the record `merging` with the pull request's head and returns; the tick then runs the repo's gate on
that head, merges, and closes the record. It runs the gate's own script for that pull request then and there (`check_cadence.py
--pr`, §6 rule 10's check), not the detached reading the tick keeps every five minutes. The gate ends
one of four ways, and a refusal names the failing row:

- **it passes**, and the home merges by cadence step 5's line at that head, the squash signed
  `Merged-by: shiftlead-home` and with no model, since the home runs none;
- **a cause a session can cure** — the head is not the one the verdict recorded, the checks are red,
  the pull request conflicts, the review row fails, or a ledger or board row fails — takes the
  outcome's `refused` move;
- **a cause only a person can cure** — `reach`, which waits for a person's Go, and any other row that
  asks for the person — sends the entry to the person whatever `refused` says and spends no limit,
  with the answer *Try the merge again*; the person may merge by hand instead;
- **no reading** — the script is missing, fails to run, or reads *unknown* — leaves the record
  `merging`; the home tries again on later passes for an hour, then sends the entry to the person,
  spending no limit.

**The gate's review row needs no new input.** It reads what it reads today, a `cadence-review:` comment
on the pull request (§4.9b *The reader*; the cadence's §4). When a review stage ends as `ship` the home
posts that comment for the head the verdict recorded — `SHIP`, the stage's model, code or docs, the
count of findings — and when one ends as `changes-wanted` it posts the review as `BLOCK`, which the
next `ship` supersedes, the row reading the latest. So the reviewer's model on the comment is the
review stage's, and the cadence's `review-model` is not asked. **A route to merge with no
review comment keeps today's rule.** The built-in `build` flow already merges with nothing waiting on
a reader, and passes the row because its builder runs the cadence's independent review (a fresh
subagent on the cadence's `review-model`) and posts the comment itself before it ends its stage. The
check generalises that: for each design or build stage it works out whether `merge` can be reached
from it without passing a review stage that runs every time, and for such a stage the home adds
that step — run the cadence's independent review and post its comment before `work-pushed` — to the
mechanics the session is told, whatever brief the stage picks; it is in no brief's text. A passed `only-when` stage posts nothing,
so it does not count as such a review. The flow's own check is
the head: for `ship` sent to merge, the head being merged must be the head that verdict recorded; for
`work-pushed`, the head pushed. Nothing in agent-cadence changes. **A flow with a `merge` destination
is not usable in a repo the gate does not serve** (no pinned agent-cadence), the reason shown.
A push after `ao stage end` only makes the head check fail,
which the `refused` move handles. **A crash spends no limit**: a record left `merging` is the tick's reconcile act's (below), which acts
only when the home has no merge of its own running for it — the forge shows the pull request merged,
and the record is closed; it is still open, and the four steps are run again.

**An outcome the flow does not list goes to the person.** Three destinations are fixed and written by
no flow: a design entry whose pull request merged **waits for its parts** (*A design entry archives
with its last build*, below), an entry whose session is lost is **offered again** (below), and a live
check's `check-waits` **merges and closes its record** (*A live check under a flow*, below). **A
merged pull request ends its entry wherever it stands**, which the tick's reconcile act carries out:
the person merging by hand needs no stage, so *the person merges* is written `ship: person`.

**Limits.** A limit may sit on any move to a stage, forward or back, and on `refused`. `limit: 3`
lets an entry take that move three times; the fourth goes to the person. The count is per entry and
per move. **`max-moves`** caps the whole trip: an entry may make that many moves between stages (25
where unwritten), and the next one, the 26th, goes to the person wherever it is. **What counts** is a
move from one stage to another, *this stage again* included; a move to the person or to merge does
not, and neither does a move that was blocked or a move the person's answer causes. A move's own
limit is checked before the cap. **A question raised
by a limit or by the cap always offers *Carry on***, beside any answers the flow wrote: it takes the
move that was blocked and starts that move's count and the cap's count again. An answer in the
person's own words there takes the blocked move too, and the destination's fresh session is given
it. Only an answer at a limit or the cap restarts counts, that move's and the cap's; an answer
anywhere else restarts none. There is no separate allowance for a far-reaching design (dropped on
purpose, 2026-11-21): *Carry on* is the allowance, so the extra rounds are the person's call and
cost one question.

**Ways in.** A new entry has no stage. `takes` says which stage it starts in: `design-first` (an
entry whose `Kind:` asks for a design before code), `other` (one ready to build) or `any`. Each kind
has exactly one stage that takes it, a flow with no design stage writing `takes: any` on its first
build stage; a review stage takes none. **An entry's first record is written when it is first offered to a session**, not
before: the home offers an entry with no record that is pickable by the rules a lane reads today (§6
rule 6: not blocked, not a part that waits, its `Owner:` neither the person nor the anchor) to a
session of the stage that takes its `Kind:`, within the team's size, and writes the record then.
**Where an open pull request is already the entry's work**, the record is written with its branch
and pull request and the session is told of them as a session of a stage entered again is. §4.9e
*Work in flight* gives the rule: the match is the branch name holding the entry's id; a fork's and a
filing pull request are never its work, nor a branch that holds two entries' ids; an entry whose
pull request is a draft, or is held by a live session, is not offered while that lasts; and the seat for pull requests nobody holds skips
what this rule takes.
This is how work in flight at the switch-over is taken up. An
entry nobody has been offered has no record, so a team's switch of flow finds nothing of it to move. **`Owner:` keeps the meaning it has**: ledgerboard's field is
unchanged, it says whose the entry is (a person, the anchor, or a role word), and under
a flow it is read for that alone — that a team's flow may take the entry, or that none does — never for
a stage; **which team's** is the entry's `Team:` line where its repo has several teams, and the repo's
one team where it has one (§4.4 *An entry names its team*); where the entry is afterwards is the stage
record's. At the cut-over an `Owner:` whose role
word is `grinder` is read as `builder`, and the removal build (TD-2056) rewrites the open entries' values in
its own pull request.

**A review that runs only sometimes.** `only-when: protected-files` on a review stage means it reads
only pull requests that touch the repo's protected files, the paths `.shiftlead.yml`'s `held:` lists
(*What is the repo's*, below). For any other pull request the stage is **passed without a session and
counts as `ship`**: the home writes that move. The check warns, and does not refuse, where a review stage runs on the model of a
stage whose work it reads.

**Audits start on a clock.** An audit is no stage and takes no entry through the flow. It has a
`name`, a `model`, `every` (`<n> merged-pull-requests`, `<n> hours` or `<n> days`) and a `brief`
that says where it looks. When its clock comes round the home starts a fresh session with that
brief; it files each problem it finds as an entry of its own, which enters the flow by its way in,
fixes nothing, and ends with the same command as `findings-filed`, `nothing-found` (both finish the
run, as `done`) or `other`. **A run holds a run record, not an entry**: the audit's file on the state
branch, keyed by team and audit name, carries its last run, written **when the run starts**, with the
session that holds it, a lease, and the merge commit that was main's head then; an audit does not start
while its last run still holds its lease; `<n> merged-pull-requests` counts the pull requests merged
since that commit, and hours and days run from that start. **A run whose session is lost** is
offered again once; lost again, the audit waits for its next clock and the person is told with one
note. An audit's `other` has no entry to carry a decision, so the home adds one plain line to the board, of
the form the gate's append class accepts (a `Due:` and no detail block), naming the audit and the run;
it offers no answers, and closing it does nothing more: the next run comes on the clock. This and
a job's line to the person (§4.9d *How each one runs*) are the board lines the host agent writes (§6). Nothing is sent to an audit. The docs and test
auditors of §4.9b's *Seats with a trigger* are two audits of the `design-wise` flow. There is no hunt entry: a
hunt across parts of the code is an audit with the `code` brief or one of the person's own. An
audit's `brief:` is `docs`, `tests`, `code` or the name of a brief of the person's own, and it may
carry `also:` (*What a stage's session is told*, below).

**Built-in seats are no part of a flow.** Five seats stand outside every path: the **tech lead**
(answers sessions' questions, §4.9b), **board answers**, **pull requests nobody holds**, the
**prompts seat** (answers a permission prompt where the org has no director) and the **sweeper**
(§4.9b *The sweep*). There is no manager under a format-3 flow (§4.9d *How each one runs*). **A flow names none of them and has no key
for them**: each one's model, and the logins it runs on, are a **built-in set**'s, which a repo uses
whole and the Built-in seats page sets (§4.9d *The built-in seats and their page*); their triggers, briefs
and rights are their own sections'. **Four of the five act for a repo, not for a team** — board
answers, pull requests nobody holds, the prompts seat and the sweeper — and run while any of the
repo's teams is started; the tech lead acts for one team's sessions and runs while it is started, and
on while a wound-down team's sessions finish. The tech lead's reading of protected files is no longer the
seat's: it is a review stage. Where the org has a director (§4.9b), *the director* as a destination
beside *the person* is a later entry's. Mail changes no stage and is outside the flow (§4.10).

**Two of the five are not seats today.** A board line the person decided, and a pull request nobody
holds (a red one, or a filing pull request, §4.4), are today **work orders in the free-pick lane**
(§6 rule 6), taken by whichever grinder picks next. A format-3 flow has no lane, so each becomes a
built-in seat whose work is a **job**: a record of its own, a holder, and this section's Offer, Lost
and Silent, its pull request read by the team's review stages (§4.9d *How each one runs* gives the
whole of it), made by a build of its own before the cut-over:

- **Board answers.** Trigger: a board line reads decided, and it is not the covering item of an entry
  whose stage record waits on the person or is about to (those the home applies itself). The home starts a job for each such line, one session at a time on the seat's model; its brief
  is the work order's words as they are today — do what the person decided, in a pull request, and
  close the line.
- **Pull requests nobody holds.** Trigger: the repo's reading shows a red pull request or a filing
  pull request no session holds and no stage record names, past the bounds §4.4 gives each, and that is not the work of a pickable entry with no record (*Ways in*, §4.9e *Work in flight*). The home starts
  a job for it, one session at a time; its brief is that work order's words — read why it is red, cure it or say why
  not, never a fork's.

Both start only while one of the repo's teams is started, on the model and logins of the built-in set
the repo uses (§4.9d *The built-in seats and their page*), and wait where no login of that set is usable, and
neither takes an entry through the stages.

**The stage record.** Where an entry is — its flow, stage, holder, branch and pull request, when it
entered, each move's count, the moves so far, its verdicts, and what it waits on — is ShiftLead's own
record, one file per entry on **one dedicated branch of the repo, `shiftlead/state`**, beside the
audits' run records (§4.4 *The stage record*). **The home is the one writer of that branch.** `ao stage
end` is a call to the home, and the home's own acts go through the same writer; no session pushes to
the branch, so two writers never race and a session needs no credential for it. The home creates the
branch at a team's first start, and each write is a commit it pushes, never a pull request: a pull
request per move would spend the forge's write limits and run main's precheck for a line of state. A
push the forge refuses (a branch rule) makes the team's flow **not usable**, the reason shown where
the flow is. The branch is the durable copy: any machine can read it, and a home that restarts or is
reset reads its records back from it. **Claims stay at the home** (§4.8 *A claim is a lease*): which
session holds an entry is the lease, mirrored on the record, and several homes working one repo is
TD-2033's question.

**The home acts only where no session will.** The tick (§6) reads the stage records and has six
acts. **A pass takes at most one act on a record**, the first of these whose condition holds, so two
acts never meet on one record, and nothing outside these six moves a record. **The pass runs at the home once the cut-over's marker stands, at most once a minute and never beside the last**, a thread for each repo with switched teams, from the repo facts the home last read (§4.4 *Repo facts*); a repo not read yet waits for its reading. **The acts that start a
session — offer, offer again, start an audit — run only while the team is started, inside its
schedule, and not held by the usage gate** (§6); the others run whenever the home does. **A holder
the person or the home stopped or holds** (a team's Stop, a pause, the usage gate, a suspended
session), or one the tick is moving to another login (§4.9e *A session moves down the list*), is neither lost nor silent: its entry waits with it. **§6 rule 1's crash restart never
applies to a stage's or an audit's session**: one that exits is the lost rule's alone, and a clean
exit after `ao stage end` is no crash.

1. **Reconcile** — the record disagrees with the forge, the ledger, the board or its flow (the cases
   below, a record whose stage key the flow no longer has among them), or is marked `merging`.
2. **Apply the person's answer** — the record waits on the person and its entry's gate has been
   lifted since: the home maps the lifted label to a move by the answer map on the record and makes
   it, keeping the form's words as `answer` for the next session. A lift on an entry whose record
   has moved on (the person merged by hand meanwhile) is applied to nothing, and the entry's Log
   says so.
3. **Pass** — the record has no holder, waits on nothing, and is in an `only-when` stage with nothing
   to read.
4. **Offer again** — the record has a holder that is **lost** or **silent**. With `offers` at 2 this
   is the second loss, and the act sends the entry to the person. With `offers` at 1 the
   home ends the old holder's session, clears the holder and offers the entry afresh, counting the
   offer; it spends neither a limit nor the cap. `offers` counts only a loss that happened while the
   team was running and not held: a holder ended by a Stop or a hold is offered again when the team
   runs, and the count stands. At a second loss (`offers` 2) the entry goes to the
   person. An audit's run is offered again the same way, and at its second loss the audit waits for
   its next clock and the person is told. **Lost**: the holder's session has ended, acted on at once,
   or its lease lapsed with no outcome (`LEASE_TTL`, 12 hours). **Silent**: a live holder that has
   taken no turn for 2 hours and has no open ask or wait of its own and no permission prompt
   pending (the prompt has its own answerers, §4.9d *How each one runs*); the person is never silent.
5. **Offer** — the record has no holder and waits on nothing, or a pickable entry has no record yet
   (*Ways in*); within the team's size, the home starts a fresh session of the stage, names it the
   holder with `offers` 1, and **writes its claim** on the entry as the session takes it. The lease is
   renewed as every lease is today, by claiming again (§4.8 *A claim is a lease*; nothing else
   refreshes one), which the mechanics a stage's session is told ask of one that works past half a
   day.
   **A live session of the stage that no open record names** and that has not reported its stage
   over (a crash between its start and its record, or an end that failed) holds the stage's name, so
   the home ends it once two passes running read it so, and the entry is offered afresh; one whose
   claim is done or dropped is left to exit, and one on a node not read is left alone.
6. **Start an audit** — its clock came round and its last run holds no lease.

A move to the person is written in the order *A move to the person is the entry's decision* gives:
the record's intent, the pull request, the record's wait. The re-offer of a lost holder's entry
is new with this design and is built with these acts; §6 rule 6 tells no lane of a lease that lapses
unreleased. Reconcile's cases:

- a pull request that **merged** ends its entry, whoever merged it (a hand merge, or a merge whose
  command died before its last write); a design entry then waits for its parts; a record marked
  `check_waits` then closes, whatever it waited on, ahead of landing any intent (*A live check under a flow*, below); any other record closes when the ledger reads its entry
  archived, and an entry still open goes to the person (*Who archives the entry*, above);
- **the last part merging** releases a design entry that waits for its parts: where the last build's
  own pull request archived the design with it the record is closed, and where it did not (two builds
  merging together each saw the other open) the home archives it (*Who archives the entry*, above);
- a pull request **closed unmerged** sends its entry to the person, the Ask saying so;
- an entry **archived by hand** has its record closed; one **reopened** has no record of its closed pull request, and is offered
  afresh by its way in once it is pickable, with no branch or pull request carried over; an entry
  **renumbered** has its record moved to the new id;
- a record marked `merging` has its gate run and its merge made, as *The merge gate under a flow*
  says, when the home has no merge running for it;
- a record whose stage key its flow no longer has, or has under another kind, goes to the person, the
  flow's stages the answers, its holder's session ended (*A switch or a rename re-keys the records*,
  below; §4.9d *The flow pick and a switch*) — with three exceptions: **one that already waits on the
  person is left until its answer**, whatever became of its stage, and is asked once more only where
  the answer names a stage the flow lacks; **one that has made no move yet** has its session ended and
  re-enters by the flow's way in for its `Kind:`, keeping its branch and its pull request where it has
  opened one; and one marked `merging` is the case above;
- a record written under another flow than the team's copy — the copy of the team the record belongs
  to, `flows/<team>.yml` — whose stage both have under one kind, is rewritten to the copy's flow: its
  stage and holder stand, and the counts of moves the new flow lacks are dropped;
- an entry whose `Team:` line now names another team has its holder's session ended and its record
  closed here, and enters that team's flow by its way in; the home writes the entry's branch and open pull
  request on the new record, so the new team's first session carries on from what is pushed. Where
  the closed record waited on the person, the home also clears what it set for the question — the
  entry's `Blocked by: decision (<person>)`, Ask and Answers through the ledger's writer, and the
  covering board item closed — in one pull request of its own, the route by which it set them (*A move
  to the person is the entry's decision*), in that move's order: the intent on the record, the pull
  request, and **the record closed only when that pull request has merged**, the entry entering the new
  team's flow then and not before;
- a record whose intent to go to the person has no pull request yet has it landed; one that waits
  on the person whose entry carries no gate and no lifted answer has the gate and its item set again;
  and an entry that carries the home's gate whose record does not yet wait is marked as waiting.

It moves no entry for any other reason. **A closed record is
kept thirty days** on the branch's head, for the page and for a reopen to read, and is then removed in
the tick's own commit; the branch's history keeps it.

**A claim's chip is its stage.** Each row of a team card's *TDs in motion* (§4.5a) leads with a chip
that says where the entry is now, read from its stage record: the stage's name, in the colour of its
kind (design indigo, build blue, review amber) and in the flow's order; grey **you** while the record
waits on the person; *merged* or *closed* beside the stage once its pull request is no longer open;
and, for a claim with no stage record (a person's own session, a team of the first shape), its
holder's role in grey. The chip is derived at the view and is never a reason for a rule to act.
Paul, 2026-11-12: *accuracy is key here, the user needs to be able to trust the ui* — a chip says
only what the record shows.

**What a stage's session is told.** A session's opening prompt is, in order: ShiftLead's mechanics
(the turn that ends to wait, mail, the usage gate), how work is taken and ended (`ao stage end`,
its outcomes and the facts each is checked on), the repo's rules (its supplement, §4.8), and **the
stage's brief**. The brief says the job; the path is not in it, since the outcomes are the path.
Where the entry's record already carries a branch and a pull request — a later stage, a re-entry, an
entry moved from another team — the mechanics name them, and the session works on that branch.
**Every stage and every audit picks one brief from a list and may add to it** (Paul, 2026-11-21).
The list holds the **standard briefs** that ship with ShiftLead — one each for design, build and
review, and three for audits, `docs`, `tests` and `code` — and the person's own. A stage with no
`brief:` takes its kind's standard brief; `brief: <name>` picks one of the person's own in its
place; an audit always names its brief. **`also: <text>`** is appended to whichever brief is
picked, so a standard brief keeps improving with ShiftLead while the flow's own addition stays. A
brief of the person's own is written on the **Briefs page**, belongs to one kind (design, build,
review or audit), and is offered only to a stage or audit of that kind; the standard briefs are
drawn there read-only. **Where a brief lives**: the standard briefs are the package's; a brief made on
the Briefs page is the org's, a Markdown file beside the org's flows (`~/.shiftlead/briefs/<name>.md`),
usable by every org flow; a flow's own briefs are in its directory, `briefs/<name>.md`. A brief of the person's own
says its kind in its front matter (a `---` block holding `kind: design`, `build`, `review` or `audit`); the standard ones are `shiftlead/briefs/standard/<name>.md`, their kinds the package's. A repo's flow
may name only a standard brief or one in its own directory, since the org's files are the home's and
do not reach a node, and the check refuses any other. The built-in session roles are named for the kinds, **designer**,
**builder** and **reviewer**, and `grinder` is renamed `builder` by the removal build (§4.8, §4.9e).

**A live check under a flow** (TD-2114). A pickable live check enters by the stage that takes `other` or
`any`, a build stage in every built-in flow, and its session is told what a live check is **in the mechanics, whatever brief
the stage picks**, since a brief of the person's own may replace the standard one and none of them
is written for a check. Where the entry's `Kind:` is `live-check` the mechanics say that this
replaces any building the brief asks for: the session writes no code; it reads the live copy and
never presses it, a check that needs a press being made on a scratch home (§4.9b *What the grinder
does*); a build found not live takes a fresh gate by §4.9b's naming rule (*A live check waits on a gate*); a new entry takes its id from `ao td reserve` and is filed with `ledger.py new`, a gate and an archive are `ledger.py`'s, the board item is `board_edit.py add`'s, and the look is `ao msg` (§4.10 *A look*); and it ends one of the four ways §4.9b gives, each a pull request of ledger and board files alone:

| What the check found | The pull request | The outcome |
|---|---|---|
| **It holds** | what was read is written on the entry, and the entry is archived | `work-pushed`, the flow's own route to review or merge |
| **It does not** | a new entry says what is wrong, and the check is `Blocked by` it | `check-waits` |
| **It waits for an event nobody can cause**, its build not being live among them | what was read is noted, and the entry gains its `event` or `until` gate | `check-waits` |
| **It is the person's to judge** | the look is sent first; the entry gains `decision (<person>)`, its Ask naming the look's mail id, with the board's `decide` item | `check-waits` |

**`check-waits` is a fixed move, written by no flow**, so no flow file changes and a stage's `outs`
never list it. It goes to `merge` past any review stage, since what it merges is a note and a gate
and the entry is not finished: the mechanics therefore tell the session to run the cadence's
fact-check of the pull request and post its `cadence-review:` comment first, as they tell a stage
with no review on its route (*The gate's review row needs no new input*, above). A merge the gate
refuses for a cause a session can cure comes back to this stage, at most three times on the
stage's one `refused` count, and then goes to the person; a cause only a person can cure goes to the person, as for any merge.

**A pull request a review stage has read is not merged past it.** Where the record holds a verdict on
this pull request (a check first ended as *It holds*, then sent back), `check-waits` is refused, since
the session's own comment would supersede the reviewer's `BLOCK`; the session ends with `other`, which
goes to the person.

**Once merged the record closes, and the entry is open behind its blocker.** This is the one record
that closes with its entry open. Nothing waits on the record: while the entry is blocked no act
offers it, and **when it is pickable again** (its fix archived, its event or day come, or the person's
lifting answer) it is an entry with a closed record, which the Offer act gives a first offer by the
flow's way in for its `Kind:`, as it does a reopened entry. So a stage renamed or a team moved
meanwhile needs no case of its own. The fresh session starts a new branch, its name holding the
entry's id and not already on origin, reads the entry's Log and
checks again; a person's answer to a look is read there, since the home did not ask it. Each pull
request must add a blocker that holds, so a check cannot come straight back; the counts start again
with each record.

**A merge the person takes over.** An accepted `check-waits` marks the record `check_waits` with its
pull request's number, which stays through a refused merge and a wait on the person; any other
outcome the session later ends with clears it, and only a merge of that pull request acts on it. Where the gate's refusal is one only a person can cure, or the third cured refusal
has passed, the record waits on the person as for any merge. If they merge by hand, reconcile sees
the record's `pr` merged and equal to the mark and closes the record: **this case is read ahead of
`land-intent`**, right after an archived entry's. The
question's nonce is `asked.nonce`, or `intent.nonce` where a crash left the intent unrecorded. A
question whose nonce is not on the entry never landed, and its intent is dropped. Where the nonce is
on the entry, the home first clears what it set, in the order of a team move (*an entry whose
`Team:` line now names another team*, above): it marks the record `clearing`, lands the clearing pull
request, and closes the record once that has merged, so no stale gate of its own blocks the first
offer. Where there is none on the entry, a `decision` the pull request wrote stands and the record closes at
once; the person resolves any conflict between the two in the merge they make.

**The built-in flows.**

- **`design-wise`** (named so by Paul, 2026-11-22, TD-2075: the first shape's flow on this path is `td`, a name
  that says nothing, and the format-3 one never carries it): *Design* (takes `design-first`) → two design reads on two models → *Fact-check* → merge;
  *Build* (takes `other`) → *Review* → *Protected read* (`only-when: protected-files`) → merge; each
  `changes-wanted` and refused merge back to *Design* or *Build* with `limit: 3`; two audits, docs
  every 10 merged pull requests and tests every 6 hours.
- **`build-review`**: *Build* (takes `any`) → *Review* → merge.
- **`build`**: *Build* (takes `any`) → merge; no review stage, its builder running the cadence's
  independent review.

A built-in is read-only on the page and is changed by copying it. The models they ship with are the
package's defaults and are a person's to change in a copy. Whether a stage's model has passed a smoke run on the
tool that will run it, and where that is recorded and drawn, is TD-2046's design.

**A flow is usable only when it flows.** The check (`ao flow check <file>`, the page's *Does it
flow?*, and every read of a flow) holds these, each refused with the stage and outcome it is about:

1. Every destination is a stage that exists, or `merge` or `person`; of the moves a flow writes, only
   `work-pushed` and `ship` go to `merge`; nothing goes to an audit.
2. Every outcome a stage lists belongs to its kind.
3. **Every loop has a limit**: where an entry can travel from a stage back to it without passing the
   person, a move on that route carries a limit, a refused merge's move included. Loops are found
   from the moves, never from the order of `stages:`.
4. Every pull request that can be opened can reach a `merge`, or a `work-pushed` or `ship` that goes
   to the person.
5. A stage outcome never goes to `done`.
6. Each kind of new entry has exactly one way in, and it is no review stage.
7. Stage and audit names are unique and no reserved word; each stage has a kind and a model.
8. Every stage can be reached, by `takes` or as a destination.
9. `max-moves` is a whole number of 2 or more.
10. Every audit has a name, a model, an `every` and a brief; a `brief:` names a standard brief or one of
    the person's own, of the stage's or audit's kind, and a repo's flow names none of the org's.

11. For each design or build stage the check works out whether `merge` can be reached without passing
    a review stage that runs every time; it refuses nothing for it, and says which stages therefore
    have the builder's independent review added to their mechanics.

It warns, without refusing, on a review stage that shares its writer's model, and prints what goes
to the person. A flow that fails is **not usable**: listed as such by `ao org`, saved by no page,
and run by no team.

stage, *this stage again, with a fresh session*, *merge it* with its *if the merge is refused* pick,

reached from its rail beside Settings, Tools, Briefs, Teams and Built-in seats (§4.9d *The page*).

**A team runs one flow, and which is the team page's.** Which flow a team runs, how many sessions it
may have in each stage at once and which logins they use are §4.9d's (TD-1153, the frame of
[ADR 2026-11-18](../decisions/2026-11-18-tools-flows-teams.md)); every team runs a flow. *Within the
team's size*, above, is §4.9d *Sessions at once*: one number per stage and one for the team. **A switch
or a rename re-keys the records.** When the Flows page saves a rename of a stage in an org flow, the
same save rewrites the stage, the counts and the moves of every open record in that stage to the new
key, and the sessions-at-once number under the old key for every team that runs the flow (§4.9d
*The flow pick and a switch*). Whatever the cause — a team's switch to another flow, a repo flow changed by a pull request, a
file edited by hand — **a record whose stage key the flow no longer has, or has under another kind,
is sent to the person by the tick**, its answers the flow's stages, and the session that held it is
ended by the home; a record that has made no move yet re-enters by the new flow's way in instead. The page **refuses to delete a stage, or change its
kind, while entries are in it**, naming them. **A flow that stops passing its check keeps its last
good version in use**: the state branch holds, per team, the copy of the flow its records were
written under (`flows/<team>.yml`), replaced only by a version that passes; the tick runs that copy
and tells the person once, with the check's problems, until the flow passes again. A team's switch
to another flow is the person's press on the team page, takes effect at once, and replaces that copy
(§4.9d *The flow pick and a switch*, which gives each record's case). **A repo's flow changes by a pull request**: the Flows page draws it
read-only, and its *The file* tab is the text a person copies into that pull request; there is no
other control for it, on a node team's repo as on the home's.

**What ends a design's rounds, and what is far-reaching** (TD-1954; Paul, 2026-11-21). A design's rounds are passes
through its flow's review stages. They end when the last review ships and the design merges, when a limit or the
total cap brings the entry to the person, or at the person's word; nothing else ends them. Each review stage reads
on every pass, on its own model: no rule changes who reads by round, and no session judges that a design's rounds
are over. **What is far-reaching** is the cadence's (§4.8 of `cadence.md`) and
unchanged: a design is far-reaching when it changes what every session reads (roles, briefs, the spec, the
glossary), who acts or decides for the person, what waits for the person, or something that cannot be undone, and
any doubt counts as far-reaching. The design's author marks it, with the reason, on the `Reach:` line of the
design's review record (`docs/reviews/TD-<design>.md`). A repo may name its far-reaching files in a
`[far-reaching]` table of `docs/cadence.toml`, and a design whose builds change a matching file is far-reaching
whatever its mark; this repo's file has no such table yet. The cadence check has a `reach` row, and under a flow it
is one of the rows only a person can cure (*The merge gate under a flow*, above).

**The designer records its PR** (TD-1526). Once a design PR is open — its number is the forge's — the
designer appends it to the design entry's **`Design PR:`** section in that same PR: `ledger.py edit
TD-<design> --section "Design PR" --from <file>`, the file the old list with `, #<n>` after it. A later
round's PR (a bought round's own entry is `Part of` the design) is appended to the design's list, never to
the round's entry; a design PR closed unmerged never reaches the list, its edit landing only with its merge. The
section lands with the merge, since the ledger is read against origin; until then the PR's title links it,
so the title leads with the entry's id and the word *design* — *TD-1526 design: …*; a bought round's, and a `Hold`
revision's, leads with its own entry's id (*TD-<round>: TD-<design>'s …*, its entry `Part of` the design) and is linked once it
merges and appends its number. The section is what an item about the design links
(§4.5 screen 6 *An item about a design links the design's PR*); it stays when the design archives.

**The designer writes the synopsis** (TD-1527). Every design PR writes the design's synopsis,
**`docs/synopses/TD-<design>.md`** (§4.5 screen 6 *A design links its synopsis*): the first round's PR makes
it, and each later round's PR — a bought round's or a `Hold` revision's among them (cadence §4.8's answers to the end-of-rounds item; each runs under an entry of its own, `Part of` the design, as the designer brief files it, its PR titled with that entry's id, *The designer records its PR* above, and so never the design link until it merges) — rewrites it whole, in the
present tense, so it says what the design says at that PR's head. It is written last, after the round's fixes,
and is in the closing fact-check's diff like any file of the PR, which checks it says nothing the design does
not and leaves out none of the design's choices the person would weigh. **Its shape:** a `# TD-<n>: <the
entry's title>` heading (the title with its backticks dropped), then four `##` sections in this order — *What it does*, *The key choices, and why*,
*What it rules out*, *What you will see* — each a few sentences or short bullets, the whole at most 40
non-blank lines as committed, its headings counted, each line wrapped at 120 columns (a synopsis's own rule, the test's), so it reads on one screen. **Its writing rule** is a message to the person's (§4.10 *How a message to
a person is written*), read cold: plain words, no finding id (`F12`), no function, file, path or line
reference, no backticks; a ledger id (`TD-1476`) only where it names other work the person knows by it.
Paul's example of the level, for TD-1476: *each pool member is a separate record, so the design stays
simple; members show on the team as seats; later members carry a backup indicator; pools only on question
seats, the techlead's is a later design.* `docs/synopses/README.md` states the shape and the rule, and a test
holds every synopsis to them (its heading's `# TD-<n>: ` prefix — the title after it is not compared, so a retitled entry never turns it red — its sections, its length, and no `F<n>`, backtick, `.py`, or `:<digits>` after a word holding a `/` or ending in a file extension). The cadence's own part — that a design's end-of-rounds item links its synopsis in every repo — is asked of agent-cadence on its own ledger (`ao td add --repo agent-cadence`), by the designer once this design merges; TD-1527's Log names the entry. The
synopsis is the design's alone: a build entry, a review record and an end-of-rounds item's detail keep

**What the designer carries from one design to the next** (TD-1721; Paul, 2026-11-13). The designer's **context
bound is 150k**, not 300k, set in this repo's `.shiftlead.yml` (`roles.designer.context`, which wins over `org.yml`'s
per key, §4.8 *A role has a context bound*), since the number is measured on this repo's designs. The bound is written on the record at the start and carried
through every restart and a person's Apply, so it reaches the designer only at its next start from the team's
definition, a team Stop and Start, which is the person's. §6 rule 5 tells a
member it is over only between entries, and a design whose rounds are running is a claim in progress, so the bound
does not end a run while a round runs: once a design is finished past 150k, the designer is told when it next idles
between entries and ends its run, and the next design starts in a fresh run, at about 67k on its first turn (the
median over the five designs' 17 sessions, the cost model's *For TD-1721*), not carrying the
last design's 236k to 299k into every turn of its own. Over the five designs at Opus 5.5's weights, a fresh run at
each design's start would have spent 19% less of the designer's $88.82, about $3.40 a design. Ending a run between
a design's rounds on purpose as well would have saved 29% in all, and this design does not: a run that ends
mid-design loses why each fix was made, which the review record does not hold, so the next run's fixes risk
reopening the last's. A design waiting on someone with its PR open — a `steer` or an `ask` about it, or a reader — is a

go on in a fresh one; that is accepted, since the open question and the review record name what the next step
reads, and the cost of a cold start is the price of the smaller bound. §4.8 *A designer's context* is

**A design entry archives with its last build** (TD-693; read from `Part of:` since TD-1129, [ADR
2026-10-27](../decisions/2026-10-27-part-of.md) §2). A design names none of its builds: each build names
its design in **`Part of:`** (cadence §2.4), and the design stays in the ledger as *Designed*, not
pickable while an entry naming it is open; its own `Blocked by:` keeps only what must land first. A build
is filed by the design stage in the design's own pull request, so it exists, held where the design's
rounds have not ended, when that pull request merges, and it never waits on its design: a part blocked by its parent
or an ancestor is a cycle, an error of `ledger.py --check`. The rule is any parent's, a design's builds or a feature's subtasks alike: when the parent's `Blocked by:` is
empty, or every id in it is a local id that is archived, with no `decision (…)`, the PR that archives the
last of its parts archives the parent too, in the same commit. One that also waits on a `decision (…)` or
another repo's item stays until that is settled, and is then the fallback's, below — resolving
`<repo>#TD-n` is the home's, not the build session's. The build's session moves the design entry to the
archive with a `**Resolved:**` line naming each build and the PR that merged it (the first shape's `td` flow's
`build.md`). A part that is itself a parent archives one level per PR: a grandparent left with no open
part is pickable, and nothing cascades — a design grandparent is the fallback's below, and any other is
taken by the lane its `Kind:` puts it in, whose session archives it as an item of its own when nothing is
left to do (or the person's **Done…**). *Last* is read when that PR is made: no
other entry naming the design in `Part of:` is left in the ledger on `origin/<default>`. Two builds merging close together may each see
the other still open and leave the design entry. The tick's reconcile act then finds a design entry
that waits for its parts with none left open, and the home archives it (*Who archives the entry*,
above). In a repo with no team the last build's PR
carries the design entry all the same, whoever made it. One left behind there is the person's: the
Repo page's *every build archived — archive this entry* asks it of them, since there is no design
lane to take it.

**What is the repo's: `held:`.** A repo's `.shiftlead.yml` has one top-level key, **`held:`**, its
**protected files**: the paths a review stage with `only-when: protected-files` reads before a pull
request on them merges — a list, or named sets, read as their union (`["src/sessionorc/**",
"docs/briefs/**"]` for shiftlead). It is the repo's knowledge, so a flow never carries it. The home's
reading reads it too, against each open pull request's files (§4.4).

**One flow per team; more kinds of work are more teams.** A team runs one flow at a time. Different
kinds of work on one repo — building the ledger's entries, checking production, a UI-design pass —
are different teams on that repo, each with its own flow, and they hand work on **through the
ledger**, which is already the queue every team reads. A *prod-check* team whose flow is one audit
files what it finds as ledger entries, and the TD team's build stage takes them like any other;
neither team knows of the other. Each team keeps its own schedule, stop time and reserve (§5
`teams.<team>`).

Rejected: **a reviewer that reads only a design's first round** (TD-1721's Fable in round 1 alone: a stage
reads on every pass, and a rule keyed on the round is one more thing a flow's author cannot see on the page).
**A session that judges when a design's rounds end** (TD-1911's techlead judge: a limit or the person ends them,
which the flow already says). **A triage kind** (ranking and refusing entries is the person's, or an interactive
session's). **A test kind** (running and fixing tests is build's; a stage that only fixes tests is a
build stage with its own brief). **Hunt entries, and a hunt that files its own next entry** (nobody
would file one; a clock on the audit needs no entry for a run that finds nothing, and a run that
dies does not take the next with it). **One session across two kinds of work, and a `one-owner`
flow** (that is an interactive session; a stage is one kind, so the check stays small). **Work
carried on a branch with no pull request** (the verdict and the merge gate live on the pull request;
revisited if users ask). **A review's *reads it as* setting** (one brief reads whatever was pushed; a
narrower read is a brief of the person's own). **The stage record as a pull request per move** (the
forge's write limits, and main's whole precheck for a line of state). **A merge stage** (a session
only to merge spends a model on a command). **Reading the builder's own independent review as a
review stage** (it is a subagent's check inside building, which a flow with no review stage relies
on; a review stage is a separate session on a model the flow names). **A far-reaching round limit the session claims** (the
person's answer at the limit is the allowance). **A flow per entry** (per team). **Stages merged by
key across layers** (two lists have no one merge). **Several flows running at once on one team**
(which flow an entry belongs to is *which team* when a team runs one). **A stage a team may skip**
(the flow is said plainly and changed).
