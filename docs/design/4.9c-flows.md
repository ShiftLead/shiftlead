### 4.9c Flows: the path an entry takes through a team

**TD-307, TD-314, TD-1954; the first shape built by TD-309, TD-313, TD-315, the repos moved onto it by TD-310; the shape below is TD-1954's, built by the entries that name it in `Part of:`.** The dated record is `scripts/history.py 4.9c`; this section says what is true now.

**Terms used below.** A **flow** is the path a ledger entry takes from filed to done: a list of
**stages**, a list of **audits**, and a model for each **support seat**. A **stage** does one **kind**
of work (`design`, `build` or `review`) on one model. A session ends its stage by reporting one of
the kind's fixed **outcomes**; the flow says where each outcome sends the entry, its **next**. A
**limit** is how many times an entry may take one move before it comes to the person. The **stage
record** is where an entry is now. The person is in every flow and is no stage.

**A flow is records, not prose.** A flow is one file, `flow.yml`, in a directory with the briefs it
names. It holds no sentence a session must interpret to know where work goes: every stage has a
kind, every kind has fixed outcomes, and every outcome has one destination. A person, or a session
given only the format's description, writes a flow and runs the check (*A flow is usable only when
it flows*, below); three trials on Sonnet and Haiku wrote working flows from the description alone
(`docs/mockups/reviews/td1954-src/trial/`, the description, the check and the requests). A change to
the path is a change to a flow or a switch to another, never an edit to a repo's prose.

```yaml
# shiftlead/flows/build-review/flow.yml
format: 3
name: build-review
max-moves: 25                     # optional; 25 when absent
stages:
  - name: Build                   # free text, unique in the flow
    does: build                   # design, build or review
    model: opus                   # a model family the Tools page lists (§4.2b)
    takes: any                    # which new entries start here
    work-pushed: review           # an outcome, and its next
  - name: Review
    does: review
    model: sonnet
    ship: {to: merge, refused: {to: build, limit: 3}}
    changes-wanted: {to: build, limit: 3}
audits:                           # optional
  - {name: Docs audit, model: sonnet, every: 10 merged-pull-requests, brief: docs}
support: {tech-lead: opus}        # optional; each seat's model, the rest at their defaults
```

A stray key, at the top or in a stage, is refused naming it. `format: 3` is required: the first
shape's files (`stages:` of `role`, `lane`, `brief`) are format 1, and a file with no `format:` is
refused with the words that say so.

**Where flows and roles live: each a directory, whole.** A flow is a directory holding **`flow.yml`**
(its stages) and its stage briefs; a role defined outside the package is a directory holding
**`role.yml`** (its `ROLE_KEYS`, `kind` among them) and **`template.md`** (its mechanics, with the
template slots), which makes it a peer of a preset. They live in three places, resolved as a team's
name is (§4.9 *The org is an aggregate*) — the org's over a repo's over the package's, so an install
overrides a repo's without a PR:

- **the package**: `shiftlead/flows/<name>/` for the built-in flows; the built-in roles are the
  presets (`repoconfig.PRESETS`, `shiftlead/briefs/<role>.md`), each with its `kind`;
- **the org**: `~/.shiftlead/flows/<name>/` and `~/.shiftlead/roles/<name>/`, every team's to use, kept
  in the home's history beside the four files it already tracks (§4.9 *What is left at the home has
  a history*), committed by the home as `org.yml` is;
- **a repo**: `<repo>/.shiftlead/flows/<name>/` and `<repo>/.shiftlead/roles/<name>/`, its own teams'
  only (two repos may each define one name, since neither sees the other's), changed by PR.

A flow's or a role's name is its directory's. **Each is replaced whole, never merged by key**: two
stage lists have no one merge, and a role defined in two places is the org's. **A directory may not
take a preset's name** — refused when read and by `ao org check` — since a preset is the package's
and is redefined by key only (§4.8); nor may a flow directory take a built-in flow's name (`td`,
`build-review`, `build`): a repo or an install that wants other words defines its own flow under its
own name, so a built-in's stage briefs are never a repo's prose by another road. A repo's role
directory the org's shadows is said by `ao org`, as a shadowed team is. What layers by key is unchanged and is not a definition:
`org.yml`'s `roles:` overlay (a role's profile for this install) and a repo's `.shiftlead.yml`
`roles:` (its supplement brief, §4.8), each over the role wherever it is defined. The two orders
differ on purpose — definitions resolve the org's over a repo's, whole; overlays lay the repo's over
the org's, per key (`repoconfig.resolve_role`). **A `roles:` key naming
no preset and no directory is refused** when the file is read (*unknown role*, naming the
directories that would define it): an overlay is not a definition. A repo's `.shiftlead.yml` is
refused as it is read; `org.yml`'s `roles:` may lay over a role a repo defines, which the org file
cannot see, so its key naming nothing is refused where the role is resolved (a start, a flow's
check) and named by `ao org check` against every role directory it can see. A role directory that
is not whole is left out of `ao roles` and the pick-lists, and named by `ao org check`. A role defined in a directory writes its `kind` in `role.yml` (`worker`
where unwritten); an overlay never does. The YAML files keep no `flows:` key: a flow is found by its directory.
**An org flow or role is not usable by a team on a node** (§4.4a): a node team's roles and briefs
are read on the node, and the org's directories are the home's; such a team is told so as *not
followable* (*hunt cannot be followed by cm-grind: an org flow, and cm-grind runs on contractmatch —
define it in the repo*; likewise a repo flow of cm-grind's naming an org role, *security is an org
role*). Whether a node team can follow a flow is read as its start reads the node — the client
asks the node's files (`teams.Files`, `host_files`) for the repo's flow and role directories and the
briefs, so a repo-local flow or role the node's checkout does not hold yet (a branch not merged
there) is *not followable* by name, and a node that does not answer reads *unknown*, never
followable. A package flow rides the wheel and a repo's the checkout, so both reach a
node; the org's directories are not copied to nodes.

**A stage is one kind of work, one model, one fresh session.** An entry is in one stage at a time.
Every time an entry enters a stage, a **fresh session** on the stage's model takes it: it reads the
entry, its pull request and any review on it, does what is still needed, reports an outcome, and
ends its run. No session keeps an entry across stages, and none carries on from one kind of work to
another: one session that designs and then builds, or reviews and then fixes, is what a person's own
interactive session is for. A stage's keys are `name`, `does`, `model`, `takes`, `only-when`, `brief`,
`also` and its kind's outcomes.

| `does` | What its session does | Outcomes |
|---|---|---|
| `design` | writes the design for the entry and files the builds it needs | `work-pushed`, `not-needed` |
| `build` | writes the code, tests or documents, or continues what an earlier stage pushed | `work-pushed`, `design-needs-changing`, `not-needed` |
| `review` | reads whatever is on the entry's pull request and gives a verdict | `ship`, `changes-wanted` |

Every stage also has **`other`**: no listed outcome fits. It needs a reason, goes to the person
unless the flow says otherwise, and the kind's brief names it the last choice.

**All of an entry's work is on one pull request.** The first stage that pushes work opens it and
later build stages push onto it. Running and fixing the tests is `build`'s; a narrower read (a
fact-check, a security review) is a `review` stage with a brief of the person's own, or an `also`. There is no merge stage,
no test stage and no stage of two kinds.

**A stage's key is its name.** The key is the name in lower case with spaces as hyphens (`Second
read` is `second-read`); a destination names a key, and the stage chip reads the name. Renaming a
stage on the Flows page re-keys every destination in the file in the same save, and the stage
records of entries in it (*A switch or a rename re-keys the records*, below). The order of `stages:`
is for reading: only the destinations say where an entry goes.

**An outcome is the session's word, checked.** A session ends its stage with one command,
**`ao stage end <outcome> [--reason "…"]`** (§4.7), run in its worktree. Until it runs the command it
is working: a red check or a failing test is no outcome. The command checks the outcome's fact and
**refuses an outcome the facts contradict**, saying which fact, so the session carries on; accepted,
it writes the stage record's move and the session's part is over.

| Outcome | Checked first |
|---|---|
| `work-pushed` | the entry's branch is pushed and its pull request is open; its precheck is green, unless the next is another build stage, which is expected to finish the work (a tests-first stage ends red on purpose) |
| `ship` | a verdict is recorded on the pull request's latest push |
| `changes-wanted` | a verdict is recorded |
| `not-needed`, `design-needs-changing`, `other` | a reason is given |

When a fact needs the pull request, the command reads the forge itself; the session never states it.

**Where an outcome goes.** A stage writes `<outcome>: <destination>`:

- **a stage's key** — the entry moves there; with `{to: <key>, limit: n}` at most `n` times.
- **`merge`** — allowed on `work-pushed` and `ship` alone. The command runs the repo's merge gate on
  what is there now (§6 rule 10) and merges; no session of its own is started, so no model is spent on
  it. A merge is **refused** when the pull request changed after its verdict, is red, or conflicts;
  `{to: merge, refused: {to: build, limit: 3}}` says where a refused merge goes, and plain `merge`
  sends it to the person.
- **`person`** — the entry waits for the person, with one item on their board that carries the
  stage, the outcome and the reason (§4.4 *The stage record*). `{to: person, answers: {"Try again":
  build, "Drop it": done}}` offers answers that each name a destination; an answer in the person's
  own words goes back to the stage that asked, where a fresh session reads it.
- **`done`** — the entry is finished with nothing to merge; refused on `work-pushed` and `ship`,
  which would leave a pull request open.

**An outcome the flow does not list goes to the person.** Two destinations are fixed and written by
no flow: a design entry whose pull request merged **waits for its parts** (*A design entry archives
with its last build*, below), and an entry whose session is lost is **offered again** (below). **A
merged pull request ends its entry wherever it stands**: the person merging by hand needs no stage,
so *the person merges* is written `ship: person`.

**Limits.** A limit may sit on any move to a stage, forward or back, and on `refused`. `limit: 3`
lets an entry take that move three times; the fourth goes to the person. The count is per entry and
per move, and starts again only when the person answers at a limit. **`max-moves`** caps the whole
trip: after that many moves between stages (25 where unwritten) the entry comes to the person
wherever it is. There is no separate allowance for a far-reaching design (dropped on purpose,
2026-11-21): at a limit the person answers *carry on*, which restarts the count, so the extra rounds
are the person's call and cost one question.

**Ways in.** A new entry has no stage. `takes` says which stage it starts in: `design-first` (an
entry whose `Kind:` asks for a design before code), `other` (one ready to build) or `any`. Each kind
has exactly one stage that takes it, a flow with no design stage writing `takes: any` on its first
build stage; a review stage takes none. An entry's `Owner:` line, where it names a stage's key, is
read once as its way in and nothing else reads it: ledgerboard's field is unchanged, and where an
entry is afterwards is the stage record's.

**A review that runs only sometimes.** `only-when: protected-files` on a review stage means it reads
only pull requests that touch the repo's protected files, the paths `.shiftlead.yml`'s `held:` lists
(*What is the repo's*, below). For any other pull request the stage is **passed without a session and
counts as `ship`**: the home writes that move. Reviews run one after another, never two at once on
one pull request. The check warns, and does not refuse, where a review stage runs on the model of a
stage whose work it reads.

**Audits start on a clock.** An audit is no stage and takes no entry through the flow. It has a
`name`, a `model`, `every` (`<n> merged-pull-requests`, `<n> hours` or `<n> days`) and a `brief`
that says where it looks. When its clock comes round the home starts a fresh session with that
brief; it files each problem it finds as an entry of its own, which enters the flow by its way in,
fixes nothing, and ends as `findings-filed`, `nothing-found` (both finish the run) or `other` (the
person, the item naming the audit and the run). Nothing is sent to an audit. The docs and test
auditors of §4.9b's *Seats with a trigger* are two audits of the `td` flow. There is no hunt entry: a
hunt across parts of the code is an audit with the `code` brief or one of the person's own. An
audit's `brief:` is `docs`, `tests`, `code` or the name of a brief of the person's own, and it may
carry `also:` (*What a stage's session is told*, below).

**Support seats take a model and nothing else.** Five seats are in every flow and are no part of the
path: the **tech lead** (answers members' questions, §4.9b), **board answers** (acts on what the
person decided), **pull requests nobody holds** (§4.4), the **manager** (§4.9) and the **sweeper**
(§4.9b *The sweep*). A flow's `support:` gives each a model under its key (`tech-lead`,
`board-answers`, `unheld-pull-requests`, `manager`, `sweeper`), a seat left out running on the package's
default; their triggers, briefs and rights are their own sections' and no flow changes them. The tech
lead's reading of protected files is no longer the seat's: it is a review stage. Where the org has a
director (§4.9b), *the director* as a destination beside *the person* is a later entry's. Mail
changes no stage and is outside the flow (§4.10).

**The stage record.** Where an entry is — its flow, stage, when it entered, each move's count, the
moves so far, and what it waits on — is ShiftLead's own record, one file per entry on **one
dedicated branch of the repo, `shiftlead/state`**, beside the audits' last runs (§4.4 *The stage
record*). It is written only by `ao stage end` and the home's own use of the same writer, each write
a commit pushed by compare-and-swap as `cadence/ledger-ids` is (a push that loses the race is
re-read and tried again), never a pull request: a pull request per move would spend the forge's
write limits and run main's precheck for a line of state. The branch is in the repo, so the record
survives a home's reset and is readable from any machine. **Claims stay at the home** (§4.8 *A claim
is a lease*): which session holds an entry now is the lease, and whether claims move to the branch
too, which would let several orgs work one repo, is TD-2033's question.

**The home acts only where no session will.** The tick (§6) reads the stage records and does five
things, each through the same writer: it **offers** an entry in a stage with no holder to a fresh
session of that stage, within the team's size; it **passes** an `only-when` stage that has nothing
to read; it **starts** an audit whose clock came round; it **offers again** an entry whose session
is lost (its lease lapsed with no outcome, which §6 rule 6 does not re-offer today, TD-899's gap, and
must) or **silent** (a live session that holds the entry and has done nothing for the bound, once,
then the person; the person is never silent); and it **applies the person's answer** to a board
item as the move the answer names. It audits what the command checked and moves no entry for any
other reason.

**A claim's chip is its stage.** Each row of a team card's *TDs in motion* (§4.5a) leads with a chip
that says where the entry is now, read from its stage record: the stage's name, in the colour of its
kind (design indigo, build blue, review amber) and in the flow's order; grey **you** while the record
waits on the person; *merged* or *closed* beside the stage once its pull request is no longer open;
and, for a claim with no stage record (a person's own session, a team of the first shape), its
holder's role in grey. The chip is derived at the view and is never a reason for a rule to act.
Paul, 2026-11-12: *accuracy is key here, the user needs to be able to trust the ui* — a chip says
only what the record shows.

**What a stage's session is told.** A session's opening prompt is, in order: ShiftLead's mechanics
(the turn that ends to wait, mail, the usage gate), how work is taken and ended (`ao stage end`,
its outcomes and the facts each is checked on), the repo's rules (its supplement, §4.8), and **the
stage's brief**. The brief says the job; the path is not in it, since the outcomes are the path.
**Every stage and every audit picks one brief from a list and may add to it** (Paul, 2026-11-21).
The list holds the **standard briefs** that ship with ShiftLead — one each for design, build and
review, and three for audits, `docs`, `tests` and `code` — and the person's own. A stage with no
`brief:` takes its kind's standard brief; `brief: <name>` picks one of the person's own in its
place; an audit always names its brief. **`also: <text>`** is appended to whichever brief is
picked, so a standard brief keeps improving with ShiftLead while the flow's own addition stays. A
brief of the person's own is written on the **Briefs page**, belongs to one kind (design, build,
review or audit), and is offered only to a stage or audit of that kind; the standard briefs are
drawn there read-only. The built-in session roles are named for the kinds, **designer**,
**builder** and **reviewer**, and `grinder` is renamed `builder` at the cut-over (§4.8).

**The built-in flows.**

- **`td`**: *Design* (takes `design-first`) → two design reads on two models → *Fact-check* → merge;
  *Build* (takes `other`) → *Review* → *Protected read* (`only-when: protected-files`) → merge; each
  `changes-wanted` and refused merge back to *Design* or *Build* with `limit: 3`; two audits, docs
  every 10 merged pull requests and tests every 6 hours.
- **`build-review`**: *Build* (takes `any`) → *Review* → merge.
- **`build`**: *Build* (takes `any`) → merge, nothing reviewed.

A built-in is read-only on the page and is changed by copying it. The models they ship with are the
package's defaults and are a person's to change in a copy.

**A flow is usable only when it flows.** The check (`ao flow check <file>`, the page's *Does it
flow?*, and every read of a flow) holds these, each refused with the stage and outcome it is about:

1. Every destination is a stage that exists, or `merge`, `person` or `done`; only `work-pushed` and
   `ship` go to `merge`; nothing goes to an audit.
2. Every outcome a stage lists belongs to its kind.
3. **Every loop has a limit**: where an entry can travel from a stage back to it without passing the
   person, a move on that route carries a limit, a refused merge's move included. Loops are found
   from the moves, never from the order of `stages:`.
4. Every pull request that can be opened can reach a `merge`, or a `work-pushed` or `ship` that goes
   to the person.
5. `work-pushed` and `ship` never go to `done`.
6. Each kind of new entry has exactly one way in, and it is no review stage.
7. Stage and audit names are unique and no reserved word; each stage has a kind and a model.
8. Every stage can be reached, by `takes` or as a destination.
9. `max-moves` is a whole number of 2 or more.
10. Every audit has a name, a model, an `every` and a brief; a `brief:` names a standard brief or one of
    the person's own, of the stage's or audit's kind.

It warns, without refusing, on a review stage that shares its writer's model, and prints what goes
to the person. A flow that fails is **not usable**: listed as such by `ao org`, saved by no page,
and run by no team.

**The Flows page** (§4.5a; the working prototype is `docs/mockups/reviews/td1954-src/prototype.html`,
its views `docs/mockups/reviews/2026-11-21-td1954-flows-td-1440.png` and
`2026-11-21-td1954-flows-editing-1440.png`). The left column lists the built-in flows and the
person's own, a dot on one with problems, and under a flow of the person's the three kinds of stage:
a click adds a stage of that kind after the open one, and a drag puts it where it is dropped. The
head carries the flow's name, *It flows* or the count of problems, **Copy**, **Delete** and **Save**
(disabled while the check fails), and the total cap. Three tabs: **Stages**, a card per stage with
its name, key, kind, model, what it takes, a review's *runs* setting, the kind's description, a
**brief** link that shows what the session is told with the brief's pick and the *also* text, and a row per outcome under *Outcome / Checked first / Next*, each Next a pick (a
stage, *this stage again, with a fresh session*, *merge it* with its *if the merge is refused* pick,
*you*, *done*) with a limit field; below them **Audits**, a card each with its clock, added and
removed there, and **Support**, each seat's model; **Walk an entry**, which starts an entry of either
kind or lets an audit's clock come round and follows the outcomes the person picks, limits and the
cap included; and **The file**, the `flow.yml` as it will be saved. A problem is drawn on the row it
is about, in the check's words.

**A team runs one flow, and which is the team page's.** Which flow a team runs, how many sessions it
may have in each stage at once and which logins they use are the team page's (TD-1153, the frame of
[ADR 2026-11-18](../decisions/2026-11-18-tools-flows-teams.md)); every team runs a flow. **A switch
or a rename re-keys the records**: when a team's flow changes, or a stage is renamed, each open
entry's stage record is rewritten to the stage of the same key in the new flow, and an entry whose
stage has none comes to the person with the stages it may go to as the item's answers. That rule is
carried to the team page's round, which says who presses it.

**What this replaces.** The first shape compiled a flow, at a client, into each member's lane,
reader chain and brief, and nothing moved an entry (*What a flow compiles to*, *A review stage any
seat may hold*, *Switching*, the sit-out, the ask a builder sent its reader, `--verdict` on a reply
and `ao pr held`'s walk of the chain). Under format 3 none of that is the flow's: a stage's session
is started for an entry, a review is a stage the entry is in, and the reader hears of a pull request
by being started on it. Those mechanisms are removed at the **one cut-over window** the ADR names,
with the first shape's `flows:` list, `teams.<team>.flow` and `ao team flow`; until that window's
builds land the code runs the first shape, whose text is this section at the parent of TD-1954's
design merge.

**Not yet carried into the flow (TD-1954).** The next two paragraphs, a design's reviewers by round
(TD-1721) and the judge that ends a routine design's rounds (TD-1911), are written for the first
shape. Under `td` a design's reads are review stages that run on every pass, so *Fable in round 1
alone* has no stage to say it, and the judge is no stage yet; both stand as written until a round
with the person settles how they sit in the flow. The `reach` row of the cadence check is unchanged
either way: a build that matches `[far-reaching]` waits for a person's Go.

**Who reviews a design's rounds** (TD-1721, a part of TD-1711; re-scoped by Paul, 2026-11-13, from a second seat
that applies the fixes, which the cost model showed would save about 2% of a design's spend; the rule is his answer of
2026-11-13). **Fable reads a design in round 1, and Sonnet in every round.** Round 1's design review is a Fable
review, then a Sonnet one, as every round's was before; from round 2 on, a bought round's and a `Hold` revision's
rounds among them, a round's design review is one Sonnet review, with two exceptions, where Fable reads again:
- **a long design**: in a round past round 4 by the review record's count (a bought round's and a `Hold` revision's
  rounds carry the count on, though a revision's cap starts again), once its Sonnet review has raised a build-changing finding, the fixer
  applies that review's fixes and a Fable review reads the design in the same round, so a round past 4 that still
  finds build-changing work has both reviewers before it ends (Sonnet first here, since its finding is what calls
  Fable back), and such a round never ends them by the stop rule, since Sonnet's finding is build-changing; it adds nothing to a round where Fable has already
  read (a major release's, below). A Fable finding that reopens Sonnet's names its id and is adopted as any finding is (the designer brief's
  *Adopt each finding by the template's three tiers*), and a fix of it that no review reads falls under the brief's
  *A fix no review has read*;
- **a design for a major release**: every round is Fable then Sonnet, each review's fixes applied before the next
  reads, as in round 1. A major release is a version of any repo the
  design's builds change (shiftlead, ledgerboard, agent-cadence) whose first
  number changes (ledgerboard v3.0, for example). The designer states it beside the design's class, before round 1,
  in the design entry's Log; one that becomes a major release's later (its builds or the person's word say so) is
  stated then, and every round from the next is Fable then Sonnet. A design not so stated is not one.
The fact-checks, the cap, the stop rule (read over that round's design reviews, so a round with only Sonnet's ends the
rounds when Sonnet's raises nothing build-changing), the record and the end-of-rounds item are cadence §4.8's and
unchanged (who judges is *Who ends a design's rounds*, below); each reviewer is still a fresh subagent given the worktree's path, and Fable's review stays Paul's
exception to the cadence's *never the same* (the designer brief). A design whose round 1 has run takes the rule from
its next round to start after the brief that writes it merges. **Why**, from [the cost
model](../decisions/2026-11-12-design-cost-model.md) (*For TD-1721*): a Fable review cost $3.41 on the mean and a
Sonnet one $0.51 (27 and 83 reviews over five designs, Sonnet's counting its fact-checks), so Fable is about two thirds of a design's reviewers' spend
and two fifths of its whole; and Fable's yield of findings only a design review would catch falls after round 1 —
2.12 for each review in round 1, 1.25 in round 2, 0.66 and 0.77 in rounds 3 and 4 (41 designs), though 1.59 again in
the long designs' rounds past 4, which the first exception answers — while Sonnet, reading second, still raises 1.27
in round 1. On the 41 designs' review counts, a design's reviewers cost about $20 with Fable then Sonnet in every
round and about $9 with Fable in round 1 alone (the long designs' Fable rounds past 4 add to that); Sonnet alone,
round 1 included, about $6, was the third choice. What a round without Fable leaves silent is not measured, since
Sonnet has always read second: the 139 findings of that kind Fable raised after round 1 (3.4 for each design) are the
ones at risk, and the trial that would have read the real designs' escapes did not run (*The trial of the new shape*, below), so a loss there is unmeasured.

**Who ends a design's rounds** (TD-1911; Paul, 2026-11-16: the person decides far-reaching designs, a new seat or
flow, and not routine ones, *add a button that does X*). How the rounds end is cadence §4.8's (agent-cadence TD-281,
TD-288): the designer marks the design `routine` or `far-reaching` beside its class, runs the closing fact-check,
runs `review_stats.py --verdict TD-<design>` and does the step its `next:` line names; the verdict is counted, never
chosen, and a **judge** confirms or raises it. ShiftLead adds three things, and nothing else:
- **The judge is the team's techlead seat**, the seat the designer's brief names for its steers and asks (its
  `{techlead}` slot). On `next: judge` the designer sends that seat an `ask` about the

  `CONFIRM` of `Go` is then **the judge's Go**, `Go by: judge (techlead)` (or `judge` for the default judge), and the

- **What is far-reaching here.** The designer marks a design far-reaching where a passage its own PR changes says
  who may act, answer, merge or decide for the person: a role's or seat's rights, which seats a flow has, a
  permission, a delegation, what reaches the person and what does not. The test is the passage, not the file: a

  far-reaching. The designer names those passages on the record's `Reach:` line, whatever its builds touch; the

**A design entry archives with its last build** (TD-693; read from `Part of:` since TD-1129, [ADR
2026-10-27](../decisions/2026-10-27-part-of.md) §2). A design names none of its builds: each build names
its design in **`Part of:`** (cadence §2.4), and the design stays in the ledger as *Designed*, not
pickable while an entry naming it is open; its own `Blocked by:` keeps only what must land first. A build
is filed once its design's round has merged, so it never waits on its design: a part blocked by its parent
or an ancestor is a cycle, an error of `ledger.py --check`. The rule is any parent's, a design's builds or a feature's subtasks alike: when the parent's `Blocked by:` is
empty, or every id in it is a local id that is archived, with no `decision (…)`, the PR that archives the
last of its parts archives the parent too, in the same commit. One that also waits on a `decision (…)` or
another repo's item stays until that is settled, and is then the fallback's, below — resolving
`<repo>#TD-n` is the home's, not the build session's. The build's session moves the design entry to the
archive with a `**Resolved:**` line naming each build and the PR that merged it (the td flow's
`build.md`). A part that is itself a parent archives one level per PR: a grandparent left with no open
part is pickable, and nothing cascades — a design grandparent is the fallback's below, and any other is
taken by the lane its `Kind:` puts it in, whose session archives it as an item of its own when nothing is
left to do (or the person's **Done…**). *Last* is read when that PR is made: no
other entry naming the design in `Part of:` is left in the ledger on `origin/<default>`. Two builds merging close together may each see
the other still open and leave the design entry. It is then pickable, since everything it waits on
is archived, and so it is in the design stage's lane. Its designer archives it as an item of its
own, which is the rule from before 2026-10-14, kept as the fallback. In a repo with no team the last build's PR
carries the design entry all the same, whoever made it. One left behind there is the person's: the
Repo page's *every build archived — archive this entry* asks it of them, since there is no design
lane to take it.

**What is the repo's: `held:`.** A repo's `.shiftlead.yml` has one top-level key, **`held:`**, its
**protected files**: the paths a review stage with `only-when: protected-files` reads before a pull
request on them merges — a list, or named sets, read as their union (`["src/sessionorc/**",
"docs/briefs/**"]` for shiftlead). It is the repo's knowledge, so a flow never carries it. The home's
reading reads it too, against each open pull request's files (§4.4).

**One flow per team; more kinds of work are more teams.** A team runs one flow at a time. Different
kinds of work on one repo — building the ledger's entries, checking production, a UI-design pass —
are different teams on that repo, each with its own flow, and they hand work on **through the
ledger**, which is already the queue every team reads. A *prod-check* team whose flow is one audit
files what it finds as ledger entries, and the TD team's build stage takes them like any other;
neither team knows of the other. Each team keeps its own schedule, stop time and reserve (§5
`teams.<team>`).

Rejected: **a triage kind** (ranking and refusing entries is the person's, or an interactive
session's). **A test kind** (running and fixing tests is build's; a stage that only fixes tests is a
build stage with its own brief). **Hunt entries, and a hunt that files its own next entry** (nobody
would file one; a clock on the audit needs no entry for a run that finds nothing, and a run that
dies does not take the next with it). **One session across two kinds of work, and a `one-owner`
flow** (that is an interactive session; a stage is one kind, so the check stays small). **Work
carried on a branch with no pull request** (the verdict and the merge gate live on the pull request;
revisited if users ask). **A review's *reads it as* setting** (one brief reads whatever was pushed; a
narrower read is a brief of the person's own). **The stage record as a pull request per move** (the
forge's write limits, and main's whole precheck for a line of state). **A merge stage** (a session
only to merge spends a model on a command). **A far-reaching round limit the session claims** (the
person's answer at the limit is the allowance). **A flow per entry** (per team). **Stages merged by
key across layers** (two lists have no one merge). **Several flows running at once on one team**
(which flow an entry belongs to is *which team* when a team runs one). **A stage a team may skip**
(the flow is said plainly and changed).
