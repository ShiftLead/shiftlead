### 4.6 Transport and terminal mechanics

- **One long-lived ssh per host, JSON lines over it.** The UI holds this link to the **home**
  host agent only; every other host agent holds its own link to the home, dialing out (§4.4a);
  the JSON-lines protocol, the backoff and the `unreachable` diagnosis below carry over to that
  link, which additionally multiplexes requests by id. The UI keeps `ssh host shiftlead-agent
  serve` open and speaks newline-delimited JSON requests/responses on its stdin/stdout (the same
  protocol the CLI speaks to the Unix socket locally). No per-call ssh handshake, so a Sessions page
  refresh across hosts is one round trip, and no argument ever reaches a remote shell — ssh's
  argv-joining is never used for data. The connection is re-opened with backoff when it drops.
  Terminal attaches to a session on another host (`ssh -tt host tmux attach -t <name>`) are
  separate ssh processes and reuse the same master via `ControlMaster auto` / `ControlPersist`
  in a config file the UI writes and passes with `-F`, so a person's own ssh config is untouched.
- **`unreachable` is diagnosed, not assumed.** The transport distinguishes *ssh failed* (host
  down or asleep) from *ssh ok, agent RPC failed* (agent crashed, stale socket). Both grey the
  cards; the banner says which ("laptop unreachable" vs "agent down on host1"), and **Retry**
  on the second case also tries `systemctl --user restart shiftlead-agent` over ssh.
- **Creation is serialised per directory** inside the host agent (one `asyncio.Lock` per
  resolved path), which makes the anchor rule (§9 invariant 2) a guarantee rather than a check
  two clicks can race past.
- **Attach behaviour with another client present.** tmux's default `window-size latest` means a
  browser Focus and a VS Code `tmux attach` on the same session re-size each other's view as
  each is used. Phase 1 accepts and tests this; `window-size manual` plus a fixed `default-size`
  is the fallback if the reflow upsets Claude Code's TUI. **A Focus tells tmux its grid once per gesture**
  (TD-794): the page sends `{"resize": [cols, rows]}` with the last grid once the terminal's box has been
  still for 150 ms, and none when tmux already has that grid (`AO.resizeSender`) — a drag of the panel's
  edge, a put away or a window resize fires the box's observer once a frame, and each resize makes the
  tool repaint over lines tmux has kept. **The page says when it happens**
  (TD-474; built by TD-480): while a terminal is attached the bridge reads tmux's
  `#{session_attached}` and the window's size (`display-message -p`, every five seconds; the rows
  counted with the status bar's lines, as a client's grid counts them) and sends
  a text frame `{"clients": n, "window": [cols, rows]}` whenever either changes — the attach's own
  word, as the `read_only` frame is: not pane output, no backoff reset — and the page draws the
  terminal mark *resized by another client* (*Reconnect contract*, below) while `clients` is above
  one and the window's size is not its own grid's, cleared when they agree again.
- **Reconnect contract.** The pty lives in the UI process. If that process or the websocket
  drops, the browser reconnects with backoff and the fresh `tmux attach` redraws the current
  screen; nothing is replayed from the run log. Three rules make that loop terminate (TD-029):
  the backoff resets on the first byte of **pane output**, never on open — a connection the
  server accepts and then ends is not a working terminal; a **dead attach is final**, so the
  server closes 4404 (the one code the client never retries) whenever the attach process exits
  non-zero or without ever painting a screen, not only when the record already says the pane is
  gone; and a pushed `closed` or `pane: false` delta ends the terminal from the page itself,
  because the push is authoritative and arrives before any reconnect could — `kill` and `close`
  announce it as they return rather than waiting for the next tick. `send-keys` is a host-agent
  RPC independent of any attached pty, so a Send never depends on a Focus being open. **The
  terminal mark** (TD-474; built by TD-480): the Focus header carries, beside the state pill, one
  mark at a time for what the terminal is doing, in this order of precedence — *reconnecting…*
  while the terminal socket is closed and a retry is pending, drawn after the same three-second
  grace as the host agent's down banner (§4.5 *Browser mechanics*), so a navigation and a
  promote's restart draw nothing; *resized by another client* (above); *no output for Ns*,
  counting up, when the socket is open, the record reads `working` and no pane byte has arrived
  for thirty seconds — never on an `idle` session, where silence is the normal case — cleared by
  the next byte. Each mark's hover says what it means and what to do (§4.5a). Each event — a close
  with its code and reason, a reopen, the first byte after a silence, a resize seen — goes to the
  browser's console with its time, `[shiftlead] terminal …`, so the next freeze names its cause;
  the grey retry line written into the terminal stays. The
  terminal shows tmux's scrollback (`history-limit`) only; the run log is a download, never a
  terminal source.
- **The disconnect card** (TD-923). A Focus whose UI process is down is a blank pane and a retry line: the
  one reload (§4.5 *A reconnect reloads once, never in a loop*) empties the terminal until its
  attach paints; the wait is where the person wonders what the stall is costing. So while the
  terminal mark reads *reconnecting…*, a card between the Focus header and the pane says what
  the page already holds of spend: this session's, its team's and All's, today and this week,
  as the Spend page reads them (§4.4 *Spend per seat*) — **each row money and tokens**: the
  subscription's API-equivalent (`≈$`, never a bill) and a metered profile's bill (`$`) as two
  figures, never one sum, since one is what was paid and the other what it would have cost (a
  scope on one kind of profile draws one) — the one place the card departs from the Spend page,
  which folds a mixed sum to `≈$` (§4.5 screen 13); then the tokens, every kind summed (*4.1M tok*, the
  chip's short shape, the four kinds on hover — the one rule the Spend page draws by too, §4.4 *Spend per seat*; its All row, money and tokens alike, is every seat's sum, so *outside shiftlead*, which the page's whole holds, is not in it), because *we used a million tokens on this* is a
  thing people say and the bill is not —
  the account's windows under them as the top bar's chip last read them (§4.5a **usage chip**;
  the reset as its hover gives it),
  and *as of HH:MM* at its foot, the time of the reading. **Nothing is fetched while the link
  is down**: the figures are the Spend reading the page takes at its load and at each
  reconnect (`/api/spend`, one read per scope and window — its team and All, day and week, with
  `top=all` so its own row is in the reading), and the last `usage` event, both kept in `sessionStorage` under the session's id so the reloaded page draws them
  before its attach answers; a figure the page never got reads *no reading*. The card is drawn
  after the mark's grace, so a navigation and a promote's restart draw nothing; **never over the
  pane**, so a screen the terminal still holds stays readable; and the grey retry line with its
  countdown stays the terminal's, unchanged. It goes with the mark, on the first pane byte. It
  is a card, not a game: the person was mid-task, and what the stall costs is the one thing the
  page can tell them that the pane cannot. **The state is reachable on demand**:
  `scripts/focus_drop.py` opens a Focus in the smoke's browser (`scripts/smoke.py --setup`),
  holds `/term/` and `/events` closed for a given time, and writes the screenshot — so the card
  is reviewed from a picture, and a change to the reconnect path is seen before it is merged.
- **Scrollback is tmux's, reached through tmux (TD-022).** tmux repaints the client in place and
  keeps the history itself, so xterm.js runs with no local buffer. Shift+PageUp / Shift+PageDown
  scroll it by a bridge message the UI turns into `copy-mode -e -u` / `page-down` against the
  session (there is no escape sequence for copy mode). **The mouse is the browser's.** The attach sets no mouse option (a session an earlier attach set `mouse on` on
  keeps it until it is started again, since the option is the session's), tmux asks for no tracking, and xterm.js keeps
  the mouse: **a plain drag selects in the browser**, Shift+drag does the same (with no tracking,
  Shift is nothing to xterm.js, so the habit costs nothing and needs no setting), and
  **Shift+click grows or shrinks the selection** — xterm.js's own selection service does it
  (`shiftKey → _handleIncrementalClick`, read in the vendored source), as VS Code's terminal
  does. **The wheel still scrolls tmux's history**: the page catches `wheel` on the terminal and
  sends the scroll message Shift+PageUp sends, with a line count — `{scroll: up|down, lines: n}`,
  the notches of one animation frame batched into one message — which the bridge turns into
  `copy-mode -e` then `send-keys -X -N n scroll-up` / `scroll-down` against the session, so a
  notch is lines, not a page, and `-e` leaves copy mode at the bottom as before. The wheel is a
  tmux command per frame down the bridge, never a mouse report: the read-only attach passes it as
  it passes every scroll message.
  **A finger's drag scrolls it too (TD-986)**: a touch screen sends no `wheel`, so the page catches
  a one-finger touch on the terminal (`touchstart` / `touchmove` / `touchend`, in the capture phase,
  before xterm.js's own touch handling) and turns its vertical travel into the same message — the
  vertical pixels moved over the cell's height (the wheel's own `clientHeight / rows`), in lines, a frame's worth batched into one
  `{scroll: up|down, lines: n}` with the fraction carried to the next, as the wheel's notches are
  (`AO.wheelStep`). The content follows the finger: a drag **down** brings older lines into view
  (`up`), a drag up newer ones. A touch that moves less than 10 px vertically before it lifts is a **tap**, and
  stays the browser's — it focuses the terminal, which raises the phone's keyboard; past 10 px the
  touch is a scroll until it lifts, so no tap follows it, and its lines are counted from where it
  started, the first 10 px included. Sideways travel is no scroll and nothing else (tmux's history
  has no sideways). One pure function, `AO.touchStep(total, sent)`, beside `AO.wheelStep`, takes the
  touch's vertical travel since it started and the travel already turned into scroll, and returns
  `{add, sent}` — `add` is 0 while `|total|` is under 10 px and nothing has been sent, then
  `total - sent` — so the first 10 px count once and nothing twice; the caller divides `add` by
  the cell height and negates it into the wheel's accumulator. There is no fling: the history moves while
  the finger does. The terminal is `touch-action: pinch-zoom` — set on `.termbox` and on xterm.js's own `.xterm`, `.xterm-viewport` and `.xterm-screen`, since the viewport is a scroll container of its own and a touch on it would not read its parent's value — so a drag on it never scrolls the page
  underneath, and two fingers put down together still zoom the page; a second finger joining a
  scroll that has begun ends the scroll, and the touch stays inert until every finger has lifted. **A touch does not select**: xterm.js 5.5 has no
  touch selection, so a long press is not a gesture of the terminal's, and the `contextmenu` a long
  press fires is not the right-click paste (*Copy / Paste*, §4.5a): the page's `contextmenu` listener
  still prevents the browser's own menu but pastes nothing (no `pasteClip()`) when the last
  pointer was a touch, and draws no menu of its own, read from a `pointerdown` listener on `#term` in the capture phase
  (pointer events still fire for a touch whose `touchstart` is prevented), each new `pointerdown`
  replacing the last, so a mouse after a touch on a hybrid device right-clicks as before. Text is copied on a phone from the Transcript (screen 9), whose
  page is the browser's own text. Desktop scrolling, selection and the read-only attach are
  unchanged, and so is TD-667's rule: a drag is a scroll, not typing.
  **Typing returns the pane to the live screen** (TD-667; Paul, 2026-10-13: *have the Focus
  terminal unscroll to the prompt input when a user starts typing in it … typing into the composer
  should not do this, just in the terminal portion*). In copy mode tmux reads keys as copy-mode
  commands, so a key typed into a scrolled-back pane is otherwise swallowed. So **the bridge leaves
  copy mode before a typed key**, as a local terminal jumps to the prompt on input:
  - **What counts as typing**: a key frame from xterm.js that does not start with ESC and holds a
    printable character (a key, a fast burst, IME text, a paste with bracketed paste off); Enter,
    Tab or Backspace alone; or a bracketed paste (the one ESC-led frame that counts, from its
    `ESC [200~` opener). Everything else passes as it does today and stays copy mode's: every other
    frame that starts with ESC — arrows, function keys, and the replies xterm.js sends to
    the program's own queries on the same channel (a device report, a cursor position, a focus
    event), which must never move a person out of the history they are reading — and Ctrl+C and
    Escape, which are copy mode's *cancel*, so a person leaving copy mode with them never interrupts
    the program, and any other control byte. Neither the wheel nor Shift+PageUp / PageDown is a key frame.
  - **Who knows the pane is scrolled: the bridge**, from its own scroll messages. Any scroll
    message sets its *scrolled* mark. A counted key frame while the mark stands first runs
    **`copy-mode -q`** against the session and clears the mark, then writes the key. When the pane
    is no longer in a mode (`-e` left it at the bottom), the command does nothing. A copy mode some
    other client entered is not seen: the mark is this attach's, and reading `#{pane_in_mode}` on
    every key would cost a tmux call per keystroke.
  - **In order**: the bridge runs the tmux commands it spawns one at a time, each awaited to its
    end, in the order its frames came. A key waits for the leave before it, and a leave never
    overtakes the scroll before it. A leave that fails or passes two seconds is logged, and the
    key is written anyway.
  - A read-only attach drops key frames before any of this, so nothing is left. A program's own
    mode (`less`, `vi` in the pane) is not tmux's copy mode, and is untouched.
  - **The composer is not the terminal**: typing in it leaves the pane where it is. **Send** is
    another matter. The host agent's paste reaches a pane in copy mode, but its Enter is the
    mode's, so the prompt would stick (checked on tmux 3.5a). Every paste-and-Enter the host agent
    makes (§4.3 *Prompt injection*) therefore leaves copy mode first, and a press of **Send** returns
    the pane to the live screen, as the prompt lands.
  **A jump to a prompt** (TD-975; the Focus Prompts card, §4.5). A press on a row sends the bridge
  `{jump: [{drawn, whole}, …]}`: the `drawn` openings and their `whole` marks (§4.2 `prompts`) of the card's prompts from the newest down
  to the pressed one, those without one left out. A pressed prompt without one is a miss at the page,
  and nothing is sent. tmux's own search is not enough. `search-backward-text` finds the nearest match
  from the cursor, so a short prompt (*yes*) lands on the newest *yes*, in the history or in the tool's
  output. A resize repaint draws every prompt again (TD-794). So **the bridge walks the history
  itself**:
  - **One read, the view held.** One tmux command through the scroll's prefix leaves any copy mode,
    enters it again and reads the pane: `copy-mode -q ; copy-mode -e ; display -p '#{history_size}' ;
    capture-pane -p -S - -E -`, each command with the session's target (`-t =<id>:`) as `scroll_argv`'s
    are. The `-q` comes first because `copy-mode -e` on a pane already in mode keeps that mode's older
    view. Its first output line is `history_size`; the rest are the rows, and row *i* is the *i*-th line
    after that one. It is plain text, with no escapes and no joining: the tool wraps its
    own lines, so a prompt's first row is a row of its own. Copy mode's view holds still as output
    arrives (checked on tmux 3.5a), so the read is the view the landing scrolls. `history-limit`
    (§4.1) bounds the read, and a read that runs past `JUMP_WITHIN` (five seconds) is a miss.
  - **The walk.** Each row, and each opening alike, is compared with its leading whitespace stripped,
    its trailing spaces trimmed and a non-breaking space read as a space, since the tool may draw its
    glyph indented and followed by one. An opening marked `whole` holds its prompt's whole first line and must equal the
    row, so *yes* does not count *yes please*. Any other is matched as the row's start. The bridge
    reads the mark and never a tool's glyph or cut. From the bottom row up, it looks for a row that matches the newest prompt's
    `drawn`, then above that for the next one's, and so on down to the pressed one's. Each is found
    above the last, so the newest copy of a repainted conversation is the one walked, and a newer
    prompt with the same opening is passed on the way. A newer prompt that is not found is skipped,
    and the walk goes on from where it stood. A skipped newer prompt with the same opening as the
    pressed one gives the pressed one its row, so the landing is that newer prompt's; this is accepted,
    as both rows read the same. The walk looks only for the card's own openings, so a dialog's
    `❯ 1. Yes` counts only where a prompt's opening is that very row.
  - **The landing.** A found row at index *i* of the read (0 its first row) is scrolled to the
    terminal's top by copy mode's `goto-line` with *history_size − i*, the lines above the live
    screen. A row on the live screen at the read lands the same way, with `goto-line 0`: the mode
    keeps the read's view, so a turn still printing does not scroll the row away. The jump sets the bridge's *scrolled* mark, as any scroll message does, so a typed key leaves
    copy mode (TD-667).
  - **The answer** is a text frame on the socket, `{jumped: true}` or `{jumped: false}`. The page's
    socket handler takes it as it takes the `read_only` and `clients` frames, and never writes it to the
    terminal. A press waits for its frame at most `JUMP_WITHIN` and two seconds more, and a socket that
    closes first makes it a miss at the page; a press while one waits is ignored, so each frame answers
    the one press pending; a frame with no press pending is dropped. A jump queued behind a scroll
    can land after the page gave up, leaving the pane scrolled under a row that reads a miss; this is
    accepted. The bridge ignores a `jump` that is not a list of at most `RECENT_PROMPTS`
    objects, each a string `drawn` of at most 200 characters and a boolean `whole`, as it ignores a bad
    scroll count. A miss at the
    bridge runs `copy-mode -q`, so the pane is on the live screen. A miss at the page sends nothing and
    leaves the pane as it was.
  - **In order.** The jump is one of the tmux commands the bridge runs one at a time (*In order*,
    above): a key typed while it runs waits for it, bounded by `JUMP_WITHIN`. A read-only attach
    passes it as it passes a scroll message.
  **A program that asks for the mouse gets it**: one in the pane that asks for mouse tracking
  itself (htop, a mouse-enabled `less`) has its request passed out to xterm.js by tmux, mouse off
  or not, and xterm.js's reports passed back in, so inside it a plain drag and a click go to the
  program, and **Shift+drag** still selects in the browser off a Mac — xterm.js forces its own
  selection with Shift while tracking is on (on a Mac, Option, only where
  `macOptionClickForcesSelection` is set). The wheel
  never reaches it: the page's own handler still sends the scroll message. In a read-only attach
  the program gets nothing: a mouse report is a key frame, and the read-only bridge drops every
  one. Claude Code asks for none, so ordinary Focus use is a plain drag that selects. No
  per-session escape: a setting over which drag selects is the thing this removes. **Copy on
  select** is the one choice left, and it is the person's (§4.5a *Focus: copy on select*, §5
  `person.terminal.copy_on_select`).
  **A URL in the pane is a link** (TD-421; mockup `Focus.dc.html`). xterm.js's own web-links addon
  (`@xterm/addon-web-links`, the release paired with the vendored `@xterm/xterm`) reads the
  screen's text as it is drawn: a run that its regex takes as `http://` or `https://` — those two
  schemes and no other; the addon's regex, never one of ours — is **underlined on hover**, with the
  pointer, and **Ctrl+click opens it** (Cmd+click on a Mac: VS Code's terminal convention) in a **new tab**, `noopener`, as the browser's address bar would open it. A plain
  click does nothing, since a plain click is the start of a drag and a drag over a link still
  selects (§4.6 above: the mouse is the browser's); a plain tap on a touch screen does nothing
  either, and the phone's press is TD-003's narrow mode to name. What makes this safe under TD-071's
  rule — *nothing on a page is a control that parses what an agent printed* — is that it is not a
  control from the text: it does one thing, open what is already written, opens nothing without a
  press, the press is a modifier the hand must hold, and the URL it opens is the text under the
  pointer, read before the press; a session can print a URL, as it can print anything, and the
  person decides. **A cut row is joined before the addon reads it** (TD-494): a program that breaks its
  own lines at the width prints rows with no wrap mark, and the addon
  follows a URL onto the next row only when xterm marked it wrapped, so it reads the screen through a view
  where a row counts as wrapped when the row above is full to its last column and it begins with a
  URL character that starts no `scheme://` of its own; the addon's regex still decides, and a link's
  range spans its rows, so the whole underlines and one press opens the whole. Two rows that merely
  meet at the width, the second starting a URL of its own, stay two; a URL that ends on the last
  column above a row of words starting flush left reads them into it, since the screen carries nothing
  that tells that row from a cut one. The two schemes are the whole allow-list: `javascript:`, `data:` and `file:` are
  not links here, as §5's scheme rule refuses them for the editor button. It **reads, so a read-only
  Focus has it** (TD-096: the press sends nothing down the bridge; the tab is the browser's); a
  pop-out window has it as Focus has it. **No person setting**: a link that opens only on a
  modifier+click takes nothing from anyone, and copy on select is untouched — the drag that ends
  on a link copies as any drag does. A program that asks for the mouse (above) takes the click
  before the addon sees it, as it takes every click.
  **A hyperlink in the pane is a link** (TD-845). A program can print a link as a label with its target
  hidden, an OSC 8 hyperlink (`ESC ] 8 ; ; <url> ST <label> ESC ] 8 ; ; ST`): Claude Code prints an
  Artifact, a PR or a doc that way (*Report: ⧉ Team Spend by Seat*). It does so whenever it believes
  the terminal draws one, and inside tmux 3.4 or later it does (its own check reads `TERM_PROGRAM=tmux`
  and the version; otherwise it prints `label (url)`, which the URL rule above takes). tmux keeps a
  pane's hyperlinks but sends them only to a client that has the `hyperlinks` terminal feature, and its
  default `terminal-features` gives no `xterm*` client that feature. So **the pty bridge's attach asks
  for it for that one client**: `tmux -T hyperlinks attach`, the container node's `docker exec … tmux
  attach` too. `-T` is the client's own flag and sets no server, session or window option, so the attach
  still sets nothing (§9 invariant 1). It carries into copy mode, so a link scrolled back is still a
  link. On an older tmux at or above the 3.2 floor the flag changes nothing. `-T` has been there since
  tmux 3.2, and a node's tmux is held to that floor already by `new-session -e`; tmux skips a feature name it does not know and attaches as before (tmux 3.5a does so
  with a made-up name). Before 3.4, tmux has no hyperlinks to send, and Claude Code there prints the URL
  beside its label. **`ao focus` does not ask**: the person's own terminal is theirs to describe to
  tmux (`terminal-features` in their tmux config), and one that cannot draw a hyperlink would print
  its bytes. **On the page**, xterm.js parses OSC 8 itself, and its OSC link provider underlines the
  label on hover with the pointer. The provider reads one row at a time, so a label wrapped over two
  rows underlines the hovered row's part, and either part opens the same target. It passes on only an
  `http:` or `https:` target, the URL rule's allow-list. Anything else, `javascript:`, `data:` and
  `file:` among them, is no hyperlink: the label is text, read by the URL and path rules as any text
  is. The Focus terminal sets xterm's `linkHandler`, so **the press is the URL's**: `activate` hands
  the target to `AO.paneLink`, so Ctrl+click (Cmd+click on a Mac) opens it in a new tab with
  `noopener`, and a plain click or tap does nothing. xterm's fallback, a `confirm()` box on a plain
  click, never runs. **The target can be read before the press**, since the label is not the URL:
  `hover` sets the pane's `title` to the target, so the browser's own tooltip shows it when the pointer
  rests, and `leave` clears it, as VS Code's terminal shows a hyperlink's target. Where a cell is both
  a hyperlink's label and a URL or a path run, xterm's own provider comes first, so the hyperlink's
  target is the one that opens and shows, whatever the label says. TD-071's rule holds as it does for
  the URL: one act, opening the target the program attached, readable on a rest of the pointer, and
  only on a modifier press. A read-only Focus and a pop-out have it, as they have the URL
  rule. No setting.
  **A path in the pane is a link** (TD-493; mockup `Focus.dc.html`). Beside the URL, a **file the
  session names** — `src/shiftlead/cli.py:364` in an answer, `Edit(scripts/x.py)` on a tool
  line, an absolute path — is the same kind of link, opened in the person's editor: the **Session** card's
  **editor** button (§4.5a *Focus side panel, Session card: VS Code — the editor button*; §5 `person.open_in`) pointed at the file
  instead of the session's directory. **The shape** is a link provider of the page's own, registered
  beside the addon: a run with a `/` in it — relative, `./`, `~/` or absolute — with an optional
  `:line` or `:line:col`, the bracket or sentence stop at its tail not part of it; a bare word is
  never a candidate, and a run inside a URL is the URL's. **What makes it a link is the host, not
  the shape**: the shape only asks. When the pointer reaches a row with candidates, the page asks
  the `paths` RPC on the record's host once for that row — the record's id and the row's runs, at
  most eight, each bounded — and the host answers, for each, the resolved absolute path or nothing:
  a relative run resolved against the record's `dir`, `~` as the session's user's home, the real
  path taken, and a **regular file on the record's host that the session's user can read** answers
  (TD-688; Paul, 2026-10-14: *add links in our transcripts to any file that is actually available on
  the corresponding machine (e.g. ~/.bashrc would not have a link currently)*; it was *in our repo*,
  a regular file under the record's `dir` or its `repo`). The bound has four parts:
  - **The real path is judged**, so a symlink out of the checkout answers when its target is such a
    file.
  - **A directory** is the header button's, never a link.
  - **A credential file stays text whatever the stat says** (`PATHS_PRIVATE`, one constant beside
    `PATHS_RUNS_MAX`, matched on the real path). A press would put such a file in an editor tab,
    where a screen share or a pasted screenshot shows it. The page needs no reason, so the answer is
    nothing, as for a missing file. The list is a floor, not a guarantee, and it is easy to extend:
    - **Whole trees**: everything under `/proc`, `/sys` and `/dev`. A process's `environ` there is
      a readable regular file holding the secrets Doppler injected.
    - **A credential directory anywhere in the path**, by component, in any user's home: `.ssh`,
      `.gnupg`, `.aws`, `.doppler`, `.kube`, `.password-store`, and `.config/doppler`,

- **Run-log retention.** A session's log is bounded by its lifetime; retention is by age: logs
  of `exited`/`closed` sessions are deleted after `runs_keep_days` (default 30) on the agent's
  tick. Live logs are never truncated, so invariant 3 holds while the session exists. A session's
  attachments (`attachments/<session>/`) go by the same sweep and the same bound, kept while a record
  of the session is live (§4.4 *An attachment's life*, TD-419); an upload's `.part` nothing has
  written to for an hour goes on the same sweep whatever the bound (§4.4 *Attachment drop*, TD-473).
  **The Add entry form's draft folders** (`attachments/<draft>/`, §4.4 *The Add entry form's draft*,
  TD-630) by their `claimed.json`: one with none is removed an hour after its last write, whatever
  the bound and before the sweep's other rules can return; one claimed by a session lives as that
  session's own folder does; one claimed by a hand is removed `runs_keep_days` after the claim.
- **A read-only attach (TD-096).** The attach is opened read-only when the record says
  `unattended` at open: the pump drops every key frame (str and bytes) and passes resize and
  scroll — the wheel among them, since with the mouse the browser's it is a scroll message and
  never a mouse report — and
  the page is told
  so in the first frame, a text frame `{"read_only": true}` that is not pane output and resets no
  backoff (TD-029). The rule is enforced in the UI process, not by the terminal widget — a
  client setting can be undone from a devtools console, and the point is that a person cannot
  type into a worker by accident. A mode change seen in the feed re-attaches.
- **pty bridge implementation.** `ptyprocess` (or `pexpect`'s pty layer) for the child pty, so
  controlling-tty, `SIGWINCH` and teardown are handled by a maintained library; the UI adds only
  the asyncio read loop and the websocket framing. The "about 150 lines" in §10 assumes this.
  The pty's output is queued for the socket, **one send per read of the queue**: whatever the pty
  wrote while the loop was busy goes as one frame of up to a quarter megabyte, never one per pty
  read; and the queue is bounded
  — past a megabyte unsent the pty is no longer read, so tmux holds the output as it does for any
  slow client, and below a quarter of that it is read again (TD-611).
