### 4.6 Transport and terminal mechanics

- **One long-lived ssh per host, JSON lines over it.** The UI holds this link to the **home**
  host agent only; every other host agent holds its own link to the home, dialing out (§4.4a);
  the JSON-lines protocol, the backoff and the `unreachable` diagnosis below carry over to that
  link, which additionally multiplexes requests by id. The UI keeps `ssh host shiftlead-agent
  serve` open and speaks newline-delimited JSON requests/responses on its stdin/stdout (the same
  protocol the CLI speaks to the Unix socket locally). No per-call ssh handshake, so a Sessions page
  refresh across hosts is one round trip, and no argument ever reaches a remote shell — ssh's
  argv-joining is never used for data. The connection is re-opened with backoff when it drops.
  Terminal attaches to a session on another host (`ssh -tt host tmux attach -t <name>`) are
  separate ssh processes and reuse the same master via `ControlMaster auto` / `ControlPersist`
  in a config file the UI writes and passes with `-F`, so a person's own ssh config is untouched.
- **`unreachable` is diagnosed, not assumed.** The transport distinguishes *ssh failed* (host
  down or asleep) from *ssh ok, agent RPC failed* (agent crashed, stale socket). Both grey the
  cards; the banner says which ("laptop unreachable" vs "agent down on host1"), and **Retry**
  on the second case also tries `systemctl --user restart shiftlead-agent` over ssh.
- **Creation is serialised per directory** inside the host agent (one `asyncio.Lock` per
  resolved path), which makes the anchor rule (§9 invariant 2) a guarantee rather than a check
  two clicks can race past.
- **Attach behaviour with another client present.** **A session's window is pinned at one grid**
  (TD-1919): `new-session -x <cols> -y <rows>` starts the tool at the person's grid (`person.terminal.grid`,
  §5), so it is never resized while it starts (tmux 3.5a makes a detached window exactly that grid, its
  status line on or off, so the chained `status off` resizes nothing), and sets the window's `window-size manual` in the same
  invocation as `remain-on-exit`; the host agent's start sets `window-size manual` on every `ao-*` window,
  at the size it has, whatever it read before (a server whose global option is `manual` included), as it turns their status bar off (below) — never
  through the server's global options, so the person's own sessions keep following their clients. No
  client sizes the window after that: a reload, a reattach, a drag of the panel's edge, a put away, a face
  or size from Settings, the phone's keyboard, a turn or a pinch, a second tab, a VS Code `tmux attach` and
  `ao focus` leave the pane's grid as it is, so no client makes the tool repaint over lines tmux has kept. A
  node still running a wheel from before the pin makes windows that follow their clients until its first
  fit, which pins as a side effect (`resize-window` sets `manual`).
  The measurement behind it (TD-794, TD-1919; tmux 3.5a, Claude Code on Haiku streaming thirty labelled
  paragraphs): with the window following its client, a width change while it streamed repeated 5 to 13 of
  the thirty in tmux's history, a height change lost 3 to 4, and a reattach at another size did both;
  pinned, every paragraph was there once through the same churn and six reattaches, in 8 of 8 runs — one
  tool, one window size; the live test's pinned mode (`tests/test_resize_repaint_live.py`) guards it, and
  attaches a client at another size than the window while it streams. **The terminal draws at the
  pane's grid, not at its box's.** The bridge reads the window's size before it attaches and opens the
  attach's pty at that size (a reading that fails, bounded at three seconds, opens it at
  `person.terminal.grid`, else 120 × 40, and sends that grid as the frame below; the five-second reading goes on, and the first good one that differs resizes the pty and sends its frame as any change does), so tmux draws this client as the window; the page puts no `cols` or `rows` on the socket's address, and the bridge ignores any it is given; it sends the page
  `{"grid": [cols, rows]}` before the first pane byte, and again whenever its reading of the window
  (every five seconds while attached, `display-message -p`) changes, having first resized its own pty to
  it, so a fit made from another browser leaves no bridge's client at the old size — the attach's own word,
  as the `read_only` frame is: not pane output, no backoff reset. The page sizes its terminal to that grid,
  opening it at the first frame's, and never fits it to its box. **A box smaller than the grid**: the terminal's box (`.termbox`) is the
  scroll container, `overflow-x: auto` and `overflow-y: hidden`, holding the terminal at the grid's own
  pixel size. Only the grid is drawn in the terminal's colour: the gap around it is the `.xterm`'s own border, and `.termbox` itself is the page's background. A run below the top row is scrolled to its row past that border, so the box never shows a part of the row above it.   last row with any text on it (`term.buffer.active`: a row whose `translateToString(true)` is not empty, so a row of coloured blanks is empty), a run that would start above the top row starting at it and one that would leave the cursor's row above it starting at that row — the

  `/clear`, a full-screen program's prompt at its top) — set again on every cursor move, box change (the

  scrollbar: a sideways wheel or Shift+wheel (the terminal's wheel listener, which keeps the browser's own scroll off, adds the travel of an event with `shiftKey` or more sideways than vertical travel to `scrollLeft`, its travel the larger of `deltaX` and `deltaY` with its sign (a Shift event carries its travel on either axis, by browser), scaled as its `deltaMode` says (a line the renderer's cell width, a page the box's `clientWidth`), and sends no `scroll`, so Shift+wheel no longer scrolls history) or a sideways finger (the TD-986 handler sets `scrollLeft`, since
  the phone's terminal is `touch-action: none`, its drag locked to the axis on which it first travels 10 px) moves it, and while the terminal has focus the cursor's
  column is kept in view as keys are typed; the helper text box is focused with `preventScroll`, so the
  browser never moves the box itself. **A larger box** leaves the room right of and below the
  grid empty, in the page's background. Another client at another size sees what tmux draws for it: a
  smaller one a view of the window that follows the cursor, a larger one the window with tmux's fill
  around it.
  **A session has no tmux
  status bar** (TD-1410): the session's name, its state and its host are in the Focus header, and when
  a window is resized (as one was by its clients before the pin), tmux redraws the bar on a new bottom row while the browser's terminal
  keeps the old copy as content, so stale bars would fill the pane. `new-session` sets `status off` beside
  `remain-on-exit`, and the host agent's start turns it off on every `ao-*` session that still has it, never
  through the server's global options, so the person's own sessions keep their bar. A person's own
  `tmux attach` on an `ao-*` session (VS Code's) shows no bar either. The `grid` frame counts the window's rows
  with the status bar's lines, as a client's grid counts them, which are none.
- **Fit to window: the person resizes on demand** (TD-1919, §4.5a **Fit to window**). The one thing that
  changes a pinned window's grid is the person's press, for a new monitor or a new window. The page
  waits until the pane is quiet — the record `idle` with nothing of its own running (§4.2 *Working on its
  own*: the view's `own_work` empty; any other state, `limited` and `unreachable` among them, waits as a
  busy one does) and no pane byte for two seconds — then sends `{"fit": [cols, rows]}`, its box's grid computed at
  that moment (on a phone, from the box measured at the press with the keyboard and every sheet down, below), and the bridge sets the window to it (`resize-window`), reads the window again, resizes its own pty to that
  reading and answers at once with its `grid` frame, so a failed command answers with the grid the window kept (another browser's bridge learns it at its next five-second reading, a delay
  accepted); a fit equal to the pane's grid sends nothing, and a page resizes its terminal only on a `grid`
  frame that differs from its own. **The box is measured** when the fit is sent: while the page is hidden or
  the box has no size the fit is held until it is visible again (the five minutes still counting); a page
  whose proposal is not finite sends nothing. **One helper measures** (`AO.boxGrid()`): `.termbox`'s
  rendered size (`getBoundingClientRect()`, `.termbox` the `.xterm`'s own parent, no wrapper) less its
  padding and borders and the `.xterm`'s own border (the gap), whether or not its sideways scrollbar shows, over the terminal's current cell size (the
  renderer's CSS cell, which the fit addon reads too), each figure floored; the Fit's send, the equal test, the item's drawing, the title and the pinch's note
  all read it, so no figure subtracts the scrollbar and another not. The scrollbar shows only while the
  pane is wider than the box, which a fit ends, so measuring past it gives the grid the box has once fitted
  and keeps the equal test steady (until then the bottom run shown is the rows above the scrollbar).
  **On a phone**, where the box moves with the keyboard, the banners and the key bar, the helper divides
  not the live box but the box's pixels kept with the keyboard and every sheet down (below), by the
  current cell size, so a pinch or a font size changes the grid it gives with no new measurement. The
  keyboard is up while the terminal or any editable element has focus (§4.5, never a guess from the
  viewport). The box's pixels are kept on load and on every change of the box while the keyboard and every
  sheet are down (a banner, the key bar), never a box with no size and never before the phone's layout
  applies; a turn of the phone (`screen.orientation`'s `change` event, read on a coarse pointer alone, never the
  orientation query, which flips with Android's keyboard resizing the content and with a desktop window's shape) or a crossing of the narrow
  layout's query (the page's layout, `html.phonefocus`, flipping) drops them (kept pixels carry `screen.orientation.type` from their keep, and pixels of another type than the screen's are dropped, whichever of the box's change and the `change` event comes first; where `screen.orientation` is absent, as on iOS before 16.4, `window`'s `orientationchange` stands for the `change` and `window.orientation` for the type), since the other
  layout's box is not this one's, and a turn or a crossing while a fit waits cancels it with the passing
  note *not fitted — the screen changed, press again*. **Every press measures afresh** (a press on **Cancel fit** measures nothing: it ends the wait and sends nothing), since focus is not
  the keyboard (one put away by the phone's own *Done* leaves the terminal focused): the press blurs any
  focused field and closes the sheet, then keeps the box's pixels at the first animation frame, after the
  page's own relayout, at which the box's height has not changed for 100 ms with nothing editable focused, and goes on as any press does:
  the equal test, the quiet wait, the send. From the press until its hold ends the layout holds as it does
  while a field is focused, the narrow query read again once the hold ends, so a blur that leaves a landscape
  tablet's keyboard up for a moment crosses nothing, and the layout at the press is the fit's; a turn during
  the hold ends the press with the same note as a turn during a wait, a press while a hold runs is ignored, a
  page hidden during it ends the press with nothing kept and no note, and a `visualViewport` `resize` whose
  `scale` differs from the last one's is a zoom, never the keyboard's fall. The 100 ms counts from the press when nothing was focused; when
  the press blurred a field, from the first `visualViewport` `resize` after the blur, the keyboard's fall
  (on a phone the box follows that event alone; on a coarse-pointer wide page it follows the layout viewport, and the hold reads the box either way), and if none comes within the limit and nothing is focused, the
  keyboard was not up (a hardware keyboard, or one put away by *Done*) and the box is kept as it is. The
  limit is one second, counted from the press, and bounds only the wait for that first `resize`; once it
  comes, the hold has a limit of its own, one second from that `resize`; a hold counted from the press (nothing
  was focused) has its one second from the press, and a field focused when either limit passes takes the fallback below. TD-1948 measures the keyboard's fall on an iPhone and an Android phone, records the
  figures in its history and raises the limit if either is longer. A wide layout on a coarse pointer (a
  tablet past the narrow query, `(pointer: coarse)`) presses the same way, blur and hold, so its fit, which
  becomes `person.terminal.grid`, is never taken with its keyboard up; the pixels its hold keeps are this fit's
  alone (the kept pixels stay the phone's), and while the fit waits they are kept again on every change of
  the box while nothing editable is focused and no sheet is open, as a phone's are, so a split view resized or a
  panel put away during the wait is the box it sends: the equal test and the send divide them by
  the current cell size, the setting's write being the grid sent and answered, however the keyboard stands by the send, and a turn or a crossing of the narrow query
  while it waits cancels it with the same note as a phone's. If no frame qualifies within the hold's limit
  (a field focused again), it uses the pixels kept before it; with none kept (a Focus opened with the keyboard up, the phone
  just turned, or any coarse-pointer wide page, which keeps none before its hold) it keeps nothing, sends nothing and notes *put the keyboard down, then press again* (a narrow desktop window on a fine pointer, where focus stands for the keyboard and nothing turns, can keep stale pixels for the title and the equal test while the terminal stays focused, and its press waits the second for a `resize` that never comes before it measures: accepted) over
  the terminal, where the pinch's note shows. On a phone the item is drawn on every live record with a terminal (a `scheduled` record has none), whatever
  the kept pixels say (they can be stale while focus stays), and an equal press answers *already this
  size*; until pixels are kept the helper reads the live box, so the title and the pinch's note show its
  grid; with the
  keyboard up the kept pixels stand, so neither the title, the equal test nor the pinch's note reads a box
  a dozen rows short. A coarse-pointer wide page keeps no pixels outside a fit, so its item and title read the
  live box, its keyboard up included, which is accepted: only the press's hold measures what it sends.
  A press whose grid equals the pane's sends nothing and closes the sheet with the
  passing note *already this size*. **The bridge bounds a fit** by the setting's own bounds, columns 20–500 and rows
  5–200 (one constant beside `TERMINAL_KEYS`), refusing and logging any other, so no client can size a
  window to nothing. The page checks the same bounds at the press, before any wait, and again at the
  send: a box whose grid falls outside them (a phone's short box at a large pinch) sends nothing, ends any
  wait and notes *not fitted — this box is too small* (or *too large*) where *already this size* shows, so
  a page's fit never waits on a refusal. While a fit waits its control reads **Cancel fit**, and from the press on, its hold included, it takes no pending mark, *more ▾*'s menu folding on the press as any menu does; a box whose grid becomes the pane's
  meanwhile (another browser's fit, the window resized back) ends the wait quietly. A record with no agent (a shell, a
  command run) fits at once: a shell repaints no history, and its silence says nothing. While it waits the
  terminal mark reads *fitting when idle…* (*Reconnect contract*, below); a second press cancels it, as do
  a closed socket and a reload, and after five minutes the wait ends with the passing note *not fitted —
  the session stayed busy*. A `waiting` or `stalled?` record waits too: only an ended turn was measured. **It never interrupts the turn or
  stops the tool**, by measurement (the same test, a pinned 100×20 window, two runs of each way, the counts in
  `docs/history/TD-1919.md`): stopping the tool's processes across the change (`SIGSTOP`, the resize,
  `SIGCONT`) made it redraw its whole reply, every paragraph twice; clearing tmux's history and asking the
  tool for a redraw (Ctrl+L) left only the last screen, 23 to 28 of the thirty gone; interrupting the turn
  first and then waiting did no better than waiting. At idle, with or without an interrupt first, a larger grid left every paragraph once in
  6 of 8 runs and repeated one in the other two; fewer columns repeated the last 1 to 10 paragraphs in each
  of 6 runs, and fewer rows alone lost the last paragraph but one in 2 of 2. So the cost is paid once per
  fit and never per gesture, and the control's hover says that a smaller grid can repeat or drop the last
  lines of the history. **On the wide layout a fit also becomes `person.terminal.grid`**, the grid every
  later session starts at, written through `set_settings` (§4.4a *Settings, replicated*), so a new monitor
  takes one press. The setting is written only once the bridge's `grid` frame answers the fit — the first
  `grid` frame on that socket equal to the grid sent, within ten seconds of the send; with none, nothing is written and
  a passing note says *not fitted* — never on a cancelled, timed-out or refused one; a write the home refuses (offline) leaves the fit standing and the
  default as it was, with a passing note. A phone's fit (the narrow query, §4.5 *Phone layout*) and a popped-out window's (§4.5
  *Pop out*) set this session's grid alone. A read-only attach passes a fit (it types nothing), so an
  `unattended` session is fitted without a Take over. A
  fit pressed in another browser reaches this one as a `grid` frame. Nothing else sends a grid: the page's
  old `{"resize": [cols, rows]}` message is gone, and a bridge that receives one ignores it.
- **Reconnect contract.** The pty lives in the UI process. If that process or the websocket
  drops, the browser reconnects with backoff and the fresh `tmux attach` redraws the current
  screen; nothing is replayed from the run log. Three rules make that loop terminate (TD-029):
  the backoff resets on the first byte of **pane output**, never on open — a connection the
  server accepts and then ends is not a working terminal; a **dead attach is final**, so the
  server closes 4404 (the one code the client never retries) whenever the attach process exits
  non-zero or without ever painting a screen, not only when the record already says the pane is
  gone; and a pushed `closed` or `pane: false` delta ends the terminal from the page itself,
  because the push is authoritative and arrives before any reconnect could — `kill` and `close`
  announce it as they return rather than waiting for the next tick. `send-keys` is a host-agent
  RPC independent of any attached pty, so a Send never depends on a Focus being open. **The
  terminal mark** (TD-474; built by TD-480): the Focus header carries, beside the state pill, one
  mark at a time for what the terminal is doing, in this order of precedence — *reconnecting…*
  while the terminal socket is closed and a retry is pending, drawn after the same three-second
  grace as the host agent's down banner (§4.5 *Browser mechanics*), so a navigation and a
  promote's restart draw nothing; *fitting when idle…* while a **Fit to window** waits for the pane to be quiet (above); *no output for Ns*,
  counting up, when the socket is open, the record reads `working` and no pane byte has arrived
  for thirty seconds — never on an `idle` session, where silence is the normal case — cleared by
  the next byte. Each mark's hover says what it means and what to do (§4.5a). Each event — a close
  with its code and reason, a reopen, the first byte after a silence, a `grid` frame received — goes to the
  browser's console with its time, `[shiftlead] terminal …`, so the next freeze names its cause;
  the grey retry line written into the terminal stays. The
  terminal shows tmux's scrollback (`history-limit`) only; the run log is a download, never a
  terminal source.
- **The disconnect card** (TD-923). A Focus whose UI process is down is a blank pane and a retry line: the
  one reload (§4.5 *A reconnect reloads once, never in a loop*) empties the terminal until its
  attach paints; the wait is where the person wonders what the stall is costing. So while the
  terminal mark reads *reconnecting…*, a card between the Focus header and the pane says what
  the page already holds of spend: this session's, its team's and All's, today and this week,
  as the Spend page reads them (§4.4 *Spend per seat*) — **each row money and tokens**: the
  subscription's API-equivalent (`≈$`, never a bill) and a metered profile's bill (`$`) as two
  figures, never one sum, since one is what was paid and the other what it would have cost (a
  scope on one kind of profile draws one) — the one place the card departs from the Spend page,
  which folds a mixed sum to `≈$` (§4.5 screen 13); then the tokens, every kind summed (*4.1M tok*, the
  chip's short shape, the four kinds on hover — the one rule the Spend page draws by too, §4.4 *Spend per seat*; its All row, money and tokens alike, is every seat's sum, so *outside shiftlead*, which the page's whole holds, is not in it), because *we used a million tokens on this* is a
  thing people say and the bill is not —
  the account's windows under them as the top bar's chip last read them (§4.5a **usage chip**;
  the reset as its hover gives it),
  and *as of HH:MM* at its foot, the time of the reading. **Nothing is fetched while the link
  is down**: the figures are the Spend reading the page takes at its load and at each
  reconnect (`/api/spend`, one read per scope and window — its team and All, day and week, with
  `top=all` so its own row is in the reading), and the last `usage` event, both kept in `sessionStorage` under the session's id so the reloaded page draws them
  before its attach answers; a figure the page never got reads *no reading*. The card is drawn
  after the mark's grace, so a navigation and a promote's restart draw nothing; **never over the
  pane**, so a screen the terminal still holds stays readable; and the grey retry line with its
  countdown stays the terminal's, unchanged. It goes with the mark, on the first pane byte. It
  is a card, not a game: the person was mid-task, and what the stall costs is the one thing the
  page can tell them that the pane cannot. **The state is reachable on demand**:
  `scripts/focus_drop.py` opens a Focus in the smoke's browser (`scripts/smoke.py --setup`),
  holds `/term/` and `/events` closed for a given time, and writes the screenshot — so the card
  is reviewed from a picture, and a change to the reconnect path is seen before it is merged.
- **Scrollback is tmux's, reached through tmux (TD-022).** tmux repaints the client in place and
  keeps the history itself, so xterm.js runs with no local buffer. Shift+PageUp / Shift+PageDown
  scroll it by a bridge message the UI turns into `copy-mode -e -u` / `page-down` against the
  session, a page of the pane's height, or, while the box is shorter than the grid, a page of the box's rows less one, at least one, which moves the view within the grid first and sends only the rest as a `{scroll, lines}` (*Attach behaviour with another client present*) (there is no escape sequence for copy mode). **The mouse is the browser's.** The attach sets no mouse option (a session an earlier attach set `mouse on` on
  keeps it until it is started again, since the option is the session's), tmux asks for no tracking, and xterm.js keeps
  the mouse: **a plain drag selects in the browser**, Shift+drag does the same (with no tracking,
  Shift is nothing to xterm.js, so the habit costs nothing and needs no setting), and
  **Shift+click grows or shrinks the selection** — xterm.js's own selection service does it
  (`shiftKey → _handleIncrementalClick`, read in the vendored source), as VS Code's terminal
  does. **A selection is one screen, and a copy is its rows (TD-1263).** xterm.js holds only the screen (no
  local buffer, above), so a drag held past the top or bottom row has nothing to scroll and stops at the
  edge, and a wheel turn during it repaints other text under the rows the selection holds. What Copy,
  Ctrl+C and copy on select write is xterm.js's `getSelection()`: the selected rows, joined where xterm.js
  marked a row wrapped and a newline at every other row's end. xterm.js marks it where tmux let the
  terminal wrap a line the program wrote past the width, on the live screen; on a view scrolled into the
  history tmux places each row with a cursor move, and the mark is lost (checked on tmux 3.5a). A tool
  that wraps its own lines (Claude Code does: *A jump to a prompt*, below) leaves no mark anywhere, so
  its wrapped line copies as rows, each continuation with its indent. **Neither is mended in the pane**
  (Paul, 2026-10-30: *we do not want to break/frustrate users with "fixes" that do not behave
  consistently*). A selection kept in history coordinates and read back by `capture-pane -J` would race
  tmux's repaints and move every copy onto an asynchronous road; tmux's own copy mode under `mouse on`
  would take the mouse back from the browser (TD-174); and a join of a tool's own wrap is a guess from
  the rows' look, which joins two real lines whenever one ends near the width and the next begins with
  a long word. TD-494's cut rule (`AO.cutRows`: the row above full to its last column) is exact for a
  word cut mid-word, but joins a real line exactly the width wide to the next, and Claude Code's word
  wrap stops short of the width, so it mends neither the common case nor every time. **Text longer than a screen, or wrapped, is copied whole from the Transcript** (§4.5
  screen 9: the tool's own file, drawn as the browser's own text), and the pane says so at the two
  moments the limit bites, as a note added to the toast the release or the copy already draws (*copied*,
  *clipboard blocked …*), one note a toast, the edge's first:
  - **A drag that went past the edge.** A mouse's selection drag (a finger's selects nothing, below) begun on the terminal whose pointer, button held,
    went a row's height or more above or below the rows shown (the box's edge where the box is shorter than the grid, else the screen's) adds, on its
    release, when the selection then touches that row (`term.getSelectionPosition()`, read at
    the release), *— the selection stops at the screen's edge; Transcript has the whole conversation*,
    to *copied* or *clipboard blocked …* alike, since the limit holds either way. With copy on select
    off, or drawn disabled for want of a secure context, the release copies nothing.
    Then the note is the toast alone, without its dash, drawn as a hint rather than a copy (not green).
    The drag's mark is cleared by each press on the terminal and read and cleared by the next `mouseup`
    on the page, whether or not the selection changed, and draws its note only on a release whose drag
    moved the selection; a press with Shift (a Shift+click, or a Shift+drag) clears it and sets none. The mark holds for the drag once

  terminal unscroll to the prompt input when a user starts typing in it … typing into the composer
  should not do this, just in the terminal portion*). In copy mode tmux reads keys as copy-mode
  commands, so a key typed into a scrolled-back pane is otherwise swallowed. So **the bridge leaves
  copy mode before a typed key**, as a local terminal jumps to the prompt on input:
  - **What counts as typing**: a key frame from xterm.js that does not start with ESC and holds a
    printable character (a key, a fast burst, IME text, a paste with bracketed paste off); Enter,
    Tab or Backspace alone; or a bracketed paste (the one ESC-led frame that counts, from its
    `ESC [200~` opener). Everything else passes as it does today and stays copy mode's: every other
    frame that starts with ESC — arrows, function keys, and the replies xterm.js sends to
    the program's own queries on the same channel (a device report, a cursor position, a focus
    event), which must never move a person out of the history they are reading — and Ctrl+C and
    Escape, which are copy mode's *cancel*, so a person leaving copy mode with them never interrupts
    the program, and any other control byte. Neither the wheel nor Shift+PageUp / PageDown is a key frame.
  - **Who knows the pane is scrolled: the bridge**, from its own scroll messages. Any scroll
    message sets its *scrolled* mark. A counted key frame while the mark stands first runs
    **`copy-mode -q`** against the session and clears the mark, then writes the key. When the pane
    is no longer in a mode (`-e` left it at the bottom), the command does nothing. A copy mode some
    other client entered is not seen: the mark is this attach's, and reading `#{pane_in_mode}` on
    every key would cost a tmux call per keystroke.
  - **In order**: the bridge runs the tmux commands it spawns one at a time, each awaited to its
    end, in the order its frames came. A key waits for the leave before it, and a leave never
    overtakes the scroll before it. A leave that fails or passes two seconds is logged, and the
    key is written anyway.

    mode (`less`, `vi` in the pane) is not tmux's copy mode, and is untouched.

    another matter. The host agent's paste reaches a pane in copy mode, but its Enter is the
    mode's, so the prompt would stick (checked on tmux 3.5a). Every paste-and-Enter the host agent
    makes (§4.3 *Prompt injection*) therefore leaves copy mode first, and a press of **Send** returns
    the pane to the live screen, as the prompt lands.
  **A jump to a prompt** (TD-975; the Focus Prompts card, §4.5). A press on a row sends the bridge
  `{jump: [{drawn, whole}, …]}`: the `drawn` openings and their `whole` marks (§4.2 `prompts`) of the card's prompts from the newest down
  to the pressed one, those without one left out. A pressed prompt without one is a miss at the page,
  and nothing is sent. tmux's own search is not enough. `search-backward-text` finds the nearest match
  from the cursor, so a short prompt (*yes*) lands on the newest *yes*, in the history or in the tool's
  output. A resize repaint draws every prompt again (TD-794). So **the bridge walks the history
  itself**:
  - **One read, the view held.** One tmux command through the scroll's prefix leaves any copy mode,
    enters it again and reads the pane: `copy-mode -q ; copy-mode -e ; display -p '#{history_size}' ;
    capture-pane -p -S - -E -`, each command with the session's target (`-t =<id>:`) as `scroll_argv`'s
    are. The `-q` comes first because `copy-mode -e` on a pane already in mode keeps that mode's older
    view. Its first output line is `history_size`; the rest are the rows, and row *i* is the *i*-th line
    after that one. It is plain text, with no escapes and no joining: the tool wraps its
    own lines, so a prompt's first row is a row of its own. Copy mode's view holds still as output
    arrives (checked on tmux 3.5a), so the read is the view the landing scrolls. `history-limit`
    (§4.1) bounds the read, and a read that runs past `JUMP_WITHIN` (five seconds) is a miss.
  - **The walk.** Each row, and each opening alike, is compared with its leading whitespace stripped,
    its trailing spaces trimmed and a non-breaking space read as a space, since the tool may draw its
    glyph indented and followed by one. An opening marked `whole` holds its prompt's whole first line and must equal the
    row, so *yes* does not count *yes please*. Any other is matched as the row's start. The bridge
    reads the mark and never a tool's glyph or cut. From the bottom row up, it looks for a row that matches the newest prompt's
    `drawn`, then above that for the next one's, and so on down to the pressed one's. Each is found
    above the last, so the newest copy of a repainted conversation is the one walked, and a newer
    prompt with the same opening is passed on the way. A newer prompt that is not found is skipped,
    and the walk goes on from where it stood. A skipped newer prompt with the same opening as the
    pressed one gives the pressed one its row, so the landing is that newer prompt's; this is accepted,
    as both rows read the same. The walk looks only for the card's own openings, so a dialog's
    `❯ 1. Yes` counts only where a prompt's opening is that very row.
  - **The landing.** A found row at index *i* of the read (0 its first row) is scrolled to the
    terminal's top by copy mode's `goto-line` with *history_size − i*, the lines above the live
    screen. A row on the live screen at the read lands the same way, with `goto-line 0`: the mode
    keeps the read's view, so a turn still printing does not scroll the row away. The jump sets the bridge's *scrolled* mark, as any scroll message does, so a typed key leaves
    copy mode (TD-667). The answer carries the landed row's row on the pane and the cursor's, `{jumped: true, row: r, cursor: c}`: *r* 0 for a row found in history, which `goto-line` puts on the pane's top, and *i − history_size* for a row on the live screen, which stays where it is; *c* the pane's `cursor_y`, read with the jump's read, where copy mode's cursor sits once the jump re-enters it. At the page, it sets the vertical view to start at that row (no lower than the grid's last box-height run allows) and starts the keep anew with *c* as its settled row (*A box smaller than the grid*), so in a box shorter than the grid the landed row is the top row shown, or as near it as the grid's last rows allow; a downward move from a view below the run it would show moves nothing and sends its lines, an upward one moves the view as usual; `{jumped: false}` ends any keep.
  - **The answer** is a text frame on the socket, `{jumped: true, row: r, cursor: c}` or `{jumped: false}`. The page's
    socket handler takes it as it takes the `read_only` and `grid` frames, and never writes it to the
    terminal. A press waits for its frame at most `JUMP_WITHIN` and two seconds more, and a socket that
    closes first makes it a miss at the page; a press while one waits is ignored, so each frame answers
    the one press pending; a frame with no press pending is dropped, and sets no view and ends no keep (the jumper's `frame()` says whether a press was pending). A jump queued behind a scroll
    can land after the page gave up, leaving the pane scrolled under a row that reads a miss; this is
    accepted. The bridge ignores a `jump` that is not a list of at most `RECENT_PROMPTS`
    objects, each a string `drawn` of at most 200 characters and a boolean `whole`, as it ignores a bad
    scroll count. A miss at the
    bridge runs `copy-mode -q`, so the pane is on the live screen. A miss at the page sends nothing and
    leaves the pane as it was.
  - **In order.** The jump is one of the tmux commands the bridge runs one at a time (*In order*,
    above): a key typed while it runs waits for it, bounded by `JUMP_WITHIN`. A read-only attach
    passes it as it passes a scroll message.

- **A read-only attach (TD-096).** The attach is opened read-only when the record says
  `unattended` at open: the pump drops every key frame (str and bytes) and passes a `fit` and
  scroll — the wheel among them, since with the mouse the browser's it is a scroll message and
  never a mouse report — and
  the page is told
  so in the first frame, a text frame `{"read_only": true}` that is not pane output and resets no
  backoff (TD-029). The rule is enforced in the UI process, not by the terminal widget — a
  client setting can be undone from a devtools console, and the point is that a person cannot
  type into a worker by accident. A mode change seen in the feed re-attaches.
- **pty bridge implementation.** `ptyprocess` (or `pexpect`'s pty layer) for the child pty, so
  controlling-tty, `SIGWINCH` and teardown are handled by a maintained library; the UI adds only
  the asyncio read loop and the websocket framing. The "about 150 lines" in §10 assumes this.
  The pty's output is queued for the socket, **one send per read of the queue**: whatever the pty
  wrote while the loop was busy goes as one frame of up to a quarter megabyte, never one per pty
  read; and the queue is bounded
  — past a megabyte unsent the pty is no longer read, so tmux holds the output as it does for any
  slow client, and below a quarter of that it is read again (TD-611).
