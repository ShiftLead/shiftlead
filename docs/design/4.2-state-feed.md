### 4.2 State feed: hooks first, scraping as a labelled fallback

The states the person cares about are emitted by the tools that have hooks. An adapter installs a
hook script that writes `~/.shiftlead/sessions/<session-id>.json`. Hooks reach a session **per
launch, as a settings layer** (Claude Code: `claude --settings ~/.shiftlead/claude-hooks/<profile>.json`,
generated at launch), never by editing the person's own `settings.json` and never per repo:
sessions run in plain directories too, hand-started sessions stay untouched, and a repo's own hooks
(agent-cadence's SessionStart guards) keep running alongside. **The layer also carries agent-cadence's
one SessionStart line** — every adapter's launch does, §4.3 *A repo's start hooks are every adapter's to run* — (`scripts/cadence_hooks.sh --session-start`, guarded by `[ -x ]`; cadence
§3), byte-identical to agent-cadence's seed (a parity pair; `CADENCE_HOOK_LINE`, its test reading agent-cadence's
`files/.claude/settings.json` at `origin/HEAD` of the agent-cadence checkout the tests already use, `$AGENT_CADENCE_SOURCE` or `~/agent-cadence`, TD-1022). The line reads the **main checkout** — the
first entry of `git worktree list --porcelain`, computed live, so it holds in a container as on the host — and has two modes
(dev-cadence TD-129, its plan 2026-10-25 *Decisions* 4–5). **Pinned**: where that checkout's `docs/cadence.toml` has a
table header written exactly `[agent-cadence]` (a grep, the form agent-cadence's shims detect — `sessionorc.cadence.hook_pinned`
reads it the same way: the hooks' view, which is not the readers' `cadence.pinned` — a parsed pin with no lock left,
§5 — in a repo pinned while it still holds its lock), it runs `agent-cadence hook session-start` in the session directory, the launcher on `PATH`
resolving the pin; a launcher that cannot run the pin (exit 2) prints one line saying the cadence hooks did not
run, and none on `PATH` one line saying so with the launcher's install line, into the session's context — never a
silent nothing. **Copied** (no pin):
it runs the main checkout's runner, `scripts/cadence_hooks.sh`; agent-cadence's runner finds its children beside
itself, and a consumer's copy is what its last sync carried. Either way it falls back to the directory's own copy outside a git repo: a worktree on an older branch runs the current hook set against itself, where
`$CLAUDE_PROJECT_DIR` alone ran that branch's copy. In a container node the launcher is found as `ao` is: the venv carries it vendored
(`sessionorc/agent_cadence.py`, TD-1014) with a console script `agent-cadence` over it in its `bin`, and the generated Dockerfile links `/usr/local/bin/agent-cadence` to it
beside `/usr/local/bin/ao` (§4.4a, TD-998's rule; the venv's `bin` stays off `PATH`); until that link is built a
pinned repo's session there prints the no-launcher line, whose install line is the person's machine's and wrong for
a node — accepted for that window, since no served repo is pinned before TD-1014 is live and a node built
before the link gets it with `ao host rebuild <name>`. On the home the session's `PATH` is the person's, where they
installed the launcher once per machine (agent-cadence's install line). **A repo's own line is not always enough**: the layer leaves its line
out where the session directory's `.claude/settings.json` already runs agent-cadence's hooks (each would run twice),
and in a pinned repo only a line that reads the pin counts as running them — a repo still carrying a pre-pin line
(the person has not yet re-seeded it: agent-cadence keeps `.claude/settings.json` as a seed and never rewrites it, so the
Repo page's *predates the pin* warning, §5 *The seams*, is the one signal) gets the layer's
line beside its own, whose copied runner is gone and runs nothing (in a repo pinned by hand with its copy still there, the old runner runs
as well, a double run accepted for that window, which the same warning names). The pinned test is the marker `agent-cadence hook session-start`: a later
seed calling the launcher by another word would read as not running the hooks, and both lines would run, until
ShiftLead's copy follows — the Repo page's *not one this build knows* is that signal, and accepted as such. One known limit, recorded and not fixed since the bytes are the pair: a consumer that is itself a git submodule gets its parent's `.git/modules` gitdir as the first entry, so the set silently does not run there. An unattended launch's layer also refuses the tool's own peer
messages (`crossSessionInbound: refuse`, §4.10 *The tool's own peer channel*, TD-064) and turns off the tool's
suggested next prompt (`promptSuggestionEnabled: false`, TD-201): nobody reads one at an unattended pane, generating
it spends usage after every turn, and it is the suspect for the event that woke an idle session after its `Stop`. It uses the cadence line when
the session directory's own `.claude/settings.json` — the worktree's copy, the file the tool loads
— does not already run those hooks (either shape of the line counts as wired, so nothing runs twice); a directory
that wires nothing gets the current set, and the line is a no-op outside an agent-cadence consumer. A directory that wires them
itself gets the plain layer, or each hook would run twice; an older per-hook block counts as wiring
them, so that worktree runs only the hooks its block names until its branch carries the runner
line. Rules and tools stay in the repo, where a hand-started session, a human or a clone elsewhere
need them without shiftlead; only the wiring for shiftlead's own sessions lives here.

The hook script (`shiftlead-hook`) knows its session from `SHIFTLEAD_SESSION` and its agent from
`SHIFTLEAD_HOME`; the host agent sets both on the tmux session at creation, explicitly, because the
tmux server may predate the host agent and carry another environment
([ADR](../decisions/2026-09-06-adopt-dev-cadence.md)). Beside them it sets `AGENT_NAME`, the name the Sessions page shows
(the automatic one for a blank name, with any shown suffix), for every adapter's session: agent-cadence's
`prepare-commit-msg` hook writes it into a commit as a co-author (TD-185). **And the model** (TD-638;
Paul, 2026-10-13: *as we start using more models, recording which did what is a good idea*): it sets
**`AGENT_MODEL`**, the profile's declared model as the profile names it, with its adapter in front
(`claude-code/opus` — an alias, since the full id is known only once the tool reports it; absent
where the profile names none), and **`AGENT_MODEL_FILE`**, a file in the session's own git directory
(`git rev-parse --absolute-git-dir` in its directory, `/shiftlead-agent-model`; one per worktree as
one session is, §9 invariant 2), which the host agent writes with `<adapter>/<model in full>` whenever
the record's `model` in use is set or changes — both places that set it, the hook's SessionStart and
`PostModelSwitch` and the tick's transcript read (§4.2a) — so a commit made after a switch names the
model then in use, and the hook reads a file, never `ao` (§8). The hook writes **one trailer,
`Agent-Model: <adapter>/<model>`** (`Agent-Model: claude-code/claude-opus-5-5`), the file's line
first, else `AGENT_MODEL` (the alias, before the tool has reported one), else nothing, **replacing**
one already there (an amend after a switch names the new model); not a second `Co-Authored-By`, since a model is no git identity and the
forge would draw it as a person. A subagent's model is not named: the commit is the session's. A
review's model is the `cadence-review:` line's, already (cadence §4.9). Built by TD-644 and TD-645. An event it cannot deliver because nothing
answers on the socket is appended to `events/<session>.jsonl`, stamped with when it happened, and
the tick applies the file on its next pass — **except a queued state older than one that reached
the record live meanwhile**, which is skipped (its session id, model and subagent count still
apply), because a call that timed out while the next one got through would otherwise overwrite a
fresh state with a stale one (TD-169); **an error in the reply is the host agent answering** — a refusal (§4.8a) or a bug —
never an outage, so it goes to the hook's stderr and is never queued (TD-115). shiftlead chooses Claude Code's session uuid
at launch (`--session-id`), so `adapter_id` is known from birth; a resume passes `--resume <id>`.
With it the record carries **`transcript`**, the path of the file the tool writes on the record's host
(as the adapter's hook reports it: Claude Code's `transcript_path`, in every hook payload), set when
`adapter_id` is and pushed with it, so a page can link the file (§4.5a *Focus header* **‹› VS Code**,
TD-578) without a read; a `/clear`'s new id brings its new file; absent where the hook reports none.
**First-run quirk**: no hook reports the "trust this folder?" dialog, so the adapter marks the
directory trusted in the tool's `.claude.json` before launch. Nor does any hook report the tool's own first-run
screens on a config it has never used — the text-style picker, then *Select login method* — so a
screen rule reads each as `needs-you`, a question answered in the terminal (TD-296 #6).

The hook payload → state mapping:

```json
{"session_id": "...", "name": "tdgrind-1", "kind": "interactive", "tool": "claude-code",
 "tmux": "ao-samscrape-tdgrind-1",
 "cwd": "/home/kmaster/samscrape/.claude/worktrees/tdgrind-1",
 "state": "needs-you", "since": "2026-09-04T15:02:11Z",
 "pending": {"kind": "permission", "text": "Bash: git push origin td-301"},
 "confidence": "hook"}
```

A tool event names itself to the host agent (`event`: `PreToolUse:Bash`), and the host agent logs the
one that turns a hook-confirmed `idle` session `working`, since an event that is not a turn's
start can do that and leave the session reading `stalled?` unrung (TD-201). The line is how the
next one is named; a turn's own `UserPromptSubmit` is never logged. **The record's `files`** — the Focus
Session card's recent files (§4.5 item 4) — **are git's, not the hook's** (TD-538; until then the
`PostToolUse` of an edit carried `file`, which missed every change a shell, a script, a `git mv` or a
rebase made, and showed nothing for a tool without that hook; Paul's form, 2026-10-10: *a simple git diff
--name-only from the base would give us the full list and we would not have to track anything separately*).
They are **computed on each read and never kept**: read with the status read
(`GIT_EVERY`, per live session, on the record's host): the paths the session's work has changed
against its base — every path the porcelain holds, changed or untracked, and every path in the commits
from `merge-base HEAD origin/<default>` (the cadence's default-branch rule; with no origin, nothing but
the tree; a session on `main` itself lists its tree and its unpushed commits by the same rule) to `HEAD` — each `{path, at, sha}`: `at` the file's modification time for a path the porcelain
holds, else the committer time of the newest of those commits that touched it, which is `sha`, absent
while the path is dirty; newest first, a path once, the newest twenty kept. One `git log --name-only`
over the branch's commits beside the status, taken again only when the status's `oid` or its porcelain
changed, so a quiet session costs one status as before; the list is `git diff --name-only <base>` and the
untracked paths, the times and shas from that one log. **Nothing is remembered**: after a squash merge the
base has caught up with `HEAD` and the list is the tree's alone, empty when it is clean — the merged files
are the PR's, on main's log, where a person reads them — and a restart has nothing to start empty, since
the next read computes the list again. The base follows a rebase, since `merge-base` moves with it, where
the worktree's creation commit would list every file other PRs changed in between.
A hook carries no `file` and no adapter reports one: a change is a change whatever made it, and the
`shell` adapter shows the same list, which is the contract's neutrality (§4.3).

**The Git card's pick** (§4.5a *Focus side panel, Git card: the pick*; TD-856; Paul, 2026-10-17: *add a
picker to choose to show those files that have been edited in previous commits (e.g. HEAD~1, HEAD~2, plus
one to show all for the session) and also add arrows for navigating them up or down*) reads beyond the
record, on a pick and never on the tick: the **`git_files {id, pick}`** read, served on the record's host
from the record's `dir` (a node's record through `read`, `NODE_READS`' sixth, §4.4a), ungated (§9
invariant 11), running git and stat and nothing else. Its answer: **`commits`**, the newest ten commits
on `HEAD`'s first-parent line (`git log --first-parent -n 10`), each `{ref, sha, subject, at, author}` —
`ref` git's own name, `HEAD`, `HEAD~1` … `HEAD~9`, so the newest commit is `HEAD` and a pick never
renames git; whether or not the branch's own, since after a merge or on `main` the person still asks
*what did the last commit touch*. **`files`**, by `pick`: `tree` — the porcelain's lines as `GitInfo.files`
holds them, at most twenty (the page draws the pushed record's and never asks for this one); a **sha** of
`commits` — the paths that one commit changed against its first parent (`git diff --name-status -M` from
`<sha>^1`, the empty tree for a root commit), each `{code, path}`, `code` git's letter (`A`, `M`, `D`,
`T`, `R` with the new path); `session` — the record's `files` read (`changed_files`, above) with a
limit of a hundred in place of twenty and each path's code beside it (the porcelain's own for one it holds,
as *Working tree* draws it — `M`, `??` —, else its letter in `git diff --name-status <base>`), newest first, with **`more`**, the count past the
hundred. Each path in `files` is repo-relative, and one not in the tree now carries **`gone: true`**
(a stat, on the host). A sha no longer among the ten is refused in words (*not among the last ten
commits*), and so is a `pick` that is none of the three. Nothing is kept: each pick reads git again.

**The record's `links`** — the Session card's recent links (§4.5 item 4; TD-543) — are the `http` and
`https` URLs the session's transcript holds in the assistant's text and in tool results, read by the
adapter's `links` read (§4.3) on the record's host, **incrementally from a byte cursor** as `spend` reads
(never the whole file each pass; a cursor past the file's end means the tool rewrote it, and the read
starts at 0 again), on the tick once per `LINKS_EVERY` for every live record with a tool session id,
attended too, in a thread. Each is `{url, at}`, `at` the entry's own time; a URL once, its newest time,
newest first, the newest twenty kept; a URL whose host is `localhost` or a loopback address is left
out, as is one in a person's prompt — the list is what the session printed, not what it was told. A
record without a tool session id (a `shell`, a command run) holds none, and an adapter without the read
reports none: the card draws nothing. The pane's own link detection is never the source: the addon reads
the row under the pointer, and a scan of every painted row would sit on the keystroke path (TD-422, TD-501).

**The record's `prompts`** are the Focus Prompts card's rows (§4.5 *The Prompts card*; TD-975). They are the
prompts the transcript holds at the conversation's top level, read by the adapter's `prompts` read (§4.3) on
the record's host from a byte cursor of their own, in the same pass as `links` and on the same terms: once per
`LINKS_EVERY`, attended records too, in a thread, the cursor started again at 0 past the file's end. A record
is also read on the next tick after its hook reports a turn started by a prompt (the neutral event's
`prompt`) or the main thread's turn end (a main-thread `idle`, never a subagent's). The core reads those
neutral keys and never a hook's own name. So a prompt the person just sent is on the card within seconds, and
its reply by the turn's end at the latest. Each entry is `{at, text, drawn, whole, reply, from}`:
- `at` is the entry's own time, and `text` the prompt's opening, its first 300 characters.
- `drawn` is the opening of the pane row the tool draws first for the prompt, as the adapter knows its tool
  draws one, its form set by the adapter's captured pane (§4.3) and never assumed, or none where the
  adapter knows of none. `whole` says `drawn` holds the prompt's whole first line, uncut, so a row must
  equal it rather than begin with it. The adapter sets it, since only it knows its glyph and its cut. The
  pair is what the jump looks for (§4.6 *A jump to a
  prompt*).
- `reply` is the first non-empty line of the first text the session wrote after the prompt and before the
  next one, capped at 200 characters. A prompt that ended a read gets its reply from a later read: the read reports
  the first text past its cursor before any prompt, and that fills the newest entry's `reply` while it has
  none.
- `from` says who typed the prompt. It is set once, as the entry is first read, from the record's `sends`
  (§4.10), and never matched later, since `sends` keeps only `SENDS_KEEP`. The read runs on the node
  that holds the pane and reads that node's own `sends`, which the home merges by id (§4.4a). Each `sends` entry is matched to
  one prompt at most:
  - **The brief.** A prompt whose text begins with the brief's fixed lead line (`BRIEF_LINE`, §4.1, typed
    as keys before the paste in the same prompt) is *the brief*, `from: brief`, entry or no entry. The line is the
    home's and no person types it, and the `system` entry *(the brief)* is written only once the
    composer has taken the brief, which can be after the read the prompt hook makes due. Such a prompt
    consumes the *(the brief)* entry when there is one. A *(the brief)* entry no such prompt consumed
    names the earliest prompt within a minute either side of its time, also `from: brief`, for a brief
    sent without the line.
  - **Any other send.** The oldest entry not yet matched whose text's first line is the prompt's, both
    cut to `text`'s 300 characters (a long `ao send` is cut in `text`), made
    before the prompt, gives its `from`, whatever its verdict. The entry is written at the gate, before
    the paste (`_record_send`), on the node that holds the pane and so on the transcript's clock; it
    always precedes its prompt, and a stuck paste can still land later. The first
    lines are compared with their whitespace stripped. Oldest first, because a busy session's queue
    lands its sends in the order they came. There is no other time bound: a send to a busy session
    waits in the tool's queue until the turn ends, and a policy prompt retried on each tick lands late.
    A `keys` entry is matched by the same rule and harmlessly: its text is key names (`1 Enter`), which
    no prompt's first line is.
    So `from` is the person (the composer's Send, a chip), a session's id (its `ao send`, in the stored
    form §4.4a gives `sends`, which the UI host names as the Inbox does, adding `from_name` from the known records), `brief` (the card's *the brief*), or `system` (the
    card's *the policy*: the
    policy's fixed lines: a pause, a resume, a wrap-up, an idle nudge, a held PR's line, and the rest
    it types).
  - **No entry.** A prompt no entry matches was typed into the terminal, where keys carry no envelope,
    and is the person's.

**An entry already held** is matched by `at` and `text`. It keeps its `from`, and takes the read's
`reply` while it has none. A reread from 0 (a host agent's restart, since the cursor is held in memory, or
a cursor past the file's end) therefore changes nothing it already holds, and the leading reply applies
only to a read from a cursor past 0. **The view**: `prompts` rides
every view of the record, as `links` does, the stream's deltas included, since Focus redraws its side
cards from each delta. The view carries each entry trimmed, its `text` to 120 characters and its `reply`
to 100, enough for the row and its hover; the record keeps the full values, which the merge reads. A
full list then adds about 7 KB to a record's view, and the list pages do not draw it.

The home's doorbell (§4.10: its own *you have n unread* line) is typed with no `sends` entry, so it would
otherwise read as the person's. The core leaves out a prompt whose first line has the doorbell's form, and
the adapter never does: it says nothing the Inbox card does not. The record keeps the newest twenty (`RECENT_PROMPTS`). A new tool session id, from a `/clear` or a
resume onto another id, starts the list and the cursor again from the new file's start, as the Transcript
page reads the new file. A record without a tool session id holds none, and an adapter without the read
reports none: the card is not drawn. The pane is never the source, as for `links`: the walk that lands a
jump reads it only on a press (§4.6). On a node's record the field is the node's, written by its tick, as
`links` is (§4.4a).

`unreachable` shows at the host level first: the host chip in the top bar goes hollow and one
banner row in the Sessions page says "laptop unreachable since 14:02 · 2 sessions". A `volatile` host asleep
sorts with `idle` (grey); a non-volatile host that stops answering sorts right after `stalled?`
(red). No new colour.

**Permissions are answered through the hook, not through keystrokes.** Claude Code's
`PermissionRequest` hook may return the decision itself: the adapter's hook script asks the host
agent and blocks, and the UI's **Allow** / **Deny** (card, phone) answer the host agent. For the
main thread the terminal dialog is **not** held back — it is drawn as the hook starts waiting, with a
`permission_prompt` notification — but the hook's answer still resolves it while the hook blocks,
so both channels work at once and the host agent keeps the buttons up (it ignores that
notification while its waiter is live).

**A subagent's dialog is held back.** While the hook blocks, the pane draws nothing for it. The
dialog (*Bash command · from the general-purpose agent*) appears only once the hook returns without a
decision: at its timeout, or when its waiter ends (captured on Claude Code 2.1.307, TD-947). So for a
subagent's prompt, **Allow** / **Deny** are the only channel until the deadline, and the pending says
so.
- **The adapter's fields.** The adapter marks the prompt, and every hook event from inside a
  subagent, with the neutral field `subagent`: the subagent's own id (Claude Code's `agent_id`). The
  prompt also carries `subagent_name`, the name it is shown by (Claude Code's `agent_type`,
  *general-purpose*). The core reads neither field's source. The pending keeps both, with
  `pane_held: true`.
- **The words.** The card, the Inbox row and Focus draw *from the <subagent_name> subagent · the pane
  shows nothing until <deadline>* beside the buttons, where a main-thread prompt draws only its time
  left. After the fall-through, the line is *from the <subagent_name> subagent* beside **Focus**. A send to
  the record is refused with *a subagent's permission is pending: press Allow / Deny
  (the pane shows nothing until <deadline>)*, not with *answer it in the terminal*.
- **No reason line.** The card carries none from the tool: the payload has none, and a reason such as
  auto mode's classifier's is drawn only in the dialog.
- **No foreground case.** Every subagent of that version runs in the background (the capture asked for a
  foreground one, `foreground/`, and got a background one whose request landed mid-turn): an `Agent` call
  returns at once, and its caller may end its turn while it runs.
- **The wait** is the profile's `permission_wait`, as for any prompt. A shorter one would move the
  answer to a pane that nobody watches on an unattended member.
- **The state.** The record reads `needs-you` while a subagent waits, whether or not its main thread is
  idle. The record has one pending and one place to answer it, the session's work waits on that
  subagent, and mail to it waits as mail to any `needs-you` record does (§4.10). This is the default
  of steer m-eb7735f10367, which the techlead answered (m-1495cc38d7e4).

**A waiter is keyed by its call.** Claude Code's `PermissionRequest` names no call on either road. The
asking tool's own `PreToolUse` does, and it lands just before, with the call's `tool_use_id` and the same
tool and input (every capture). So:
- The adapter gives both events a `call_sig`: a digest of the tool name and its input. It marks every tool
  event with the neutral `call`: `start` on a call's first event (Claude Code's `PreToolUse`), `end` on its last
  (`PostToolUse`), so the core tells the two apart without reading the tool's event names.
- The core keeps each thread's open `PreToolUse` calls, the main thread being its own: the last eight per
  session and `subagent`, for at most sixteen threads per session (the oldest dropped). A thread's list is
  dropped at its `SubagentStop`, at a `subagents_reset` and at the session's end; the tool's own id that never
  started (every subagent capture has one) is dropped with the oldest. A call leaves the list when a permission takes it or when its own `PostToolUse`
  lands, since a permission comes between a call's two events. A queued event, replayed after an outage,
  touches no list: the lists live in memory, and no waiter outlived the outage.
- A subagent's tool events carry their `tool_use_id` (and a `PreToolUse` its `call_sig`) beside `subagent`,
  with no state.
- A permission is keyed by its own `tool_use_id` where the event carries one (Claude Code's carries none;
  a test stub's may). Else it takes the oldest unmatched call of its thread with the same `call_sig`, is
  keyed by that call's `tool_use_id`, and consumes it, so two parallel calls with one signature are matched in
  order.
- One that matches nothing is keyed `<session>:<time>`, as before, and any event from the same thread
  ends it.
- A main-thread waiter keyed by its call is also ended by any main-thread `call: start` event or question:
  a call's `PreToolUse` is its first event and the asked call's own already came, so it is another call
  starting. Its dialog is drawn, so a pane answer is always possible, and a pane **Deny** (or an allowed call
  that fails) gives the asked call no `PostToolUse`: the turn's next call is the first sign. A parallel call's
  `PostToolUse` still ends nothing (TD-629's rule, live for the first time now that the permission is matched
  to its call; until this design every main-thread waiter was keyed by its time and ended by any event).
  The one wrong end is a parallel batch's sibling whose `PreToolUse` lands after the request; no capture
  shows it, and the notice below catches it. A subagent's waiter has no such end: its dialog is not drawn.

An answer in the terminal ends the waiter: the asking thread's next hook event shows it moved past the
dialog: the asked call's own tool event, or one that names no call (a `Stop`, a prompt, a subagent's
`SubagentStop`), or on the main thread any `call: start` event or question. A `SubagentStart` ends nothing. A
`notice`-marked event ends nothing either, though it carries a `needs-you` question: it never reaches the
waiters, and the notice rule below handles it first (else the `permission_prompt` notice, six seconds after the
dialog, would end the very waiter it announces). A parallel call's `call: end` event ends nothing and leaves the
buttons up. The trail reads *answered in the terminal*. Answered in the pane, a subagent's call goes on, and its own
`PostToolUse` names it (captured). **The thread scopes it**:
- A waiter with a `subagent` is ended only by an event that carries the same `subagent`: one of that
  subagent's own tool events, or its `SubagentStop`, which carries the id (captured). The session's end
  and a `subagents_reset` end it too, and so does `subagents` reaching 0.
- The main thread's `Stop`, prompt or tool event ends no subagent's waiter. A subagent's event ends no
  main-thread waiter.
- A `subagent` that matches no waiter ends nothing. Every subagent capture holds one such event, about
  thirty seconds after the request, inside or outside the wait: a tool event or a `SubagentStop` whose id had
  no `SubagentStart`, the tool's own. Such a `SubagentStop` moves no count either while every counted
  subagent has its id, so it never brings `subagents` to 0 under a live subagent's waiter (TD-960); a count
  above the ids (an id-less start, or a record saved by an older build) is still taken down by one.

**Open prompts are a stack; the main thread's state is kept beneath it.** The waiter map keys each
waiter `(session, tool_use_id)` to its future and its thread (`subagent` or none). The record keeps every
open prompt in `pendings`, oldest first, persisted. The record's `pending` is the newest of them, and the
record reads `needs-you` while any is open. When the first prompt opens, the record keeps the state it replaced as `kept`: the state, its pending, its
confidence and its `since`, whatever it reads, a `needs-you` from the screen or title road too. So an emptied
stack always has a `kept` to go back to. The first push takes over the screen road's own saved state (it
pops `_hook_state` for the record), so nothing restores an older state later. A `kept` screen-road
`needs-you` is restored as it was, `scraped`, and marked for a recheck: the next tick runs the adapter's rules
once against the pane's tail whatever the hook's freshness (`_screen_gone` runs only when no hook is fresh,
and the stack just made one so). A rule still matching leaves it; none, and the record reads `idle` at `tick`.
The restore captures nothing itself, so a node's record is rechecked by the tick that owns its pane. A `kept`
title-road `needs-you` is restored and the title's next verdict clears it.
- **Every hook-road `needs-you` entry lives in `pendings`**, the first one too; a screen or title road's
  `needs-you` is its road's alone, outside the stack. A new prompt of either thread goes on
  top. A main-thread question (an `AskUserQuestion`, an elicitation) goes on top too, since it is answerable in
  the pane now, and it replaces an older main-thread question entry, as it replaces the one pending today. A
  question event writes nothing into `kept` beyond the first push's capture.
- **The tool's `permission_prompt` notification** (the adapter marks it `notice: permission_prompt`, a neutral
  field) is dropped while any permission or fallen-through question is open, or within `NOTICE_LAG` (10 s) of the
  last *sure* end: it announces the dialog of one already in the stack, and it lands about six seconds after
  the dialog is drawn (every subagent capture). An end is sure when it is a decision (**Allow**, **Deny**, a
  rule), the asked call's own event, or an event naming no call (a `Stop`, a prompt, a `SubagentStop`); each
  sets the session's last sure end. Any other end (another call's `call: start` or a question on the main thread,
  or another call's event ending a time-keyed waiter) clears it, so the notice that follows is pushed: if that end
  was wrong, the dialog is still up and the notice is the only road that sees it (the screen road is idle while a
  hook is fresh); if right, the next main-thread event removes the question within seconds. A fall-through ends
  nothing (its entry stays open), and the session's end drops all. The last sure end is kept in memory per
  session; a restart loses it, and at most one notice is then pushed. Otherwise it is pushed as a question, as today.
- **Each entry has its own deadline**: `Pending.deadline`, the hook's start plus the profile's `permission_wait`.
  The held line names the entry's own.
- **The screen and title roads write nothing** while `pendings` is open: the screen rules and the title verdict
  (*A rule's verdict lasts as long as its screen*, *A title the tool writes its state into*) are skipped for the
  record, so the stack is the one writer of `pending`. A held subagent prompt has no screen anyway.
- **A main-thread event with no pending** (a `Stop`, a prompt, a tool event), while `pendings` is open, first
  writes its state into `kept`, with a fresh `since` where the state changed and `kept`'s own where it did not.
  With nothing open it sets the record as today, and `kept` stays unset. Then it ends its entries:
  - while a main-thread waiter is live, it ends that waiter's own entry, through `_end_waiters`, and no
    subagent's;
  - with no main-thread waiter live, it removes the main-thread questions, as it replaces the one pending
    today — and, for a tool with no permission channel (§4.3 *Permissions: no channel*), the main-thread
    permissions too: none has a waiter, so its next event is the dialog answered in the terminal.
  So a `Stop` that ends a main-thread prompt answered in the dialog leaves the record `idle`, its own state.
  While a subagent's prompt stays open, the record stays `needs-you` and the `Stop` is not lost.
- **The record's own ends take it whatever is open.** `exited` or `closed` drops `pendings` and `kept`.
  The poll's `limited` is not applied over `needs-you`, as today.
- **A prompt that ends** leaves the stack wherever it sits, and its waiter finds it by its `tool_use_id`.
  A fall-through turns its own entry into the question form in place, top or not. When the stack empties,
  the record goes back to `kept`, with `kept`'s confidence and `since` (`set_state` takes a `since`). So
  the idle clock (Ready to close, the nudge, the cache's lapse) reads the main thread's own time. `rev` is not
  restored: the doorbell's stretch is a new one, and a ring is still gated by the unread count having risen.
- **A main-thread prompt's Allow / Deny** end its own entry. With the stack then empty, they set `working` as
  today, since the asked call runs in the turn. With entries left, they write `working` (with no pending) into
  `kept`, and the record reads `needs-you` on the newest entry left.
  A subagent's **Allow** / **Deny** only end its own entry. Setting `working` for a subagent's prompt would
  turn an idle main thread `working`, and it would read `stalled?`.

A subagent's prompt can end in three ways:
- answered in the terminal, by its own next event;
- answered by **Allow** / **Deny**;
- fallen through: its entry becomes the terminal's question, keeping the prompt's text, `subagent` and
  `subagent_name`, with `pane_held: false`. That subagent's next event, *any* event of its thread, or its
  `SubagentStop` ends the question: with the dialog drawn and no waiter live, any event of the thread means
  it was answered, and a pane **Deny** gives the asked call no `PostToolUse`. The call-keyed rule
  (another call's event ends nothing) holds only while a waiter is live.

**Every entry is answerable where it is drawn.** The card and Focus draw a line per entry, newest first, as the
team facet does, each permission with its own **Allow** / **Deny** and each question with **Focus**. `ao allow`
and `ao deny <id>` answer the newest *permission* entry, not the newest entry, and `--call <tool_use_id>` names
another.

The `permission_prompt` notification that follows the drawn dialog does not replace a question's text with
the tool's generic *Claude needs your permission*.

**The rules and the director seat** need no subagent field: `_by_rule` matches a prompt's tool and input,
and a subagent's is answered as the main thread's is. Its *Answered for you* entry names the subagent
(*from the general-purpose subagent*); on a node, the `answered_by_rule` request carries `subagent_name` for the
home that files it.

**The Inbox draws one row per record**, from its `pending` (the newest entry), and the trail keeps the last
answer's word.

**A node pushes** `pendings` and `kept` with its record, as it pushes `pending`. `pendings` and `kept` join it. A home older
than the node drops what it does not know, and draws a held prompt's plain buttons. That skew is accepted.

**A waiter does not outlive the host agent.** Waiters live in its memory. When it starts, a record saved by an older version with a hook-road `pending` (confidence `hook`) and no
`pendings` has it moved into `pendings` first, with `kept` set to `idle` at `tick` confidence and its own
`since`: the main thread's state is not known, and the next event or tick reads it. A screen or title road's
`pending` stays its road's. Then every entry of `pendings` that is a permission with no live waiter turns into the
question form: the hook's call failed,
so the tool drew its dialog. The entry gets `pane_held: false`, **Focus** and no buttons. If nobody
answers before the hook timeout, the terminal dialog is the only channel left and the card's
buttons collapse to **Focus**; a waiter whose record has already moved on sets nothing. The timeout is per
profile (`permission_wait` in `profiles.yml`), default 10 minutes for interactive sessions — long
enough to reach a phone. Unattended workers pre-authorise their tool set in the repo's tool
settings (the allowlist tdgrind ships), so they rarely reach the hook; when one does, the host agent
first matches the person's `permissions:` rules for its role and answers a match at once, then hands
an unmatched prompt to the org's director seat where one is defined, and only then leaves it to the
person as `needs-you` with its age (§4.9b *The director seat answers permission prompts for the
person*, TD-636, built by TD-641 and TD-642); an interactive session's prompt goes to the person alone. Questions and
multi-option menus always show pending text plus **Focus** (a question that reaches the hook reads
as its first question, as one does on the `PreToolUse` road) — never buttons — since the hook does
not carry the option list, and typing "1" into a pane on the assumption that a dialog is still up
is a race we refuse to run.

`limited` is distinct from `needs-you` because nothing the person does in the session unblocks it
(the turn waits on the account, so only another account or the reset does — a dialog's *retry* or
*stop* clears the screen, not the cap, §4.3 *The limit dialog*), and from
`stalled?` because it is explained. The card shows the reset time and offers **Switch profile**

the pane's limit message is the scraped fallback. The poll lifts a `limited` when its reading has no cap, as

composer, gone once answered, §4.3 *The limit dialog*), which lasts as long as its screen (below)
whatever the poll reads; the poll asks the record's own tail whether that rule still matches, so a
restart forgets nothing. The screen road leaves a poll-marked `limited` alone against a `limited` verdict, so a
scraped limit message never overwrites the poll's reset (§4.3 *The limit dialog*). A lifted scraped record goes back to the state its verdict replaced. A
lift of a non-modal verdict lasts until the rule next matches: a limit message still on screen sets
`limited` again on the next tick, which is Claude Code's today and outside this rule. Gemini CLI's limit dialog names no reset, and an
API-key home has no endpoint, so such a record reads `limited` with no reset time (§4.3 *The limit
dialog*).

`ready_when` (the **Ready to close** checklist) is evaluated by the host agent when a session goes
`idle` or `exited`:

- **Agent not working**, first: the session's own state is `idle` or `exited`. Any other state fails
  the row and names it — *agent working — wait or Wrap up*, or the state's own word (*needs you*,
  *stalled?*, *limited*) — so a session mid-turn is never *ready to close* on any surface, and the
  card's *more ▾* **Close** is disabled with the reason. The pages hold no second test of the state
  beside the checklist. Like the outcomes, mail and members rows it is unconditional and has no name
  in `.shiftlead.yml`.
- `git status --porcelain` empty.
- Branch pushed — **one measure, computed once by the host agent and read by everything that
  asks** (TD-080): the card's *n unpushed* flag, this checklist, the Inbox row built from it, and
  `ao team stop --close` (§4.9a). *Pushed* asks *does this work exist only on this machine*, never
  *is it merged*, and the first rule that applies answers it: (1) the branch has its own
  remote-tracking ref, `origin/<branch>` — the count of `git rev-list --count origin/<branch>..HEAD`,
  whatever the upstream is or whether one is configured; (2) no such ref but an upstream — the
  commits ahead of it whose patch it does not hold (`git rev-list --count --cherry-pick
  --right-only <upstream>...HEAD`), and 0 when the upstream holds the branch's content whole (a
  merge of `HEAD` into it, `git merge-tree --write-tree`, leaves its tree as it is), so a branch cut
  from `origin/main` and squash-merged, its remote branch deleted, reads pushed (TD-701);
  (3) neither — a detached `HEAD`, or a branch never pushed — pushed only when
  `HEAD` is contained in some remote-tracking branch (`git branch -r --contains HEAD`: a worker
  that merged and sits on a detached `origin/main`), otherwise **not pushed**, which is exactly the
  stranded work the check exists for. `origin` is the remote shiftlead assumes everywhere
  (worktrees are cut from it); a branch pushed only to another remote reads by rule 2 or 3. The
  host agent never fetches for this — it reads the refs it has — and reports `git.unpushed` and
  `git.pushed_against` (the ref, or `remote branches`, or nothing), so a page says
  *3 unpushed · vs origin/td-080*. Rejected: *ahead of the upstream* as the measure — it is
  *unmerged* when the upstream is `origin/main`, and a row that is always there teaches a person
  to ignore the row.
- `gh pr view --json state` merged (when the branch has a PR).
- No live subagents (Claude Code: `SubagentStop` balances `SubagentStart`; other adapters: nothing
  running under the pane).
- **No background shells running** (TD-761): the record's `shells` is empty — the tool's live
  background tasks, read from the process tree by the adapter's `background` (*Working on its own*).
- **No live member**: for a session that other sessions list in `controllers`, none of them is
  live — read from the control graph, so it covers a manager, a director and a hand-attached
  controller alike, and a session that controls nothing never sees the item. A manager on call is
  closed between its fills over working members, which is its normal state: the tick, not the
  manager, runs them (§6 rule 3); the way to end a team is its Stop (§4.9).
- **Outcomes reported** (§4.10 *Outcomes*): nothing the person answered is still
  owed an outcome.
- **Mail read**: no unread entry in the
  session's inbox — the same fact `ao progress none` is refused on (§4.9a), carried here for a
  session that exits some other way and never declares at all.
- The ledger/attention board touched since the session started (agent-cadence repos).

Each item is a named check in `.shiftlead.yml` so other repos can pick their own subset. The Focus
view shows the checklist live with a **Close** button that enables when it passes; an idle card
that passes shows "ready to close ✓" and a one-click Close; an `exited` card shows the failing
items. Closing is always the person's act: the checklist is a readiness signal, never a verdict.
This is the stranded-work audit with teeth.

A record's `confidence` is one of four: **`hook`** (the tool reported it), **`title`** (the tool
wrote it into its terminal title, *A title the tool writes its state into* below; TD-112),
**`scraped`** (a classifier read it off the screen) and **`tick`** (the host agent observed it: a
pane dead or gone, a kill, a close, `stalled?` — TD-490). Adapters without a usable hook set get a **pane classifier** and `"confidence": "scraped"`. The UI
shows the badge for `scraped` alone, so a guessed state is never mistaken for a reported or an
observed one; a `title` state is the tool's report and is not badged. No adapter may write a
scraped state with `confidence: hook`. The classifier's shape (TD-015): one versioned rule
manifest per tool, evaluated over the bottom of the pane, with `ao explain <session>` printing the
rule that fired and the evidence, and `ao explain --file` for fixtures. The same rules give
`limited` from the tool's own limit message and a `stalled?` that can say why. Scraped never
outranks a fresh hook state — fresh meaning a hook reported within the stall window; a session no
hook has reported on yet (the trust dialog appears before any hook fires) takes the classifier's
verdict at once. **A rule's verdict lasts as long as its screen** (TD-306): on a hook-fed session,
once no rule matches and no hook is fresh, the record goes back to the state the verdict replaced —
a hook's state and pending, labelled `hook`, or the tick's `stalled?` — and never to one an earlier
episode kept, since a hook that sets the state drops what was kept; or to `idle` (`scraped`) when no
hook has reported, since the launch's `working` is an assumption. It does not wait for the tool's
next hook, which on a quiet session is the next turn. **A title the tool writes its state into**
(TD-112; Gemini CLI's title, read by its leading glyph: `◇` ready, `✦` responding, `✋` action required) is the tool's own word, not a parse of
the screen: a state read from it carries **`confidence: title`**, replaces a hook state older than
one tick (not the stall window), and counts as hook-confirmed for every rule that acts only on one —
the doorbell (§4.10), the nudge, rule 5, the wrap-up — which read `confidence in (hook, title)`.
A title reading is **not held for its screen**: it replaces the hook state outright and drops what it
replaced, as a hook's own report does, so *A rule's verdict lasts as long as its screen* (below)
goes back for a `scraped` verdict alone; and for such an adapter the screen rule is asked inside
the stall window, a hook older than one tick being the title's to overrule, and its verdict ends on
the same test — once no rule matches and no hook is younger than one tick. The screen's end is read
before the title, so the replaced state comes back first and the title is compared with it on the
next tick; a `scraped` record with nothing to restore (a title adapter's, the screen gone, nothing saved: always `idle`) takes the
title's verdict even where it names the record's own state, re-written `title`, so it is told. Before a hook has reached the
record the title is not read, so *takes the classifier's verdict at once* (above) is the scraped
classifier's alone. `ao explain --file` takes a title beside the tail, so a fixture can carry one. `exited`, `closed` and `stalled?` are the tick's own
readings, not a rule's, written with `confidence: tick`, and stay — except that a `title` verdict of
`◇` or `✋` ends a `stalled?` (§4.3 *The second adapter*).

**Unseen idle.** An **interactive** `idle` session nobody has looked at since it finished
(`since > seen_at`; Focus sets `seen_at`) renders "idle · unseen" and sorts above plain `idle` —
the morning triage case. **Never on an `unattended` session**: its result is its
record, which the tick reads (§6), the person is not expected to open it, and its slot already says *out of work*
with Close session as the act — so a finished worker is plain `idle`, and the mark keys on the
`unattended` field. The word is *idle*, not *finished*: *finished* is a member that declared
itself out of work (§4.9a), and this is a turn nobody has looked at, not a run that is over.
Not a state: `idle` stays `idle` in every payload.

**Waiting.** *Waiting* means the session needs a person or another session — something outside its
own purview (TD-734; Paul, 2026-10-15: *I would expect WAITING to only apply when a session needs
input from the user or another session*). An `idle` session is drawn *waiting* (§4.5 *The card's
anatomy*) on one of two readings and no other: the person inbox holds an open `ask` or `steer` from
it whose `about` names a reference (`work.waiting_of`, the **waiting** mark's source, §4.5a; an ask
in prose names nothing and makes no wait), or a seat's `prs_waiting.asks` holds its ask for the PR of
one of its claims (`progress`, `claimed`: the claim's `pr`, `review_pr`, or the open PR whose branch
names the reference) — *waiting · review #1302 with the techlead*, the reader by its role. **A claim
whose PR is open with no reader holding it is no wait**: the author's next move is its own — the
cadence check, a CI run it will re-read, the merge — so it reads plain `idle`, and an idle author
stuck on its own PR is the one to look at, which a *waiting* pill would hide. Read on the view from
what the page already holds, never declared and never stored: `idle` stays `idle` in every payload,
and the concluded test (§6 rule 9) reads the state and the declarations as before. A session in `ao
wait` is mid-turn — the RPC holds its tool call — so it reads `working` and never *waiting*; an
`ask` to another session that is not a held PR's is not read (the page holds the person inbox and the
seats' `prs_waiting.asks`, nothing else). Was, until 2026-10-15 (TD-418, TD-428): any claim whose PR
the repo reading held open drew *waiting · review #N*, so an author mid-cadence read as waiting on
someone when nobody but itself would move.

**Working on its own.** An `idle` session whose own work goes on while its turn has ended is drawn
*working* (TD-734): a **live subagent** — `subagents` above zero (§4.2's Ready to close item *No live
subagents*) and a subagent's hook within `STALL_AFTER` (`subagent_at`: the time of the last
`SubagentStart`, `SubagentStop` or tool hook from inside a subagent, kept on the record beside
`subagents`, never moved back: an event drained late sets the later of the two times; the adapter says so with `subagent_seen`, and the core reads no tool's field, §4.3). The pill is the green *working*, composed as *waiting* is and ranked with `working`, its
ending *working · 2 subagents*; `idle` stays `idle` in every payload, and Ready to close reads the count
as before. **Live is one helper's reading**, `subagents_live(record, now)` — `subagents` above zero
and `subagent_at` within `STALL_AFTER` of `now` — which the host agent's view carries as
`subagents_live` (`agent_serve._view`, and the tick's *finished* reading) for every page and RPC
reader — the card, the team header, the Sessions rollup, `work.finished` — and which §6 rules 3, 4 and 9
call on the record with the tick's `now`: one test, so the card and the tick cannot disagree. The
tick's time-driven pass keeps each record's last value and pushes the record when it flips, since
no event changes it then. Past `STALL_AFTER` with no subagent hook the record reads plain `idle`, so a
lost `SubagentStop` never draws a session working for good, and **the count is reset to zero** by a
`SessionStart` of source `startup`, `resume` or `clear` (the adapter's `subagents_reset`, never on
`compact`) and by the record's exit, since no subagent outlives its process or its conversation. The
idle nudge (§6 rule 4) passes over a member it draws *working* and counts its idle stretch from the
later of `since` and `subagent_at`, so a member whose last subagent has just ended is not nudged at
once; §6 rule 3's seat close and rule 9's *finished* read it as not idle either, so a seat that
ended its turn on a reviewer subagent is not closed under it; a team header's and the Sessions page's counts
count it with `working`. **One order** decides the pill: where a wait reads, *idle · unseen* (an
interactive session's cue to go and look, TD-418) and then *waiting*, since what needs someone
outranks what runs; where none does, *working* on its own and then *idle · unseen* — the person's
own session mid-`/cadence` reads *working*, and its unseen cue, armed by the Stop, shows once the
subagent ends (a result that wakes a turn re-arms it at that turn's Stop) — then `idle`; and the slot's ending: a declared ending (`out_of_work`,

merge. The tool's footer read *1 shell*, while the card read *ready to close ✓* and offered
**Close session**, one press from killing the wait and the merge after it.
- **The read is the adapter's** (§4.3 `background`): given the pane's process, it returns the
  tool's live shell tasks, `[{pid, start, cmd}]`. For Claude Code, it walks from the pane's pid
  (the tick's pane list, `#{pane_pid}`) to the first process, the pane's own included, whose
  `comm` is `claude`, bounded as §4.8a's walk is. An ao launch's pane *is* that process, while
  a hand-started session's sits under a shell. No `claude` found is `None`. The tasks are that
  process's direct children that are the tool's command wrapper (`/bin/bash -c source <config
  dir>/shell-snapshots/…`, seen 2026-10-15 under 2.1.290), and `cmd` is the argv of the wrapper's
  first child (*timeout 1500 gh pr checks 1893 --watch*). An MCP server is also a child, but not
  that wrapper, so it is never counted. Children are read from `/proc/<pid>/task/<pid>/children`,
  or, on a kernel without it, from each process's `ppid`.
- **When it is read.** A foreground call's wrapper has the same shape as a background one, so the
  read is taken only when no foreground call can be running: the record is `idle` and **no
  subagent is live** (a subagent's own calls run under the same process while its caller's turn has
  ended). Otherwise the last reading is kept. A `Stop` turns the record `idle` when its hook is
  applied, between ticks, so the first read is on the next tick: for up to one tick (`TICK_SECONDS`,
  two seconds) a fresh `Stop` reads *ready to close ✓* over a shell. That is accepted, since the
  press it guards takes longer to make.
- **The record's `shells`**: the tick's time-driven pass reads each such record of this host
  whose adapter has `background`, attended or not, off the loop as `context` is. It writes
  **`shells: [{pid, start, cmd, since}]`** (`since` when this host first saw that `pid` and
  `start`) and **`shells_at`**, the last tick that read a **live** shell (below), never moved
  back. Both are node-owned (`NODE_OWNED`, as `subagent_at` is), so a node's reading carries home.
  The record is pushed when the list changes, and when `shells_live` flips, as `subagents_live`'s
  flips are (`_subagent_flips`). **No reset or bound is needed for the count itself**: a reading
  is of processes that are there now, so a task that ended is gone at the next read. Every exit
  path (`exited`, `closed`, the tool's `SessionEnd`) clears `shells`, where `set_state` clears
  the subagent count on exit.
- **What it draws.** A shell is *working on its own*, as a live subagent is. The pill is the
  green *working*, ending *working · 1 shell* (*working · 2 subagents · 1 shell*), in the same
  place in *One order*. The slot's ending names the oldest shell, *working · 1 shell: timeout 1500
  gh pr checks 1893 … · 4m*. Ready to close gains the row **no background shells running**,
  which fails while `shells` holds one (*1 background shell running — gh pr checks 1893 …*), so
  *ready to close ✓* and **Close session** wait for it (§4.5a). A shell's age is from `since`,
  this host's first sight of it while the record was idle, not the process's start. Under a live
  subagent the list is the last one read, so a shell that ended meanwhile stays named until the
  subagent ends; Ready to close fails on the subagent then anyway.
- **What the rules read.** **`shells_live(record, now)`** is the rules' reading, beside
  `subagents_live`: a shell whose `since` is within `SHELL_WAIT` (two hours, `SEAT_PR_WAIT`'s
  length, beside it in `agent_common`). It is longer than `subagents_live`'s `STALL_AFTER` because
  a shell sends no heartbeat, and the waits it holds, CI and a deploy, run long. §6 rule 3's seat
  close, rule 4's idle nudge and its `open` cause, and rule 9's *finished* read it as not idle, as
  they read a live subagent. Their stretches are counted from the later of the record's `since`,
  `subagent_at` and `shells_at` (`agent_common.idle_from`). Since `shells_at` moves only for a
  live shell, a shell past `SHELL_WAIT` holds none of them.
- **A shell that never ends** (a server left in the background) still fails Ready to close, since
  a Close would still kill it. Past `SHELL_WAIT` the row says so, *1 background shell running 3h —
  stop it in the session, or Close kills it*. On the person's own session, a Ready to close whose
  only failing row is such a shell offers **Close** in *more ▾*, with a confirm that names the
  shell (§4.5a *Close session*).
- **`ao doing` stays**: the line still says what the shell is for (*CI on #1302, then the merge*),
  which `cmd` cannot, and the role briefs keep asking for it.
- Rejected: counting from the hooks the adapter gets (a `PostToolUse` of `Bash` with

**`send` confirms the prompt took.** `send` refuses while a permission or question is pending.
Every `send` to an adapter that can read its tool's composer (§4.3 `composer`) waits for the
pasted text to paint before pressing Enter, then requires the composer to empty; if it does not,
Enter is pressed once more as `C-m`, and if the text is still there the call fails with
`prompt-stuck` — the text left where the person can see it, never re-pasted. The paint-wait exists
because an Enter that reaches Claude Code before it has read the paste is dropped (TD-027). The
Claude Code adapter's composer read counts painted text only: the tool's faint suggested next
prompt — often the session's own last prompt — is not an unsubmitted prompt. With `wait` it also
returns only after the session has started on *this* prompt and settled again (`idle`,
`needs-you`, `exited`, `closed`, `limited`, `stalled?`): a busy session queues the text, so the
wait first lets the current turn end — a stop on a question or an exit is returned as is, prompt
still queued — then requires the next turn to start. Busy and *started* are both read against the state as it was
just before the paste, not after the submit: the tool reports this prompt's own start the moment
Enter lands, often while the composer is still being checked, so a turn that began, or began and
ended, during the typing counts as this prompt's (TD-204). It fails with `prompt-stalled` when nothing
starts within a few seconds of the moment it could, `timeout` after the caller's limit, and
`removed` if the record goes away — so a policy's wrap-up request (§6) is known to have landed,
and no text is ever re-sent on a guess (TD-016). The record is the one the text was typed into: an id that
another record takes in the meantime ends the wait as `removed` too (TD-261).

Liveness cross-check: the host agent also watches the pipe-pane log's mtime; a `working` state
with no output for longer than the adapter's `stall_after` is shown as `stalled?`, which is how a
credential lapse surfaces without a 401 regex.

**Takeovers happen to worker panes.** A Claude Code pane driven from Anthropic's Remote Control is
stood down when another device connects to the same session: the tool says so on the pane
(Remote Control disconnected, another connection took over, standing down with a close code) and
the footer carries a failed `/rc`. The pane lives, the tool answers, and nothing is driving it.
That is not `idle`, which is a session resting between turns (TD-032). A screen rule reads the
banner as `stalled?` with a note saying so, and a `stalled?` card shows that note above its tail.
