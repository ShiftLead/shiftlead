### 4.7 CLI

Package and canonical command: `shiftlead`. The package also registers `ao` as an alias
(`ao status`, `ao new`, `ao shell`, `ao focus <name>`, `ao off --now`), a separate console-script
entry so anyone with a colliding `ao` can drop it without losing anything. The CLI is a thin
client of the host agent RPC — it never touches tmux itself (§9 invariant 1), with one read-only
exception: `ao focus <id>` and `ao new --attach` / `ao shell --attach` run `tmux attach` on the
session, the terminal's Focus screen, which creates, kills and types nothing (under `--json` the
attach argv is printed instead). That is how a session started from any terminal gets a
first-class card: `ao new --attach` where you would have typed `claude` (TD-010 b).

**Every subcommand:** takes `--json` and prints the RPC result with the ids the next call needs
(TD-018); every subcommand that takes an id also takes a bare name, resolved within the current
repo or directory (TD-030). The CLI reads the calling session from `SHIFTLEAD_SESSION`, the
variable the hook uses (§4.2), and sends it as the request envelope's `caller` with every RPC
(TD-028): that is how a report lands on the right record and how the agent tells a worker acting
on another session from a person typing in a terminal (§4.8). The CLI follows herdr's JSON-first
CLI and skill file ([ADR](../decisions/2026-09-10-herdr-spike.md)).

**Naming.** `ao new <name>` applies §4.1's name rule and says so: a live holder is refused with
"`aotest` is running — `ao focus ao-shiftlead-tests-aotest`, or pick another name" (exit 1, the
holder's id under `--json`); an exited or closed holder is superseded and the reply names the
previous run's log.

**Skills.** `ao --skill` prints the rules an agent driving `ao` from inside a session must
follow (TD-019); `ao --skill > .claude/skills/ao/SKILL.md` installs it in a repo (the New-session
install offer is phase 5). `ao team --skill` (TD-067) prints how to **stand a team up** — the
node, the project and the team definition, the roles and their briefs, and `ao team
list / start / status / stop`, each step a command. It is the page a repo's first team is stood
up from, with no brief written for it (TD-623): what the repo's ledger and rules need first, what
each lane word takes in `lane_matches` and what only a brief fences (an `Owner:` a bare `free-pick`
never reads, the board's decided lines and red PRs in every `free-pick` lane), the node's `env`
file, logins and token scope and what the node does to the repo's devcontainer, and that a team
reads only its own repo's PRs, so an umbrella over sibling repos lands paired PRs. Both ship in the package (beside `skill.md`)
so they print anywhere `ao` runs, a container node with no checkout included, and both exit
during parsing, so they need neither a host agent nor `team`'s required subcommand. The README
points at them; there is no copy under `docs/`, which would drift.

**Explain.** `ao explain <id>` prints a session's screen, the rule that fires on it and whether
it applies; `ao explain --file` classifies a saved screen (TD-015).

**Transcript.** `ao transcript <id> [-n N] [--before OFFSET] [--raw]` prints what a session said
and did, without resuming it (§4.5 screen 9, TD-154): the last N turns (20) as the pane draws
them — `>` the prompt, the assistant's text, `⏺ Tool(first line)` per call with its result folded
to its first line, *thought · n lines*, *n subagent turns* — through the `transcript` RPC on the
record's host, a read gated by nobody. `--json` prints the adapter's neutral entries and the
offset `--before` takes for the turns before them; `--raw` prints the file's own lines instead,
the last N of them, for a reader that wants the tool's shape. A record with no tool session id is
refused with what it is (*a shell has no transcript*). A read-only verb, listed beside `tail` and
`explain` in `ao --skill`: what a manager reads before deciding a quiet member has stalled
(TD-091's moment), and what a person reads instead of Resume. The offset `--before` takes is given only
when an earlier prompt exists — the read goes back as far as the prompt before the ones it holds, so
*earlier turns* never opens on nothing but the tool's bookkeeping — and Claude Code's subagents,
which the tool now writes to their own files beside the session, are read from there and folded
under the Agent call whose id their record names (an older file's inline sidechain entries fold
under the Agent call before them).

**Reporting (§4.8, §4.9a).** Each is a small RPC on the calling session's own record — `--id`
for another's, since the channels are ungated:
- `ao progress claim TD-027`, `ao progress done TD-027 --pr 59`, `ao progress drop TD-027 --why "..."`, and `ao progress done TD-027 --pr 59 --slice` for a merged PR that leaves the entry claimed (§4.8); a `done` naming a PR whose required checks failed or are still running on its head is refused, naming them (§4.8 *A `done` with a PR is told what its checks read*, TD-637, TD-658);
- `ao progress none --why "..."` — the session found no work it may pick (§4.9a);
- `ao progress restart --why "..."` — the session's run is over and its lane is not (§4.9a *A run that ends with work left*);
- `ao finding TD-029 --priority low`;
- `ao log "<line>"` appends one stamped line to the session's round log, `ao log --tail n` reads it back (§4.8 *A session's round log*): the manager's memory across runs, its own record only, never a report;
- `ao status -v` prints the same report line the card will, and `--json` the entries. A PR that
  is no longer open is marked as the card marks it, `TD-066 → #158 merged` (§4.5a card **report
  line**): the CLI reads `repos` once per call, and where that read is
  refused (a node offline) or holds no such PR the line is printed unmarked. The mark is in the
  text only; `--json` carries the entries as the record holds them. A claim holding slices prints
  them on a line of its own, *slices: TD-309 #1025, #1027*, a slice the tick derived marked `~`
  (§4.8).
- `ao status -v` prints each record's seat-ledger figure (§4.4 *Spend per seat*, TD-818) — *spend ≈$12.40 today · ≈$61 week · past 200k 18%*, `$` for a metered profile, *spend unknown* where the adapter cannot read it, and no line where the record spent nothing this week — and `-v --json` a `spend` object of `{day, week, past_200k, past_300k, unit}` on each such record, the two shares today's, read from the `seats` RPC with `by: record` (a plain `ao status --json` does not ask for it).
- `ao status` prints an `idle` record working on its own (§4.2 *Working on its own*) as its card draws it: *working* in the state column, ranked with the working, and the card's ending after the mode — *· 1 shell*, *· 2 subagents* — from the view's `subagents_live` and `shells_live` (`ending.own_work`, one helper the card and the CLI share); nothing pending; a wait the home reads (§4.2 *Waiting*) does not change it, as on the card (§4.2 *One order*, TD-1222), and under `-v` the wait is still printed on its own line, while the card's review wait stays the card's. `--json` keeps `idle` (TD-1147).
- `ao status -v` prints each record's context reading — *context 231k of 1M, bound 200k*, and *(over)* past it — and `--json` the `context` and `context_bound` fields (§6 rule 5).
- `ao status -v` prints a closed record's closer in the card's words — *closed by you*, *closed by manager-dc-1*, *closed itself*, *closed by the tick · team finished* — and `--json` the `closer` field: a line under the record's, the words then the close's age.
- `ao status -v` prints an exited record's ending in the card's words (§4.5 row 5 (b), `ending.exit_words`) — *exited · code 1*, *killed by manager-dc-1*, *pane gone · found 16:50 by a host agent down since 12:30* — and `--json` the `ended` field; `ao status` marks `~` a `scraped` state alone, never a `tick` one (TD-490).
- `ao status -v` prints a record's `restarts` on a `restarts:` line, newest first — three, then *+n earlier* — each its `why` as written and its age, the doorbell's as *cache lapsed · idle 5h · 191k* (§4.10) and one whose close or replay failed with *· failed* (`ending.restart_words`); `--json` the `restarts` field.

**A person in the team.** `ao new <name> --team <team>` (§4.9 *A person in the team*) is the terminal's form of the New session form's Team pick: the badge and the group, the team's manager — live, or a seat on call, which it says in one line, *under manager-ao-1 · on call: whoever fills the seat may act on it* — as a controller, and the record's `review` from the role's or else the team's — the reader a grinder has, so a person's held PR waits for the techlead as a worker's does. With `--role`, the brief names the team's seat and manager, as a team start's does.

**Presets and grants.** `ao new --role grinder --lane free-pick` (`shiftlead.repoconfig`): the preset fills the brief from its template with `{lane}` filled and `--brief <path>` in its `{repo}` slot (§4.8; `--prompt` is raw text and fills nothing, and is refused beside `--brief`), the
lane's default, its grants, its `profile` unless `-p` is given, and its `controllers:` — else the
repo's — when `--controller` is not, resolved from names to ids in the session's directory (a
configured name that is not running is skipped with one line naming it and the file, never an
error; an explicit `--controller` that does not resolve is an error). `--lane` takes lane words
(`free-pick` or `design-first`, narrowed by `owner:<word>`) and is scan-and-choose over the lane's shared list;
`--lane TD-027,TD-019`, a list of references, is still accepted and kept as written, but matches
nothing in the in-lanes reader (§4.8): nothing hands an entry to a session. `ao roles` lists what the repo and the package define, marking each role's
source. `--grant control` adds a grant a preset lacks, and works without a preset. `ao grant <id>
control` / `ao revoke <id> control` edit a running session's grants (the `set_grants` RPC;
`ao status -v` and `--json` show `capabilities`).

**Membership (TD-036).** `ao control <controller> add|remove <session>…` edits membership from
the manager's side — *this manager controls these sessions* — while the list itself lives on each
target: one `set_controllers` call per target, so a refusal names the session it refused and the
rest still stand. `ao new --controller <id>…` sets it at create, and `ao new` prints one line when
a session starts with nobody able to act on it. `ao status -v` prints both directions: `under:`
from the record, `members:` derived across the records, never stored.

team in `settings.yml` that no definition names (a repo renamed its team); a repo whose ledger's `Team` vocabulary declares a team no definition of the repo holds (naming the entries that carry it), or, where the repo's definitions hold two or more teams, does not name one of them (whatever the vocabulary's size, none included), or whose entries need a team where no team of the repo has a techlead seat to tag them (§4.4 *An entry names its team*, TD-730); and, as warnings
that do not fail it, a registered checkout off its default branch or holding changes, and a repo

node both refuse and name the home. It
reads and writes nothing; a session may run it. A

where it is started*; a file of the remainder reads its last commit, *not committed yet*, or *not
there*, and a home that is no work tree yet says so once. The check prints each lack as
*lacking: …* and each warning as *warning: …*, then *n lacking* or *ok: n teams*; under `--json`
it is `{ok, lacks, warnings}` with the same exit code. A team's profile, brief and checkout are

**`ao org check --root <dir>`** (TD-942) reads the repo file at `<dir>` — a worktree of a checkout
registered on this host, or that checkout itself, on any branch — in place of that checkout's own, so a definition is checked on the branch
it is written on, before it merges: the briefs, primer and role directories it names are read under
`<dir>` too, and every other repo is read as without it. `<dir>` belongs to the checkout in this
host's registry (`hosts.local_host().repos()`) whose `git rev-parse --path-format=absolute
--git-common-dir` is `<dir>`'s, paths resolved — where `<dir>` is itself a registered path that entry,
else the first entry in the registry's order with that common directory, the others read as without
`--root`; a `<dir>` that is not its own work tree's top (`git -C <dir> rev-parse --show-toplevel`,
resolved, so a subdirectory, a `.git` or a bare repo is refused), or matches no checkout of this
host's registry (one held only on a node included), is refused, *`<dir>` is not a checkout of a
registered repo*, exit 2. **Where `<dir>` stands in** is one mapping, `{<registered root>: <dir>}`, handed
to each reader that takes the registry's roots; `roots` itself stays the registry, so `held_elsewhere` reads the registered names as without
`--root`; the root loop's entry for the stood-in checkout tests `<dir>` (its *not there* and its
`.agentorc.yml`-only lack, TD-553) and gives no checkout-state warning for either path.
`repoconfig.visible` and `flowdefs.visible` read that repo's role directories and flows at `<dir>`;
`org.with_repos` and `merge_repo_teams` read its `.shiftlead.yml` at `<dir>` and keep the repo's name
and `org.checkouts` key the registered root's (its directory name, never `<dir>`'s basename), each
team's `source` the file at `<dir>` it was read from, and the checkout's path on this host `<dir>` —
written over a path the org file's project gives for this host, which the mapping overrides as it
does the registry's — so `teams.plan` reads the briefs and primer there unchanged; and `team_lacks` pairs `readings[<registered root>]` with the teams whose checkout is
`<dir>` through the same mapping, so the ledger's `Team` declaration, read as merged, is checked
against the branch's teams. A team of that repo that `place:` lands on another host has only its
definition read from `<dir>`: its briefs and primer are read on that host's checkout as it stands,
and the check says so as a warning, *`<team>`: briefs read on `<host>`'s checkout, not at `<dir>`*. The output says what it
read, a first line *checking `<repo>` at `<dir>`*, and `--json` carries `root: {repo, dir}`. Without `--root` the
`root` key is absent, never `null`. Only `check` takes `--root`; `ao org` alone does not. The
checkout-state warnings (off its default branch, holding changes) are not given for `<dir>`, which is
on a branch by design, nor for the registered checkout it stands for — the registered checkout
itself, given as `<dir>`, included. **The
definition at `<dir>` stands for the registered checkout everywhere**, under that checkout's name and
path: every reading that is not the definition's — the repo's ledger and its `Team` declaration, the
board, the PR readings — is the home's reading of that checkout, so a branch that adds a team and the
ledger's `Team` line together is checked against the ledger as merged, and its flows, `commands`,
`gate` and `held` are the file's at `<dir>`.

**Entries (§4.9 *Add an entry to the ledger*).**
`ao td add [--repo <name>] [--type debt|feature] [--priority high|medium|low] [--team <team>] ["<words>"]` is the terminal's form of **Hand to
the techlead**: the words — the argument, or standard input when there is none — go as the
person's `ask` to the techlead seat of the repo's team (`--team` the form's **Team** pick: that team's seat, and `entry.team`, TD-730; a name no team of the repo has is refused, naming the repo's teams), carrying `entry` and marked `handed`;
`--priority` is the form's **Priority** pick, *medium* when absent (TD-851). The
repo defaults to the one the command is run in — its main checkout, from a worktree too. It prints
the message's id and when it will be read, as `ao msg` does, and is refused in words where the form's button is disabled. **From a session, only for another repo**
(TD-995): a session's `ao td add --repo <X>` goes as the session's `ask` to X's question seat, carrying `entry` but **not
`handed`** — a handed entry is the person's, and its seat owes the person an outcome — so it is a plain `ask`, and like a handed entry
it takes **no bound**: the seat replies once its PR is merged, and only the open `ask` holds the seat on call through a
fact-check, CI or a reader that can outlast a day; the seat's reply closes it, which also frees the sender's one open
question to that seat (§4.10). The seat judges it: it drafts the entry and lands it by PR, or replies why
not. From a session the client sends `repo` as typed (and `team` where given) and reads neither the local registry nor
`org.yml`, which a node does not have; the home resolves both from its records, as `ao msg --repo` does. A session's call carries no `--draft` (a draft folder is the
person's form's) and is refused one in words; with no `--repo` it is refused at the client, since the repo it is run in is its
own. For the session's own repo — the resolved seat record's `repo` is the caller's record's, on the same host; a name shared
with a repo on another host is another repo, and a caller whose record names no `repo` has no ledger of its own, so
every repo is another to it — it is refused as before: a session that wants
an entry in its own ledger writes it on its branch (cadence §2) and reports it with `ao finding`, which declares a ref the
session wrote and files nothing anywhere else. The form's other way has no
verb of its own: `ao new <name> --team <team> --role <role>` starts the session, and a terminal
has no composer to fill.
`ao td reserve [--repo <name>] [--count <n>]` reserves the next free ledger id for the repo, or `n` in a
row (at most 10), taken from the counter on origin through the home, and recorded (§4.4 *A ledger
entry's id is handed out by the home*), and prints one line an id, *reserved TD-1234* (TD-1200). **Every call spends
what it reserves**: an id it printed is a gap in the ledger unless an entry takes it, so it is run to
file entries, never to look. **A probe of the home is a read** — `ao repo`, `ao status` — never a reserve. A take
the counter did not reserve (`reserved` false, below) prints *TD-1234 (not reserved on origin's counter)*, its
reason on standard error as now. A script reads the ids from `--json`'s `ids`, never from the lines.
**`ao td next` is its old name**, kept as an alias: the same flags and the same call, and its standard output the
bare ids one a line as before, so a script started from an old brief does not break mid-run; it adds one line on
standard error, *ao td next is now ao td reserve — it reserved TD-1234* (the ids joined with *, *), or *— it handed out TD-1234* where `reserved` is false:
with `--json` or without, after the reply's other standard-error lines, and only on a reply that gave ids — a refusal
prints its refusal alone. Its `--json` output is `reserve`'s, byte for byte. **The home's RPC stays `td_next`**, and so
do the functions behind it: only the verb a person types is renamed. The alias goes once no package brief, design
section but this paragraph, help text or pinned cadence (cadence §2.10) names `ao td next`, and this paragraph's alias
sentences go with it (TD-1202); a ledger entry is a record of its day, so the ledger's entries are not counted. Unlike `ao td add` it is open to every session and to the
person: it writes no ledger, only the counter and `ids.json`. The repo defaults as `ao td add`'s does, and is sent by its registered name, or by its origin's
`owner/repo` when that name is shared, with the branch of the directory it runs in when that directory is
a checkout of the repo named (§4.4 *The branch*). `--json` gives `{repo,
ids, unread, reserved, why, warnings, taken_by, taken_by_line, question}`, where `unread` names the open PRs that could not be read, and an unread PR
is also said on standard error. An id given but not reserved on the counter (the script's fallback) is said on
standard error too, *not reserved on origin's counter: <why>*, and the exit is still 0; so is each warning.
A `taken_by_line` is said on standard error as *write `**Taken by:** <by>` in each entry's header (cadence
§2.10)*, the script's own words, with `--json` or without, as the other standard-error lines are; a null one is
no line, and standard output stays the reserve lines (or the JSON) alone. Where the repo sets `review-outcomes` on,
`question` is the script's filing question (§4.4 *The filing question*), said on standard error last, after the ids and
every other standard-error line (the alias's too), with `--json` or without; it is null otherwise, and no line. A home that predates
`taken_by` and `taken_by_line` answers without them, and the CLI gives both as null; one that predates `question`
answers without it, and the CLI gives it as null.
`reserved` is true on the home's own road, which has no counter: there it means recorded in `ids.json`, not
reserved on origin. A repo whose origin names no forge has the script's *no forge* warning on a first take and in its fallback,
the takes that read the PRs. It is refused, with the reason, when the
script refuses or the fetch of `origin/<default>` fails.

  marked `plain` also points at the wrong port (*point the tunnel at 127.0.0.1:<route port>*). It

  url, team, aud, allow: [<email>]}`; the email is asked for when `--allow` does not give it, and
  with no terminal to ask on the command is refused, naming `--allow`. Which port the tunnel
  reaches behind Access is the guide's step; the plain port's refusal of `Cf-Access-Jwt-Assertion`
  (§4.5b) is what catches it, on the person's first visit.
- **`off`**: removes `reach:`, and for `tailscale` turns off its own handler, if there is one (`tailscale
  serve --https=443 off`) — never `serve reset`, which would end the person's other serves; for
  `cloudflare` it removes only `reach:`, the tunnel and the Access application staying the
  person's. The route port then refuses everything and closes the websockets it carried (§4.5b).

`--allow <login>` (repeatable) replaces the allowed list on either route; the list holds the
person's own logins (§1: one person runs the sessions; the home has no second person to let in).

**`ao schedule`** (§6 *Schedule*, §5 `settings.yml`; not built — TD-133): with no
arguments prints every team's rule and when it next fires — *ao-grind · starts at the reset of
grind's week — Thu 07:00*, or *no schedule*; `ao schedule <team> reset --profile <p> --window
<label>` sets one and `ao schedule <team> off` clears it — `teams.<team>.schedule` in
`settings.yml` (§5) — through `set_settings`, refused to a session as `ao gate` is. The client checks the team is defined (`org.yml` or a repo's `teams:`,
which the host agent does not read) and that an adapter of the profile reports the label, and
refuses naming which; the rule takes effect on the next tick.

**`ao prefs`** (§4.9b *The director answers what is passed up to it*, TD-657): with no arguments
prints the preference layers in the order the director reads them — the package's, the person's
(their agent-cadence layer's `shiftlead/preferences.md`, §4.8 *The person's own additions*), each registered repo's `.shiftlead/preferences.md` — with the level
in force (the org's and each repo's override), the last groom pass and any proposal standing.
`ao prefs groom` makes the director due for `groom` now; `ao prefs interview` starts the person's
interactive session with `interview.md`; `ao prefs accept` and `ao prefs discard` are the Inbox row's
**Accept** and **Discard** — those four a person's own, refused to a session as `set_settings` is.
`ao prefs propose <file> --why "<line>"` hands the home a proposed person's file, the director seat's
and an interactive session's alone. The level and the cadence are set as any setting is, on the
Settings page's **Director** card (`director.level`, `director.groom`, `repos.<repo>.director.level`).

**`ao restart <session>`** (§6 rule 2 *A person's restart*): a person's press in the terminal — the `restart` RPC, refused to a session as
`set_settings` is — on a supervised `idle`, `exited` or `closed` record with a launch record:
closes it if still there under the tick's clean-and-pushed test, replays it from the launch
record as that record was started, clears `restart_wanted`, `restart_ceiling`, `restart_blocked` and
`restarts`, and prints the new record's line as `ao status` would; a refusal says what is left
or why not (*2 uncommitted*, *no launch record — use Resume with changes…*, *working*). `ao
status -v` shows `restarts: [{why: person}]` on the record afterwards.

**`ao new --at`, `ao at`** (§6 *Start time*): `ao new
--unattended --at 20:00 | +2h | <ISO> …` creates a `scheduled` record and prints *starts 20:00*;
`ao at <session> <when>` moves a scheduled start, `ao at <session> now` starts it at once, and
`ao close` on a scheduled record cancels it. Parsed as `--until` is — *the next 20:00* is a
question about the caller's clock — and gated as an acting call (`set_start`, beside `set_stop`).
`ao status -v` prints *starts 20:00* by the *stops* formatter.

`ao close` on a `closed` record whose start made its worktree runs the reap again and kills nothing; its close stamps stand. While the directory is still there it weighs the worktree and its branches; once the directory is gone it weighs the branches `branch_kept` names, or, after a removal by hand, the branches its stale registration and its launch name give, once `git worktree prune` has run (§4.1 *A close reaps the worktree it made*, TD-978).

**`ao migrate`** (TD-060): the one-time move from the project's old machine names, with no session
running. It stops and removes the user units `agentorc-agent` and `agentorc-ui`, renames
`~/.agentorc` to `~/.shiftlead`, rewrites the old names inside its small text files (the YAML and
JSON at its top, the launch records, each node's `hosts.yml` and `profiles.yml`; never a log or a
record), removes the generated hook files under `claude-hooks/` (each launch writes its own) and each
container node's venv (its scripts name the old mount; `ao host up` installs it again, the node's logins kept), and
prints what is left: the root line first, whose `install --system` stops and removes the old
system units and starts the new tmux server (§4.1), then `ao service install` from the new venv. Refused while the tmux server
holds a session, when there is no `~/.agentorc`, and when `~/.shiftlead` already exists. The code
reads no old name after it; a repo's `.agentorc.yml` is the repo's to rename (§5).
