### 4.5 UI

Single web process (FastAPI + websockets; plain server-rendered pages with a small amount of JS
and xterm.js — no SPA build step, so other devs can run it with one command). Talks to each host
over ssh: JSON RPC over `ssh host shiftlead-agent rpc`, and one pty per open terminal running
`ssh -tt host tmux attach -t <session>` (`tmux attach` directly for `transport: local`), bridged
to xterm.js over a websocket; resize is a `TIOCSWINSZ` on that pty, which ssh forwards. No
terminal daemon on the hosts. Adding a host is `shiftlead host add vps user@vps` + installing the
agent there.

The page links its own stylesheet and script with a hash of each file (`/static/app.css?v=…`), so
the first page after a promote fetches the new files instead of a copy the browser still holds.

Screens:

1. **Org** (home): a **card grid**, grouped by team when any live session carries a team badge
   (§4.9); not a table, since a grid keeps each session's facts grouped and shows a live tail.
   The **more** menu holds Wrap up, Kill (confirms), Close (enabled only when Ready to close
   passes; a card that passes also shows it inline, §4.2), Open shell here, Copy tmux command. A
   scraped state shows as a dashed pill outline.

   **The card's anatomy (TD-095).** A **full card** — every card outside a live team's group, *No
   team*'s above all — is **six rows, the same six on every card, in the same places, at one
   height** — a row with nothing to say stays, empty, rather than moving what is below it.
   1. **Name and state**: the session's name, the tool's title beside it **only when it differs
      from the name**, and the state pill, always at the right.
   2. **What it is**: the role's label and icon; the mode — never pressable, its toggle in
      **more** and on the Focus header — drawn so that **the person's own sessions stand out**:
      *unattended* is a plain, quiet word, the common case on a team; ***interactive*** takes the
      `person` icon and the text's full strength (a worker a person has taken over by flipping it
      is theirs too). **`person` is reserved for this mark**: it leaves the set a role's `icon:`
      may name (§4.8 — no built-in uses it; a repo's role that names it is refused when the file
      is read, with the reason), so a card never shows one glyph for two reasons. Then the marks
      (unread, identity, suspended); the **stops** note (§6) as plain text after the mode; and at
      the right **the one clock on a card**: how long it has been in this state — the record's
      `since`, counted in the browser.
   3. **Where**, alone and at full width: `branch <name>`, shortened in the middle so both ends
      read, whole on hover; `detached at <short sha>` for a detached HEAD; the directory for a
      session with no repo (a shell, a plain directory); `wt/<name> ·` in front **only when the
      worktree is not the session's own name**; and, **outside a team's own group, `host / repo ·`
      (or `host / directory`) in front of all of it** — inside one the header says it. ***under
      `<controller>`*** ends the row where it is drawn at all (below). The dirty / unpushed flag
      sits at the right.
   4. **What runs it, and what it reports**: tool · account · model at the left, on every card
      (a team's members commonly differ), then the **context reading** — *· 231k*, red past the
      role's bound (the bound in its title), absent where the adapter cannot tell (§6 rule 5);
      the report line at the right — progress, and the findings count beside it — **a reference
      shown once** (`#359 · 1/2 done`, never `#359 → #359`).
   5. **The slot**, always two lines and a caption; a longer text is clamped, whole on hover and
      in Focus. **One text, the first that applies** — the order of §4.5a's **doing** row, with
      the endings named: (a) **what needs a person or explains a stop** — the pending permission
      or question, a `limited` session's reset text, a `stalled?` rule's note, an unreachable
      host's reason (the `host_note` row), and, for a prompt pending on a host out of reach,
      *answer it at `<host>`*; (b) **an ending** — **an exit, and how** (`ending.exit_words`, from the record's `ended`,
      TD-490): *exited · code N* for a dead pane or a hook that carried the code, *exited · <reason>*
      for the tool's own end with no code (`logout`, `prompt_input_exit` as *the composer closed*,
      `other`), *killed by you* / *killed by <name>* for a kill (§4.5a **Kill**, `ao kill`) — *killed itself* for a
      session's own, *killed by the tick · stop time* for the home's (§6 *Stop time*) — *pane
      gone · found 12:31* when the tick found the tmux session gone, and *pane gone · found 16:50 by a
      host agent down since 12:30* when that was the agent's first tick after a start (the gap is the
      previous run's last tick, kept in `host.json`) — a record whose `wrapup_at` precedes the exit
      adds *· after wrap-up*; **a close, and by whom**
      (`shiftlead/ending.py`'s `closer_words`, which the card and `ao status -v` share): *closed
      by you* for a person's — the UI, or `ao` outside a session — *closed by manager-dc-1* for a
      session's (`ao close`, or the per-member close of `ao team stop --close`, run inside one),
      *closed itself* for a session's own, *closed by the tick · <why>* for the home's — *team
      finished* (§6 rule 9), *for a restart* (rule 2), *brief changed* and *flow changed* (rule 7
      and its second trigger, §4.9c), *cache lapsed* (rule 7's third, §4.10), *flow sat it out* (§4.9c), *seat done* (rule 3) — the
      tick's closes; rule 8's start closes nothing, a Start's close of a concluded session is the
      presser's, and a person's Restart closes as the person's — and bare *closed* for a record
      with no closer (one written before the field, a node older than it, and a person's Close
      made at the node itself, which the home's copy never sees — the hover says those three),
      the hover adding the time; *restarts exhausted · 3 in 2 h* (§6); or a declaration, *out of
      work* or *restart wanted* (an early one says *early — for a person*, a repeat *repeats
      TD-229 — for a person*), the fixed words then the first line of its reason — **and a closed
      or exited record that declared keeps the declaration after its ending**, *closed by
      manager-dc-1 — out of work: nothing pickable on dev-cadence's ledger*, since the
      declaration is what explains the close — and after a declaration, or alone on a session
      that declared nothing, the wait where the session is waiting on the person (§4.5a
      *waiting* mark: *out of work · waiting on you: TD-222 until 09:57*); (c) **what the session
      says it is doing**, working or idle, and where it says nothing, the **brief changed** mark
      (§6 rule 7), which is not an ending and never hides a `doing` line; (d) the last output
      line, or *at prompt*. **The caption, the first that applies**: the time a pending answer
      has left (*via hook · 4m left*); ***ready to close ✓*** whenever the checklist passes — the
      one place that fact lives, whatever the text above it, so an idle session that passes
      keeps its last word in the slot and gains the caption and the button; *says · `<age>`*
      under a `doing` line; else empty.
   6. **The foot**, whose **first button is the next act, by state** (Allow / Deny, Close
      session, Forget and Switch profile / Wait live in the foot, never in the slot): `needs-you`
      with a hook permission → **Allow**, **Deny**; `limited` → **Switch profile…**, **Wait**;
      `exited` → **Forget**, whether or not it also reads *ready to close ✓* (there is no process
      left to close); *ready to close ✓* on a session still there (`idle`) → **Close session**;
      `closed` → **Forget** as well (nothing is left to close there either, and the record goes
      by itself a day after the close); a pane that is gone on any other state → **Details**;
      everything else — `working`, `idle`, `stalled?`, a question to answer in the terminal — →
      **Focus**. Then Focus (or Details) where it was not first, the **editor** button, and
      **more** at the right. **The menu draws what applies to the state**: on a `closed` card,
      and on any card whose pane is gone, *more ⋯* holds Message… (a closed record's mail is read
      on its resume, §4.10), Restart where the record is restartable, and Forget (not on a seat
      the definition names, which is never forgotten here) — not Wrap up, Kill, Close, the mode's
      toggle, Open shell here, Pop out or Copy tmux command, which act on a process or a pane
      that is not there. Left out, not dimmed: dimmed is for a control that applies and is
      refused for a reason worth a hover, and *the process is gone* is already the pill. **How
      long a closed card stays** is said where the card says it is closed: the slot's hover reads
      *closed … at <time> · forgotten by itself a day after the close* (`CLOSED_KEEP`, §4.4), and
      the Details page's banner says the same beside its Forget. **Resume** stays on that banner
      and off the card: a closed session is the person's *done* (§4.2), and resuming one is the
      rare road back; a supervised record's Restart is on the card already (§4.5a **more ▾**).

   **The foot is quiet, and quiet never looks disabled**: the next act is an **outlined** button
   at the text's normal strength, the others are **plain links** at normal strength, and **among
   the foot's controls, *dimmed* means disabled and nothing else** (a gone controller's chip, a
   stale reading and an unreachable card are dim for their own reasons; none is a button). The
   only **filled** button a card carries is **Allow**, on a *needs you* card, where loud is right.
   **The editor button is the person's**: label and link come from the person's UI configuration
   (§5 *The person's own*) — VS Code by default, another editor, or none, which removes the
   button from every card and from Focus.

   **An ending is said once per place**: the pill says the **state and nothing else** — a session
   that declared itself out of work is still `idle` (*idle · unseen* until a person has looked,
   §4.2), since a declaration is not a state (§4.9a); the slot says how it ended; the caption
   says *ready to close ✓*; the button does it. There is no grey *finished* pill.

   **One composed pill, as *idle · unseen* is: a seat with nobody in it reads *on call*** (TD-097;
   trigger seats TD-098). An `exited` or `closed` record that the team definition names as a seat
   (§4.9b; by name, as `teamrun.wound_down` keys, never by role; keyed on `teamrun.seat_ids`) is
   drawn with the grey pill *◇ on call*; the state stays `exited` or `closed` in every payload;
   the slot says what would make it come — *on call — comes on the next question*, *on call —
   runs after 10 PRs*, *on call — runs every 6h*, *on call — comes when a member needs a reading* (a manager on call, §6 rule 3 `team`), from the seat's trigger, with the tick's count toward a `prs:` trigger after it
   (*· 4 of 10*, from `seat_count`, §6 rule 3 — nothing when there is no reading, never *0 of
   10*); a seat at the fill ceiling reads *fills exhausted · 6 in 1 h* instead, an ending; the
   caption is *last came · `<age>`* (*last ran* for a trigger seat) from the record's `since`;
   the report is the record's own report line (*3 answered*, *2 filed*); the foot's first button
   is **Message…** (the same control as *more*'s and the Focus header's, §4.5a) — asking it is
   how it comes — then Details, and never Forget or Close session while the definition names it.
   A filled seat is an ordinary card in its live state. The team's header counts them apart: *2
   on call*. Not *exited*, *empty* or *available*: the first looks like a failure, the other two
   like something the person has to do.

   **One composed pill more: an `idle` session that waits on someone reads *waiting*** (TD-418,
   TD-734: a person or another session, nothing else). Teal, its own Agents pill and filter word
   (`state:waiting`), its place in the order after `working`; the state stays `idle` in every payload
   (§4.2 *Waiting*). The pill's reason is the slot's ending and its hover: *waiting · review #1302
   with the techlead* while the reader holds the author's ask for that PR — an open PR no reader
   holds is no wait, and its author reads `idle`; *waiting on you: TD-222* (the **waiting** mark,
   §4.5a: an open `ask` or `steer` to the person whose `about` names a reference,
   `work.waiting_of`); *with the techlead* is read from the seat's `prs_waiting.asks`. So **idle
   means nothing of its own is running and nobody else holds it**, and an idle member whose lane count is solid (§4.5a *card: compact*)
   is the one to look at. *idle · unseen* wins over *waiting* on an interactive session that
   waits: it is the person's cue to go and look, and the slot still says the wait. **An `idle`
   session with a live subagent or a background shell reads *working*** (§4.2 *Working on its own*, TD-761): the green pill, ranked
   and filtered with `working` (`state:working`), its ending *working · 2 subagents* or *working · 1 shell*, in §4.2's one
   order; it stays `idle` in every payload.

   **The page names a seat by its role, never by its function** (TD-418): where a flow's reader
   is a seat the page says *the techlead* — the seat's role, as its card is titled — in *waiting ·
   review #1302 with the techlead*, the header's *PRs waiting* hover, Settings' *the techlead's
   queue past its bound*; a reader that is the person is *you*. `reader` stays the word of
   §4.9b, the records and the code.

   Nothing on a card carries a second **state** age: row 2's clock is the only one, and an ending
   is dated by it, never in the slot — a `doing` line's *says · `<age>`* caption (§4.8) is the
   line's age, not the session's. **Inside a team's own group a card drops what the group says**:
   its `team` badge, and *under `<manager>`* when that is its only controller; outside one — *No
   team*, a filtered or flat grid — both are drawn, and host / repo leads row 3. **The team's
   header** is one row (TD-418): the team, the host its sessions share (the repo is the heading it
   sits under, §4.9 *The Org page*: project → repo → team, TD-722), the flow chip, the team's marks and its controls, and the counts by state while it is
   folded (§4.5a *team groups*) — and **not** its manager's name, state or
   report, which are on the manager's card, the first in the group. The *No repo* section, and a
   repo's no-team strip, are headed by their count and nothing else.

   **Colour (tokens, both themes, contrast checked):** *working* is **green** — alive; *idle* is
   **blue** — alive, at rest, and may be spoken to; *idle · unseen* is idle's blue with its own
   glyph and words — `idle` in every payload (§4.2); *waiting* is **teal** (`--waiting`) — at rest
   on someone else's move, `idle` in every payload as *idle · unseen* is; everything over or out of
   reach (*exited*, *closed*, *unreachable*, which keeps its dimmed card) is one grey, each with its
   own stylesheet rule; *ready to close ✓* and *closed by you* are the neutral text colour with a
   grey rule, so **on a card green means working and nothing else** (Focus's checklist keeps its
   green ticks — a different thing on a different page); the card has no `--done` token; amber
   *needs you* (ringed) and red *stalled?* are the loudest things on the page, and *limited* keeps
   its violet. Blue is also the accent for what is new (unread, *new* mail): an idle card with
   unread mail is blue twice, at rest and spoken to. The legend (`docs/mockups/gen.py`, *States &
   badges*) follows the tokens.

   **One order, no control.** Inside a group: the manager's card first, whatever its mode; then
   by urgency (`needs-you` → `limited` → `stalled?` → `unreachable` on a non-volatile host →
   `working` → `waiting` (§4.2) → unseen `idle` (§4.2) → `idle` / `unreachable` on a volatile host →
   `exited` → `closed`); within one urgency — one value of the rank the server sorts by — an
   `interactive` session ahead of an unattended one, so the key is **(rank, interactive first,
   name)**; a worker that needs a person still outranks the person's own idle session. Between
   groups, a live team with a `needs-you` session sits above the other live teams. A `needs-you`
   card is ringed and counted in the page header. There is no **Urgent first / Pinned** toggle:
   team cards arrange the page, and the place to work through what needs a person is the Inbox.

   **The keyboard (TD-124).** Every act on the grid has a key, and the key is the button pressed:
   `j` / `k` move **the ring** — keyboard focus, drawn as a focus ring on the card, apart from
   the amber *needs you* ring — through the cards in the order above; `g` then a team's initial
   or a group's number jumps between teams; `Enter` opens the ringed card's Focus, `Shift+Enter`
   pops it out, `a` / `d` answer its permission; `1` / `2` / `n` are the pages and the New session
   form, `/` the filter, `?` the overlay that lists all of it. Single keys, live only while
   nothing editable has focus, each naming a control of §4.5a (its **keys** rows); the mouse
   loses nothing. No chords and no remappable map.

   A **Due** strip above the grid lists the dev-cadence board items overdue or due today, each
   with Snooze and Done (agent write-back, §4.4); collapsed to a count when empty. Unreachable
   hosts get one banner row. Command-kind sessions are hidden unless the filter carries
   `kind:command`. **+ New ▾** holds **Session**, the form, and **Shell** (host + directory,
   nothing else), and on Focus, **Open shell here** (a shell in the same directory as the session
   being viewed, its Focus opened in a new tab or, as Pop out opens one, a window — never in place
   of the page it was pressed on; §4.5a *Focus: Open shell here*, TD-577).
   **The Org, team-first (TD-176).** The unit a person watches is the team, and the questions are
   the team's: is anyone stuck, is review keeping up, what waits on me. So the Org leads with a
   **rollup**, each team's card carries a **summary**, and a team member's card is **compact**;
   the full six-row card above stays for the sessions a person drives alone (a repo's no-team strip,
   and *No repo*). **Teams sit under their repo** (TD-722, §4.9 *The Org page*): project headings,
   a repo's line carrying its **Repo facet** once, then its teams' cards,
   so the Repo facet below is the repo's line's and a team card carries the other two. Rendered:
   `docs/mockups/reviews/2026-09-26-org-team-first-design.png`; the artboard is
   `docs/mockups/OrgTeamFirst.dc.html`.

     rollup*): **Agents (n)** — every state's count as a plain coloured pill, *needs you (1)*,
     *working (5)*, *waiting (1)*, in the grid's urgency order, the count in parentheses after the

     **TDs in motion (n)** — a stacked bar by phase (below) with a legend; **PRs in motion (n)** —
     the window picker (day · week · month) and two sized blocks, *opened* and *closed* in the
     window, with the open count and how many wait on review under them; **Needs you (n)** —
     *answer needed* (a permission or question standing in a member's pane: what stops a session

     teams, drawn only while one is open: a question that waits in the mail) and *in the Inbox*

   - **A team's card**: the header, one row (name, `host / repo`, the flow chip, ✉ n, *answered for
     you*, the **spend** figure — the team's seat-ledger figure today, `≈$41 today`, a link to screen
     13 on this team (§4.5a *team card: spend*), absent while the team spent nothing today — Wind down / Stop now, the fold with the session count, the ***i*** whose panel holds the
     definition) — no state chips, the member cards say it — then **two facets**, TDs in motion and
     Answer needed / Doing, then the members; the **Repo** facet, described here with them, is drawn
     once on the repo's line above the repo's teams (TD-722, §4.9 *The Org page*). **Repo** (§4.5a *team card: Repo facet*): the repo's name, a link to its page;
     **Technical debt (n open)** with its own selector *open · day · week · month* — on *open* two

     other — the numbers inside and a legend under; what of it the team's lanes take and whose
     the rest is, §4.4 *In a team's lanes*, is an ***i*** beside the heading, and each member's

     **Pull requests (n open)** with the window picker and the two blocks; under them the oldest

     **phase**, its priority as a letter, the reference, the entry's title, the member, its PR when

   **Focus watches (TD-096).** Typing into an unattended session lands in the middle of its
   work, and nothing tells its manager. So on every `unattended` session, whatever its state,
   Focus opens **read-only**: the bridge does not forward keys (the rule is the server's, in the
   attach, not a client setting — a read-only attach drops key frames and passes only resize and
   scroll), the composer is closed, and a grey line over the terminal says so. What stays is
   every act on the record that is not a keystroke: Allow / Deny (a permission is answered
   through the hook, never the keyboard), **Message…** (mail types nothing), Wrap up, Kill, Open
   shell here, the side panels, and **Copy**, which reads the terminal's selection. **Paste** is
   inert on a read-only Focus, since it goes through the terminal as keys do; the page says so
   where it would have pasted. **Take over** is one press: it flips the session to `interactive`
   — §4.5a's mode toggle, under the name of what it does — and re-attaches with the keyboard, so
   that from then on nothing else types beside the person: a controller's `send`, `keys`,
   `kill`, `close`, and the `create` a restart is, are refused on an interactive target (§9
   invariant 5), and the policies leave it alone (§6). It changes nothing else on the record: a
   stop time, a sent wrap-up, an `out_of_work` or `restart_wanted` declaration stay written and
   are simply not acted on while the person holds it. **Hand back** flips it to `unattended`
   again and the attach returns to read-only; its manager's next round and the policies' next
   tick pick it up as any member, with whatever is on the record — except a stop time that fell
   due while the person held it, which Hand back clears (a deadline that has passed is not one;
   the page's second call is `set_stop` with no time, and its hint says so). A stop time still
   ahead stays. A manager never infers that a member was disturbed: it reads the mode, a field,
   and an `interactive` member is left alone and is not a crash, a stall or a lapse. The attach
   reads the mode once, when it opens, and the page re-attaches when the feed shows the mode
   change — its own press or another tab's; the host agent pushes a `set_mode` at once, as it
   does a `set_stop`. On a phone, Focus is the same page, and Take over is the same one press. An
   `interactive` session sees none of this.

   widget in the page: alt-tab, tiling, a second monitor, and a pane that stays on screen while
   another is looked at. So a Focus can be **popped out** into its own browser window: the Focus

   session and nothing else. The header, the composer, the side panels and every act Focus

   `window.open` by name is the whole mechanism. Its size and position are the person's,
   remembered per session in the browser as a team's fold is, defaulting to a window that fits a
   100-column terminal; nothing about a window is written to the record. **The title is the
   point** — it is what the switcher shows — so every Focus, popped out or in a tab, is titled
   `<name> · <state>` (`AO.focusTitle`, set at load and on every pushed delta), the name first,

   browser's. A window whose session exits shows the exited banner and its Details as a tab

   mail rows' **Dismiss** is not offered: a board line is closed on the board. Among the
   section's rows it sorts by the answer's date, oldest first. It leaves the section when its
   line is closed, as any board line is closed. **It comes back when nobody has acted for
   `BOARD_WAIT_DAYS` (3)** civil days after the answer's date — the `decided` date, or the last
   reply's — measured against the reader's `today`: to where it would be drawn unanswered, which
   for a decided item is *Needs you*, counted (the reader's rule makes it due under every mode),
   and for a replied one is *Needs you* when it is due and the board's horizon when it is not.
   The row then says so — *decided Oct 3 — no session has acted in 3 d*, or *replied Oct 3 — …*
   — with the board row's controls: a work order nobody picks up is the person's to notice, a
   session to start or a line to close. A further Reply is a new answer, and the days start again
   from its date. **The line on the board is untouched by all of this**: it stays open and due as
   its session's work order (cadence §3.5), the reader still lists a decided item first for every
   session started in the repo, a decide still wakes nobody (§4.4), and where the Inbox draws the
   row is the whole change. A reply that reached a live lease holder is also that holder's debt
   (§4.10 *A board reply owes an outcome too*), a row of its own in the same section: the note is
   the holder's, the board row is the line's. **No mail row needs the same cure**: an `ask` or a
   `steer` is closed by its answer and is then under *Waiting on them* or FYI; the two that stay
   counted after an answer — an asker that exited without reporting, and a `blocked` outcome —
   are counted on purpose (§4.10 *Outcomes*).

   **What is snoozed is in none of the three sections and in no count until its time** (§4.10
   *Snooze*), in the **Snoozed (n)** fold under the sections — a sub-heading with *back on their
   dates · not counted* beside it, closed by default, soonest first, the shape of the board's
   *Not due yet*: each row as its kind draws it, with every control its kind has and *snoozed
   until <t>* on its line, its **Snooze ▾** picking a new time with *now* among the choices; a
   press that answers, closes or dismisses the row ends the snooze with it. There is no
   **Unsnooze**: a snooze is a date, as a board item's is, and never a way to lose mail. One row
   per thing with the controls of its kind in place (§4.5a) — **one row renderer per kind**, so a
   kind joins a section without touching the rest. A mail row carries its sender's name and the
   `team` its envelope carries; a state row is built from the card's own view (its pill, `title`,
   `doing` line, team and role badge); both carry **Open** to Focus on the session that needs the
   person, while that record still exists. **The rail** (below) narrows every section — a state
   and a message carry their session's `team` badge; a board item carries its repo, which the
   rail's **Repos** group narrows by, and a team pick narrows to the team's repo (§4.5a *the rail*,
   TD-722) — and its **find** box matches every word typed against a
   row's whole visible text. The Org keeps every needs-you mark it has: the Inbox is a second way
   to the same things, not a replacement. Nothing on the page is built from text a session wrote
   except as text — a rendered message is text, from a closed markdown subset and the UI's own
   renderer, and a link to an outside host is the one pressable thing it may make, drawn as one
   (§4.10): a suggested answer is a structured field of the envelope, never parsed out of a
   message.

   States and mail are split into sections by one server-side function, `inbox_sections`, which
   renders the page on load and on the poll, so the top bar's number and the page cannot
   disagree; the whole message is on the page with no scroll box — its first paragraph drawn, the
   rest one press away under *details*. The poll is **a person's read of the person inbox, which
   marks nothing** (§4.10), so the page refreshes every few seconds without emptying the depths,
   which count what is unread *or* open. State rows come from one fresh `list` on each render,
   since the pushed stream is per record and this page is per person — a row whose state changed
   between polls is corrected by the next one, and a permission answered here leaves at once.
   **Board items** are the host agent's reading (§4.4 *Each reading has one owner*, TD-614): the
   page reads `boards` from the `repos` RPC and runs no reader of its own. That reading parses them
   **in-process through `ledgerboard.py`** ([ADR 2026-10-12](../decisions/2026-10-12-ledgerboard-dev-cadence-shiftlead.md);
   TD-584, built by TD-585) — every open item of each board the roster's repos declare (§5
   `board:`; the page sorts what is due, *The board's horizon* below), parsed by the one module
   the formats have, never by a dev-cadence script and never by a second parser; each item's
   `session`, `host`, `refs`, `answers`, `decided` and detail block are fields of its record —
   at most once a minute and off the page's loop, and read again at once after a Snooze, Done or
   Reply; each due item is a counted *Needs you* row (its
   repo — written *ContractMatch · samscrape* where its project has several repos, and no team
   badge, since the board is the repo's (TD-722, built by TD-741) — its due words, the whole text as text, **Open board** at
   its line, and its sender's standing — *still on TD-122*, *moved on*, *gone* — so a reply's
   destination is known before the press) whose **Snooze ▾**, **Done** and **Reply** are §4.4's
   write-back. A reader that fails is said in a note above the rows, never shown as a clear board.

   **The board's horizon (TD-207).** What the Inbox shows of a board is a setting, and the page
   says which is in force. **The read** is every open item — one read, at the same cadence —
   and the page sorts each item by the `due` its record carries against today, through
   ledgerboard's `(item, today)` functions: no second parser, and no second read. **Due now** is the same under every
   mode: an item due today or earlier is a counted *Needs you* row, and no mode hides one — *past
   due* counts today, since a line dated today is one the person was meant to see today. **The
   mode** is `person.inbox.board_show` (§5), one of four, and it decides which items that are
   **not yet due** are drawn:
   - **`next:<n>`**, *the next n per repo* (n from 1 to 50; **the default is `next:10`**): for
     each repo's board, its n soonest open items, whatever their dates, the due ones among them,
     so a board with twelve due shows twelve and none ahead, and one with two due shows eight
     ahead. A board is the repo's and is counted once, whichever teams work the repo (TD-722);
     the setting keeps its word `next:<n>`.
   - **`due`**, *only what is past due*: nothing ahead.
   - **`<n>d`**, *due within n days* (1 to 365): what is due and what falls due inside the
     window; `7d` is **due this week**, the name the pick gives it.
   - **`all`**: every open item.

   Three kinds of item stand outside the dates. An item with **no date** sorts after the
   dated ones: it is shown under `all`, takes a place under `next:` once the dated ones have
   theirs, and is hidden under `due` and `<n>d`. A **decided** item is a due row whatever its
   date, as the reader surfaces it: it is drawn under *Waiting on them* while it waits on its
   session, and is this due row again after `BOARD_WAIT_DAYS` (*A board item the person answered
   waits on them*, above). An item whose date could not be read (`due_error`) is a due row too,
   and takes none of the n places.

   **Coming up** is what the mode draws ahead, in *Later* (the section, above) under a plain sub-heading,
   **Not due yet (n)** with *shown by your board items shown setting · not counted* beside it —
   the setting's name a link to Settings → You, so the heading says both what these are and why
   they are here — soonest first: the same row and the same controls (Snooze, Done, Reply, Open
   board), its due words *due in 6 d · Oct 4*, drawn in the quiet colour a not-yet-due thing has,
   and **counted nowhere** — not in the section's count, the top bar's number, the rail's *Needs
   you*, the Org rollup's *m overdue* (`overdue_n`) or the Due strip when it is built, all of
   which keep meaning *due now*. **The fold holds what the mode hides**: **not shown (n)**,
   closed, under the rows; opening it draws those items for this page view, in this browser, and
   changes no setting. Neither is a section, and the rail's *Urgency* group lists neither; the
   rail's *board items* kind counts the board rows on the page as every rail count does — the due
   rows, the ones coming up, and the fold's once it is opened — so the first paint's count and the
   page's own agree. **The line** closes the board rows whatever the mode, and is the page saying
   its mode: *showing the next 10 board items per repo · 14 not shown, the next due Oct 12 — show
   · Settings*; with nothing hidden, *showing the next 10 board items per repo · nothing hidden*;
   under `due`, *showing board items that are due · 5 not shown, the next due Oct 4 — show*;
   under `7d`, *showing board items due this week · 3 not shown, the next due Oct 12 — show*,
   and under another number of days *due within 14 days*; under `all`, *showing every board
   item*. Whatever the mode, nothing hidden reads *· nothing hidden* and draws no fold. **show**
   opens the fold; *Settings* is a link to the **You** card. An item whose date the reader could
   not read (`due_error`) is a due row with the reader's words, never hidden by a mode. The Repo
   page's *Waiting on you* (screen 11) is the same rows filtered to the repo, the rows coming up,
   the fold and the line with them. **The sessions' word**: the grinder preset says that a
   summary or a message naming a board line says *on the board, due <date>*, and that a line the
   person should see today is dated today — so *left for you* never sends the person to a page
   that does not draw it.

   **Boards are read against origin (TD-208).** Every board line a session writes reaches origin
   by a merged PR, and the registry's roots are main checkouts that move only when someone pulls,
   so the read is **against origin**: the host agent fetches the repo's default branch (hang-proofed,
   pruning nothing; it moves the remote-tracking ref and no local branch or working file) and, where
   the checkout's board is **merely behind** — untouched here since the merge-base, moved on origin —
   reads the board from `origin/<default>` (`sessionorc.workorders`, in-process through ledgerboard,
   built by TD-585 slice 3; no dev-cadence script runs). Whether a
   board was read from origin is the reading's `source` field, and what the compare found is
   `fetch_case` — *skipped*, *none*, *matches*, *behind*, *local* or *both* — beside its sentence,
   `fetch_note`, and `fetch_why` for a skip; the page chooses its note by `fetch_case` alone (TD-585
   slice 5) and never draws the sentence — a skipped fetch's note names `fetch_why`.
   **The read is the host agent's** (§4.4 *Each reading has one owner*, *The boards*; built by
   TD-615): origin's side is fetched on the repo reading's `REPOS_EVERY` pass — a fetching read
   stopped at its bound (45 s) reads the checkout's board under *fetch skipped (timeout)*, so a dead
   remote costs the origin view and never the board — the checkout's is read again on `BOARD_EVERY` when its file or the
   day has moved, and **a press** — Snooze, Done, Reply, Decide, *Put on the board* — is read again
   by the host agent before its RPC answers, from its own tree (origin's head with the press
   landed) under the *behind* note. The page draws the reading the `repos` RPC gives and reads no
   board itself, so no page waits on the network. A reading that failed keeps its last items, and
   the note above the rows says which board, since when and why.
   What the read against origin found is said, by board, in **one note above that repo's first board row**
   in each list the page draws (*Needs you*, *Not due yet*, the *not shown* fold, the Repo
   page's *Waiting on you*), drawn as text; the phrases are one table in the code, and a test
   fails on a phrase the read writes that the table does not know:
   - *matches origin*, or *no board on origin*: no note.
   - *behind*: *read from origin/main: this checkout has not pulled it yet* — nothing is hidden;
     the note's tail is the pull's standing (§6 *Pull*): *— the host agent pulls it once `<name>`
     is idle* (the occupant it waits on; *once it is idle* when it cannot read the occupant's
     state), *— it could not be pulled: <git's reason>*, *— pulling is off for this repo*, or no
     tail when the pass has not reached the repo yet.
   - *local edits not pushed*: *board edits made here are not on origin* — nothing is hidden;
     the rows are the checkout's.
   - *both sides changed*, or no common history: *this checkout's board and origin's have both
     changed: showing the checkout's, and what origin added is not shown — pull* — drawn in the
     warning colour, since rows are hidden and the page must not look clear when it is not.
   - *fetch skipped*, or the read stopped at its bound: *origin could not be reached (<the
     reason>): showing the checkout's board as of its last pull*.
   **Every row is actionable, whichever file its board was read from.** The write-back edits
   origin's line and not the checkout's (§4.4), so a board read from origin is exactly the file it
   will edit, and a board read from the checkout holds the same lines unless the checkout is ahead
   — then a line origin lacks is refused by the write-back, which says so. **The host agent
   pulls**: a checkout merely behind is fast-forwarded by the home's tick when git allows and the
   anchor session is idle (§6 *Pull*), so *behind* is a passing state and its note says when it
   will pass; a checkout ahead, or on another branch, is the person's as it was, and the note says
   that too. **Not covered**: a board that exists on origin and not in the checkout at all (the
   read names the boards it finds on disk), and `ao repo`'s due count (§4.7), which stays a read of
   the checkout.

   **Layout (TD-082; mockup `Inbox.dc.html`).** *The page is one centred column*, 1100 px at
   most: a queue reads in order, top to bottom, and a message's text runs the width of its row;
   not a grid of rows, which breaks the order. *A section is a heading, not a box*: its name, its
   count, and an **i** mark holding the paragraph that says what the section is — a tooltip on
   hover and focus and, pressed, opened in place under the heading, pushing the rows down rather
   than covering one; the browser remembers which are open; the page has no closing paragraph. *A
   row is a card*: its own surface, a hover state, and a focus ring — a row is a tab stop, and its
   controls follow it in tab order — and `j` / `k` move that focus row by row, `Enter`, `a`, `d`,
   `r`, `s` and `x` pressing the ringed row's own Open, Allow, Deny, Reply, Snooze and Dismiss or
   Done (§4.5a **keys**). What says *what a row is* — the state pill, the kind label (`ask`,
   `steer`, `outcome · blocked`, `trail`) — is flat and unbordered and is never a control;
   everything bordered is one (a state or an alarm mark must never look pressable). A session's
   name is printed once: the tool's own title is left out when it only repeats the name. **Times
   never draw as a placeholder**: an age and a time left are durations, which need no time zone,
   so the server renders them in words (*18m ago*, *21m left*) and the page's script only keeps
   them moving and adds the local clock time on hover. **FYI's fold is its heading**: the section
   is a native disclosure, its heading line the toggle, with the disclosure's own unbordered ▾
   before the name and no second fold control anywhere; an FYI entry newer than this browser last
   saw is marked *new* (the browser's own memory, as the fold is — nothing on the entry or at the
   home changes, so reading still changes no row) — the same comparison that opens the section by
   itself (§4.5a *the FYI count*), a mark and never a control. None of this adds, removes or
   renames a control of any row.

   **A control answers the press** (TD-338). Three rules — the first about a control, and so every
   page's; the other two about a row, and so this page's. (1) **One look for every bordered
   control**: `.btn` and each of its variants share the pointer's hover (the `--hover` wash on a
   bordered or a ghost one; a filled one a shade darker), the press (sunk — an inset shadow and the
   darker shade — for as long as the button is held) and the keyboard's `:focus-visible` ring (the
   row's own, `--link`, 2 px); a variant differs in its colours at rest and in nothing else, so a
   ghost Open and a plain Done read as pressable the same way, and a disabled control keeps its
   dimmed look and takes no hover. (2) **A press answers in the same frame**: before its request
   leaves, the pressed control and the rest of the row's are disabled and the row is marked
   **pending** — dimmed, `aria-busy`, its age giving way to the control's own verb under way
   (*checking off…*, *snoozing…*, *dismissing…*, *sending…*, *suspending…*, *deciding…*; one table
   in the page's script, §4.5a); a control that opens a composer first (Reply, Not right…, Put on
   the board) marks the row once the composer sends. (3) **A row whose press takes it away leaves
   on the press**: Done, Snooze, Dismiss, Delete, Allow, Deny, Go with it, Restart and Resume take
   their row out as the request leaves, the ring handed to the next row, and the toast says the
   press was taken and the landing is under way — *checking off — landing on the board…* — **a
   toast that waits**: it has no clock until the answer comes; the answer rewrites it (*checked off
   — landed on the board on origin*) and starts its clock, and a refusal rewrites it as the failure
   in the server's words, while the next refresh draws the row back where it was, carrying *not
   checked off: <the server's words>* on its own error line (the one a mail row's refused write
   already has) until the row's next press or the page's reload — nothing at the home holds it.
   **Suspend** and a board **decide** keep their row (§4.8a; §4.4 *Decide*): pending in place,
   then redrawn by the answer. The keys press the same controls and get the same answer (§4.5a
   **keys**). The feel is the page's, and nothing at the home changes: the board write-back stays
   one request, open from the press to the commit's landing (§4.4; `BOUND`, 40 s) — the row is
   gone at the press already, and a failure reaches the person the same way whether the request
   waits for it or a later event reports it, so the home records no landing in flight and the
   Inbox gains no row kind for one; a tab closed mid-landing changes nothing, since the host agent
   finishes the commit and the next poll draws what the board says.

   **The rail (TD-129; mockups `Inbox.dc.html`, `InboxRail.dc.html`).** Left of the column,
   sticky, 200 px, starting under the title — *Inbox* has the top line to itself, and the rail's
   head lines up with the first section heading: **Clear filters**, the find box, then three groups
   of toggles. *Urgency* — the page's own sections in the page's order, each with its count; the group is named for what orders them (needs you, on a clock, waiting on them,
   none), not *Sections* nor *State*. *Teams* —
   every team a row on the page carries, then *no team*, each with its **Needs you** count, since
   *which team needs me* is the question the rail answers at a glance. *Kinds* — the coarse kind
   of a row, each with its count: *questions* (an `ask`, a passed-up question), *steering* (a
   `steer`), *session states* (the state rows — a permission, a question, `limited`, `stalled?`, an
   exit with unpushed work, a restart, an alarm, a promote), *board items*, *notes* (`note`,
   `system`, replies, answered-for-you, outcomes), *trail*. Every line is a toggle, and the rule is
   the one every faceted list uses: **within a group the picks are OR'd, across groups AND'd, and a
   group with nothing picked means all of it.** So *grind* alone is the whole queue for one team;
   *grind* + *FYI* is that team's FYI; *Needs you* + *questions* is what a person owes an answer to,
   any team. **Every count is a count of rows on the page now** — the rows that pass every pick and
   the find — so the numbers never disagree with what is drawn: a picked line reads its share of
   the page; an unpicked line in a group where something is picked reads *0*, dimmed, because it
   contributes nothing until pressed; an unpicked line in a group where nothing is picked reads its
   share of the page under the other groups' picks, which is what it would keep if pressed alone;
   never the mail-client convention, where a line's count is taken under the *other* groups' picks.
   **Every count on the page is written the same way: a plain number while nothing is picked or
   typed, and *n of all* while anything is**, on every rail line and every section heading alike,
   *all* being the line's count with no filter at all, so one glance says a filter is on and what
   it hides; a line that reads *0* stays, dimmed, so a pick can be undone and its *of all* says
   what pressing it would bring. The case the rail is shaped for: press a team, work its *Needs
   you* rows until its count reads nothing, press the next. A section not picked is not drawn; a
   section picked and emptied by the other groups draws its heading and its empty line: the
   queue's order is the page's one layout rule, and a filter shows or hides rows, never re-orders
   them. **The top bar's number is never filtered**: it stays *Needs you* whole (§4.5a), which is
   the *all* of the rail's *Needs you* line; the page's title row is the word *Inbox* alone, and
   what the number counts and how it differs from the Org's is the rail's *Needs you* line's
   hover. One press clears — **Clear filters**, always in place at the rail's head and disabled
   while nothing is picked or typed, so the toggles never move under the pointer on the press that
   filtered — and it empties the find box too. The picks are the page's URL —
   `/inbox?team=grind,none&sec=needs,fyi&kind=questions&find=…` — so a filtered Inbox is a link
   and `Back` undoes a press; the browser remembers the last picks for a bare `/inbox` and writes
   them back into the URL (`replaceState`), so a link copied from the bar is always the page as
   seen. A row's team badge is the same press as the rail's line for its team; there is no typed
   `team:` syntax, since a filter that is a control is not typed. The counts come from
   `inbox_sections`, the split the page and the poll already read, computed once per render over
   every row, so the rail, the headings and the top bar cannot disagree; TD-131 names a rail over
   thousands of entries as the size that would move the counts into a store. Not a tree (*All*,
   then each team, then its sections as leaves): its leaves would be the page's headings a second
   time, and flat groups reach every leaf in one or two presses and keep the order.

   **Find (TD-129).** The rail's box. Every word typed must match, in any order, as a substring of
   the row's whole visible text, which the server lowercases once into `data-find` on every row
   kind — a mail row's sender, team, kind, `about`, PR and text; a state row's name, pill, title,
   `doing` and its explanation; a board row's repo and text; a trail row's name, kind, `how` and
   text; the identity-alarm row's host and alarm words — and a word that is a number also matches
   `#` before it (*517* finds *#517*). A match inside a folded section (FYI, the Snoozed fold)
   unfolds it for the duration of the find and folds it back when the box empties, unless the
   person had it open; the count beside the box reads *n of all*, and holds its line while empty,
   so the first word typed moves no toggle. **The find is a fourth group with one pick, AND'd
   with the rail's**: *guardians* pressed and *jeff* typed shows the
   guardians' rows that carry *jeff* — *jeffrey* among them, a word matching as a substring — and
   the rail's counts follow the find as they follow every other pick. Nothing is written: it is the
   browser's filter over the rows it has, and the poll re-applies it. `/` focuses it and `Esc`
   leaves it.

   **The message page (TD-129; mockup `InboxMessage.dc.html`).** `/inbox/<id>`: one mail entry,
   whole. Reached from a mail row — its text is the link, and `Enter` on the ringed row (*keys*,
   §4.5a) — and from a trail row's *re*, which names the entry it closes. A state row and a board
   row have no page: a state is the card's and a board item the board's, so their **Open** and
   **Open board** stay what they are. The page is the same centred column, in three parts, in this
   order — the answer under the message, the thread after it, so nothing scrolls unless a full
   review of the thread is wanted. At its head **Back** (and `Esc`), which returns to the list at
   the same row, ringed, with the filters as they were — the list's URL travels with the page.
   **First the entry**: its subject as the page's heading and the tab's title, *<subject> · Inbox · ShiftLead* (§4.10 *A subject on every entry*), its head as on its row (sender, team, kind, `about`, `pr` as a link, age,
   and `answered` by whom and when once it is closed); the text whole, in §4.10's shape (first
   paragraph, then *details*, open here, since a page is for reading). **Then the answer**: the
   row's own controls again, the same RPCs and the same confirms, the suggested answers in their
   dashed group, so the entry is answered here and the page returns to the list when the answer
   removes the row from the section it was in. **Then the thread**, under its own heading with its
   count: what the entry answers and what answered it — the question it replies to, the replies it
   drew, the person's own reply among them, the outcome under the question it closes (§4.10
   *Outcomes*), the pass-up with the passer's recommendation (§4.9b), and the `system` notes that
   say what the home did with it — oldest first, each in its own kind's row shape, none of it a
   control built from text. The data is already on the envelope: every copy of a message carries
   `root`, the id of the first `ask` or `note` its chain replies to, and `reply_to`, `outcome`,
   `passed_up`, `recommend` and `closed_by` beside it (`sessionorc.models.MailEntry`). What the
   person inbox does not hold is the person's own replies — a reply lives in the asker's inbox and
   the sender's outbox, and the person inbox keeps no sent list (§4.10) — so the thread is gathered
   **at the home, by `root`, across the person inbox and every record's inbox and outbox**, one
   entry per id, by a person-only read that marks nothing (`thread`, §4.7; the person is a party
   to every thread that reached their inbox, and a thread that went through a techlead first is
   read back to its start). It reaches as far as retention keeps it: an entry pruned from every
   mailbox is a gap the page says in one line (*earlier entries pruned*), never a blank. `j` / `k`
   on the page move to the next and previous entry of the list as it was filtered, so a team's
   questions read one after another without going back. An entry retention has pruned reads
   *gone: pruned <t> ago* with **Back**, never a blank; one another host holds reads the refusal
   in words (§4.4a). The page marks nothing read: it is the person's read, as the list is (§4.10).
   No preview pane: at any width the entry opens as its page, and the pane, if it is ever wanted,
   is this page drawn beside the list.

9. **Transcript** (`/transcript/<id>`; mockup `Transcript.dc.html`): **a read of what a session
   said and did, without resuming it.** A resume is the wrong tool for reading: it creates a live
   session and a record, it is a lifecycle event a manager may act on, and it has to be closed
   again. The transcript is a file on the session's host that its adapter already locates
   (`transcript_path`, §4.3); reading it is a read, gated by nobody (§9 invariant 11). **The page

   sent, drawn as the pane draws it (`>`), the assistant's text in full, each tool call collapsed

   and a thought as one folded line (*thought · n lines*) where the file holds any. The turns of a
   subagent (a sidechain — §4.2a's rule for the model in use already tells them apart) are not the
   session's and are folded under the Agent call that started them, with their count. A compaction
   is one line where it happened. Nothing else in the file is drawn: the tool's bookkeeping lines
   (mode, title, snapshots, the hook attachments) are the tool's, and the raw file is a press away.

   use (§4.2a) — and what it is: the file's path on its host, its size, the first and last
   timestamps, the count of turns shown (the read goes backwards from the end and never counts the
   whole file, so *the last 20 turns* is the count, growing with each *earlier turns*). **Beside
   the head**: **VS Code**, the editor button's link (§5 *The person's own*) pointed at the file
   rather than the directory — the raw file's reader, which the Focus header also offers beside
   **Transcript** (§4.5a *Focus header* **‹› VS Code**, TD-578), so a live session's whole file is
   in the editor one press from its terminal. The page opens on the **last twenty turns**
   and offers **earlier turns** above them, twenty at a press, read backwards from the file by byte
   offset, so the transcript of a long run costs what is read and no more; a live session's page
   is a snapshot at the moment it was opened, refreshed by the browser's reload and by nothing else
   — the terminal is the live view, the transcript is the record. **Everything on it is text**:
   the only controls are the folds, *earlier turns* and VS Code; nothing a session wrote becomes a
   button. Reached from the Focus header on **any state** (§4.5a *Focus header* **Transcript**) —
   a live worker gone quiet is read here rather than resumed or sent to — and from each Resumable
   row (screen 4, phase 4). Absent where there is nothing to read: a record without a tool session
   id (a `shell`, a command run, a session whose hook never reported one) offers no Transcript, and
   `ao transcript` says which. **The adapter renders, the core draws**: `read_transcript` (§4.3)
   turns the tool's file into a neutral list of entries — a prompt, text, a thought, a tool call
   with its result, a compaction, a sidechain group — and no field name of the tool's leaves the
   adapter, as no usage field does; the page, `ao transcript` and the `transcript` RPC read only
   that shape, so a second adapter's transcript draws on the same page. **Where it is read**: the
   `transcript` RPC is served on the record's host, since the file is there; for a node's record
   the home asks the node through `read` as it asks for `tail` (§4.4a *Reads of a pane, and of a
   transcript*: `NODE_READS` is `tail`, `explain`, `log_tail`, `transcript`, and `paths` for the
   pane's file links, §4.6), refused as
   unreachable while the link is down, and the file is never copied to the home. **Which record**:
   the transcript is located from the record's own `adapter_id`, `dir`, `adapter` and `profile`,
   so an `exited` record reads the run it held and a `closed` one left behind by a resume
   (`superseded_by`) still reads its own; the successor's page reads what the successor's tool
   session wrote, which for Claude Code carries the conversation on. Forgetting a record takes its
   pointer with it; the file stays, for the Resumable list's index. The CLI's form is
   `ao transcript` (§4.7).

Security: the UI can type into a shell as you, so it is root-equivalent. **Never a bare public
port.** The UI is reached over the person's own route, and holds no credential beyond the host
ssh keys. §4.5b has the routes and the reasoning; in the order they are offered:

- **Tailscale** — a free account, the client on the home and on the phone, and `ao connect
  tailscale`: `tailscale serve` puts HTTPS on the home's `*.ts.net` name, with no domain, no
  server, and nobody in the middle who can read it — Tailscale vouching for the login (§4.5b);
- **Cloudflare Tunnel + Access** (designed, built when asked, TD-656), for a device that cannot run
  Tailscale — a hostname on the person's domain, reachable from anywhere with a login in front,
  and `ao connect cloudflare`;
- **`ssh -L`**, always.

`ao connect tailscale` sets the Tailscale route up (§4.7); `cloudflare` waits for TD-656. With no
route set, the UI is reached over `ssh -L`. Each route's proxy is pointed at the UI's **route port** (8766), on which every request carries
the identity the route proves and the person's is required (§4.5b *The route port*). Default until a
route is set: the UI binds to `127.0.0.1` — the plain port 8765 and, on the home, the route port 8766, one pair of
defaults that `ao ui`, `shiftlead-ui` and `ao service install` share (`shiftlead.service`), the
unit carrying whatever its install was given — and the laptop reaches the plain port through
`ssh -L 8765:127.0.0.1:8765 kmaster`.

Browser mechanics:

- **Live state** comes over one `/events` websocket per browser tab, pushing per-session
  deltas (state, pending, age, tail, ready-to-close) and host reachability; the page patches
  the DOM by session id. Pages are server-rendered on load and never fully re-rendered after.
  Reconnect with backoff; on reconnect the page reloads its snapshot once, and never in a loop
  (*A reconnect reloads once, never in a loop*, below). **The team groups**
  — every header and the rollup, read over the whole fleet, the costly part of a delta — ride on
  a delta only when it can move a card or a count (`SHAPE_KEYS`: the record's state, team,
  controllers, name, seat or mode, or a record the stream has not seen) and on the stream's
  first, always — a new card is placed by its own delta's groups; any other delta (a pane's tail,
  a context reading, a claim) leaves them to one `groups` event at most every `HEADS_EVERY` (a
  second), not sent when equal to the last one sent. One reading is read and sent at a time, so
  an older one never follows a newer. **The Focus and Inbox pages take a light stream** (`/events?light=1`, Focus adding
  `focus=<id>`): their own session's deltas whole, without card markup; another record's as
  `{id, state}` only when one of `SHAPE_KEYS` or `LIGHT_KEYS` moved (a lane, a report, a claim,
  *unseen*, open work, a declaration: what the Inbox's rows draw), which is what its re-reads key on;
  Focus's own delta again when the record that moved, or went, is one of its controllers or members,
  or was a member until that delta (its members and *under* chip, from the fleet the stream keeps — Focus reads no `/api/sessions`);
  a repo's `repos` push as its root and PR marks alone (`pr_marks: null` for a repo dropped) —
  never the repo's facts, which run to most of a megabyte a push and come every minute; and no groups. **Every stream, light or full, carries `counts`** — the
  top bar's numbers, kept once by the UI process and sent when they change (§4.4 *Each reading has
  one owner*, TD-614) — so no page polls the person inbox for them; and a card's view is computed
  once per delta for every stream, a PR's marks sent once per repo, never per session.
- **Card order**: the server's, per group (§4.5 screen 1); the client re-sorts a group by the
  same key when a delta changes a card's rank. Nothing about the order is stored in the browser.
- **Permission countdown**: the delta carries the deadline once; the browser counts down
  locally. The timeout transition (buttons collapse to Focus) arrives as an ordinary state
  delta, never from the local clock reaching zero.
- **Tail hygiene**: the host agent strips ANSI and control bytes and caps the tail (lines and
  width) before it enters a session record; templates autoescape. Pane output is untrusted
  text everywhere it is shown outside xterm.js.
- **Keyboard focus** on Focus: clicking the terminal or the composer gives it focus; after
  **Send**, focus returns to the terminal so a follow-up menu can be answered at once; `Esc`
  in the composer folds it to its bar, the draft kept, and moves focus to the terminal; `Tab` inside the terminal passes through to the
  pane. A pending permission or question shows a hint on the composer ("answer in the terminal
  above") instead of accepting Send.
- **Keys on every page**: one `keydown` handler on the document, which returns at once when the
  event's target is editable (an input, a textarea, anything `contenteditable`, the terminal's
  element) or a modifier other than Shift is held, and otherwise looks the key up in one table
  of *(key, page, control)* and presses that control's element — the same click handler, so a
  key can do nothing a button cannot. The `?` overlay is rendered from the same table (§4.5a
  **keys**, **?** overlay).
- **The theme is set before the first paint** (TD-737): a script in every page's `<head>`, before
  the stylesheet, reads the remembered theme (else the system's) and writes `html[data-theme]`, so a
  page change never paints the other theme first; a read that fails is dark, the browser's canvas
  before any CSS is dark (`color-scheme: dark light`), and each theme sets its own `color-scheme`,
  so scrollbars and native controls follow the chosen theme, not the system's. `app.js`'s
  `applyTheme` makes the same read again at load, a stored value that is not a theme being the
  system's, and the toggle writes through it.
- **Errors**: every RPC-triggered control reports failure the same way — a toast on the Org,
  an inline banner in the Focus header — with the host agent's error text and a Retry where one
  makes sense. There is no silent failure path.
- **The host agent's down banner** (*host agent unreachable* on the Org, the Inbox and Settings, and
  the top bar's host dot) waits out a grace of three seconds: the event socket's close draws it
  only when no message or reconnect has come within the grace, a close the page caused by leaving
  draws nothing, and the Inbox, which reads it from its poll, asks again after the grace and draws
  it only when that poll fails too — so a navigation and a promote's two-second restart draw
  nothing, and a real outage still shows within seconds.
- **A reconnect reloads once, never in a loop** (TD-692). This holds on every page with a stream
  (every `connectEvents` caller: the Org, the repo page, Focus, a popped Focus; the Inbox and
  Settings read by their poll). The
  stream is *up* at its first message that is not an `error` event. `connectEvents` handles `error`
  itself, before the page's handler: it toasts the text (`FAILED`) once per page load and leaves the
  stream as it was. It does not clear the down banner, does not count the stream up and does not
  reload, and its *reconnected* mark is left as it was, so the next real message reloads once. So a
  stream that fails each time it opens never reloads the page. It keeps reconnecting with backoff,
  the delay put back to half a second at the first message that is not `error`, not at the socket's
  open (a socket the UI accepts and then closes opens every time). The Org draws its down banner
  after the grace; the repo page and Focus have none, and show the toast.
  That is the known cause of the 2026-10-14 loop. Any other loop, such as a stream that comes up and
  then closes each time, is stopped by the bound. The page reloads when a stream comes up after a
  close, as before, but it first records the reload's time in `sessionStorage`, keyed by the page's
  path, and drops the times older than 60 seconds. When three times are already recorded, the reload
  is held back, and three are the most ever recorded. The page then takes the stream as its own: it
  clears its *reconnected* mark, draws the *reload-loop banner* once, and patches from that message
  on. The banner reads *This page reloaded 3 times in a minute when its stream came back, so it
  stopped; what it shows may be behind.* with **Reload** (§4.5a *every page: reload-loop banner*).
  The page marks its own reload in the same storage just before it makes it, and counts it once: the
  messages that still arrive before the page goes are the same reload. A load that finds the
  mark removes it and keeps the times. A load that does not find it, the person's own (F5, a link,
  **Reload**), clears them. Storage that throws counts nothing, and the page reloads as before. The
  page puts on its stream its script's own hash, the `v=` value of the `app.js` link it loaded, and
  its path: `?page=<hash>&at=<path>`. The UI writes one warning to its console log (`uvicorn.error`,
  the UI unit's journal) when one client address opens `/events` from one path more than 20 times in
  60 seconds: *events: <addr> opened /events n times in 60s from <path> (page <hash>, this UI serves
  <hash>)*. The address may be a proxy's or the tailnet's, shared by every tab behind it, so the
  count is kept per address and path. A promote's two-second restart costs a tab two or three opens,
  a reload loop about thirty a minute, and a stream that fails at each open about six a minute once
  its backoff reaches ten seconds. The line is written at most once per address and path
  every 10 minutes. When the one subscriber that feeds every stream fails, it is already
  logged with its traceback before each stream is sent `error` (`Fanout`, *the events stream
  failed*). The `events` handler's own failure is logged the same way, to the UI's console log, at
  most once a minute; the subscriber's warning keeps no limit.
