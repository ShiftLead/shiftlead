### 4.4 Host agent

Python, one process per host, started by the same systemd user unit. Responsibilities:

- Enumerate sessions (tmux + state dir), merge, serve JSON over a local Unix socket. A tick reads
  the pane list and the tails in threads and reconciles afterwards, and an RPC runs on the loop in
  between: a pane list **older than the kill that ended a record never revives it** (TD-063), or
  an `exited` session comes back as `idle` and then refuses its own `remove`.
- Create / kill / send / resume sessions (the only writer).
- **Its own tmux server and its own repos, on any home but the default** (TD-298): `serve` drives the
  server `SHIFTLEAD_TMUX_SOCKET` names (`tmux -L <name>`), the default server only when it is unset, and
  a home other than `~/.shiftlead` with no `repos_registry:` reads `repos.txt` under itself (§5) — so a
  scratch home, as `scripts/look_home.py` stands up, lists, pulls and promotes nothing of the machine's.
- Per-repo `git status --porcelain=v2 --branch` for every checkout and worktree the registry
  lists, cached with a short TTL.
- **Repo facts** (§4.5 screens 1 and 11): for every checkout the registry lists, at the
  home, readings kept in `repos.json` beside `usage.json`, served by the `repos` RPC and pushed as
  a `repos` event when any changes (`repo: null` for a checkout the registry dropped; a node
  forwards the RPC and refuses it offline, §4.4a), the shape `usage` has. The RPC serves a reading whole, or without
  each dotted path its **`omit`** names — a path walks a mapping by key and every item of a list, and
  one that names nothing is no error (TD-746): a page passes what it never draws — every page the
  ledger's month (`ledger.recent`, which only the agent reads, to build `completed`) and the month's PR
  fields no mark reads (a PR of `recent` keeps its number, state, title and link); the Org, the Repo
  page, Focus and a card an entry's detail block too, the Inbox `completed` — so a page is not sent the
  whole reading to draw a part of it. A **`subscribe`** takes the same `omit`, and each `repos` event
  it is sent — the seed and every push — is the reading without those paths (TD-754): the UI's one
  subscriber, and the Inbox's counts keeper, ask with the Org's omit, which is what its run keeps
  and draws. Every other reader (`ao repo`, a team's lanes) reads it whole.
  **The seams** (§5 *The
  seams*; TD-584, built by TD-591): the reading carries, per repo, as **`seams`** (`sessionorc.seams`),
  whether its ledger at `ledger:` parses through `ledgerboard.py` and its `Ledgerboard:` major (the
  reader's reason when not), and for each of `board:`, `gate:` and `worktree_setup:` whether it is *set*, *defaulted* (the
  dev-cadence file the checkout holds) or *absent* — read from `.shiftlead.yml` and the checkout on
  the same five-minute cadence; the Repo page's missing-seam lines (§4.5a) and `ao doctor`'s
  **repos** check (§4.7) draw it and read nothing themselves. **Pull requests**: two
  `gh pr list --json number,title,url,state,createdAt,closedAt,mergedAt,headRefName,headRefOid,author,isDraft`
  reads in the checkout — `--state open` for the open list, and `--state all --search
  updated:>=<a month ago> --limit 1000` for the month's PRs (GitHub's search stops at 1000 results
  whatever the limit, so the reading says `recent_cut` when it fills it: `recent` is then the newest
  1000) — and one `gh api graphql` read of the windows' counts, six `search(type: ISSUE) { issueCount }`
  queries (`is:pr created:>` and `is:pr closed:>` each window's start), since a busy repo closes more
  than 1000 PRs in a month and a list's length would be a floor — **every five
  minutes** in a thread, never per tick, once per
  remote (two checkouts of one repo are one read); kept as the open list plus, per window (the
  last day, 7 days and 30 days, rolling), the counts *opened* (`createdAt` in the window) and *closed*
  (`closedAt` or `mergedAt` in it, a merge being a close) — GitHub's totals; a count that could not be read is
  the reading's `error`, never the list's length — and the month's PRs as `recent`, each kept PR
  with its `head` (`headRefOid`), which §6 rule 10 reads — and, on the open list alone,
  **`checks`** (*green*, *red*, *pending* or *none*, folded from `statusCheckRollup`: red when any
  check run concluded `FAILURE`, `CANCELLED`, `TIMED_OUT`, `ACTION_REQUIRED` or `STARTUP_FAILURE` or a
  commit status reads `FAILURE` or `ERROR` — a check waiting on an approval, or whose runner never
  started, is red too — pending while any runs, green when all passed)
  and **`conflicting`** (`mergeStateStatus` is `DIRTY`), with **`red_since`**, the reading that
  first saw it red or conflicting, kept while it stays so (TD-613; the open read's `--json` gains
  the two fields), and its **`base`** (`baseRefName`); beside them **`required`**, `{<base>: [names]}`
  for each base an open PR names — the check names its protection and its rulesets require, which a
  `done` naming a PR is read against (§4.8 *A `done` with a PR is told what its checks read*, TD-637),
  a base whose read failed keeping its last names with the why in `required_error`; a read that failed keeps the last
  reading and records `error` and `failed_at`, so the page can say *could not look* — an outage
  is never zero PRs, the rule `_count_seats` already follows for merges (`merged_prs` answers
  `None`, never `[]`). **The ledger**: the repo's `ledger:` file (`.shiftlead.yml`, default
  `docs/technical_debt.md`) read when its mtime moves, its history every five minutes, by `sessionorc.ledger` — the one reader of
  the entry's header fields (`## TD-NNN: title`, `**Priority:**`, `**Owner:**`, `**Kind:**`,
  `**Type:**`, `**Blocked by:**`), kept as
  `{entries: [...], by_priority, by_kind, at}`; an entry counts while its section is in the file.
  **Pickable is derived, never written** (TD-223). It is cadence §2.4's
  rule, the one dev-cadence's `scripts/ledger.py --pickable` applies, so a repo's own tool and
  the home give one answer: an entry is **blocked** while its `**Blocked by:**` names an entry
  that is not archived — one still open, or one found in neither the ledger nor its archive,
  which keeps the block — or names a `decision (<who>)`, or holds an item the rule cannot read
  (neither an id nor a decision, or an item listed after the decision's comma; what follows the
  decision with no comma is its pointer and is never read), which keeps the block
  too; every other entry is **pickable**, one with no such line or an empty one included. An
  id written `<repo>#TD-NNN` (cadence §2.4, TD-071 there; `owner/name#TD-NNN` where two repos
  share a name) names **another repo's entry**: the home looks for that repo among the
  checkouts its registry lists (the host's `repos()`), as the script's roster does: `<repo>` is
  a checkout's directory name and `owner/name` its origin, and it reads that checkout's
  `docs/technical_debt.md` and `docs/technical_debt_archive.md` at `origin/<default>`, or in the
  working tree where that ref is missing —
  archived there, the block lifts; open there, it blocks; a repo the registry does not list, a
  name two checkouts share, a ledger that cannot be read, or
  an id in neither of that repo's files, keeps the block. The script asks cadence's roster and
  the home its own: `repos.txt` under the home with dev-cadence's `~/.config/dev-cadence/repos.txt`
  imported when it exists (§5 *Repos*; TD-584, built by TD-590), so the two agree on every repo the
  cadence lists unless `hosts.yml`'s `repos_registry` or the script's `DEV_CADENCE_REG_DIR` moves
  one of them; the resolver the home hands `ledgerboard.py`'s `pickable()` reads its own roster
  and answers `(state, why)`, the `why` going into the flag. The
  reader takes the archive from beside the ledger (the ledger's name with `_archive` before
  its suffix, which for the default is cadence's `technical_debt_archive.md`, the one name the script
  looks for unless it is handed `--archive`; none there,
  nothing is archived), and each entry carries `type` (`debt` where unwritten), `blocked_by`
  (what still blocks, the decision and an unread item among them, as the script lists them)
  and the derived `pickable`. The pick order is the rank's (*The Queue*, below): the person's placement, else Priority, then debt
  before feature, then id — until TD-769, the summary table's order in place of id. **No header line is
  needed**: an entry with no `Kind:` reads as `build` and one with no `Owner:` as anyone's, so
  a ledger that carries only Priority, Type, Status and `Blocked by:`, as dev-cadence's does, is
  read whole. *What a worker may take* is then the lane's (§6 rule 6): pickable, of the
  lane's kind, of the lane's owners. **The page's kinds**, tested in this order so that each
  entry has one: *for you* — **what waits on the person, and only that** (TD-367): `Owner: paul`, or blocked by `decision (paul)` — such an entry's reading also carries `added` (its `Added:` date), `answers` (its `**Answers:**` line, cadence §3.5's form, where it has one) and `detail` (its **Why** and **Fix** paragraphs, clipped as a board item's block is), for its block on its Queue card (§4.5 screen 12; screen 6 *The ledger's entries that wait on you*, an Inbox row under *Later* until TD-771) —, the holder read
  lower-cased so `decision (Paul)` is the same word; the person's owner word is the one the
  ledger's `Fields:` line declares for them, `paul` here, so a `Kind: decision` entry is the
  person's only when its `Owner:` is, and one owned by anyone else is *blocked* when it waits on an entry, else *other*, below (the Queue draws the person's on their cards, §4.5 screen 12 and screen 6 *The
  ledger's entries that wait on you*),
  *blocked* (its `Blocked by:` holds any item other than a `decision (…)` — an open id, a cross-repo
  or unreadable one; archived ids have already dropped out in `ledger.entries` — whatever its `Kind:`
  and whatever decision stands beside it: the code's not-pickable less what decisions alone hold,
  so a designed entry waiting on its build is here and not the designer's, as is a live check blocked on an open entry — TD-418),
  *design* (`Kind: design-first`: the designer's list,
  less what waits on the person or another entry, which the tests above took — **and an entry of any
  kind blocked by `decision (designer)` alone** (TD-367): a decision owed to the designer is design
  work, and the entry is the designer's, in its lane by §6 rule 6, until the decision is made and the
  PR that writes it drops the item from `Blocked by:`), *live check* (`Kind: live-check`, its build
  live or not: a live one is not counted *pickable*, though a `free-pick` lane still takes it),
  *pickable* (pickable, `Kind: build` or none: work a lane can start), *evaluation* (`Kind: evaluation`, dev-cadence's word: **no lane takes it** since the anchor seat is retired (§4.9b *No anchor seat*), so the reader flags each one beside *other*'s, *TD-NNN: no lane takes an evaluation — write it as a build whose Fix is the write-up, or as design-first*, for its owner to rewrite; an unblocked `Kind: decision` that is not the person's is *other*), else **other — a residue that should be empty**: an entry no
  test above takes — a `decision (<anyone else>)` alone among them — is a **flag** of this reader,
  *TD-NNN: fits no page kind — check its Owner, Kind and Blocked by*, said on the Repo page's *other*
  list and by `ao repo`, and still drawn on the bar so nothing is hidden (`scripts/ledger.py` is
  dev-cadence's synced file, so its `--check` gains the flag there or not at all). **A written
  `Pickable:` line is not read**: a ledger that still
  carries one is read as if it did not, as the script reads the line as a field that overrides
  nothing (cadence §2.12), so the home and the script differ by no entry. What nothing blocks
  and a grinder still cannot build — *built, the live look is left*, *needs an attended run*,
  *a synced file* — is said by the entry's `Kind:` or its `Owner:`, and the lanes carry their
  owner words (§6 rule 6), so an unblocked entry of one owner is in no lane that names another; an `Owner:` no team's lane takes is counted under *the rest* (*rest · <owner> n*, *In a team's lanes*, below), which is how a repo whose teams have no member for its work says so.

  **A new entry settles before it is pickable** (TD-707), so the person has time to change it or add
  to it, while a designer's builds go at once. A ledger PR takes
  10–15 minutes through the cadence, so a window in which the person must finish an edit is too short;
  the window is one in which the person can **hold** the entry, at once and with no PR — and a hold is
  not the window's alone: the person may hold any open entry, settled or not, whoever holds its claim
  (TD-731).
  - **How long, by Kind.** `settle:` maps an entry's `**Kind:**` to a duration — `{design-first: 10m}`
    — read by the home: the repo's `.shiftlead.yml` `settle:` (§5) wins, key by key, over the
    install's `settle:` in `settings.yml` (§5, the Settings page's **settle**), which wins over the
    built-in `{design-first: 5m}`. A Kind no layer lists settles 0, so a designer's builds (`Kind:
    build`) and every live check go at once. The entry's own `Kind:` line decides, as `Kind:` decides
    the page's kinds above: an entry with no `Kind:` reads as `build`. A `design-first` finding from an
    auditor or a hunter settles as any does.
  - **The clock** is the home's, kept by the host agent beside the reading and not by the reader,
    which stays a function of the checkout's text: when a ledger reading (above) first holds an id,
    the agent records `{at, sig}` for it in `ledger_seen.json` beside `ids.json`, keyed by origin as `ids.json` is, `sig`
    being a hash of the entry's section text. The reading is of the registered checkout, which §6
    *Pull* keeps at `origin/<default>`, so a branch's entry is never seen. **The first reading of a repo
    records every id it holds as settled** (`at` the epoch), so the build, a new home or a newly
    registered repo freezes no ledger. An entry **settles** at `at` plus its Kind's duration; while it
    is settling, an edit that changes `sig` restarts the window (the person still adding thoughts),
    and once it has settled an edit changes nothing.
  - **What settling withholds.** Pickable stays cadence §2.4's rule above, which a repo's own script
    applies, and the agent annotates the reading's entries from `ledger_seen.json` before any
    reader sees them, adding **`settling: {until}`** to an entry that has not settled, so
    `lane_matches` and `in_lanes`, which read an entry alone, need no store: every
    reader of a lane — §6 rule 6's news, rule 8's lanes and `work_waiting`, the lane counts a Start's
    confirm and the card draw, `ao repo` — counts it as not pickable, and its page kind is unchanged.
    So a lane's news of it is told once it settles, not when it lands. **`ao progress claim`** on a
    settling or held entry is refused, *TD-707 settles until 05:28* or *TD-707 is held by the person
    since 05:20*, and `--force` does not pass it: the lease's override is about another session's
    claim, and this is the person's window.
  - **Hold.** The person may hold **any open entry, settling or settled** (TD-731): **Hold** on its
    Repo page row (§4.5a *Repo page: Hold / Release on an entry*), on its Inbox row once held (§4.5
    screen 6), or `ao td hold <id> [--repo <name>]` (§4.7), the home's `td_hold
    {repo, id, release}` RPC, which writes `held: {at, by}` on the id's `ledger_seen.json` entry —
    the home's record, not a ledger edit, so it holds at once. A held entry reads **`held: {at}`** in
    the reading and is withheld as a settling one is, **until Release and nothing else** (`ao td hold
    <id> --release`, or the row's **Release**), which makes it pickable at once, its record settled
    (`at` the epoch), so a later edit changes nothing. **An edit does not end a hold**: it records
    the new `sig` and the entry stays held, so a conversation that amends an entry by PR, once or five
    times, keeps it out of every lane until the person says it is ready. Holding a held entry changes
    nothing. It is a person's own act, one name in
    `PERSON_ONLY` (§4.8 *A person's own act is a named RPC*) and the home's alone (`modes.HOME_EDITS`:
    a node forwards it and refuses it offline): the page's press, `ao td hold` from the
    person's shell, and refused to every session, since a worker must never hold an entry of its own
    lane and the gate reads no other line. An id the home's clock does not hold yet is refused,
    saying the next reading records it.
  - **A claimed entry is held all the same**, since a hold takes no lease: an open entry with a live
    declared lease on it (`_lease_holders`, §4.8 *A claim is a lease*) is held, the claim stands, and
    the home tells each **unattended** holder in a `note` from the person, `--about` the id — *TD-724
    is held by the person: stop at the step in hand, push, leave its PR open and unmerged, and drop
    the entry: `ao progress drop TD-724 --why "held by the person"`. A Release makes it pickable
    again.* — mail from the person, which a session takes as an instruction (§4.10). Where an unattended
    holder's claim names a PR (its `pr` or `review_pr`), the seat whose inbox holds an open `ask` carrying that
    PR — its reader, §4.9b `prs_waiting.asks` — is told the same in a second `note`: *TD-724 is held by
    the person: leave PR #1840 unmerged until they release it* — found by the open `ask`s in the
    inboxes of the graph's live records (the states `_lease_holders` skips skipped here too) whose
    `pr` is that number, each seat told once however many holders name it; the person is no record,
    so where they are the reader nobody is told, and they pressed the hold. The hold is
    written first: a note that cannot be sent is named in the reply's `untold` (*could not tell <name>: <why>*)
    and never refuses the hold, and a hold on an entry already held writes nothing and tells nobody
    again. The claim
    refusal above then keeps any session from claiming it again until the Release, and whoever then
    claims it finds the dropped claimer's PR as any open PR on the entry. An interactive holder
    (`unattended: false`) is the person's own and is told nothing. The RPC's reply carries `told`, the
    holders and readers it mailed, `readers`, the readers among them, beside `untold`, and `ao td hold` and the page's toast name both (*TD-724 held · grinder-ao-2
    told to drop it*). The note is read when the holder's turn ends (§4.10 *When it is read*), so a
    merge already under way in that turn is not stopped: the hold is the person's quickest press, not
    a lock on the PR. Rejected: refusing a hold on a claimed entry and leaving the person to mail the
    holder or its manager (TD-724's case on 2026-10-15, stopped by hand, is the one this press is for).
  - **An entry can land held** (TD-731): `ao td next --held` (§4.7) records each id it hands out as
    held on the clock before any reading holds it (`{held: {at, by}}` and no `sig` yet), so the entry
    is held from its first reading and never settles on its own: what a conversation with the person
    files waits for their Release, however many PRs amend it meanwhile. `--held` is the person's, and
    an **interactive** session's (`unattended: false`: the person is at its keyboard),
    which is the session filing an entry with the person; an unattended caller, and a caller the graph
    does not hold (as `person_only` reads one), is refused in its own words, not `person_only`'s, which
    an interactive session passes here: *--held is the person's and an interactive session's: <caller>
    is unattended* (or *is not a session this home holds*). A held pre-record is not
    a reading: a repo's first reading is the first that finds no record with an `at` under its key, so
    every id it holds is still recorded settled. An id taken with `--held` and never filed leaves an
    inert record; it cannot be released before its entry lands, since `td_hold` reads the entry. It is `td_next`'s own rule, a branch of an RPC every session calls (§4.8 *What is not in
    the list*), and it only ever makes an entry less pickable: the Release stays in `PERSON_ONLY`. The
    package's `entry.md` (§4.9 *Add an entry to the ledger*) says so: *an interactive session filing
    an entry the person is still deciding takes its id with `ao td next --held`*.
  - **Never settled**: a decided board line and a red PR's work order (§4.4 *Board write-back*, *A red
    PR nobody holds*), which are not ledger entries; every Kind the map leaves at 0.
  - **Shown where it is read, not pushed**: `ao repo` prints *settles in 7m* or *held 2h* after the
    entry's owner, and the Repo page's row draws the same with its Hold or Release. No Inbox row for a
    settling entry: the window is minutes long, and a row that leaves before it is read is noise; an
    entry the person files they know of, and one a session files the Repo page shows. **A held entry
    waits on the person** — drawn on its Queue card, *held (person)* (§4.5 screen 12; an Inbox row, *ledger · held*, under *Later* until TD-771) — since
    it waits on the person with no end, and a hold forgotten there would hold the entry for good.

  **An entry says what it waits for** (TD-715), so a lane whose every entry waits reads as waiting, not
  as work left. The page's kinds (above) say whether an entry is blocked by another entry or a
  decision; a pickable entry may still wait on something no `Blocked by:` item can name.
  - **The `**Waits:**` line** is this repo's own header field, written in the header block after `Kind:`, declared on the ledger's `Fields:` line
    (`Waits = until | event`, cadence §2.12), so `scripts/ledger.py --check` validates its first word and
    the cadence's `Blocked by:` rule is untouched. It has two shapes:
    - **`until <date>`**, a date in the home's local time: *`**Waits:** until 2026-10-16 — CI runs on or
      after 10-16`*. The entry waits until that day begins; from then the line reads as unwritten,
      and the entry is told as new to a lane whose member declared out of work before it (§6 rule 6).
    - **`event`**, a thing that happens and that nobody in the lane can cause: *`**Waits:** event — the next
      cadence-sync PR`*. The entry waits until the line is edited away.
    - **What waits on the person is not a `Waits:` line**: it is `Blocked by: decision (paul)`, with what
      the person must do written after it as the decision's pointer (*`decision (paul) — a
      permissions: rule for …`*), or `Owner: paul` where the whole entry is the person's to run (an
      evaluation that needs an attended session). Both already read *for you* (above) and join the person's
      count; `decision (paul)` leaves every lane, and `Owner: paul` every lane that names an owner (a
      `free-pick` lane with no `owner:` word still takes a pickable one, *A member's own count* below).
  - **What a wait does.** The reader reads the line from the entry's text (`waits: {on, date, why}`; a
    `until` with no readable date is waiting with no end, and the reader flags it, *TD-NNN: Waits:
    until names no date*). Whether it still waits needs the clock, so the agent's marking pass that
    adds `settling` (above) adds **`waiting: {on, until}`** to an entry whose wait stands. It runs on
    each reading it carries, so a date's wait ends on its day. A marked entry is withheld as a
    settling one is: it matches no lane, its page kind is unchanged, and rule 6 tells a member of it
    once the wait ends. **`ao progress claim`** on a waiting entry is refused, *TD-463 waits until
    2026-10-16*. Unlike a settling entry, `--force` passes it, since the session may know that the
    event has come; that session's PR removes the line.
  - **Counted apart.** `in_lanes` (below) counts what a lane would take but for its wait as
    **`waiting`**, `{until: [ids], event: [ids]}`, apart from the kinds' counts and the rest, and each
    member gains its own `waiting` ids beside `ids`, which leave them out. So a member out of work
    with nothing it can take and entries that wait is not *out of work with n*, and reads as waiting
    (§4.5a *card: compact*, *Repo page: waits mark*; §4.7 `ao repo`).
  - **Who writes it.** The session that reads an entry it cannot take for one of these reasons writes
    the line, in one ledger PR per run before it declares out of work, and only on entries that do not
    yet say why (the briefs, `docs/briefs/`). A written entry leaves the lane, so the next run does not
    read it again and the PRs do not repeat. `ao progress none --why` is never parsed for it.

  **An entry names its team** (TD-730) where its repo has more than one, so each team's lanes take
  its own work. A repo has any number of teams (§4.9 *Teams*), each with its own lanes, and an
  `Owner:` names only a role word: without a team on the entry, two teams' grinders both take every
  pickable `Owner: grinder` entry, and a claim keeps them off one entry at once but keeps no work
  with its team.
  - **The `**Team:**` line** is this repo's own header field, as `Waits:` is: written after `Kind:`
    (after `Waits:` where both are), its first word a team's name, *`**Team:** db`*. **Its
    vocabulary is the ledger's own `Fields:` line**, `Team = db | compliance` (cadence §2.12), so
    `scripts/ledger.py --check` refuses a misspelt or undeclared name in any cadence repo, and
    dev-cadence reads past the field. The declaration is this install's list of the repo's teams
    (one org per install, §4.9), committed to the repo, and it is what the home reads: the host
    agent reads no definition (§4.9 *Where definitions live*), and the ledger is text it already
    reads. The reading carries the list, in its order, as `declared_teams` on the repo. Its order
    is the repo's order of teams wherever one is picked for the repo: the tagging seat (below) and
    Add entry's blank **Team** pick (§4.9 *Where there is no seat*). Team names compare
    case-folded, as ledgerboard reads a field's first word.
  - **When it is required.** Where the vocabulary names **two or more** teams, an open entry whose
    page kind a lane takes (*pickable*, *design*, *live check*) requires the line. An entry that is
    *for you*, *blocked*, an *evaluation* or *other* needs none until it becomes one a lane takes,
    which is when a lane first wants it. A vocabulary of one name, or none, requires nothing, so a
    repo with one team writes nothing and no existing entry is edited. A `Team:` line on a ledger
    that declares no `Team` vocabulary is the cadence's undeclared field (an error under `ledger.py
    --check --since`, §2.12), so the line is written only where the vocabulary names two or more.
  - **The move from one team to two.** The definition of a team is a file edit on one install, and
    the declaration is a ledger PR, so the two are made apart; three things keep them together:
    - **The PR that declares the second name tags** every open entry the requirement covers, so
      no lane loses its work while the tagging seat catches up. The tagging seat (below) is for
      what is filed untagged later.
    - **`ao team start` refuses** a team whose repo's definitions hold two or more teams and whose
      ledger's vocabulary does not name it, in words that give the fix: *ops: shiftlead has two
      teams and its ledger's Fields: line does not declare ops — add `Team = ao-grind | ops`, and
      a Team: line on each open entry a lane takes, by PR*. The client checks it (`ao team start`

- Usage, **reported first and asked for last** (TD-231). The usage endpoint is no documented
  interface: the tool's own clients read it too, and its refusals carry no usable `Retry-After`.
  What a session of the tool is *told* about its limits is
  documented, so that is the source:
  - **A report.** An adapter whose tool tells its sessions their limits hands them to the host
    agent as `usage_report {windows: [{label, pct, resets}], fresh}` (§4.3), an RPC of its own
    beside `hook`, since a report is no state event. Claude Code's is its **status line**: the
    launch's `--settings` layer names `shiftlead-hook --statusline` as `statusLine`, with a
    refresh of sixty seconds so that a session deep in one long tool run still reports. The
    tool hands the command `rate_limits` on stdin (the five-hour and seven-day windows, each a
    percentage and a reset; a subscription's only, after the session's first response, from
    the client version that carries them). The adapter rounds the percentage to one decimal
    and writes the reset, which arrives as seconds since the epoch, as the instant every other
    reading carries. The command reports **when a number or a reset changed, or a minute has
    passed**, never on every redraw; it sends with a short timeout and queues nothing, since
    the tool cancels a status line that is still running when the next is due, and a report
    delivered late would be read as new.
  - **The person's own status line still shows.** A `statusLine` in a settings layer replaces
    every other, so the command runs the one it displaced — looked for in the directory's
    `.claude/settings.local.json`, then its `.claude/settings.json`, then the profile's own
    settings, the first that names one, with its padding carried over — hands it the same
    stdin and prints what it prints; with none, it prints nothing. Nothing of the person's is
    edited: the layer is the launch's, as the hooks are. Where the tool draws no status line
    at all (hooks disabled by policy, a directory not yet trusted), nothing is reported and
    the endpoint below is what is left. A session started by hand, outside shiftlead, has no
    layer and reports nothing.
  - **A report is not proof of a fresh number.** The tool redraws the status line on more
    than a new response (a compaction, a change of mode, the refresh, a window's reset), and
    hands the same `rate_limits` it was last given. So `fresh` is the adapter's word that the
    session has had a response since its last report, read from the payload's own running
    totals of the session's API work; a report that is not fresh changes no reading's age.
  - **The reading** is per account and per window, `{label, pct, resets, at, source}`, `source`
    `reported` or `asked`, and the reading's own `fetched`, `source` and `by` (the reporting
    session's name) are the newest confirmation's, which is the age the chip prints. Reports are
    **merged by what a window can do, not by who spoke last**: inside one `resets` a window's
    use never falls, so the highest percentage stands, and a later `resets` replaces the window
    outright; two resets within five minutes of each other are one window (`RESET_SLACK`: the
    status line hands epoch seconds, the endpoint an instant of its own, and a rolling window's
    reset drifts between reads). The endpoint's answer is the account's own rather than one
    session's view of it, so it sets each window it names outright, a lower number included,
    and keeps the windows it does not name, and one taken before a window's last report leaves
    that window as the report left it; `at` moves when a fresh report or an answer
    confirms the number. A window whose `resets` has passed is
    **unknown until it is read again**, never zero and never a cap: `limited` (§4.2) is not
    read from it. **A short history** is kept beside each window in `usage.json`: the newest
    reading and one per ten minutes for the three hours before it, which is what a
    projection takes its rate from (§6 *Usage gate*).
  - **A node's sessions report to their node**, which merges the report for its own gate and
    sends it on to the home over the link (`usage_report {id, account, windows, fresh}`, node to
    home; one the link could not carry, or sent before its snapshot is taken, is dropped, not
    queued, for the reason above). `account` is the key the node reads the session's profile
    under, since the node holds the profile's credentials and a profile of the same name at the
    home may be another login; the home takes it only for a record of that link's host and an
    account of that record's adapter, and remembers it per node and profile. The home merges
    the report as its own sessions' and shows the account while that session lives, never
    asking the endpoint for it; a profile a session at the home runs under keeps the home's own
    account's reading, and one two nodes key to two accounts shows the first node's by name,
    since a reading is per profile; a node's key is forgotten once no live session of that node
    runs under the profile, and a report for a record that is no live tool session sets none. A
    profile metered at the home is no bar to a node's report under that name, since the node
    withholds its own metered profiles and the name may be another login there. After a restart
    the home keeps the reading a node's profile held in `usage.json` until the node's first
    report, which merges onto it — history and all — when it is of the account the node names.
    **The home holds the account's reading and sends it back** to each node that keyed a live
    session to it, as `usage_reading {account, reading}` (home → node, a notification on the
    road the settings take: the windows, `fetched`, `source` and `by`), whenever it moved since
    that link was last told and once more on each new link, never before its snapshot, refused
    not queued. The node takes it for an account one of its live tool sessions is keyed to and
    no other, **window by window**: a window the home confirmed later, or saw roll, is the
    home's — number, `at` and history — and one the node confirmed no earlier, or saw roll
    first, stays the node's; `fetched` follows the newer confirmation, and `reason` and the
    cool-off stay the node's own, since only the node asks for its account. So a node's chip,
    gate and projection read every host's reports, and a node whose sessions are idle is not
    asked for while another host's sessions report the account.
  - **The endpoint is the fallback, on demand**: asked only when an account a live session's
    profile names has no reading younger than `USAGE_FRESH` (fifteen minutes), at most once
    per `USAGE_FRESH` per account, and after a `rate_limited` answer not for a fixed hour
    (`USAGE_COOL`; a longer `Retry-After` is kept). It is asked by the host that holds the
    profile's credentials, a node's answer travelling as a report does. An account with a
    session at work reports by itself, so the endpoint is asked for an idle or paused
    account, a client too old to report, and the first minutes after a start, when there
    may be no reading at all: nothing is paused and nothing noted on no reading.
  - **A window only the endpoint gives** (a per-model weekly one) is never in a report. It
    keeps its own age on the chip, and the endpoint is asked for it once an hour, under the
    same cool-off, while a reserve names it or its last reading stood within ten points of
    its cap; otherwise it ages to unknown and is asked for with the rest.
  - **Every reading has an age**, and a page and the gate read it: the chip prints it (§4.5a),
    `ao gate` prints it, and the gate stops trusting a number past its age (§6).
  Not used: the rate-limit headers on a model's responses, which are named in the client and
  documented nowhere.
  **The poll, as built**: each **account** a live agent session's profile names is asked its adapter's `usage_for`
  in a thread, never per tick, and only on the fallback's terms above: when its
  reading is older than `USAGE_FRESH` and at most once per `USAGE_FRESH` — so, while nothing
  reports, about every fifteen minutes — once per `(adapter, account)`, through one
  profile of that account (§4.2a), never once per profile: a shorter cadence buys nothing
  against a five-hour window while spending an allowance the tool itself shares. The ask for a window only the endpoint gives, once an hour under
  a fresh report, is `asked_only_due`'s. `limited` is read from the account's reading, so
  while nothing reports a session at its cap may show it up to fifteen minutes late; the pane's own limit
  message marks it within a tick regardless (§4.2). The last answer is cached **per account** and
  served by `usage` under every profile that shares it — the same windows, `fetched`, `reason`
  and back-off on each — streamed as a `usage` event for the top bar's per-account chip, and drives the `limited` rule
  of §4.2 (an interactive session on a profile with **any** reported window at 100% shows
  `limited` with that window's label and reset time, `working` again once the window resets —
  the core iterates the adapter's list and names no window of any tool). A fetch failure
  keeps the last answer. An account no live session's profile names is dropped from the cache
  and a `usage` event with `usage: null` for each of its profiles takes its chip off the top bar:
  one account in use is one chip.
  **A failure says why**: the adapter answers `ok` with the windows, or `rate_limited`
  (with the endpoint's `Retry-After` when it is a number; the HTTP date form is legal and not
  parsed, and an unreadable one is the fixed cool-off), `no_credentials`, `no_profile` or
  `error` — a word the core keys on, never prose. The core does three things with it and no more.
  It **logs a change of reason once**, not per poll. It **cools off on `rate_limited` alone**, and
  cools the account off, not the one profile it happened to ask through: `USAGE_COOL`, a fixed
  hour, or the `Retry-After` where that is longer, **not** capped — never a doubling, which could
  not learn a window the endpoint never names; any other answer returns to the cadence,
  since only a 429 is the endpoint asking to be asked less often. It **keeps the last good reading** with the reason
  beside it, so the chip goes stale rather than going out (*the chip went out* and *the allowance
  is spent* are different things to a person). The reading is **held across a restart**
  (`usage.json`) and so is the allowance: the first poll after a restart waits until the held
  reading's `fetched` plus the cadence, never sooner, and a cool-off's end is held on the reading (`cool_until`), so a restart inside the hour does not ask. The reason is not held.
  **A metered account's reading is a sum, not a poll** (§4.2a). On every tick each host asks the adapter `spend(profile, cursors)` (§4.3) for
  the metered profiles its live sessions run under and adds the turns to a **daily ledger per
  account**, `spend.json` beside `usage.json`: one row per account per day holding tokens by kind
  and cost, and the **cursors** — a byte offset per transcript, per host — kept thirteen months.
  The three windows are summed from it on the tick, the ledger is what survives a restart as the
  held reading does, and a turn is counted once, because a cursor moves only after the row is
  written and a turn at or before its transcript's cursor is dropped: the test is per transcript,
  never a time, since two profiles on one account read from two directories whose turns do not
  interleave by `at`. Beside each cursor the ledger keeps the last ledgered entry's `at` and `id`
  for that transcript: `at` never decreases within one file but two entries may share it, so a
  transcript read from 0 again after a rewrite (§4.3) has every entry before that `at` dropped,
  and at that `at` the entries in file order up to and including the one with that `id` — every
  entry at that `at` when none carries it, since a survivor at the old boundary is old and a new
  turn at that millisecond is a coincidence worth cents, where a re-bill is the whole turn — so a
  rewrite never re-bills, and loses at most that one coincidence. A batch read **from** the cursor
  drops every entry before that `at` too, since `at` never decreases in one file: that is what
  catches a rewrite that left the file at or past its cursor, which the adapter cannot see as one.
  Beside them the cursor keeps the last entry's `response` and tokens, and a response whose entries
  straddle two reads is counted, the second time, for what it adds over them. The test stays per
  transcript because `claude --resume` appends to the transcript it resumes, so no response
  appears in two files. On the
  first tick that finds a profile metered the cursors start at each transcript's end, so a key that
  ran unmetered for months does not bill its history to the first day; a transcript that first
  appears on a later tick starts at offset 0; a row's `cost` is written once, at that tick's prices, and a later
  change to `prices:` applies from then on and rewrites nothing — the ledger is a record of what
  was charged, as the bill is. The reading is served, streamed and held as a polled one is, and it
  is never `stale`: a sum has no failed poll; and the cap rule below is skipped for it by the
  profile's `billing`, read before the windows are, so `limited` is never marked from an amount. A

  {account, profile, prices, turns, cursors}`, a link method with a reply — the prices are the
  node's profile's, since the home may not define it. The ledger's cursors for that host's transcripts live at
  the home: it drops each turn at or before the cursor it holds for the turn's `source`, writes the
  rest, and answers with the cursors, whether the profile is seeded on that host, and the
  **account's sums**; the node advances its own on the reply. The node's first `spend` on each link
  carries no turns and no cursors: it is a read of those three, so the node starts from the cursors
  the home holds. The seeding never travels as turns — a first read returns every turn of every

  - **The word.** A PR whose failing items **all** are Actions jobs that never started reads
    **`checks: not_run`**, whatever else is still pending, since the account blocks every run to come
    as well. Any other failing item keeps it *red*: a failing commit status (`StatusContext`), a
    failing check run that is not an Actions job, or a job of any conclusion (`failure`,
    `cancelled`, `startup_failure`, `action_required`) that does not pass the three-part test. It carries
    **`not_run: {reason, kind, runs}`**, `runs` being the run ids for the row's **Re-run**
    (§4.5a).

    not-started ones out.
  - A job that cannot be read (a 404, a rate limit) is no evidence, and the PR stays *red*, as
    today.
  - The verdicts are kept on the row **by job id** (`jobs: {head, read: {<job>: …}}`), so a job is
    read once. A new head replaces the map, and a Re-run's new attempt, which has new job ids on the
    same head, is read afresh. An unreadable job is not kept, so the next reading tries it again.

  same way. The call names the repo by its registered name, never by a path, which would be a
  node's. A name two registered checkouts of different origins share is refused, naming both,

  once get different ids with no rebase. The whole call has a budget of 45 seconds from its arrival,
  the wait for the lock included, well under a client's 120-second timeout. A lock not taken 30
  seconds in refuses (*busy, ask again*). The PRs are read a few at a time until 30 seconds in, and
  a PR not read by then is *unread* (*budget*). The fetch has until 45 seconds in, and refuses when it
  does not finish. Every `gh` and `git` call runs off the host agent's event loop and is killed at
