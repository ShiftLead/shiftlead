### 4.4 Host agent

Python, one process per host, started by the same systemd user unit. Responsibilities:

- Enumerate sessions (tmux + state dir), merge, serve JSON over a local Unix socket. A tick reads
  the pane list and the tails in threads and reconciles afterwards, and an RPC runs on the loop in
  between: a pane list **older than the kill that ended a record never revives it** (TD-063), or
  an `exited` session comes back as `idle` and then refuses its own `remove`.
- Create / kill / send / resume sessions (the only writer).
- **Its own tmux server and its own repos, on any home but the default** (TD-298): `serve` drives the
  server `SHIFTLEAD_TMUX_SOCKET` names (`tmux -L <name>`), the default server only when it is unset, and
  a home other than `~/.shiftlead` with no `repos_registry:` reads `repos.txt` under itself (§5) — so a
  scratch home, as `scripts/look_home.py` stands up, lists, pulls and promotes nothing of the machine's.
- Per-repo `git status --porcelain=v2 --branch` for every checkout and worktree the registry
  lists, cached with a short TTL.
- **Repo facts** (§4.5 screens 1 and 11): for every checkout the registry lists, at the
  home, readings kept in `repos.json` beside `usage.json`, served by the `repos` RPC and pushed as
  a `repos` event when any changes (`repo: null` for a checkout the registry dropped; a node
  forwards the RPC and refuses it offline, §4.4a), the shape `usage` has. The RPC serves a reading whole, or without
  each dotted path its **`omit`** names — a path walks a mapping by key and every item of a list, and
  one that names nothing is no error (TD-746): a page passes what it never draws — every page the
  ledger's month (`ledger.recent`, which only the agent reads, to build `completed`) and the month's PR
  fields no mark reads (a PR of `recent` keeps its number, state, title and link); the Sessions page, the Repo
  page, Focus and a card an entry's detail block too, the Inbox `completed` — so a page is not sent the
  whole reading to draw a part of it. A **`subscribe`** takes the same `omit`, and each `repos` event
  it is sent — the seed and every push — is the reading without those paths (TD-754): the UI's one
  subscriber, and the Inbox's counts keeper, ask with the Sessions page's omit, which is what its run keeps
  and draws. Every other reader (`ao repo`, a team's lanes) reads it whole.

  directory's `README.md` — opens and closes nothing: the v1 headings it removes and the files it adds are
  the same entries moved, so an entry keeps its opening from the file's log, and one closed before the split
  stays closed at its closing commit. The same commit adds no entry to a derived report's rows (the squash
  commit of the split PR files nothing).

    <why>*). An interactive holder (`unattended: false`) is the person's own and is told nothing. The
    page's toast names who was told (*TD-724 · grinder-ao-2 told to drop it*). The note is read when the
    holder's turn ends (§4.10 *When it is read*), so a merge already under way in that turn is not
    stopped: the tell is the person's quickest word, not a lock on the PR.
  - **An entry can land held** (TD-1296): an entry the person is still shaping, filed by an
    interactive session (`unattended: false`: the person is at its keyboard), is filed with
    `**Blocked by:** decision (<person>)` and an `**Ask:**`, `<person>` read as above, so it is in no
    lane from its first reading and waits for the person's answer however many PRs amend it meanwhile.
    Its id is reserved as any is (`ao td reserve`, §4.7). The package's `entry.md` (§4.9 *Add an entry
    to the ledger*) says so: *an interactive session filing an entry the person is still deciding
    writes `Blocked by: decision (<person>)` with an Ask*.
  - **Never settled**: a decided board line and a red PR's work order (§4.4 *Board write-back*, *A red
    PR nobody holds*), which are not ledger entries; every Kind the map leaves at 0.
  - **Shown where it is read, not pushed**: `ao repo` prints *settles in 7m* after the entry's owner,
    and the Repo page's row draws the same. No Inbox row for a settling entry: the window is minutes
    long, and a row that leaves before it is read is noise; an entry the person files they know of,
    and one a session files the Repo page shows.

  **An entry says what it waits for** (TD-715), so a lane whose every entry waits reads as waiting, not
  as work left. The page's kinds (above) say whether an entry is blocked by another entry or a
  decision; a pickable entry may still wait on something no `Blocked by:` item can name.
  - **The `**Waits:**` line** is this repo's own header field, written in the header block after `Kind:`, declared on the ledger's `Fields:` line
    (`Waits = until | event`, cadence §2.12), so `scripts/ledger.py --check` validates its first word and
    the cadence's `Blocked by:` rule is untouched. It has two shapes:
    - **`until <date>`**, a date in the home's local time: *`**Waits:** until 2026-10-16 — CI runs on or
      after 10-16`*. The entry waits until that day begins; from then the line reads as unwritten,
      and the entry is told as new to a lane whose member declared out of work before it (§6 rule 6).
    - **`event`**, a thing that happens and that nobody in the lane can cause: *`**Waits:** event — the next
      cadence-sync PR`*. The entry waits until the line is edited away.
    - **What waits on the person is not a `Waits:` line**: it is `Blocked by: decision (paul)`, with what
      the person must do written after it as the decision's pointer (*`decision (paul) — a
      permissions: rule for …`*), or `Owner: paul` where the whole entry is the person's to run (an
      evaluation that needs an attended session). Both already read *for you* (above) and join the person's
      count; `decision (paul)` leaves every lane, and `Owner: paul` every lane that names an owner (a
      `free-pick` lane with no `owner:` word still takes a pickable one, *A member's own count* below).
  - **What a wait does.** The reader reads the line from the entry's text (`waits: {on, date, why}`; a
    `until` with no readable date is waiting with no end, and the reader flags it, *TD-NNN: Waits:
    until names no date*). Whether it still waits needs the clock, so the agent's marking pass that
    adds `settling` (above) adds **`waiting: {on, until}`** to an entry whose wait stands. It runs on
    each reading it carries, so a date's wait ends on its day. A marked entry is withheld as a
    settling one is: it matches no lane, its page kind is unchanged, and rule 6 tells a member of it
    once the wait ends. **`ao progress claim`** on a waiting entry is refused, *TD-463 waits until
    2026-10-16*. Unlike a settling entry, `--force` passes it, since the session may know that the
    event has come; that session's PR removes the line.
  - **Counted apart.** `in_lanes` (below) counts what a lane would take but for its wait as
    **`waiting`**, `{until: [ids], event: [ids]}`, apart from the kinds' counts and the rest, and each
    member gains its own `waiting` ids beside `ids`, which leave them out. So a member out of work
    with nothing it can take and entries that wait is not *out of work with n*, and reads as waiting
    (§4.5a *card: compact*, *Repo page: waits mark*; §4.7 `ao repo`).
  - **Who writes it.** The session that reads an entry it cannot take for one of these reasons writes
    the line, in one ledger PR per run before it declares out of work, and only on entries that do not
    yet say why (the briefs, `docs/briefs/`). A written entry leaves the lane, so the next run does not
    read it again and the PRs do not repeat. `ao progress none --why` is never parsed for it.

- Usage, **reported first and asked for last** (TD-231). The usage endpoint is no documented
  interface: the tool's own clients read it too, and its refusals carry no usable `Retry-After`.
  What a session of the tool is *told* about its limits is
  documented, so that is the source:
  - **A report.** An adapter whose tool tells its sessions their limits hands them to the host
    agent as `usage_report {windows: [{label, pct, resets}], fresh}` (§4.3), an RPC of its own
    beside `hook`, since a report is no state event. Claude Code's is its **status line**: the
    launch's `--settings` layer names `shiftlead-hook --statusline` as `statusLine`, with a
    refresh of sixty seconds so that a session deep in one long tool run still reports. The
    tool hands the command `rate_limits` on stdin (the five-hour and seven-day windows, each a
    percentage and a reset; a subscription's only, after the session's first response, from
    the client version that carries them). The adapter rounds the percentage to one decimal
    and writes the reset, which arrives as seconds since the epoch, as the instant every other
    reading carries. The command reports **when a number or a reset changed, or a minute has
    passed**, never on every redraw; it sends with a short timeout and queues nothing, since
    the tool cancels a status line that is still running when the next is due, and a report
    delivered late would be read as new.
  - **The person's own status line still shows.** A `statusLine` in a settings layer replaces
    every other, so the command runs the one it displaced — looked for in the directory's
    `.claude/settings.local.json`, then its `.claude/settings.json`, then the profile's own
    settings, the first that names one, with its padding carried over — hands it the same
    stdin and prints what it prints; with none, it prints nothing. Nothing of the person's is
    edited: the layer is the launch's, as the hooks are. Where the tool draws no status line
    at all (hooks disabled by policy, a directory not yet trusted), nothing is reported and
    the endpoint below is what is left. A session started by hand, outside shiftlead, has no
    layer and reports nothing.
  - **A report is not proof of a fresh number.** The tool redraws the status line on more
    than a new response (a compaction, a change of mode, the refresh, a window's reset), and
    hands the same `rate_limits` it was last given. So `fresh` is the adapter's word that the
    session has had a response since its last report, read from the payload's own running
    totals of the session's API work; a report that is not fresh changes no reading's age.
  - **The reading** is per account and per window, `{label, pct, resets, at, source}`, `source`
    `reported` or `asked`, and the reading's own `fetched`, `source` and `by` (the reporting
    session's name) are the newest confirmation's, which is the age the chip prints. Reports are
    **merged by what a window can do, not by who spoke last**: inside one `resets` a window's
    use never falls, so the highest percentage stands, and a later `resets` replaces the window
    outright; two resets within five minutes of each other are one window (`RESET_SLACK`: the
    status line hands epoch seconds, the endpoint an instant of its own, and a rolling window's
    reset drifts between reads). The endpoint's answer is the account's own rather than one
    session's view of it, so it sets each window it names outright, a lower number included,
    and keeps the windows it does not name, and one taken before a window's last report leaves
    that window as the report left it; `at` moves when a fresh report or an answer
    confirms the number. A window whose `resets` has passed is
    **unknown until it is read again**, never zero and never a cap: `limited` (§4.2) is not
    read from it. **A short history** is kept beside each window in `usage.json`: the newest
    reading and one per ten minutes for the three hours before it, which is what a
    projection takes its rate from (§6 *Usage gate*).
  - **A node's sessions report to their node**, which merges the report for its own gate and
    sends it on to the home over the link (`usage_report {id, account, windows, fresh}`, node to
    home; one the link could not carry, or sent before its snapshot is taken, is dropped, not
    queued, for the reason above). `account` is the key the node reads the session's profile
    under, since the node holds the profile's credentials and a profile of the same name at the
    home may be another login; the home takes it only for a record of that link's host and an
    account of that record's adapter, and remembers it per node and profile. The home merges
    the report as its own sessions' and shows the account while that session lives, never
    asking the endpoint for it; a profile a session at the home runs under keeps the home's own
    account's reading, and one two nodes key to two accounts shows the first node's by name,
    since a reading is per profile; a node's key is forgotten once no live session of that node
    runs under the profile, and a report for a record that is no live tool session sets none. A
    profile metered at the home is no bar to a node's report under that name, since the node
    withholds its own metered profiles and the name may be another login there. After a restart
    the home keeps the reading a node's profile held in `usage.json` until the node's first
    report, which merges onto it — history and all — when it is of the account the node names.
    **The home holds the account's reading and sends it back** to each node that keyed a live
    session to it, as `usage_reading {account, reading}` (home → node, a notification on the
    road the settings take: the windows, `fetched`, `source` and `by`), whenever it moved since
    that link was last told and once more on each new link, never before its snapshot, refused
    not queued. The node takes it for an account one of its live tool sessions is keyed to and
    no other, **window by window**: a window the home confirmed later, or saw roll, is the

- **A call that is never answered is an error, not a wait without end** (TD-063). A call waits
  `client.CALL_TIMEOUT` (120 s, the same bound the agent gives an act over its own link) and then

  the agent's socket, the client's, the link's — is opened with the same `FRAME_LIMIT` (8 MiB,

  **The reading tells a run that never started from a red one.** This holds only for a repo whose
  `origin` is on GitHub; any other repo reads as today.
  - **Which jobs are read.** For each open PR `fold_checks` would call *red*, the failing check
    runs that are GitHub Actions jobs (`detailsUrl` `…/actions/runs/<run>/job/<job>`; a job's id is
    its check run's id) are read once per head, off the loop as the other `gh` reads are. They are
    read in order, and the reading stops at the first job that started, since one real failure
    makes the PR red whatever the rest say.
  - **The cap.** Fifty jobs are read at most per PR per head. A PR whose failing jobs run past the
    cap without one that started stays *red*, since the unread rest is no evidence.
  - **The read.** It is `gh api repos/<o>/<r>/actions/jobs/<job>`, then `gh api
    repos/<o>/<r>/check-runs/<job>/annotations`.
  - **Never started** takes three things: the job is `completed`; it has no steps and no runner
    (`steps` empty, `runner_name` empty); and an annotation begins *The job was not started
    because* (any of its annotations, its level whatever; the first page of thirty is read). That
    annotation's sentence is the reason, classed *billing* when it names account
    payments or a spending limit, *other* otherwise. A job with no such annotation is a real
    failure, as is a job cancelled while queued, which has no steps and no runner too.
  - **The word.** A PR whose failing items **all** are Actions jobs that never started reads
    **`checks: not_run`**, whatever else is still pending, since the account blocks every run to come

    (§4.5a).

    not-started ones out.
  - A job that cannot be read (a 404, a rate limit) is no evidence, and the PR stays *red*, as
    today.

  **Both roads.** The home keeps what it gave in `ids.json` beside `repos.json`: `{<origin>: {last, given: [{id, by,
  at}]}}`, keyed by the repo's origin: `owner/repo` for a GitHub origin, ssh or https alike, and
  the lowercased URL otherwise, so two clones of one repo share one counter, and the lock is keyed the
  same way. The call names the repo by its registered name, never by a path, which would be a
  node's. A name two registered checkouts of different origins share is refused, naming both,
  and the CLI then sends the origin's `owner/repo`. Checkouts of one origin are one repo here: one
  counter and one remote, so the first of them serves the call. `by` is
  the envelope's `caller` as the dispatcher sets it (§4.8a: verified under `identity: enforce`, as
  claimed under `observe`), or `person` for a call with none; it is never a parameter. `given` keeps
  the newest 200. The reads and the write happen under one lock per repo, so two sessions asking at
  once get different ids with no rebase. The whole call has a budget of 45 seconds from its arrival,
  the wait for the lock included, well under a client's 120-second timeout. A lock not taken 30
  seconds in refuses (*busy, ask again*). On the home's own road the PRs are read a few at a time until 30 seconds in, and
  a PR not read by then is *unread* (*budget*). The fetch has until 45 seconds in, and refuses when it
  does not finish. Every `gh` and `git` call runs off the host agent's event loop and is killed at
  its deadline. On the script's road the lock and the budget are the same: the script runs off the event
  loop, gets what is left of the 45 seconds, and is killed at that deadline. An id given is never given again and never expires. One that is given and never
  used is a gap in the numbers, which cadence §2.2 does not forbid: ids are assigned in order and never
  reused. A PR the home could not read is named in the answer (*open PRs not read: <why>*), and the
  ids still come from the other sources. A list that fails (no `gh`, an origin that is not
  GitHub's, a rate limit) or that fills its 200 is one such line for the whole list. A PR is unread when its files cannot be listed, when its
  listing is cut (GitHub lists 3000 files at most), or when a ledger file in it has no `patch`
  (GitHub leaves out the patch of a large diff). A fetch that fails refuses the call with its reason, since
  main's ids are the floor.

  **Without the home.** A session outside the org (a cloud session, [ADR
  2026-09-24](../decisions/2026-09-24-cloud-sessions.md)), a session on a node whose link is down, or a repo
  with no home runs `scripts/ledger_next_id.py` itself (cadence §2.10: the repo's front end where it has one,
  else the script, never by hand). It reserves on the same counter, so it and the home never give one id
  twice. Where the script falls back (exit 3: a cloud session's harness pushes only its own branch), the id is
  unreserved, and the cadence check's `ledger` row is the backstop: it fails an open PR's new id that main or
  another open PR also adds.

  **Why not subtask ids** (*TD-682a*, Paul's question): the id format is ledgerboard's (its
  heading, row and item patterns match `TD-` and digits, and its `_num` reads an int), so a suffix
  would be an agent-cadence release into every consumer. It would also stop collisions only among one
  design's builds, and it would repeat what `Part of:` already says. The builds are grouped by
  `Part of:` instead (§4.5 screen 11 *its builds*).
