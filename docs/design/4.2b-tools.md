### 4.2b Tools: the CLIs, accounts and logins on a host

**Designed by TD-1953, with Paul; its builds are TD-1971 to TD-1975, and TD-1976 designs the cut-over window.** The frame is
[ADR 2026-11-18](../decisions/2026-11-18-tools-flows-teams.md). Every part of this is built and promoted
before **the switch-over**; until it a host draws only its tools (*The page*), and its logins and accounts
wait for it: in one window, each host moves from profiles (§4.2a)
to logins, and from then on it has no profiles (the frame, *One window, no dual read*). This section says
what the page shows and writes after the window, and what the window does on a host. The builds also amend
what this section changes elsewhere — §4.3's Protocol block (the reads below), §4.4a's provisioning, §4.5's
pages, §5's keys, §6's Usage card — each named in its build entry. The mockups are
`docs/mockups/reviews/2026-11-18-td1953-tools-own5-{1440,420}.png`.

**Terms used below.** A **tool** is a CLI an adapter drives (Claude Code, Grok Build, Gemini CLI). A
**login** is one home of one tool on one host: the folder a launch points the tool at, where the tool
keeps its sign-in — Claude Code's `CLAUDE_CONFIG_DIR`, Grok Build's `GROK_HOME`, Gemini CLI's
`GEMINI_CLI_HOME` (the parent of its `.gemini/`, so the tool's default is `~` itself; §4.3, each adapter's
`default_home`). It is what a team's login list names (the frame). An **account** is who a login is signed
in as, by the tool's own key for it; two logins with one key are one account, sharing one quota and one
reserve (§4.2a, TD-122, TD-1581). **Names are fixed**: a login's **name** and an
account's **key** (`<adapter>:<name>`, as today) are set when it is made and never change, so a team's
list, `director:` and every store that holds one never breaks. A name is unique per tool on a host, at most
24 characters, of letters, digits, `-` and `_` only, its first a letter or digit (a `:`, `.`, `@` or space would break a key, a commit line or a path).
A **label** is what the person reads instead, where they have set one: ✎ changes the label and nothing
else. A **tools shell** is the shell the page opens for a login (below).

#### The page

**Tools** is a page of the person's own (§4.5), for **the home's host** — its header reads *Tools on
`<host>`*, with when the host agent last read it and **Check again**. A node's tools are not drawn (*Not
here*). **A host is switched** when it has a `logins.yml` — one function, `switched`, that every Tools build
calls; who writes the file at the window is the cut-over's design. Before then the page draws the tool cards,
versions, found rows and *Not ready to run here*, and Check again and Install work; it draws no accounts or
logins, every `ao login …` and `ao account …` verb is refused, *after the switch-over*, and the reserves stay
on the Settings page's Usage card (`ao gate` unchanged). From the switch they move here. It shows, in order:

- **A card per supported tool that is installed** — an adapter is registered for it and its binary is
  found — headed by its name and the version found. Under it, drawn as a tree:
  - **each account** its logins are signed into: its label (✎), the plan the tool records, the model
    families it offers, and **the gauge**;
  - under each account, **its logins**: the label (✎), the folder's path, a model pin where it has one
    (`pinned: flash-lite`, the login's, so drawn here and not on the account), an optional note in italics,
    the state, and **⋯**;
  - **Not signed in**, a dashed group holding the tool's logins with no identity to read;
  - **a found row**, dashed: the tool's default home when it is signed in and no login yet, with **Add** —
    except for an adapter whose launch writes into its home (`own_home`, §4.3: Grok Build), whose default
    home may not be a login (§4.2a), where the row reads *the tool's own home: ShiftLead launches into a
    folder of its own* and offers + Add login instead;
  - **+ Add login**, once per tool.
- **Not ready to run here**, greyed dashed cards: a supported tool not installed on this host (with
  **Install**), a tool installed with no adapter (*Codex 0.163.0 installed: ShiftLead has no adapter for
  it yet, so no seat can run on it*), and a tool with neither (*no adapter yet*, no Install — ShiftLead
  never offers to install what it cannot run).

Wherever a label is set the page, `ao` output and commit lines show it, the name beside it where both are
drawn (`ao tools`: `claude-paul (shown as "work laptop")`). The page has no Add tool (every supported tool is
drawn already, and Check again re-reads the PATH), no default login list (*Not here*), no update check (the
version is the one found), and no host switch. It draws no smoke passes: a pass is a tool, a model and a
role, and part of whether a login is *usable* for a seat (the frame), so its record, seeding and drawing
beside each seat's model are TD-1954's; no state here reads it.

**The gauge.** One per window the account reports, the week's first: the window's use fills from the
left, the account's **reserve** is a hatched bay held from the right, and the gap is labelled *room for
unattended work: N%*. A metered account draws one per window it sums (`day`, `week`, `month`, §4.2a), its
spend against that window's amount. Under each, the reserve field (*keep back*), taking what `ao gate`
takes (§6 *Usage gate*) and written to the home's `settings.yml` through `set_settings`. An account with
no reading yet draws an empty striped gauge, *No usage reading yet*, and the field all the same, its
window labels unchecked as the Settings card says today, so a new account's first unattended run can
already be bounded (an adapter with no `usage`, Grok Build's today, is always so). A reading past its
trust age draws *stale* (TD-1680), and an account whose logins disagree on billing draws *mixed* with the
gate's reading of it (§6). The Settings page's Usage card moves here for every account of the home's host;
an account seen only on a node keeps its Settings card until nodes are drawn, and the weights stay on
Settings. An account's reading is the vendor's for the account, so it already counts every host's use, and
a node's account shares the home's reserve where its key is the same (§6 *A reserve is the account's*).

**A login's state**, from `identity` (a match or none), `credentials_ok(home)` (§4.3: True, False, or None
where it cannot tell) and the login's `billing`:

| identity | credentials_ok | drawn |
|---|---|---|
| a match | True, or None | *signed in*; *limited till T* when its account's reading says the tool's cap (§4.2) |
| a match | False | **Sign in again** (an expired sign-in); the login stays under its account. Grok Build's `credentials_ok` never answers False, so a Grok login never draws it |
| none | False, or None | in *Not signed in*, with **Sign in** |
| none | True | *signed in*, an account of its own (an API key with no identity: a Gemini AI Studio key, an `ANTHROPIC_API_KEY` in the folder's `settings.json`) |

A `GEMINI_API_KEY` in the host agent's environment signs in every Gemini login on the host with one key
the page cannot see; each such login with no identity of its own draws as an account of its own, and every
Gemini login carries the warning, *one key from the environment
signs in every Gemini login here: their reserves bind nothing in common*. A metered login is never
*limited* (§4.2a) and draws its account's amount instead. The states are read when the host agent starts,
on Check again, while a tools shell is open (below), at each launch on the login, and when a launch is
refused for its credentials (§4.3); *limited* follows the account's reading on each tick.

**Matching across a restart.** A match lives only as long as one run of the host agent (`identity`,
below), so at start each login's stored `account` stands; it is kept through a sign-out. A login with no
identity is an account of its own under a key derived from it, `<adapter>:<login name>`, which is never
written to its `account` (its reserve sits under the derived key). Each pass of reads (at start, Check
again, a tools shell's poll) is settled once all its reads are in, in this order:

1. **A change seen within the run** — a login's match differs from its own last *match* this run (none is
   not a match) — moves it to the account whose logins read that match, or draws *name its account* where
   none does.
2. **A login's first match this run** joins its stored account, unless that match equals another account's
   logins' match, or its stored account's other logins read another match.
3. **Those two cases** mark logins *these logins read different accounts*: in the first, the incoming login
   only; in the second, every login of its stored account. A marked login launches nothing, and the mark
   clears when the person's act (`ao login account`, or signing the login in again) leaves the matches
   agreeing.
4. **A login with no stored account and a match no account has** — a new login, or one that had no identity,
   whose derived key's reserve then follows *A login changes account* — draws **signed in — name its
   account** and launches nothing until the person names it, since a key is fixed for ever.

`ao login account <login> <account>` takes an account's key, or its name (the key `<adapter>:<name>`); a name
no account has makes a new key. It is refused where the result would leave a mismatch (a match another
account's logins read, or an account whose logins read another). **A retired key** is one no live login's
`account` or derived key names that a `forgotten:` login names or `settings.yml` holds a reserve under; a bare name that
composes to a retired key is refused everywhere (`ao login account <name>`, `ao login add --account`, a
suggested name), while the full key given to `ao login account` rejoins it deliberately, taking its reserve
and history. A login that is its account's only signed-in one and was signed in as someone else while the
agent was down is not caught — accepted, as storing nothing that can confirm an address is worth more (round
2's F100; the person's call to reverse).

**⋯ on a login**: *Open a shell here* (a tools shell); *Settings* (below); *Edit note*; *Forget this
login*, which moves it to `logins.yml`'s `forgotten:` and leaves the folder on disk. Forget is refused, naming them,
while a live session runs on the login, or a team's login list, `director:`, `sweep:` or a schedule names
it. When an account's last login is forgotten, its reserve stays, as an orphan reserve key does today, `ao gate`
lists it, and its entry leaves `accounts:`; its key is then retired (*Matching across a restart*), so no new
account inherits its reserve or history by name.

**A login's Settings**, each checked by §4.2a's rules (a metered login's own folder, an adapter with no
`spend` refused):

- **`billing`**, the person's: `logins.yml` holds it and it is the truth. `identity`'s reading of the
  tool's record (below) is offered at Add, and a mismatch later is drawn as a warning on the login, never
  applied — §4.2a's *never guessed* stands, the tool's record only suggesting;
- a metered login's **`prices`**: empty means a self-hosted model read in tokens, as §4.2a has it; the
  Settings page's weights for its models (§5 `spend.weights`) are offered as a fill-in;
- **`extra_args`**, **`unattended_args`** and **`permission_wait`** (§4.2a);
- a **model pin**, the person's, which must be a family the account offers.

**A login changes account** when it is first signed in or signed in as someone else: it moves under the
account its identity now reads, and launches on it from then on read that account's key. A login that was an
account of its own gives that account's reserve to the account it joins where the reserve's unit fits the
joined account's billing (a percent to a subscription, an amount to a metered one, TD-1581's rule), the
larger kept where both have one; otherwise the reserve is dropped, with a change line. A session's record
carries the **account key it was launched under** (`account`, node-owned like `tool_version`, in
`models.NODE_OWNED`: the launching host writes it at each launch of the record), so a running session
keeps its account's reserve until it ends, and the page marks the move. A team's login list names the
login, so it is unaffected.

#### Controls and verbs

Every control here gets a §4.5a row and an `ao` verb (§4.5a, the frame's last rule); the rows and their
help wording are the builds' (help text is bound to `help.py`). Every verb but `ao tools` is **person-only**
(`person_only`, §4.8: refused to a session, allowed from the person's own shell, a tools shell included); a
verb acts on the host it is run on; and the `ao login` and `ao account` verbs are refused before the switch:

| control | verb |
|---|---|
| the page | `ao tools [--json]`: the read below |
| Check again | `ao tools check` |
| ✎ on a login, on an account | `ao login label <login> [<label>]`, `ao account label <key> [<label>]` (a label only, names fixed; none clears it) |
| name its account, settle a mismatch | `ao login account <login> <key or new name>` |
| keep back | `ao gate` (today's; its `set_settings` write is person-only already) |
| + Add login, Use an existing folder, Add on a found row | `ao login add <tool> [--path <folder>] [--name <name>] [--account <name>]`: a `--path` that is a home (`is_home`) is used, one that does not exist or is empty is made a home, any other is refused; a forgotten login's folder takes back its old name, and a different `--name` is refused |
| Sign in, Sign in again, Open a shell here | `ao login shell <login>` |
| Install | `ao tools install <tool>`, which opens the tool's install shell |
| Settings | `ao login set <login> <key> <value>`, the key one of `billing`, `prices`, `extra_args`, `unattended_args`, `permission_wait`, `pin` |
| Edit note | `ao login note <login> <text>` |
| Forget this login | `ao login forget <login>` |

A login is named by its name (`<tool>:<name>` where a bare one is ambiguous), an account by its key. A
label is read only, never taken as a name. **The read** (`tools`) replies `{host, read_at, switched, tools:
[{adapter, binary, version, installed, supported, install_command, accounts: [{key, label, plan, billing,
models: {families, default, unconfirmed}, gauges, version}], logins: [{name, label, folder, account, state, mismatch, warnings, note, pin, version}], found: [{folder, own_home}]}], not_ready:
[...]}`; a login's `state` is one of `signed_in`, `limited`, `sign_in_again`, `not_signed_in`,
`name_account`, `mismatch` is the mark above, and `warnings` a list of codes the page draws on the login (`billing_mismatch`,
`env_key`, `moved_while_running`). A login with no identity is an account of its own keyed
`<adapter>:<login name>`. A login's or an account's `version` is a hash of its entry (nothing stored), and a write sends back
the one it read: a write over a newer version of that entry is refused, *<name> changed since this page read it — reload*.
The `ao` verbs read and send it themselves.

#### The tools shell

A **tools shell** is a `shell` session (§4.1) with no parent session: its id fixed and outside every
scope, `ao--tools-<adapter>-<login name folded>` for a login and `ao--tools-install-<adapter>` for an install:
`naming.slug` strips a leading `-`, so no repo, directory or name ever yields an id beginning `ao--`, and no
session today has one (§4.1 names the reservation). The fold lowercases and turns `_` into `-`; a login whose
whole id another login's shell or an install shell already has (one fold, or a hyphenated adapter name
meeting another's) is refused at Add. It runs in the person's home, not
the login's folder (which a Claude Code launch would write into that login's `.claude.json` `projects`), with
the environment `home_env(home)`. There is one of each: a second press reopens it. The host
agent types the command (`signin_command`, or `install_command`) with no Enter, and the person presses
Enter: ShiftLead runs no sign-in and no install (§4.3). It is the person's own shell. While a login's tools
shell is open the host agent reads its `identity` every few seconds, so the login moves under its account
as soon as the tool has written the sign-in.

A sign-in prints the account's email, OAuth links and device codes, and an API key is pasted there, so
**nothing of what the pane shows is kept or handed to a session**: it has **no run log** (its pane is not
piped to one; its record says `log: false`, and no page links one); every read of its pane — `tail`, the
pty bridge, search, a screen capture — is **person-only**, refused to a session; and a `send` or `keys` to
it records no text on the record (the host agent's own typed command, which is no secret, is recorded);
and the tick captures nothing of its pane, so its record's `tail` is empty and its `title`, `last_output`
and `screen_hash` unset, and the `keys` and `send` replies carry none of them (`log: false` is identity,
set at its start).
Every rule here matches on the id prefix `ao--tools-`, never on a name: `create` makes such an id only for a
tools shell (a name a person or session gives can never yield one, `naming.slug`); a pane with that prefix and no record is adopted as a tools shell, `log: false`, its name `tools-…` (the id without `ao--`, so no name starts with `-`); the tick's
capture skips it before adoption, as do the composer reads on a send, the wake and doorbell paths (it gets
no doorbell) and every other capture of a pane; and a hook report from it (a tool started there for `/login` runs
the login's hooks) is dropped at once, a `permission` report answered without a waiter. Pane reads include
`explain`, which returns the screen. This bounds ShiftLead's own reads: a session runs as the same unix user
and could run `tmux capture-pane` itself. That is
invariant 3's one exception, and invariant 11's (*reads are never gated*) (§9), and the conformance suite
checks each.

#### What the adapter reads

The adapter contract (§4.3) has some of what the page needs; the page reuses it and adds the rest. Each
read runs on the host, sends nothing anywhere, and is optional, named in the adapter's `implements`, its
check a row of the conformance suite (§4.3 *The conformance suite*):

- **reused**: `default_home(env)`; `tool_version(env)`; `credentials_ok`, in a home-taking form
  `credentials_ok(home)`; the binary each launch finds today (the PATH, then the places the adapter knows:
  Grok Build's `~/.grok/bin/grok`, Gemini CLI's npm prefix), lifted into **`find()`** so the page asks
  without launching; and **`home_env(home)`**, the environment each launch sets (`CLAUDE_CONFIG_DIR`;
  `GROK_HOME` with its launch home; `GEMINI_CLI_HOME`), lifted out of the launch — **empty where `home` is
  the tool's `default_home`**, as a launch on a profile with no `config_dir` sets nothing today (a Claude Code
  launch with `CLAUDE_CONFIG_DIR=~/.claude` would read `~/.claude/.claude.json`, another sign-in record, MCP
  servers and trust, where the unset launch reads `~/.claude.json`).
- **new**:
  - **`install_command()`**: the vendor's documented install line, confirmed at the build — Grok Build's is
    its `INSTALL_LINE`; Claude Code has none today, and Gemini CLI's `INSTALL_LINE` installs its machine
    layer (doctor's, unchanged), not the CLI.
  - **`signin_command()`**: the command alone, its environment `home_env`'s — Grok Build's `grok login`; for
    Claude Code and Gemini CLI the tool itself, signed in with its own `/login` (the row says *quit the tool
    once signed in*).
  - **`is_home(path)`**: whether a folder is this tool's home, by the files the tool writes there (for
    Gemini CLI under `<path>/.gemini/`).
  - **`identity(home, salt)`**: `{match, display, plan, billing}` or none. `match` is an HMAC-SHA256, under
    the `salt` the host agent makes at start and keeps only in memory, of the tool's account key — so two
    logins' matches compare within the running agent, and nothing written anywhere can be checked against a
    guessed address (the conformance row: one key under two salts gives two matches, two homes with one
    key give one). The key is Claude Code's `accountUuid`, from the `.claude.json` a launch
    on that home reads (`~/.claude.json` for the default home, the folder's own otherwise, as `home_env`
    sets); Grok Build's xAI user id, the `user_id` of `auth.json`'s entry (the entry is stored under the issuer and
    client id, the same for every account); Gemini CLI's active account in
    `.gemini/google_accounts.json`, which is an email. **The key never leaves the adapter**: no reply, log
    line, exception, `ao doctor` text or `--json` holds it, and the conformance row checks that a fixture's
    key appears in none. `display` is a display name where the tool records one (Claude Code's
    `displayName`, Grok Build's first name), else none, and never an email or part of one. `plan` and
    `billing` are the tool's record: Claude Code's `planDisplayName` and `billingType`; Gemini CLI's
    `selectedType` in `.gemini/settings.json` (an API key reads metered); Grok Build's `auth_mode`, which
    names no plan. `billing` is read as `subscription` or `metered`, none where the record does not say (a
    Grok Build key comes from the environment and writes no entry). Each source is confirmed against the installed
    tool at the build.
  - **`models(home, plan)`**: the model families the account offers and the family of the tool's default.
    No tool file lists them, so each adapter keeps a table of the families each plan offers, and of the
    model names each family covers; a plan the table does not know offers the adapter's whole list, marked
    *unconfirmed*. The Flows page reads this list (TD-1954).

**Known tools without an adapter** (Codex, opencode) are data, not code: a table in the `shiftlead`
adapters package naming each tool and its binary, read through the adapter registry, so no tool's name is
in core. Their `find()` is the PATH alone. A new adapter replaces its row.

The host agent reads all of this when it starts and on **Check again** (the binaries, the default homes,
every login's identity and credentials) and keeps the result; a tick reads only what it reads today
(usage, §4.4).

#### How a login is found and made

Never by guessing at names (a scan for `~/.claude-*` would mostly find test homes and scratch copies):

1. **The tool's default home**, when it is a home: a **found** row, never added unasked (it may be a
   scratch copy), and not offered where the adapter sets `own_home` (above).
2. **The logins the switch-over made** from the host's profiles (below), and every login made since.
3. **+ Add login → Use an existing folder**: the person types a path, `is_home` checks it, and it becomes
   a login.

**+ Add login** otherwise makes a new folder beside the tool's default, its path suggested
(`~/.claude-<name>`, `~/.config/grok-<name>`, `~/.gemini-<name>` holding a `.gemini/`) and the person's to
change, and opens its tools shell for **Sign in**. When `identity` first reads a match, the login joins that
account, or, where no account has it, waits for the person to name one (*signed in — name its account*,
above; `--account` names it up front, a retired key's bare name refused). A new login's name is suggested as `<tool>-<display>` and a new
account's as `<display>`, each folded to the name's characters (`Paul K` → `paul-k`), a suffix added where
it is taken (`-2`); with no display name (always so for Gemini CLI) the person types it. **Install** opens a tools shell,
in the person's home, with `install_command()` typed.

#### Where it lives

**`~/.shiftlead/logins.yml`**, the host's, is written by its host agent — and, for a container node, by the
home's provisioning (*On a node*): `logins:` (by name: tool, folder, label, note, account key, `billing`,
`prices`, `extra_args`, `unattended_args`, `permission_wait`, pin), `accounts:` (by key: label) and
`forgotten:` (by `<tool>:<name>`: its folder and account). An ended or resumable record still resolves its
folder through it, so its transcript stays readable; `ao login add --path` on that folder gives the name and
account back; any other folder is refused the name, so a record can never resolve to another folder and read
another account's transcripts (§4.3). It
replaces `profiles.yml` among the home's tracked definitions (§4.9 *What is left at the home has a
history*; §4.9's and §5's lists, and `defs.TRACKED`, at the switch-over): the host agent commits it after
each of its own writes, with the message `logins: <change>` (with `settings.yml` in the same commit where a
reserve moved), so it is never committed later as *edited by hand*. It holds no secret and no identity, and a note must not hold one: which login is which account is each
login's `account`, and an identity is compared only in the host agent's memory (`identity`, below). Its reader and writer are `sessionorc`'s (data, no tool
name in them). A settings commit's change line is composed by `agent_settings` with labels, `defs` reading
no file for meaning.

A login named outside its host — a team's login list, `director:`'s `logins:` — is resolved on the host
that launches, by name, so a list naming `claude-paul` takes each host's own `claude-paul`.

**On a node.** A node's `logins.yml` is its own and untracked; its loss costs its logins' names, accounts,
settings, notes and `forgotten:`, found again from their folders by `ao login add --path`. Forget on a node
is not refused for the home's lists (a team's, `director:`), which it cannot read. A container node's file is
written by the home's provisioning (§4.4a, amended — the cut-over's and TD-1153's build, not a Tools-page
one): a login for each name in the login lists of what runs on that node, under the home's name, its
`account` key and `billing` copied from the home's login (a node cannot compare identities with the home),
its folder `/shiftlead/profiles/<name>/` (an existing signed-in one kept), signed in by hand inside once as
today; re-provisioning adds the missing and removes none. A machine node's is made on it, its names matched
to the home's by the person. A host made after the switch-over starts with an empty `logins.yml`, so its
first login can be added.

#### What the switch-over makes

How the window runs — the order of the home and the nodes, what a host does with a launch or a repo file
of the other shape, the migration against a live host agent and its resumption, going back after activity
since the window, and how today's readers of a record's `profile` keep working — is the **cut-over's
design**, an entry of its own after the Flows and Team rounds (the frame; TD-1953's ledger lists what it
inherits). This page needs only what the switch-over must make on each host, which that design follows:

- **A login per distinct folder** among the host's profiles (a profile's `config_dir`, else the tool's
  default home; a `shell` profile, and one whose adapter is not registered, makes none), named with the
  first profile's name on it, or a name the person gives; its `billing`, `prices`, `extra_args`,
  `unattended_args` and `permission_wait` from those profiles; a pin only where every profile on the folder
  names one model, mapped to its family through the adapter's table (`gemini-reader`'s
  `gemini-3.5-flash-lite` → `flash-lite`).
- **An account per key, unchanged**: `<adapter>:<account:>`, else `<adapter>:<profile name>`
  (`profiles.account_of`), so no reserve, reading or ledger moves.
- **Refused beforehand, for the person to fix in the old shape**: profiles on one folder that disagree on
  `billing`, `prices`, `extra_args`, `unattended_args` or `permission_wait` (one that differs only in
  `permission_prompts`, `grind-ask`'s case, is a flow's seat setting, the frame); profiles on one folder that
  give more than one key today (two profiles with no `account:` are two keys, two reserves and two ledgers,
  until the person gives them one `account:` and merges their reserves by hand); two keys whose folders read
  one identity, or one key whose folders read two; a name outside the name characters or over 24 of them, or two names of one tool with one fold; one folder reached
  both as a `config_dir` and as the tool's default (two `.claude.json` under one login); a pinned model the
  adapter's table cannot map.
