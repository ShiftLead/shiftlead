### 4.2b Tools: the CLIs, accounts and logins on a host

**Designed by TD-1953 (2026-11-18, with Paul); builds to be filed at the round's end.** The frame is
[ADR 2026-11-18](../decisions/2026-11-18-tools-flows-teams.md). The Tools page, the logins and the new
launch path are built and promoted before **the switch-over**, read by nothing; in one window every launch
moves from a profile (§4.2a) to a model and a login, and from then on there are no profiles (the frame,
*One window, no dual read*). This section says what the page shows and writes after the window, and what
the window does to a host's profiles. The mockups are
`docs/mockups/reviews/2026-11-18-td1953-tools-own5-{1440,420}.png`.

**Terms used below.** A **tool** is a CLI an adapter drives (Claude Code, Grok Build, Gemini CLI). A
**login** is one home of one tool on one host: the folder a launch points the tool at, where the tool
keeps its sign-in — Claude Code's `CLAUDE_CONFIG_DIR`, Grok Build's `GROK_HOME`, Gemini CLI's
`GEMINI_CLI_HOME` (the parent of its `.gemini/`, so the tool's default is `~` itself; §4.3, each adapter's
`default_home`). It is what a team's login list names (the frame). An **account** is who a login is signed
in as, by the tool's own key for it; two logins with one key are one account, sharing one quota and one
reserve (§4.2a, TD-122, TD-1581). A **label** is the name the person reads for a login or an account,
unique per tool on a host, of letters, digits, `-` and `_` only (a `:`, `.`, `@` or space would break a key,
a commit line or a path). A login's label sits over an **id**, so a team's login list survives a rename;
an account's **key** is `<adapter>:<label>`, as today. A **tools shell** is the shell the page opens for a
login (below).

#### The page

**Tools** is a page of the person's own (§4.5), for **the home's host** — its header reads *Tools on
`<host>`*, with when the host agent last read it and **Check again**. A node's tools are not drawn (*Not
here*). It shows, in order:

- **A card per supported tool that is installed** — an adapter is registered for it and its binary is
  found — headed by its name and the version found. Under it, drawn as a tree:
  - **each account** its logins are signed into: its label (✎), the plan the tool records, the model
    families it offers, and **the gauge**;
  - under each account, **its logins**: the label (✎), the folder's path, a model pin where it has one
    (`pinned: flash-lite`, the login's, so drawn here and not on the account), an optional note in italics,
    the state, and **⋯**;
  - **Not signed in**, a dashed group holding the tool's logins with no identity to read;
  - **a found row**, dashed: the tool's default home when it is signed in and no login yet, with **Add** —
    except for an adapter whose launch writes into its home (`own_home`, §4.3: Grok Build), whose default
    home may not be a login (§4.2a), where the row reads *the tool's own home: ShiftLead launches into a
    folder of its own* and offers + Add login instead;
  - **+ Add login**, once per tool.
- **Not ready to run here**, greyed dashed cards: a supported tool not installed on this host (with
  **Install**), a tool installed with no adapter (*Codex 0.163.0 installed: ShiftLead has no adapter for
  it yet, so no seat can run on it*), and a tool with neither (*no adapter yet*, no Install — ShiftLead
  never offers to install what it cannot run).

The page has no Add tool (every supported tool is drawn already, and Check again re-reads the PATH), no
default login list (*Not here*), no update check (the version is the one found), and no host switch. It
draws no smoke passes: a pass is a tool, a model and a role, and part of whether a login is *usable* for a
seat (the frame), so its record, seeding and drawing beside each seat's model are TD-1954's; no state here
reads it.

**The gauge.** One per window the account reports, the week's first: the window's use fills from the
left, the account's **reserve** is a hatched bay held from the right, and the gap is labelled *room for
unattended work: N%*. A metered account draws one per window it sums (`day`, `week`, `month`, §4.2a), its
spend against that window's amount. Under each, the reserve field (*keep back*), taking what `ao gate`
takes (§6 *Usage gate*) and written to the home's `settings.yml` through `set_settings`. An account with
no reading yet draws an empty striped gauge, *No usage reading yet*, and the field all the same, its
window labels unchecked as the Settings card says today, so a new account's first unattended run can
already be bounded (an adapter with no `usage`, Grok Build's today, is always so). A reading past its
trust age draws *stale* (TD-1680), and an account whose logins disagree on billing draws *mixed* with the
gate's reading of it (§6). The Settings page's Usage card moves here for every account of the home's host;
an account seen only on a node keeps its Settings card until nodes are drawn, and the weights stay on
Settings. An account's reading is the vendor's for the account, so it already counts every host's use, and
a node's account shares the home's reserve where its key is the same (§6 *A reserve is the account's*).

**A login's state**, from `identity` (a key or none), `credentials_ok(home)` (§4.3: True, False, or None
where it cannot tell) and the login's `billing`:

| identity | credentials_ok | drawn |
|---|---|---|
| a key | True, or None | *signed in*; *limited till T* when its account's reading says the tool's cap (§4.2) |
| a key | False | **Sign in again** (an expired sign-in); the login stays under its account |
| none | False, or None | in *Not signed in*, with **Sign in** |
| none | True | *signed in*, an account of its own (an API key with no identity: a Gemini AI Studio key, `GEMINI_API_KEY` in the host agent's environment, an `ANTHROPIC_API_KEY` in the folder's `settings.json`) |

A metered login is never *limited* (§4.2a) and draws its account's amount instead. The states are read
when the host agent starts, on Check again, while a tools shell is open (below), at each launch on the
login, and when a launch is refused for its credentials (§4.3); an identity that changed is marked on the
login; *limited* follows the account's reading on each tick. The header's *read N ago* is their age. A
login at its account's reserve is not marked: the gauge says it.

**⋯ on a login**: *Open a shell here* (a tools shell); *Settings* (below); *Copy id*; *Edit note*;
*Forget this login*, which removes it from `logins.yml` and leaves the folder on disk. Forget is refused,
naming them, while a live session runs on the login, or a team's login list, `director:`, `sweep:` or a
schedule names it. When an account's last login is forgotten, its reserve stays, as an orphan reserve key
does today, and `ao gate` lists it.

**A login's Settings**, each checked by §4.2a's rules (a metered login's own folder, an adapter with no
`spend` refused):

- **`billing`**, the person's: `logins.yml` holds it and it is the truth. `identity`'s reading of the
  tool's record (below) is offered at Add, and a mismatch later is drawn as a warning on the login, never
  applied — §4.2a's *never guessed* stands, the tool's record only suggesting;
- a metered login's **`prices`**: empty means a self-hosted model read in tokens, as §4.2a has it; the
  Settings page's weights for its models (§5 `spend.weights`) are offered as a fill-in;
- **`extra_args`**, **`unattended_args`** and **`permission_wait`** (§4.2a);
- a **model pin**, the person's, which must be a family the account offers.

**A login changes account** when it is first signed in or signed in as someone else: it moves under the
account its identity now reads, and launches on it from then on read that account's key. A login that was an
account of its own (no key) gives that account's reserve to the account it joins where the reserve's unit
fits the joined account's billing (a percent to a subscription, an amount to a metered one, TD-1581's rule),
the larger kept where both have one; otherwise the reserve is dropped, with a change line. A session's
record carries the **account key it was launched under** (`account`, node-owned like `tool_version`: the
launching host writes it at each launch of the record), so a running session keeps its account's reserve
until it ends, and the page marks the move. A team's login list names the login, so it is unaffected.

#### Controls and verbs

Every control here gets a §4.5a row and an `ao` verb (§4.5a, the frame's last rule); the rows and their
help wording are the builds' (help text is bound to `help.py`). Each writing verb is a **person-only RPC**,
refused from a session (`SHIFTLEAD_SESSION` set) as `ao promote` is:

| control | verb |
|---|---|
| the page | `ao tools [--json]`: the read below |
| Check again | `ao tools check` |
| ✎ on a login | `ao login rename <login> <label>` |
| ✎ on an account | `ao account rename <adapter>:<label> <label>` |
| keep back | `ao gate` (today's; its `set_settings` write is person-only already) |
| + Add login, Use an existing folder, Add on a found row | `ao login add <tool> [--path <folder>] [--label <label>]` |
| Sign in, Sign in again, Open a shell here | `ao login shell <login>` |
| Install | `ao tools install <tool>`, which opens the tool's install shell |
| Settings | `ao login set <login> <key> <value>` |
| Edit note | `ao login note <login> <text>` |
| Copy id | the id, shown by `ao tools` |
| Forget this login | `ao login forget <login>` |

A login is named by its label (`<tool>:<label>` where a bare one is ambiguous) or its id, an account by its
key. **The read** (`tools`) replies `{host, read_at, tools: [{adapter, binary, version, installed,
supported, install_command, accounts: [{key, label, plan, billing, models, gauges}], logins: [{id, label,
folder, account, state, note, pin, version}], found}], not_ready: [...]}`. A login's `version` is a hash of
its entry (nothing stored), and a write sends back the one it read: a write over a newer version of that
login is refused, *<label> changed since this page read it — reload*. The `ao` verbs read and send it
themselves.

#### The tools shell

A **tools shell** is a `shell` session (§4.1) with no parent session and **no run log**: its pane is not
piped to one and its record says so (`log: false`), so no page links or serves one. For a login it is
`tools-<login id>`, its directory the login's folder and its environment `home_env(home)`; for an install,
`tools-install-<adapter>`, in the person's home. There is one of each: a second press reopens it. The host
agent types the command (`signin_command`, or `install_command`) with no Enter, and the person presses
Enter: ShiftLead runs no sign-in and no install (§4.3). It is the person's own shell. While a login's tools
shell is open the host agent reads its `identity` every few seconds, so the login moves under its account
as soon as the tool has written the sign-in. A sign-in prints the account's email, OAuth links and device
codes, and an API key is pasted there; that is why it keeps no log, invariant 3's one exception (§9).

#### What the adapter reads

The adapter contract (§4.3) has most of what the page needs; the page reuses it and adds three reads.
Each runs on the host, sends nothing anywhere, and is optional, named in the adapter's `implements`, its
check a row of the conformance suite (§4.3 *The conformance suite*):

- **reused**: `default_home(env)`; `tool_version(env)`; `credentials_ok`, in a home-taking form
  `credentials_ok(home)`; the binary each launch finds today (the PATH, then the places the adapter knows:
  Grok Build's `~/.grok/bin/grok`, Gemini CLI's npm prefix), lifted into **`find()`** so the page asks
  without launching; the adapters' `INSTALL_LINE` as **`install_command()`**; **`signin_command()`**, the
  command alone, its environment `home_env`'s — Grok Build's `grok login`, and for Claude Code and Gemini
  CLI the tool itself, signed in with its own `/login` (the row says *quit the tool once signed in*); and
  **`home_env(home)`**, the environment each launch sets (`CLAUDE_CONFIG_DIR`; `GROK_HOME` with its launch
  home; `GEMINI_CLI_HOME`), lifted out of the launch.
- **new**:
  - **`is_home(path)`**: whether a folder is this tool's home, by the files the tool writes there (for
    Gemini CLI under `<path>/.gemini/`).
  - **`identity(home)`**: `{key, display, plan, billing}` or none. `key` is the tool's account key: Claude
    Code's `accountUuid`, from the `.claude.json` the tool reads under the login's environment (inside the
    folder once a launch sets `CLAUDE_CONFIG_DIR`, which for `~/.claude` differs from the `~/.claude.json`
    an unset launch reads; the adapter reads the one a launch would); Grok Build's xAI user id, the key
    `auth.json` is stored under; Gemini CLI's active account in `.gemini/google_accounts.json`. `display` is
    a display name where the tool records one (Claude Code's `displayName`, Grok Build's first name), else
    none: **the adapter returns no email, nor any part of one**. `plan` and `billing` are the tool's record:
    Claude Code's `planDisplayName` and `billingType`; Gemini CLI's `selectedType` in `.gemini/settings.json`
    (an API key reads metered); Grok Build's `auth_mode`, which names no plan. Each source is confirmed
    against the installed tool at the build, as §4.3 does elsewhere.
  - **`models(home, plan)`**: the model families the account offers and the family of the tool's
    default. No tool file lists them, so each adapter keeps a table of the families each plan offers; a
    plan the table does not know offers the adapter's whole list, marked *unconfirmed*. The Flows page reads
    this list (TD-1954).

**Known tools without an adapter** (Codex, opencode) are data, not code: a table in the `shiftlead`
adapters package naming each tool and its binary, read through the adapter registry, so no tool's name is
in core. Their `find()` is the PATH alone. A new adapter replaces its row.

The host agent reads all of this when it starts and on **Check again** (the binaries, the default homes,
every login's identity and credentials) and keeps the result; a tick reads only what it reads today
(usage, §4.4).

#### How a login is found and made

Never by guessing at names (a scan for `~/.claude-*` would mostly find test homes and scratch copies):

1. **The tool's default home**, when it is a home: a **found** row, never added unasked (it may be a
   scratch copy), and not offered where the adapter sets `own_home` (above).
2. **The logins the switch-over made** from the host's profiles (below), and every login made since.
3. **+ Add login → Use an existing folder**: the person types a path, `is_home` checks it, and it becomes
   a login.

**+ Add login** otherwise makes a new folder beside the tool's default, its path suggested
(`~/.claude-<label>`, `~/.config/grok-<label>`, `~/.gemini-<label>` holding a `.gemini/`) and the person's
to change, and opens its tools shell for **Sign in**. When `identity` first reads a key, the login joins
that account, or a new one whose label is suggested (below). **Install** opens a tools shell, in the
person's home, with `install_command()` typed.

#### Labels, keys and where they live

**An account's key is `<adapter>:<label>`**, as today (§6 *A reserve is the account's*: `usage_gate`, the
readings, the spend ledger), so nothing is re-keyed. An account seen for the first time takes a suggested
label, `<display>` (a display name holding an `@` dropped), else the person types it; a login's suggested
label is `<tool>-<display>`. A login's id is `l-` and eight random hex characters, given when the host
first sees it; it shows where a hand edit needs one (*Copy id*, `ao tools`).

**Renaming an account** (`ao account rename`, person-only) writes, in one commit of the home's tracked
definitions: in `settings.yml`, its `usage_gate` entry moved to the new key and an alias, `accounts:
{<old key>: <new key>}`, a new top-level key of `settings.yml` (§5 lists it); and in `logins.yml`, the
account's label. Because `settings.yml` is replicated whole (§4.4a), a node and its gate read the alias too.
The spend ledger and stored readings are never rewritten: every reader of a key — the gate, the readings,
the spend ledger, a node's reported `usage` and `spend` — takes it through the alias. A rename is refused
where the new key is an existing account's or an alias's; renaming *a → b → c* rewrites the alias to point
at *c*; renaming back drops the alias. At load, an account label in `logins.yml` with no key in
`settings.yml` but an alias pointing at it is the second half of an interrupted rename, finished then.

**Which account an identity is** is remembered in `logins.yml`'s `accounts:` (by key: label and
**match**). The match is an HMAC-SHA256 of the tool's key under the host's salt, for every tool alike: a
Gemini key is an email and must not be stored, and one rule is simpler than a per-tool one. The key goes
from `identity` into that HMAC inside the host agent and into nothing else: no RPC reply, log line,
exception, `ao doctor` text or `--json`; the conformance row for `identity` checks that a fixture's address
appears in none of them. **The salt is kept out of `logins.yml`**, in `~/.shiftlead/state/salt` (mode
0600, untracked), so the tracked history cannot confirm a guessed address; a lost salt costs only a
recomputation from the logins' live identities, each login naming its account. An account seen without a
key (the state table's last row; a host-wide `GEMINI_API_KEY` makes each login on it an account of its
own, since nothing tells them apart) has no match.

**`~/.shiftlead/logins.yml`**, the host's, is written only by its host agent: `logins:` (by id: tool,
folder, label, note, account key, `billing`, `prices`, `extra_args`, `unattended_args`, `permission_wait`,
pin) and `accounts:` (by key: label, match). It replaces `profiles.yml` among the home's tracked definitions
(§4.9 *What is left at the home has a history*; §4.9's and §5's lists, and `defs.TRACKED`): the host agent
commits it after each of its own writes, with the message `logins: <change>` (with `settings.yml` in the
same commit where a reserve or an alias moved), so it is never committed later as *edited by hand*. It
holds no secret, and a note must not hold one. Its reader and writer are `sessionorc`'s (data, no tool name
in them). Every page, and the change line a settings commit carries (composed by `agent_settings` with
labels, `defs` reading no file for meaning), shows labels. A node's `logins.yml` is its own and untracked;
its loss costs its labels and notes, its logins found again from their folders by `ao login add --path`.
A login named outside its host — a team's login list, `director:`'s `logins:` — is resolved on the host
that launches, by label, so a list naming `claude-paul` takes each host's own `claude-paul`.

#### The switch-over on a host

**`ao migrate --check`**, run on every host before the window, reads the host's `profiles.yml` and names
everything `ao migrate` would refuse, for the person to fix in the old shape first:

- profiles on one folder that disagree on `billing`, `prices`, `extra_args`, `unattended_args` or
  `permission_wait` (a profile that differs only in `permission_prompts`, `grind-ask`'s case, is a flow's
  seat setting at the window, not a login's: the frame);
- two `account:` labels whose folders read one identity, or one label whose folders read two (the person
  gives the profiles one `account:`, or two);
- a label outside the label characters;
- a metered profile sharing its folder against §4.2a's rule.

**`ao migrate`**, in the window, on each host: a login per distinct folder among its profiles (a profile's
`config_dir`, else the tool's default home; a `shell` profile, and one whose adapter is not registered,
makes none), labelled with the first profile's name on it; its `billing`, `prices`, `extra_args`,
`unattended_args` and `permission_wait` from those profiles; a pin only where every profile on the folder
names the same model (`gemini-reader`'s `flash-lite`), else none, said in its report; an account per
`account:` label, matched to its identity. Keys are unchanged. `director:`, `sweep:` and each schedule's
`schedule:` take, in place of their `profile:`, its model as `model:` and its login as `logins: [<label>]`.
`profiles.yml` is moved to `~/.shiftlead/state/profiles.yml.migrated`, and the home's commit (both files,
`settings.yml`) is the one a going-back reverts (the frame). A session record from before the window derives
its `account` from its profile's key at load.

#### Not here

- **A default login list** (the frame had one per host, for sessions no team runs): dropped. A session the
  person starts picks its login where it starts (+ New, with the last one used chosen; `ao new --login`,
  else the last used), and `director:`, `sweep:` and a schedule take a `model:` and an ordered `logins:`
  (above), taken the way a seat takes its team's. A team's seats take their order from the team page
  (TD-1153).
- **A node's tools, and several hosts on one page**: drawing a node's logins needs its host agent to report
  them to the home. The reserve is not among them: it is set once per account in the home's `settings.yml`,
  and the account's reading already counts every host. Drawing a node's logins, and gathering one
  account's folders across hosts, is later work (Paul, 2026-11-18).
- **The transcript handoff** for a relaunch on another login: the frame gave it to this round, but it is a
  launch's, not a login's, so it moves to the cut-over build's design (the frame and TD-1953's ledger say
  so).
- **Adapters for Codex and opencode**: separate entries.
