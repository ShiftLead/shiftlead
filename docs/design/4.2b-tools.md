### 4.2b Tools: the CLIs, accounts and logins on a host

**Designed by TD-1953 (2026-11-18, with Paul); builds to be filed at the round's end.** The frame is
[ADR 2026-11-18](../decisions/2026-11-18-tools-flows-teams.md). Until the cut-over build that follows the
Flows (TD-1954) and Team (TD-1153) rounds, every launch still reads a profile (§4.2a); this section says
what the Tools page shows and writes, and what a login is, once built. The mockups are
`docs/mockups/reviews/2026-11-18-td1953-tools-own4-{1440,420}.png`.

**Terms used below.** A **tool** is a CLI an adapter drives (Claude Code, Grok Build, Gemini CLI). A
**login** is one config folder of one tool on one host, the folder the tool keeps its sign-in in
(Claude Code's `CLAUDE_CONFIG_DIR`, Grok Build's home, Gemini CLI's `HOME`); it is what a team's login
list names (the frame). An **account** is who a login is signed in as, by **the tool's own key** for it;
two logins with one key are one account, sharing one quota and one reserve (§4.2a, TD-122, TD-1581). A
**label** is the name the person reads for a login or an account; each sits over a hidden id, so a
rename moves nothing else.

#### The page

**Tools** is a page of the person's own (§4.5), on one host: its header reads *Tools on `<host>`*, with
when the host agent last looked and **Check again**. It shows, in order:

- **A card per supported tool that is installed** — an adapter is registered for it and its binary is
  found — headed by its name and the version found. Under it, drawn as a tree:
  - **each account** its logins are signed into: its label (✎), the plan the tool names, the models it
    offers (a login's pin narrows them, §4.2a: `flash-lite (pinned)`), and **the gauge**;
  - under each account, **its logins**: the label (✎), the folder's path, an optional note in italics
    (*conformance walks record here*), the state, and **⋯**;
  - **Not signed in**, a dashed group holding the tool's logins with no identity to read, each with
    **Sign in** where the state goes;
  - **found** rows, dashed: a folder at the tool's default home that is signed in but is no login yet,
    with the account it is signed in as and **Add**;
  - **+ Add login**, once per tool.
- **Not ready to run here**, greyed dashed cards: a supported tool not installed on this host (with
  **Install**), a tool installed with no adapter (*Codex 0.163.0 installed: ShiftLead has no adapter for
  it yet, so no seat can run on it*), and a tool with neither (*no adapter yet*, no Install — ShiftLead
  never offers to install what it cannot run).

The page has no Add tool (every supported tool is drawn already, and Check again re-reads the PATH), no
default login list (below), no smoke passes (they are a tool, a model and a role, so they are drawn on
the Flows page beside each seat's model, TD-1954), no update check (the version is the one found), and
no host switch (below).

**The gauge** is one per window the account reports, the week's first: the window's use fills from the
left, the account's **reserve** is a hatched bay held from the right, and the gap between is labelled
*room for unattended work: N%*. The reserve field (*keep back*) sits under it, taking what `ao gate`
takes (§6 *Usage gate*); a metered account's gauge is its spend against its amount (§4.2a), its field the
amount. An account with no reading yet draws an empty striped gauge and *No usage reading yet*, and no
field, since a line against no reading binds nothing; `ao gate` still sets one, as it does today. The
Settings page's Usage cards (the reserves by account) move here; its weights stay there.

**A login's state** is one of: *signed in* (green); *limited till T* (the tool's cap, §4.2); **Sign in**,
a button, where the folder has no identity to read. A login at its account's reserve is not marked: the
gauge says it.

**⋯ on a login**: *Open a shell here* (a Shell tab with the login's environment set, §4.3
`home_env`); *Edit note*; *Forget this login*, which removes it from the host's logins and leaves the
folder on disk — refused, naming them, while a live session runs on it or a team's login list names it.

#### What the adapter reads

The adapter contract (§4.3) gains reads, each local to the host, each sending nothing anywhere:

- **`find()`** — the binary's path and version, or none: the PATH, then the places the adapter knows the
  tool installs to (Grok Build's `~/.grok/bin/grok`, Gemini CLI's npm prefix), as each launch finds it
  today.
- **`install_command()`** — the vendor's documented install line, for the Shell tab.
- **`default_home()`** — the tool's own default folder (`~/.claude`, `~/.grok`, `~/.gemini`).
- **`is_home(path)`** — whether a folder is this tool's home, by the files the tool writes there.
- **`identity(path)`** — the account key, a display name and the plan, read from the tool's own files,
  or none where the folder is signed out: Claude Code's `accountUuid` (in `.claude.json`, inside the
  folder, or `~/.claude.json` for the default `~/.claude`); Grok Build's `auth.json`, keyed by the xAI
  user id; Gemini CLI's `google_accounts.json`. A login on an API key with no identity to read (a Gemini
  AI Studio key) is an account of its own, keyed by the login's id, and the person types its label.
- **`models(path)`** — the model families the account offers, and the family of the tool's default.
- **`signin_command()`** — the tool's interactive sign-in, typed into the Shell tab.

**Known tools without an adapter** (Codex, opencode) are data, not code: a table in the adapters package
naming each tool and its binary, read by the host agent to draw *Not ready to run here*. Core names no
tool (§4.3); a new adapter replaces its row.

The host agent reads all of this when it starts and on **Check again**, and keeps the result; a tick
reads only what it reads today (usage, §4.4).

#### How a login is found

Three ways, never by guessing at names (a scan for `~/.claude-*` would mostly find test homes and
scratch copies):

1. **The tool's default home**, when it is on disk. A signed-in default home that is no login is a
   **found** row; **Add** makes it one. Nothing is added unasked: the folder may be a scratch copy.
2. **The logins the host already has**: every profile's `config_dir` in `profiles.yml`, read in once at the
   cut-over (below), and every folder **+ Add login** makes.
3. **+ Add login → Use an existing folder**: the person types a path, `is_home` checks it, and it
   becomes a login.

**+ Add login** otherwise makes a new folder, its path suggested beside the tool's default
(`~/.claude-<label>`) and the person's to change, and goes straight to **Sign in**.

**Sign in** opens a Shell tab on this host with the login's environment set and `signin_command()`
typed; the person presses Enter, as every tool's sign-in is interactive and ShiftLead runs none. When the
tab's shell exits, or on Check again, `identity` is read again: the login moves under its account, and an
account seen for the first time gets a suggested label.

**Install** opens a Shell tab with `install_command()` typed, the person pressing Enter (§4.3: ShiftLead
never runs an install).

#### Labels and where they live

A suggested label is `<tool>-<person>` for a login (`claude-paul`, `grok-heather`) and the person part
for an account (`paul`), the person part from the identity's display name, else the part of its email
before the `@`. The page never shows an email in full: screenshots of it are shared.

A login's hidden id is one ShiftLead gives it when it is made; an account's is `<adapter>:<the tool's
key>`. Both live in the host's `~/.shiftlead/profiles.yml`, which gains `logins:` (by id: tool, folder,
label, note, and what §4.2a gives a profile today — `billing`, `prices`, `extra_args`, a model pin) and
`accounts:` (by id: label). **The host agent writes them, on the person's acts on this page only** — the
file has no writer today, and a session never writes it (a path under `~/.shiftlead`, §4.9b). A team's
login list, a session's record and the usage, spend and reserve keys name the ids; every page shows the
labels. So a rename changes one line, and no reserve, history or team list moves.

**Today's keys move once.** Reserves (`settings.yml` `usage_gate`), the usage readings and the spend
history are keyed `<adapter>:<account label>` today (`claude-code:paul`). The build that moves the
reserve onto this page re-keys them to the account's id, reading the old key for one release beside the
new one, as the frame's dual-read window does.

#### Not here

- **A default login list** (the frame had one per host, for sessions no team runs): dropped. A session
  the person starts picks its login where it starts: **+ New** offers the logins with the last one used
  chosen, and `ao new` takes `--login`, else the last login used. A launch no person starts and no team
  runs names its own, where it is set today by a `profile:` (§5): `director:`, `sweep:` and a schedule's
  `schedule:` each take a `model:` and an ordered `logins:` in its place at the cut-over, taken the way a
  seat takes its team's. A team's seats take their order from the team page (TD-1153). The frame's line
  is changed in this design's PR.
- **Several hosts on one page**: each host's page is its own, as each host's logins are (a node's tools
  and `profiles.yml` are its own; the frame). Gathering one account's folders across hosts needs each
  node's host agent to report its logins to the home, and is later work (Paul, 2026-11-18).
- **The cut-over** of launches from a profile to a model and a login, and the transcript handoff for a
  relaunch on another login (the frame): builds after the Flows and Team rounds.
- **Adapters for Codex and opencode**: separate entries.
