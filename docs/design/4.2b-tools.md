### 4.2b Tools: the CLIs, accounts and logins on a host

**Designed by TD-1953 (2026-11-18, with Paul); builds to be filed at the round's end.** The frame is
[ADR 2026-11-18](../decisions/2026-11-18-tools-flows-teams.md). Until the cut-over build that follows the
Flows (TD-1954) and Team (TD-1153) rounds, every launch still reads a profile (§4.2a); this section says
what the Tools page shows and writes, what a login is, and how logins and profiles live together until
then. The mockups are `docs/mockups/reviews/2026-11-18-td1953-tools-own5-{1440,420}.png`.

**Terms used below.** A **tool** is a CLI an adapter drives (Claude Code, Grok Build, Gemini CLI). A
**login** is one home of one tool on one host: the folder a launch points the tool at, where the tool
keeps its sign-in — Claude Code's `CLAUDE_CONFIG_DIR`, Grok Build's `GROK_HOME`, Gemini CLI's
`GEMINI_CLI_HOME` (the parent of its `.gemini/`, so the tool's default is `~` itself; §4.3, each adapter's
`default_home`). It is what a team's login list names (the frame). An **account** is who a login is signed
in as, by the tool's own key for it; two logins with one key are one account, sharing one quota and one
reserve (§4.2a, TD-122, TD-1581). A **label** is the name the person reads for a login or an account,
unique per host among logins and among accounts; each sits over an **id**, so a rename moves nothing
else. A **tools shell** is the shell the page opens for a login (below).

#### The page

**Tools** is a page of the person's own (§4.5), for **the home's host** — its header reads *Tools on
`<host>`*, with when the host agent last read it and **Check again**. A node's tools are not drawn (*Not
here*). It shows, in order:

- **A card per supported tool that is installed** — an adapter is registered for it and its binary is
  found — headed by its name and the version found. Under it, drawn as a tree:
  - **each account** its logins are signed into: its label (✎), the plan the tool records, the model
    families it offers, and **the gauge**;
  - under each account, **its logins**: the label (✎), the folder's path, a model pin where it has one
    (`flash-lite (pinned)`, the login's, so drawn here and not on the account), an optional note in
    italics, the state, and **⋯**;
  - **Not signed in**, a dashed group holding the tool's logins with no identity to read;
  - **a found row**, dashed: the tool's default home when it is signed in and no login yet, with its
    account's label and **Add** — except for an adapter whose launch writes into its home (`own_home`,
    §4.3: Grok Build), whose default home may not be a login (§4.2a), where the row reads *the tool's own
    home: ShiftLead launches into a folder of its own* and offers + Add login instead;
  - **+ Add login**, once per tool.
- **Not ready to run here**, greyed dashed cards: a supported tool not installed on this host (with
  **Install**), a tool installed with no adapter (*Codex 0.163.0 installed: ShiftLead has no adapter for
  it yet, so no seat can run on it*), and a tool with neither (*no adapter yet*, no Install — ShiftLead
  never offers to install what it cannot run).

The page has no Add tool (every supported tool is drawn already, and Check again re-reads the PATH), no
default login list (*Not here*), no update check (the version is the one found), and no host switch. It
draws no smoke passes: a pass is a tool, a model and a role, and part of whether a login is *usable* for a
seat (the frame), so its record, seeding and drawing beside each seat's model are TD-1954's; no state here
reads it.

**The gauge.** One per window the account reports, the week's first: the window's use fills from the
left, the account's **reserve** is a hatched bay held from the right, and the gap is labelled *room for
unattended work: N%*. A metered account draws one per window it sums (`day`, `week`, `month`, §4.2a), its
spend against that window's amount. Under each, the reserve field (*keep back*), taking what `ao gate`
takes (§6 *Usage gate*) and written to the home's `settings.yml` through `set_settings`. An account with
no reading yet draws an empty striped gauge, *No usage reading yet*, and the field all the same, its
window labels unchecked as the Settings card says today, so a new account's first unattended run can
already be bounded (an adapter with no `usage`, Grok Build's today, is always so). A reading past its
trust age draws *stale* (TD-1680), and an account whose logins disagree on billing draws *mixed* with the
gate's reading of it (§6). The Settings page's Usage card moves here for every account of the home's host;
an account seen only on a node keeps its Settings card until nodes are drawn, and the weights stay on
Settings. An account signed in on two hosts is one account and one reserve, and its reading is the
vendor's for the account, so it already counts every host's use (§6 *A reserve is the account's*).

**A login's state**, from `identity` (a key or none), `credentials_ok(home)` (§4.3: True, False, or None
where it cannot tell) and the login's `billing`:

| identity | credentials_ok | drawn |
|---|---|---|
| a key | True, or None | *signed in*; *limited till T* when its account's reading says the tool's cap (§4.2) |
| a key | False | **Sign in again** (an expired sign-in); the login stays under its account |
| none | False, or None | in *Not signed in*, with **Sign in** |
| none | True | *signed in*, an account of its own (an API key with no identity: a Gemini AI Studio key, `GEMINI_API_KEY` in the host agent's environment, an `ANTHROPIC_API_KEY` in the folder's `settings.json`) |

A metered login is never *limited* (§4.2a) and draws its account's amount instead. The states are read
when the host agent starts, on Check again, when a tools shell's pane closes, and when a launch on the
login is refused for its credentials (§4.3); *limited* follows the account's reading on each tick. The
header's *read N ago* is their age. A login at its account's reserve is not marked: the gauge says it.

**⋯ on a login**: *Open a shell here* (a tools shell); *Settings* (below); *Copy id*; *Edit note*;
*Forget this login*, which removes it from `logins.yml` and leaves the folder on disk. Forget is refused,
naming them, while a live session runs on the login, a profile resolves to it, or a team's login list,
`director:`, `sweep:` or a schedule names it. When an account's last login is forgotten, its entry,
label and reserve stay, as an orphan reserve key does today, and `ao gate` lists it.

**A login's Settings**: what §4.2a gives a profile today and a login takes over, each checked by §4.2a's
rules (a metered login's own folder, an adapter with no `spend` refused):

- **`billing`**, the person's: `logins.yml` holds it and it is the truth. `identity`'s reading of the
  tool's record (below) is offered at Add, and a mismatch later is drawn as a warning on the login, never
  applied — §4.2a's *never guessed* stands, the tool's record only suggesting;
- a metered login's **`prices`**: empty means a self-hosted model read in tokens, as §4.2a has it; the
  Settings page's weights for its models (§5 `spend.weights`) are offered as a fill-in;
- **`extra_args`**, **`unattended_args`** and **`permission_wait`** (§4.2a), the tool's flags and the
  wait a login carries;
- a **model pin**, the person's, which must be a family the account offers.

#### Controls and verbs

Every control here gets a §4.5a row and an `ao` verb (§4.5a, the frame's last rule); the rows and their
help wording are the builds' (help text is bound to `help.py`). Each writing verb is a **person-only RPC**,
refused from a session (`SHIFTLEAD_SESSION` set) as `ao promote` is:

| control | verb |
|---|---|
| the page | `ao tools [--json]`: the read below |
| Check again | `ao tools check` |
| ✎ on a login, on an account | `ao login rename <login> <label>`, `ao account rename <account> <label>` |
| keep back | `ao gate` (today's) |
| + Add login, Use an existing folder, Add on a found row | `ao login add <tool> [--path <folder>] [--label <label>]` |
| Sign in, Sign in again, Open a shell here | `ao login shell <login>` |
| Install | `ao tools install <tool>` |
| Settings | `ao login set <login> <key> <value>` |
| Edit note | `ao login note <login> <text>` |
| Copy id | the id, shown by `ao tools` |
| Forget this login | `ao login forget <login>` |

A login or an account is named by its label or its id. **The read** (`tools`) replies `{host, read_at,
version, tools: [{adapter, binary, version, installed, supported, install_command, accounts: [{id, label,
plan, billing, models, gauges}], logins: [{id, label, folder, account, state, note, pin}], found}],
not_ready: [...]}`; `version` is `logins.yml`'s, and every write sends it back: a write over a newer
version is refused, *logins.yml changed since this page read it — reload*.

#### The tools shell

A **tools shell** is a `shell` session (§4.1) named `tools-<login id>`, with no parent session, its
directory the login's folder, its environment `home_env(home)`, opened on this host as a new tab. There
is one per login: a second press reopens it. The host agent types the command (`signin_command`, or for
Install `install_command`) with no Enter, and the person presses Enter: ShiftLead runs no sign-in and no
install (§4.3). It is the person's own shell. **Its run log is removed when its pane closes** and is never
offered to a transcript, a feedback report or a reader: a sign-in prints the account's email, OAuth
links and device codes, and an API key is pasted there. That is invariant 3's one exception (§9 amended).

#### What the adapter reads

The adapter contract (§4.3) has most of what the page needs; the page reuses it and adds three reads.
Each runs on the host, sends nothing anywhere, and is optional, named in the adapter's `implements`, its
check a row of the conformance suite (§4.3 *The conformance suite*):

- **reused**: `default_home(env)`; `tool_version(env)`; `credentials_ok`, given a home-taking form
  `credentials_ok(home)` that the profile form calls; the binary each launch finds today (the PATH, then the
  places the adapter knows: Grok Build's `~/.grok/bin/grok`, Gemini CLI's npm prefix), lifted into
  **`find()`** so the page asks without launching; the adapters' `INSTALL_LINE` as **`install_command()`**;
  **`signin_command()`**, the command alone, its environment `home_env`'s — Grok Build's `grok login`, and
  for Claude Code and Gemini CLI the tool itself, signed in with its own `/login` (the row says *quit the
  tool once signed in*); and **`home_env(home)`**, the environment each launch sets (`CLAUDE_CONFIG_DIR`;
  `GROK_HOME` with its launch home; `GEMINI_CLI_HOME`), lifted out of the launch.
- **new**:
  - **`is_home(path)`**: whether a folder is this tool's home, by the files the tool writes there (for
    Gemini CLI under `<path>/.gemini/`).
  - **`identity(home)`**: `{key, display, plan, billing}` or none. `key` is the tool's account key: Claude
    Code's `accountUuid`, from the `.claude.json` the tool reads under the login's environment (inside the
    folder once a launch sets `CLAUDE_CONFIG_DIR`, which for `~/.claude` differs from the `~/.claude.json`
    an unset launch reads; the adapter reads the one a launch would); Grok Build's xAI user id, the key
    `auth.json` is stored under; Gemini CLI's active account in `.gemini/google_accounts.json`. `display` is
    a display name where the tool records one (Claude Code's `displayName`, Grok Build's first name), else
    none: **the adapter returns no email, nor any part of one**. `plan` and `billing` are the tool's record:
    Claude Code's `planDisplayName` and `billingType`; Gemini CLI's `selectedType` in `.gemini/settings.json`
    (an API key reads metered); Grok Build's `auth_mode`, which names no plan. Each source is confirmed
    against the installed tool at the build, as §4.3 does elsewhere.
  - **`models(home, plan)`**: the model families the account offers and the family of the tool's
    default. No tool file lists them, so each adapter keeps a table of the families each plan offers; a
    plan the table does not know offers the adapter's whole list, marked *unconfirmed*. The Flows page reads
    this list (TD-1954).

**Known tools without an adapter** (Codex, opencode) are data, not code: a table in the `shiftlead`
adapters package naming each tool and its binary, read through the adapter registry, so no tool's name is
in core. Their `find()` is the PATH alone. A new adapter replaces its row.

The host agent reads all of this when it starts and on **Check again** (the binaries, the default homes,
every login's identity and credentials) and keeps the result; a tick reads only what it reads today
(usage, §4.4).

#### How a login is found and made

Never by guessing at names (a scan for `~/.claude-*` would mostly find test homes and scratch copies):

1. **The tool's default home**, when it is a home: a **found** row, never added unasked (it may be a
   scratch copy), and not offered where the adapter sets `own_home` (above).
2. **Every profile's folder**, at every load (*Until the cut-over*).
3. **+ Add login → Use an existing folder**: the person types a path, `is_home` checks it, and it becomes
   a login.

**+ Add login** otherwise makes a new folder beside the tool's default, its path suggested
(`~/.claude-<label>`, `~/.config/grok-<label>`, `~/.gemini-<label>` holding a `.gemini/`) and the person's
to change, and opens its tools shell for **Sign in**. When the pane closes, `identity` is read: the login
moves under its account, and an account seen for the first time takes a suggested label. **Install** opens
a tools shell, in the person's home, with `install_command()` typed.

**A login changes account** when it is first signed in or signed in as someone else. A login that was an
account of its own (no key) gives that account's reserve to the account it joins, the larger kept where
both have one, and its spend history is read under the new account from then on (the old id mapped at
load). A login that moves between two real accounts moves alone; while a session runs on it, the page
marks the move and the session's record keeps the account it started under until it ends. A team's login
list names the login, so it is unaffected.

#### Labels, ids and where they live

A login's id is `l-` and eight hex characters, given when it is made. An account's id is
`<adapter>:a-` and sixteen hex characters of an HMAC-SHA256 of the tool's key under the **install's
account secret**, `~/.shiftlead/account.key` on the home (never in `settings.yml`, which is replicated
whole, §4.4a), copied to a node as its other provisioning is. So the same account on two hosts has one
id, while an id in `settings.yml`, a commit message, a reply or a URL cannot be checked against a guessed
address; an Add whose id collides with another key's is refused. A suggested label is `<tool>-<display>`
for a login and `<display>` for an account; with no display name, the person types it.

Both live in **`~/.shiftlead/logins.yml`**, the host's, written only by its host agent through the
person-only RPCs above: `logins:` (by id: tool, folder, label, note, `billing`, `prices`, `extra_args`,
`unattended_args`, `permission_wait`, pin) and `accounts:` (by id: label). Its reader and writer are
`sessionorc`'s (data, no tool name in them), as the usage key's reading already is. `logins.yml` is the
lasting file: `profiles.yml` goes at the cut-over (a profile survives only as what a model and a login
compile to at a launch, the frame); until then it stays the person's hand-written file, which no writer
touches, since a rewrite would lose its comments (the frame's *profiles.yml writer* becomes this file).

A team's login list, a session's record and the usage, spend and reserve keys name the ids; every page,
and the change line a `settings.yml` commit carries (`defs`), shows the labels. So a rename changes one
line, and no reserve, history or team list moves (the ledger's *renaming moves its reserve and history*:
nothing moves).

#### Until the cut-over

**A profile resolves to a login at every load**, never by a write to `profiles.yml`: by its adapter and its
resolved folder (its `config_dir`, else the tool's default home; the implicit `default` profile of a host
with no file is the default home's). A folder no login has yet becomes one, its `billing` and `prices`
from the profile; profiles on one folder that disagree on `billing` or `prices` are `ao doctor`'s, and the
first in file order seeds the login. `extra_args`, `unattended_args` and `permission_wait` stay each
profile's until the cut-over, since profiles on one folder differ in them by design (`grind-ask`). The pin
is never seeded from a profile's `model:`: it is the person's. A hand-written `login: <id or label>` on a
profile wins over its folder, a disagreement `ao doctor`'s. A `shell` profile, and one whose adapter is not
registered, makes no login. A profile's `account:` stops being read for keys: its account is its login's.

**The keys move by a window**, as the frame's dual read does. The build that brings `logins.yml` also
re-keys what is keyed `<adapter>:<account label>` today: `usage_gate`, the stored readings and the spend
ledger. Through `agent_common._usage_key`, each adapter's `account_for` and `profiles()`,
`profiles.account_of`, `settings_page._usage_key` and `agent_spend._account_of`, the key becomes the
account id. During the window:

- `usage_gate` holds **both** keys for each account, a reserve set in the window written to both; the
  gate and `ao gate` read and draw the new one and hide the old. A rollback (`ao promote --back`) below the
  build therefore still finds every reserve; the build's commit is the rollback floor once the window
  ends.
- The spend ledger and stored readings are not rewritten: an old-key → id map, kept in `logins.yml`, is
  read at load.
- A node keeps reporting label keys until its host agent runs the build; the home reads them through the
  map (the node's labels are its `profiles.yml`'s, which for a container node are the home's, copied with
  `config_dir` rewritten, §4.4a). A node on the build computes its ids itself, under the account secret it
  was given. The window ends when `ao org check` reports every node on the build, and then the old keys
  are dropped.

**Merges and splits.** Two labels that prove one account become one; its reserve is the larger (the safer
line). One label whose folders prove two accounts splits: each takes the label's reserve, the history
stays mapped to the first in file order, and labels are told apart (`paul`, `paul-2`). Each is written in
the build's `settings.yml` commit, whose change line names it.

A login made on the page before the cut-over runs a session once a profile names it (`login: <label>`, a
hand edit); the page says so on a login no profile resolves to. `ao new --login` and a login pick in + New
are the cut-over's.

#### Not here

- **A default login list** (the frame had one per host, for sessions no team runs): dropped. At the
  cut-over a session the person starts picks its login where it starts (+ New, with the last one used
  chosen; `ao new --login`, else the last used), and `director:`, `sweep:` and a schedule's `schedule:`
  each take a `model:` and an ordered `logins:` in place of their `profile:` (§5), taken the way a seat
  takes its team's. A team's seats take their order from the team page (TD-1153).
- **A node's tools, and several hosts on one page**: drawing a node's logins needs its host agent to
  report them to the home and a writer for its `logins.yml`. The reserve is not among them: it is set once
  per account in the home's `settings.yml`, and the account's reading already counts every host. Drawing a
  node's logins, and gathering one account's folders across hosts, is later work (Paul, 2026-11-18).
- **The cut-over** of launches from a profile to a model and a login.
- **The transcript handoff** for a relaunch on another login: the frame gave it to this round, but it is a
  launch's, not a login's, so it moves to the cut-over build's design (the frame and TD-1953's ledger say
  so).
- **Adapters for Codex and opencode**: separate entries.
