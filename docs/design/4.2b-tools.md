### 4.2b Tools: the CLIs, accounts and logins on a host

**Designed by TD-1953 (2026-11-18, with Paul); builds to be filed at the round's end.** The frame is
[ADR 2026-11-18](../decisions/2026-11-18-tools-flows-teams.md). Until the cut-over build that follows the
Flows (TD-1954) and Team (TD-1153) rounds, every launch still reads a profile (§4.2a); this section says
what the Tools page shows and writes, what a login is, and how logins and profiles live together until
then. The mockups are `docs/mockups/reviews/2026-11-18-td1953-tools-own4-{1440,420}.png`.

**Terms used below.** A **tool** is a CLI an adapter drives (Claude Code, Grok Build, Gemini CLI). A
**login** is one home of one tool on one host: the folder a launch points the tool at, where the tool
keeps its sign-in — Claude Code's `CLAUDE_CONFIG_DIR`, Grok Build's `GROK_HOME`, Gemini CLI's
`GEMINI_CLI_HOME` (the parent of its `.gemini/`, so the tool's default is `~` itself; §4.3, each adapter's
`default_home`). It is what a team's login list names (the frame). An **account** is who a login is signed
in as, by the tool's own key for it; two logins with one key are one account, sharing one quota and one
reserve (§4.2a, TD-122, TD-1581). A **label** is the name the person reads for a login or an account; each
sits over a hidden id, so a rename moves nothing else.

#### The page

**Tools** is a page of the person's own (§4.5), for **the home's host** — its header reads *Tools on
`<host>`*, with when the host agent last read it and **Check again**. A node's tools are not drawn (below,
*Not here*). It shows, in order:

- **A card per supported tool that is installed** — an adapter is registered for it and its binary is
  found — headed by its name and the version found. Under it, drawn as a tree:
  - **each account** its logins are signed into: its label (✎), the plan the tool names, the models it
    offers (a login's pin narrows them, §4.2a: `flash-lite (pinned)`), and **the gauge**;
  - under each account, **its logins**: the label (✎), the folder's path, an optional note in italics
    (*conformance walks record here*), the state, and **⋯**;
  - **Not signed in**, a dashed group holding the tool's logins with no identity to read, each with
    **Sign in** where the state goes;
  - **found** rows, dashed: the tool's default home, when it is signed in and no login yet, with its
    suggested account label and **Add**;
  - **+ Add login**, once per tool.
- **Not ready to run here**, greyed dashed cards: a supported tool not installed on this host (with
  **Install**), a tool installed with no adapter (*Codex 0.163.0 installed: ShiftLead has no adapter for
  it yet, so no seat can run on it*), and a tool with neither (*no adapter yet*, no Install — ShiftLead
  never offers to install what it cannot run).

The page has no Add tool (every supported tool is drawn already, and Check again re-reads the PATH), no
default login list (below), no update check (the version is the one found), and no host switch (below).
It draws no smoke passes: a pass is a tool, a model and a role, and part of whether a login is *usable* for
a seat (the frame), so its record, its seeding and its drawing beside each seat's model are TD-1954's; no
state here reads it.

**The gauge** is one per window the account reports, the week's first: the window's use fills from the
left, the account's **reserve** is a hatched bay held from the right, and the gap between is labelled
*room for unattended work: N%*. The reserve field (*keep back*) sits under it, taking what `ao gate`
takes (§6 *Usage gate*), and writes the home's `settings.yml` through `set_settings` as the Settings page's
Usage card does today; that card moves here, and its weights stay on Settings. A metered account's gauge
is its spend against its amount (§4.2a), its field the amount. An account with no reading yet draws an
empty striped gauge and *No usage reading yet*, and no field, since a line against no reading binds
nothing; `ao gate` still sets one, as it does today. An account signed in on two hosts is one account id
and one reserve (the reserve was the account's already, §6 *A reserve is the account's*).

**A login's state** is one of:

- *signed in* (green): `credentials_ok` (§4.3) passes and `identity` reads a key;
- *limited till T*: the tool's cap, from the account's reading (§4.2);
- **Sign in again**, a button: the folder has an identity but `credentials_ok` fails (Claude Code's
  refresh token expired); the login stays under its account, whose key the folder still names;
- **Sign in**, a button, in *Not signed in*: no identity to read.

The states are read when the host agent starts, on Check again, and when a launch on the login is
refused for its credentials (§4.3); *limited* follows the account's reading on each tick. The header's
*read N ago* is their age. A login at its account's reserve is not marked: the gauge says it.

**⋯ on a login**:

- *Open a shell here*: a Shell tab with the login's home set as a launch sets it;
- *Settings*: what §4.2a gives a profile today and a login takes over — `billing` (subscription or
  metered) and a metered login's `prices`, `extra_args`, and a model pin, each checked by the rules §4.2a
  states (a metered login's own folder, an adapter with no `spend` refused);
- *Edit note*;
- *Forget this login*: removes it from the host's logins and leaves the folder on disk. It is refused,
  naming them, while a live session runs on it, a profile names it, or a team's login list names it.

#### What the adapter reads

The adapter contract (§4.3) has most of what the page needs; the page reuses it and adds three reads:

- **reused**: `default_home(env)`; `credentials_ok`; `tool_version(env)`; the binary each launch finds
  today (the PATH, then the places the adapter knows: Grok Build's `~/.grok/bin/grok`, Gemini CLI's npm
  prefix), lifted into **`find()`** so the page asks without launching; the `INSTALL_LINE` the adapters
  carry, as **`install_command()`**; and the `login` line `doctor_profiles` gives (`GROK_HOME=<dir> grok
  login`), as **`signin_command(home)`**. And **`home_env(home)`**, lifting the environment each launch
  sets (`CLAUDE_CONFIG_DIR`; `GROK_HOME` with its launch home; `GEMINI_CLI_HOME`) out of the launch, for
  the Shell tabs.
- **new**:
  - **`is_home(path)`**: whether a folder is this tool's home, by the files the tool writes there (for
    Gemini CLI under `<path>/.gemini/`).
  - **`identity(home)`**: `{key, display, plan}` or none. `key` is the tool's own account key: Claude Code's
    `accountUuid`, read from the `.claude.json` the tool reads under the login's environment (inside the
    folder once a launch sets `CLAUDE_CONFIG_DIR`, which for `~/.claude` differs from the `~/.claude.json`
    an unset launch reads; the adapter reads the one a launch would); Grok Build's xAI user id, the key
    `auth.json` is stored under; Gemini CLI's active account in `.gemini/google_accounts.json`. `display` is
    the part the label is suggested from — the display name, else the part of an email before the `@` —
    and **the adapter returns no email**, so none reaches the host agent's replies, logs or the page. Each
    source is confirmed against the installed tool at the build, as §4.3 does; where the key is missing, or
    the login is an API key with no identity (a Gemini AI Studio key, an `ANTHROPIC_API_KEY` in the
    folder's `settings.json`), the login is an account of its own, keyed by the login's id, and the person
    types its label.
  - **`models(home, plan)`**: the model families the account offers and the family of the tool's
    default. No tool file lists them, so each adapter keeps a table of the families each plan offers
    (Claude Code's from its plans, Grok Build's and Gemini CLI's one row each); a plan the table does not
    know offers the adapter's whole list, marked *unconfirmed*. A pin outside the list is a Settings error.
    The Flows page reads this list (TD-1954).

Each is optional, named in the adapter's `implements`, and its conformance check is a row of the suite
(§4.3 *The conformance suite*); an adapter without `identity` draws its logins as their own accounts.

**Known tools without an adapter** (Codex, opencode) are data, not code: a table in the `shiftlead`
adapters package naming each tool and its binary, read through the adapter registry, so no tool's name is
in core and `sessionorc` imports none of it. Their `find()` is the PATH alone. A new adapter replaces its
row.

The host agent reads all of this when it starts and on **Check again** (the binaries, the default homes,
every login's identity and credentials) and keeps the result; a tick reads only what it reads today
(usage, §4.4).

#### How a login is found

Three ways, never by guessing at names (a scan for `~/.claude-*` would mostly find test homes and
scratch copies):

1. **The tool's default home** (`default_home`), when it is a home (`is_home`). A signed-in default home
   that is no login is a **found** row; **Add** makes it one. Nothing is added unasked: the folder may be a
   scratch copy.
2. **The logins the host already has**: one per distinct `config_dir` among `profiles.yml`'s profiles, made
   by the first build (below), and every folder **+ Add login** makes.
3. **+ Add login → Use an existing folder**: the person types a path, `is_home` checks it, and it
   becomes a login.

**+ Add login** otherwise makes a new folder beside the tool's default, its path suggested (`~/.claude-<label>`,
`~/.config/grok-<label>`, `~/.gemini-<label>` holding a `.gemini/`) and the person's to change, and goes
straight to **Sign in**.

**Sign in** opens a Shell tab on this host with `home_env` set and `signin_command` typed; the person
presses Enter, as every tool's sign-in is interactive and ShiftLead runs none. The host agent reads the
login again when the tab's pane closes (its tmux pane-exit, as any Shell tab's end is seen) or on Check
again: the login moves under its account, and an account seen for the first time gets a suggested label.

**Install** opens a Shell tab with `install_command()` typed, the person pressing Enter (§4.3: ShiftLead
never runs an install).

#### Labels, ids and where they live

A suggested label is `<tool>-<person>` for a login (`claude-paul`, `grok-heather`) and the person part
for an account (`paul`), from `identity`'s `display`. An email is never read past the adapter.

A login's id is one ShiftLead gives it when it is made. An account's id is `<adapter>:<hash>`, a short
hash of the tool's key, so no key — and no email, where a tool keys by one — is written to `settings.yml`,
a commit message, a reply or a URL. Both live in **`~/.shiftlead/logins.yml`**, a new file of the host's
that only the host agent writes: `logins:` (by id: tool, folder, label, note, `billing`, `prices`,
`extra_args`, pin) and `accounts:` (by id: label). `profiles.yml` stays the person's hand-written file and
no writer touches it, since it holds comments a rewrite would lose (the frame's *profiles.yml writer*
becomes this file). **The writes are person-only RPCs**, refused from a session as `ao promote` is, made
from this page's acts; each re-reads the file and refuses a write over a change it did not see.

A team's login list, a session's record and the usage, spend and reserve keys name the ids; every page
shows the labels. So a rename changes one line, and no reserve, history or team list moves (the ledger's
*renaming moves its reserve and history* is answered: nothing moves).

#### Until the cut-over

The first build makes `logins.yml` from `profiles.yml`: a login per distinct `config_dir` (the tool's
default home where a profile names none), its `billing`, `prices` and `extra_args` from the profiles on it
(profiles on one folder that disagree are named by `ao doctor` and keep their own), and an account per
identity key. Each profile then also takes its login's id (`login:`), and from that build a profile's
`config_dir` and `account` resolve through its login, so a page rename or Settings change reaches every
profile on the login; a profile's `config_dir` and `account:` lines stay readable for one release.

The same build re-keys what is keyed by the account label today (`<adapter>:<account>`: `usage_gate`, the
usage readings, the spend ledger) to the account ids, reading the old key for one release beside the new
one, as the frame's dual-read window does. Two labels that turn out to be one account become one: its
reserve is the larger of theirs (the safer line), and the change is written to the settings history.

A login made on the page before the cut-over runs a session once a profile names it (`login: <id>`, a
hand edit of `profiles.yml`); the page says so on a login no profile names.

#### Not here

- **A default login list** (the frame had one per host, for sessions no team runs): dropped. A session
  the person starts picks its login where it starts: **+ New** offers the logins with the last one used
  chosen, and `ao new` takes `--login`, else the last login used. A launch no person starts and no team
  runs names its own, where it is set today by a `profile:` (§5): `director:`, `sweep:` and a schedule's
  `schedule:` each take a `model:` and an ordered `logins:` in its place at the cut-over, taken the way a
  seat takes its team's. A team's seats take their order from the team page (TD-1153).
- **A node's tools, and several hosts on one page**: a node's tools and logins are its own (the frame),
  and drawing them needs the node's host agent to report them to the home, its own writer for its
  `logins.yml` (a container node's profiles are the home's, copied, §4.4a), and the home to learn a node's
  login names. That, and gathering one account's folders across hosts, is later work (Paul, 2026-11-18).
- **The cut-over** of launches from a profile to a model and a login, and the transcript handoff for a
  relaunch on another login (the frame): builds after the Flows and Team rounds.
- **Adapters for Codex and opencode**: separate entries.
