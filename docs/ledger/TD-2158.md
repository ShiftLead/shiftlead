## TD-2158: Each stage a session ends records its model, tool, login, spend and the flow's version, and a lost offer leaves a row

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-24
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** e4f0ddc027854ca48fea4addbc94bcbc
**Blocked by:** decision (paul)
**Part of:** TD-2077

**Why:** Part of TD-2077 (design §4.9c *What a run records, for comparing flows*). A comparison of flows needs each stage's model, tool, version, login and spend, and a flow's version, kept on the entry's stage record; today the session record that holds them is forgotten a day after it closes, the record has no flow version, and a lost offer leaves no row.

**Ask:** Should the grinders build the design that records what each flow's run leaves behind, or run one more review round first?

**Location:** src/shiftlead/stage_end.py, src/shiftlead/stage_make.py, src/shiftlead/stagerecord.py, src/sessionorc/agent_mail.py, src/sessionorc/models.py, src/sessionorc/agent.py, src/shiftlead/stage_start.py, src/shiftlead/stage_pass.py, design §4.9c

**Fix:** Write `run` as §4.9c *What a run records, for comparing flows* lists it on every history row that ends a holder: an accepted `ao stage end`'s row (`src/shiftlead/stage_end.py`), and each write of the home's that clears a holder — `stage_make.make` builds the held holder's `run` once, before it dispatches, and passes it with the case's name into the case's function (`_close`, `_wait_for_parts`, `_re_enter`, `_team_moved`, `_ask`, `_answer`, `_offer_again`), which writes it on the row it commits, since each case commits its own write: the *offer again* act's `lost` row (`{from: <stage>, to: <stage>, outcome: "lost", by: "home", reason: <the act's case>, run, at}`, its case `lost`, `silent`, `stopped` or `to-person`, written before it clears the holder or asks the person; on `to-person` the `ask` row `_ask` then writes carries no `run`, nor an `ended` row its gate branch would write, the `lost` row of the same commit carrying it), and for a reconcile case that clears one (`close`, `wait-for-parts`, `re-enter`, `team-moved`, and those that go to the person), the row that write makes, or an `ended` row (`{from: <stage>, to: <stage>, outcome: "ended", by: "home", reason: <its case>, run, at}`) where it makes none; `rewrite-flow` and `renumbered` keep or move the holder and write no `run`, and the person's answer carries none where the question cleared the holder, but where the record was only marked waiting with its holder kept (`_mark_waiting`), an answer that moves the stage (`_answer`) is the write that clears it and its `answer` row carries that holder's `run` — `_answer` commits its own write, so `make` passes it the held holder's `run` rather than attaching it after — while an answer applied to nothing (`_unapplied`, its pull request merged meanwhile) clears no holder and writes no row, the next pass's reconcile ending the holder with its own row. `run` holds `session` (the bare record id `seat_spend.json` keys by, never `<id>@<node>`), `team`, `flow`, `model`, `tool`, `tool_version` (the create in `src/sessionorc/agent.py` reads it today only for a launch carrying `seat`: read it too for a stage's session, `StageLaunch.create_params` saying it is one), `login`, `login_moves` (`null` until TD-2068 and TD-2069 put them on the session record), `started` (the session record's `created`), `ended`, `models` (per model the tokens by kind, `turns`, `figure` and `unweighed`, summed from `seat_spend.json`'s rows for that record over every day, less what this record's earlier rows carrying the same `run.session` already counted, since a stage entered again after its record was forgotten takes the same id and rows), `asks`, `flow_hash`; read from the session record, for a node's session the home's mirror of it (in `make`, the sessions the pass read before its acts; in `stage_end.call`, the host agent's registry; the spend from `seat_spend.json` as each writes); `null` for a field it does not hold, and all but `session` `null` where the record is forgotten. `_ask` writes `{from: <stage>, to: "person", outcome: "ask", by: "home", reason: <its case>, at}`, with the cleared holder's `run` where it cleared one, in the same commit as the question's intent (its `put_entry` or `record_intent` write) for the second loss (whose `ask` row carries none, its `lost` row carrying the `run`), a pull request closed, an entry merged and left open, a stage gone, and an answer naming a stage that has left the flow, and none for a gate asked again or for an entry one of these cases finds already carrying the home's gate (`_ask`'s gate branch: set waiting on the person, nothing asked), which writes an `ended` row with the `run` of the holder it clears (none after a second loss, whose `lost` row carries it); `_mark_waiting` (the gate carried while nothing waits) keeps its holder and writes no row. A move a limit or the cap stops (`_apply` in `stage_end.py`) writes its `blocked` (`{to, count}`, with `cap: true` where the cap stopped it) on its row as well as on the record. `_came` reads the history without its `lost`, `ended` and `ask` rows, and `ao stage end`'s repeat check (`stage_end.py`, today `history[-1]`) reads the last row whose `by` is not `home`, and answers a repeat with where the entry is now (`went`, which `cmd_stage_end` prints): `person` where the record waits on the person, `merge` where it waits `merging` or for its `parts`, else its `stage`, the words a first answer uses, and `done` for a closed record (its `closed_at` set, by `_close` or `_team_moved`), which no first answer uses; an audit's repeat is answered as today; §4.7's `ao stage end` says the same. Count `person_asks`, a home-owned session record field (added to `HOME_OWNED` in `src/sessionorc/models.py`, so a node's mirror never overwrites it), in the home's message handler (`rpc_msg`, `src/sessionorc/agent_mail.py`) as each ask or steer to the person lands. At each offer write `flow_hash` on the record (the SHA-256 of the canonical JSON text §4.9c gives: the flow copy's text and each stage's brief as `stage_start.brief_for` resolves it, no package or version field; the pass resolves them by the reach it starts sessions with, once a pass, and passes `offer` the text and hash, a brief that cannot be read raising the start's `TeamError` with nothing written, sorted keys, no spaces, UTF-8), rows copying it; at the first offer under a new hash write that text to `flows/versions/<hash>.json` in the offer's commit. No act reads any of it; an audit's run writes none of it, and no row of a job's record (a pull request's or a board answer's, §4.9c *Two of the five are not seats today*) carries `run`, its session's end and its review stages' rows alike (all written by `stage_job_end.end_job`, which this build leaves as it is; it takes no review verdict yet, §4.9d *Its pull request is reviewed and merged by the team's flow* designs it, still to be built); an `only-when` stage's `passed` row (`_pass`) carrying no `run` (TD-2159 keeps `findings` off them too).

**Done when:** Tests show every `run` field on an accepted stage end's row, on each of the offer-again act's four `lost` rows (and none on the `to-person` loss's `ask` row), on a reconcile case's row (none on the person's answer row where the question cleared the holder, and the holder's `run` on an `answer` row that moves the stage where `_mark_waiting` kept one, no row where the answer is applied to nothing), and on an `ended` row where a write clears a holder with no row of its own (`team-moved` among them, with no `ask` row), none on a `rewrite-flow` or a renumber (a missing field `null`, a forgotten record's all `null` but `session`); `run.models` equal to the session's `seat_spend.json` sums at that moment; `run.team` and `run.flow` kept after the record's own are rewritten; a blocked move's row carrying its `blocked` after an answer clears the record's; an `ask` row, with the cleared holder's `run` where there was one but the second loss's (its `lost` row carrying it), for each listed home question in the commit of its intent, none for a gate asked again, a gate already carried at an ask case writing an `ended` row for the holder it clears, a second loss on an entry carrying the gate writing its `lost` row alone (no `ask` or `ended` row), `_mark_waiting` writing no row and keeping its holder and none beside a session's own move to the person; and no act's choice changing with these present or absent.
