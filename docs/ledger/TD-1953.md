## TD-1953: Each CLI and its logins are set up by hand: a Tools page detects each CLI, installs it on a press, reads who each login is, and holds each subscription's reserve

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-18
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** 78f868e4658f49b09cdb4e9371413b3e
**Blocked by:** decision (paul)

**Why:** Paul, 2026-11-18, in TD-1153's conversation: "Seems like we really need CLI detection (claude code, codex, grok, etc) - with ability to install with a button press - do we auto-detect the account name used (and that its logged in) so people can have grok-paul, grok-heather variants". And: "I am imagining someone using two subscriptions (e.g. two supergrok subs) to maximize token availability ... assigning separate subs to separate seats. Eventually we could add the load balancing idea formally, but thats too much complication for now. The user can do it. It would probably make sense to have the (session/weekly) reserve settings (per sub) on this page as well."

Today no page detects a CLI: an adapter finds its binary only when it launches one, by name on the PATH (Claude Code, Gemini with an npm fallback) or at a fixed path (Grok's `~/.grok/bin/grok`, refused with an install line when missing). Accounts are named by hand in `~/.shiftlead/profiles.yml` (`account: paul`, `paul-gemini`, `paul-supergrok`), and a second login of one tool is a second config directory written by hand (`gemini-reader` beside `gemini-conformance`). Each tool keeps its login in its own config directory: Claude Code's records the email, plan and organisation; Grok's holds an `auth.json`, as Codex's does on kmaster (no Codex adapter yet); a Gemini login on an AI Studio key may carry no identity to read at all, so a suggested name falls back to the person's typing. The week reserve per account is a card on the Settings page.

Agreed order (Paul, 2026-11-18): the Tools page first, then the Flows page (TD-1954), then the team page (TD-1153), designed one at a time with the others in mind. Codex and opencode are separate efforts, later.

**Location:** src/shiftlead/adapters/*/ (detection, identity), src/shiftlead/profiles.py, ~/.shiftlead/profiles.yml, src/shiftlead/ui/settings_page.py (the reserve cards); design §4.3, §4.2a

**Ask:** Will you design the Tools page with a session: detecting and installing each CLI, reading its logins, and setting each subscription's reserve?

**Fix:** A Tools page listing each adapter's CLI: whether it is installed, its version, and an Install button that runs the vendor's documented install command after a confirm. Under each CLI its logins, one per config directory, each with its signed-in state and the identity read from the tool's own files, and an account name suggested from that identity (`grok-paul`, `grok-heather`) that the person may edit. Add login makes a new config directory and opens a Shell tab to sign in, since every tool's sign-in is interactive. Each subscription's session and week reserve moves here from the Settings page. The models each CLI offers are listed here, for the Flows page (TD-1954) to pick from. Assigning subscriptions to seats spreads usage by hand; formal load balancing is out of scope. A new adapter (Codex, opencode) supplies its own detection, install command and identity read, so the page adds rows, not code paths.

**Done when:** the design round with Paul has written the Tools page and filed its builds.
