**Why:** Paul's idea (2026-11-07, through `ao-led-tds-ledger`, m-89f5d7001d44): a Do item whose step a session could do should offer to have it done. Examples are filing an entry in another repo, a one-line config PR in another repo, and enabling a user timer on the home. Today such an item gives the person Done, Answer… and Start session, so the person either does the step or starts and drives a session for it. Of the three items that prompted this, two were written as Do items only because "X has no question seat, so no session here can file it" (TD-1025, about dev-cadence, now agent-cadence, which has a seat; TD-1044, about samscrape).

**Design PR:** #3367, #3492, #3525, #3542

**Fix:** Design round (§4.5 screen 12 *Three verbs*, §4.5a *Queue card: answers, Answer…*, §4.10, §4.7 *Entries*). The round settles:
- an answer such as *Have a session do it* on a Do item. Its press sends the step as an `ask` or a work order to the question seat or team of the repo the step is in. It falls back to the person only where no session can act (a phone, a browser, a credential, the person's own machine settings);
- which Do items offer it: how the item says its step is a session's to do, for example a board line field, or the line's `Context:` naming another repo that has a seat;
- what closes the Do item: the seat's reply, or the work's merge;
- what never goes this way: anything destructive, outward-facing, spending money, or a credential stays the person's.
- **Paul's input (2026-11-07, through `ao-led-tds-ledger`, m-ed84b11f094c).**
  - The asking session decides which seat is best placed to do the step: a repo's question seat, a team, or a named seat. It writes that seat on the Do item with one line on why. The press then routes straight there instead of the home guessing. The design still says what happens when that seat is gone or unable to answer (for an `asks` seat, TD-1476's ordered pool and the route-around apply; a team or a work order needs a fallback of its own).
  - Tentatively ("it might get messy"): the asker could prepare a script or command that performs the step. The session's note on that: a free-form command that an asker writes and a press runs is code run on the home with the person's credentials. That is the same risk §4.4's typed checks confine for event gates. If the round takes it up, it should consider a small vocabulary of typed actions (as `check:` is), or a command shown to the person and to the doing session as a suggestion, never run by the press itself. The simplest form, the asker naming the seat with the steps in plain words, may be enough.

**Done when:** A merged design that says which Do items offer the answer, where it sends the step, what closes the item and what is never sent, with its builds filed `Part of` this entry.
