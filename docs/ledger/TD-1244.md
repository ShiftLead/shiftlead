## TD-1244: Nothing pins the Add entry form's reset on open, so a *taken* name's red line and border carry into the next opening

**Priority:** Low
**Type:** debt
**Added:** 2026-10-30 (test-audit-ao-1, auditing #2679 and #2683)
**Owner:** grinder
**Kind:** build
**Status:** Open
**Location:** `src/shiftlead/ui/static/app.js` (the form's open: `nameBox.classList.remove("bad"); $("#entryline").classList.remove("bad");`, and the `textContent = ""` reset beside it); `tests/test_ui_entry.py` (`test_no_read_of_the_plan_blanks_a_line_or_disables_hand_while_it_waits`)

**Why:** #2679 (TD-1197) made `plan()` toggle a `bad` class on `#entryline` and `#entryname` when a name is not free, and added a reset to the form's open so the next opening starts clean. The only JS tests are substring greps of `app.js`, and the one that names the `bad` class slices `plan()`'s body (`body = js[js.index("    async function plan() {") : …]`), so the open-time reset is outside what it reads. Probe from a clean worktree at `origin/main` 33544fbd2: deleting `nameBox.classList.remove("bad"); $("#entryline").classList.remove("bad");` from `app.js` and running `PYTHONPATH=$PWD/src pdm run pytest -q tests/test_ui_entry.py tests/test_ui_entry_host.py tests/test_ui_repo_org.py` gives `69 passed`, the same as unmutated. So a person who types a taken name, closes the dialog and opens it again sees the red line and red border on a fresh form, and no test says otherwise. (The same three test modules, run three times, passed all three times, and every Python-side revert of #2679's and #2683's changes that I tried failed a test; this is the one gap I could show.)

**Fix:** pin the reset: either extend the grep to the open handler's slice (`assert 'classList.remove("bad")' in the open body`), or, better, run the form's script in the headless browser the UI checks already use and assert the classes are gone after a second open.

**Done when:** removing the open-time `classList.remove("bad")` calls fails a test.

**Related:** TD-1197, TD-1190, #2679
