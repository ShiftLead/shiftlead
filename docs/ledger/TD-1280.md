## TD-1280: A main-thread `TaskStop` of a background subagent ends it on the record, so Ready to close reads *no subagents running* at once

**Priority:** Medium
**Type:** debt
**Added:** 2026-10-30 (the designer, from TD-1277)
**Owner:** grinder
**Kind:** build
**Status:** Open
**Part of:** TD-1277
**Location:** `src/shiftlead/adapters/claude_code/hook.py` (the `TOOL_EVENTS` branch, beside `SubagentStart` / `SubagentStop`); `src/sessionorc/agent_tick.py` (`_apply_subagents`, and the open-calls drop that pops a thread on `subagent_delta < 0`); `tests/test_claude_adapter.py`, `tests/test_subagents_live.py`; design §4.2's hook table (the `SubagentStart`, `SubagentStop` row), *A waiter is keyed by its call*, *Ready to close* (*No live subagents*)

**Why:** TD-1277: Claude Code (2.1.314, checked) sends no `SubagentStop` for a background subagent its caller stops with `TaskStop`, so the record's `subagents` stays at one until a restart, and Ready to close reads *✗ no subagents running* on an idle session for good.

**Fix:** as §4.2's table row writes it:
- **The adapter.** A `PostToolUse` with `tool_name == "TaskStop"`, on either thread, adds `subagent_stopped: <id>` (and no `subagent_seen`: a stop is no sign of life, so `subagent_at` stays where it was) to the tool event it already returns — the main thread's tool branch and the subagent tool branch (`hook.py`, the early return for an `agent_id`) alike — the id being `tool_input.task_id`, else `tool_input.shell_id`, as a string; an empty or missing id adds nothing. The adapter does not judge whether the id is a subagent's: it cannot see the record.
- **The core.** `_apply_subagents` reads `subagent_stopped`: if the id is in `subagent_ids`, remove it and take `subagents` down by one (never below 0); otherwise nothing, so a stopped shell's, a teammate's name or an id already gone moves no count. It takes no part in the `s.subagents > len(s.subagent_ids)` fallback of an unidentified `SubagentStop`. The open-calls drop pops the stopped id's thread as a `SubagentStop`'s does, and the stopped id's waiter and pending entries end as at its `SubagentStop` (`_end_waiters(sid, None, <id>, None)` and `_end_entries` on `p.subagent == <id>`), so a session with a second subagent left is not held `needs-you` on the stopped one's permission. A queued (replayed) event still moves the count, since `_apply_subagents` runs before the `queued` gate, and skips the open-calls and waiter steps, as every queued event does. A failed stop is a `PostToolUseFailure`, not in `TOOL_EVENTS`, and sends nothing. Nothing else of the event changes: it is the main thread's `PostToolUse`, with its `call: end` and state.
- A later `SubagentStop` for the same id (should a future Claude Code send one) finds it gone and moves no count by TD-960's rule.

**Done when:** through the hook's payloads (a `SubagentStart` with `agent_id` *X*, then a main-thread `PostToolUse` of `TaskStop` with `tool_input: {task_id: X}`), the record reads `subagents: 0`, `subagent_ids: []`, and the Ready to close row reads *✓ no subagents running*; a `TaskStop` of an id not listed (a shell's `b…` id) moves nothing; a `TaskStop` from inside a subagent of a listed id ends it too; `subagent_at` does not move on a `TaskStop`; a stopped subagent's pending permission ends while a second subagent stays counted; a `SubagentStop` of *X* after the `TaskStop` moves nothing; two listed subagents and a `TaskStop` of one leave one. Tests cover each case.
