## TD-2232: Adding a second tool's login under a used name stops stored sessions finding their account

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-26
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** d9b1699150904876abd54334fd6b7d24

**Why:** Audit of #4680 and #4688 (TD-2068 slices 1 and 2). On a switched host a record stores the name of its login as its `profile`, and the name a login is read under changes when another tool gains a login of the same name. A stored record then resolves to no profile.

The design promises the opposite:

- §4.2b *Terms used below*: "**Names are fixed**: a login's **name** and an account's **key** (`<adapter>:<name>`, as today) are set when it is made and never change, so a team's list, `director:` and every store that holds one never breaks. A name is unique per tool on a host".
- §4.9e *A record's `profile`*: a launch on a login writes the login's name into the record's `profile`, "so those readers keep working", and "a lookup of a profile by name, and of its account, gives the login of that name on that host". It says nothing about two tools' logins sharing a name.

The code: `logins.profile_name` (`src/sessionorc/logins.py`) computes the name from the file as it stands, the bare name while one login has it and `<tool>:<name>` once two do, and `profiles._from_logins` lists each login under that one name only. `name_taken` allows the second login, since names are unique per tool.

Probe at a5f15d01c, a scratch `logins.yml` holding `claude-code:grind` (account `claude-code:acct-1`), then the same file with `gemini:grind` added:

    one login  : ['default', 'grind'] account_of(grind) = claude-code:acct-1
    name_taken for gemini:grind: None
    two logins : ['claude-code:grind', 'default', 'gemini:grind'] account_of(grind) = None
    get(grind) -> "unknown profile 'grind'; known: ['claude-code:grind', 'default', 'gemini:grind']"

By the code, every record written as `grind` then loses its account: a launch or resume that reads the profile is refused as unknown, and `_account_key` (`src/sessionorc/agent_spend.py`) falls back to `<adapter>:<profile>`, which is not the key a reserve for `claude-code:acct-1` is kept under (the key's own doubling on a switched host is TD-2239's). #4680's review noted it as "open in the design" and #4688's review noted only the refused replay (TD-2068's Log); no entry holds the stored record. Nothing live is harmed until a host is switched.

**Location:** src/sessionorc/logins.py, src/shiftlead/profiles.py; docs/design/4.9e-switch-over.md, docs/design/4.2b-tools.md

**Fix:** Decide how a stored record goes on resolving when a name is shared: for instance a record's `profile` is always the login's key, or the reader takes the record's `login` field first, or a bare name that one tool already has is refused for another. Write it in §4.9e *A record's `profile`* (with the naming #4680 built: the bare name or the key, and a login winning over a profile of its name) and bring §4.2b *Names are fixed* into line. File the build, due before the cut-over.

**Done when:** The design says which name a record holds and what resolves it after a second tool's login takes the name, and a build entry is filed whose test adds that second login and still reads the first record's account.
