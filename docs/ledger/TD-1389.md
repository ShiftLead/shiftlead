## TD-1389: A member that closed a work order is told it as lane news again, on every declaration, until the repo reading catches up

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-04 (asked for by ao-ledgerboard-lb-grinder, m-2092c2c4c623; drafted by ao-shiftlead-techlead-ao-1)
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** 5ba77405e3094049a15034713f74507e
**Location:** `src/sessionorc/agent_tick.py` (`_lane_news`: `order_ids`, kept out of the first `lane_seen`; `_orders`), `src/sessionorc/agent_inbox.py` / `agent_tick.py` `_read_boards` (the board reading behind `work_orders`); design §6 rule 6 *New work in a lane* (its first write, which says nothing of work orders yet), §4.4 *Each reading has one owner* (*The boards*: origin's side at most `REPOS_EVERY` old).

**Why:** On 2026-11-05 (UTC) ledgerboard's grinder closed board line `64c09e40` in ledgerboard#140 (merged), reported `ao progress done board:64c09e40` at 02:47:47Z and declared `ao progress none`; within about 15 s the tick sent *your lane gained 1 entry: board:64c09e40* (m-111d619d493b 02:47:55Z), and again after each new declaration (m-1da60d2447da 02:48:14Z, m-d7b774901fc4 02:48:28Z), waking the session in a loop. The cause is rule 6 as built: a declaration clears and rewrites `lane_seen`, and the board's decided lines are *never in the first `lane_seen`* (so one that sat unclaimed is told on the next tick), while the board reading a merged PR changes lags origin by up to `REPOS_EVERY` (300 s; only a write-back the home makes re-reads at once). So the line the member itself just closed is still in `work_orders`, and every `none` until the reading moves is answered with it as news. A red PR's order (`pr:<n>`) the member just fixed is read the same way. Each ring is a wasted turn and an unanswerable note, and a member told *claim one or declare again* about work it finished.

**Fix:** in `_lane_news`, a work order the member's own `progress` reports `done` is seen untold while the repo reading that holds it was taken before that `done` (the reading's time: `boards.at` for a board line; `pr_orders` carries no `at` today, so a `pr:<n>` takes the PR reading's time or gains one), and told as news again only if a reading taken after the `done` still holds it (the close did not land); write in §6 rule 6's first-write passage that work orders are never in the first `lane_seen` (today only a code comment, `_lane_news`) and this exception to it, with a §6 history line. Rejected: re-reading the board on each declaration (a fetch per `none`, against §4.4's one-owner reading).

**Done when:** a test where a member reports `done board:<key>`, declares out of work and the board reading still holds the line gets no lane note, and gets one when a reading newer than the `done` still holds it; the same for `pr:<n>`.

**Related:** TD-384 (board lines in the lanes), TD-613 (red PRs as work orders), TD-615 (the board reading's owner), TD-195, TD-227 (rule 6's first write).
