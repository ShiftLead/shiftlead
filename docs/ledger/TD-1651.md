**Why:** TD-1551's examination (design §4.3 *What a start reads from the prompt cache*): of 511 sessions started on kmaster from 2026-11-01 to 2026-11-11 15:00Z, each counted once, not one first request read past Claude Code's own static opening (26,931–29,267 tokens), 257 that followed another in the same working directory on the same model within the hour among them. A start in the shiftlead checkout writes 25–44K tokens fresh at the one-hour write price. What ShiftLead puts in the opening is already the same for every member of a line. What differs is Claude Code's per-session sections and agent-cadence's session-start output, so reordering ShiftLead's parts reads nothing more. Claude Code 2.1.322's `--exclude-dynamic-system-prompt-sections` moves the per-machine sections out of the system prompt, which is the one lever left.

**Ask:** Will you let TD-1551's design, which files no reorder of what a started member reads, since no first request reads past Claude Code's static opening, and files one build (TD-1651, a measuring script, a print-mode trial of Claude Code's dynamic-sections flag, adoption at launch only on a rise, and a re-check that can take it out), go to its build after four review rounds ended at the cap with every build-changing fix read, or buy one more round, or hold it with a note?

**Fix:** Design §4.3 *What a start reads from the prompt cache*. Three parts: the script, the trial, and what follows.

1. The script. Commit `scripts/cache_opening.py`, which reads Claude Code project transcripts, read-only, and prints one row per transcript.
   - Its directories are positional and repeatable, defaulting to `~/.claude/projects`. Add a profile's `config_dir`'s `projects/` where a profile has one. Directories joined by a comma (`a,b`) count as one account's, for profiles that share an account.
   - A transcript's first assistant entry is its fresh start's, since `claude --resume` appends to the transcript it resumes, so a resume never adds a row. Skip sidechain transcripts (`isSidechain`), and skip entries whose model is `<synthetic>` or whose `usage` is empty.
   - Each row holds the start time, the directory, the model id, Claude Code's `version`, and that entry's `usage` (`cache_read_input_tokens`, `cache_creation_input_tokens`).
   - Filters: `--since <ISO time>`, `--model`, `--version`, `--repo <path>` (the transcript's `cwd` equals the path or lies under it, as members' worktrees under `<repo>/.claude/worktrees/` do; a worktree elsewhere is not matched), and `--brief <text>`, repeatable (a start matching any is kept), which keeps transcripts whose first user entry holds, in any of its blocks, the typed line (`My brief for this session is pasted below`) followed by a brief starting with `<text>` (a role's first line, `You are a **designer**`). `--no-brief` keeps those without the typed line, hand-started sessions. A card's Start session and the Add entry form's start also begin with the typed line but carry no role brief, so they fall under neither filter. `--warm` keeps a start only where a predecessor began within the hour before it: any non-sidechain start read from the same directory argument (one account's cache), on the same version and model id, whatever its repo or brief, since a card's start or another repo's member shares the flagged system prompt. `--repo` and `--brief` choose the starts kept, never their predecessors (the one-hour cache the members write, §4.2a). `--cold` keeps the complement: the starts with no such start before them. For both, predecessors are read from an hour before `--since`, so the window's first hour is not all cold.
   - A summary: the count, median and range per version and model id, and the pairs in one directory within the hour.
   - Test it in `tests/test_cache_opening.py`, loading the script by path (`importlib`) as `tests/test_history.py` loads its script, over inline fixture transcripts (two member starts within the hour, a cold one, a hand start, a sidechain, and a card start in the hour before a member start, which makes that member start warm).
   - TD-1551's figures are the examination's own, from the same first-entry read. The script's output over 2026-11-01 to 2026-11-11 rechecks them, and it goes in this entry's history.
2. The trial runs outside any home, from the grinder's own shell. Unset `CLAUDE_CONFIG_DIR`, so the runs use the person's default login. Nothing under `~/.shiftlead` is used, and no session record or transcript is made.
   - Write the home's preface (`sessionorc.mail.start_context_file_text(None)`) to a file.
   - The model is the model id the script's rows show for the most recent designer starts, else for the most recent member start of any role.
   - For each run, make a fresh scratch worktree of this repo at one commit (`git worktree add --detach` under a scratch directory). In it, run `CLAUDE_CODE_PROMPT_CACHE_TTL=1h timeout 120 claude -p --no-session-persistence --output-format stream-json --verbose --permission-mode plan --model <that id> --append-system-prompt-file <preface> "Reply with the single word ok."`. The repo's own SessionStart hook runs there too; that is expected.
   - Read the first event with `type == "assistant"` and no `parent_tool_use_id`, take its `message.usage`, and stop the process. Then `git worktree remove --force` the worktree. The prompt is harmless on purpose: a brief would start real work.
   - The unflagged pair is runs A then B, B started within five minutes of A. The flagged pair is the same with `--exclude-dynamic-system-prompt-sections` added. Run each pair twice, eight runs in all, a few cents of tokens. A run that fails or times out is run again and not counted.
3. What follows, by run B's first-request read in each pair:
   - It rises when, in both repeats, the flagged B read is at least 300 tokens above the unflagged B read, and its `cache_creation_input_tokens` falls by at least half that rise. The gain is the smaller of the two repeats' read differences. Then:
     - in the Claude Code adapter's `launch` (`src/shiftlead/adapters/claude_code/__init__.py`), add `--exclude-dynamic-system-prompt-sections` to the argv on a fresh launch and a resume, only where `prof.extra_args` does not already hold it, and only where the host's `claude --help` lists it. The check never runs on the host agent's event loop. `launch` stays synchronous and only reads the adapter's cached answer, so an empty or expired cache means no flag. The answer comes from an optional adapter method `warm()`, which core calls by `getattr(ad, "warm", None)` through `asyncio.to_thread`. Core names no tool (§4.3). At the host agent's start, beside `_recover_reaps` in `src/sessionorc/agent.py`, it runs as a background task over `adapters.names()`, kept on the agent and cancelled with `_ticker`, so the socket never waits on it. A `launch` before that task ends passes no flag, so the first start after a host agent restart may lack it; that is accepted. In `rpc_create` it is awaited right after `adapters.get(adapter)`, before `_evict_for_room` holds a room slot. At both call sites, an exception from a `warm()` is logged and suppressed. `warm()` takes no arguments and returns `None`. Claude Code's `warm()` is a per-instance cache that keeps one in-flight check, which concurrent callers share: one module-level injectable function runs `self.binary --help` with a 10-second timeout. A missing binary, a timeout, a non-zero exit, or a help that lacks the flag all count as absent, remembered for five minutes only, so a passing failure or an in-place upgrade does not leave the flag off for the host agent's life. A help that lists it is kept for the process's life. `warm` is a plain `getattr` method, not one of `OPTIONAL_METHODS` nor in `implements`. The build's PR adds it as optional to §4.3's contract block and to the comment block in `src/sessionorc/adapters.py`. It runs on whichever host or node launches (§4.4a), so a host with an older Claude Code launches as before.
     - test presence on both paths, no doubling, and absence where the help lacks it or the check fails, in `tests/test_start_context.py`, where `launch`'s `--append-system-prompt-file` argv is tested. An autouse fixture in `tests/conftest.py` patches the module-level injectable function to answer absent for the whole suite, so every adapter instance (the suite's `load_all()` makes fresh ones) never runs a real `claude` or gets a machine-dependent argv. `tests/_agent_child.py`, the suite's subprocess host agent, patches the same function to answer absent, as it already patches its other machine reads. The presence tests patch it to answer present, and reset the cache of any instance they hold;
     - reword §4.3's paragraph to say the launch passes it, with the gain;
     - file the re-check (below).
   - Otherwise leave the argv alone, and reword §4.3's paragraph to say the flag was tried and reads nothing more, with the numbers. File nothing with Claude Code: that is outward-facing and the person's.
   - In both cases, record the eight runs' numbers in `docs/history/TD-1651.md` under `## §4.3`, with the size of the system prompt past the static opening as the unflagged B run shows it: its `cache_creation_input_tokens` less the first user message's.

The re-check runs only when the flag lands, and decides it on real member starts, since print mode is not a member launch. Take its id from `ao td reserve` and file it with `ledger.py new --id TD-m --title "Re-check TD-1651's dynamic-sections flag on member starts" --kind build --owner grinder --part-of TD-1551 --blocked-by "until <the UTC day 14 days after this build's own PR merges>"`. Write its `--why`, `--fix` and `--done-when` files from what follows, with the gain and this build's merge commit written in.
- Its Fix, step 1, live. `ao --json promote status` gives shiftlead's live commit (`.shiftlead.live`, the object being keyed by repo). If `git merge-base --is-ancestor <this build's merge> <live>` fails, set its `until` seven days on, add a `ledger.py note` line `deferral <n>`, and stop. With two `deferral` notes already present, do not defer again: the flag comes out as undecided.
- Step 2, measure. Run `scripts/cache_opening.py --since <the day after this build's merge> --repo /home/kmaster/shiftlead`, its directories as step 1 names them. Run it twice with one `--brief` per member role that ran, a role's first line taken from its brief template (`src/shiftlead/briefs/<role>.md`): once with `--warm`, once with `--cold`. If live took the merge more than a day after it (per `git log` of the promote, or the person's word), `--since` is that day instead. It measures kmaster's own starts. A container node's starts stay in the node, and a node that lags the promote does not change the rule.
- Step 3, decide, per Claude Code version and model id present in both sets. The baseline is the cold member median first read, the static opening, which a start with no warm predecessor reads with or without the flag. Only warm member starts can read past it. It passes when the warm member median is at least the baseline plus half the gain.
  - A version and model with fewer than 10 warm or 3 cold member starts does not count. If none counts, defer the same way, with a `deferral <n>` note. After two deferral notes of either kind, decide on the version and model with the most warm starts, if it has 5 warm and 1 cold, a single cold read standing as the baseline. Otherwise the flag comes out as undecided, since removing it costs nothing.
  - Any counted version and model that passes keeps the flag. It fails only when every counted one fails.
- On a pass, record the numbers in its history. On a fail, take the flag out of `launch` with its test, and reword §4.3's paragraph to say why, with the numbers.
- Its Done when: the numbers recorded, and the flag kept or removed accordingly.

**Done when:** `scripts/cache_opening.py` is committed with its test, and its output over TD-1551's window is in the history. The trial's eight runs' first-request `usage` numbers are in `docs/history/TD-1651.md`. Either the Claude Code adapter's launch passes `--exclude-dynamic-system-prompt-sections` on a fresh launch and a resume, not doubled, with a test holding it and the re-check entry filed, or §4.3 says the flag was tried and why it stays out. §4.3 *What a start reads from the prompt cache* says which.
