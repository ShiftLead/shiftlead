## TD-2120: A live check under a flow is told to read and never press, and can wait behind a fix or a gate

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-23
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** 744c3b5fc72d4a10b64e8c1d56f68dac
**Blocked by:** TD-2051, TD-2052
**Part of:** TD-2114

**Why:** Once flows run, a pickable live check reaches a build stage, whose brief tells a session to build. Three of a live check's four endings leave the entry open behind a new blocker or gate, and no outcome a build stage has today can carry that: `work-pushed` is refused without the archive, and a merged pull request that leaves its entry open sends it to the person.

**Location:** src/shiftlead/stage_start.py, stage_end.py, stage_merge.py, stage_acts.py, stage_make.py, stage_read.py

**Fix:** Build design §4.9c *A live check under a flow*, with the `check-waits` row of *An outcome is the session's word, checked* and reconcile's case for it.

- **The mechanics** (`stage_start.told`, the entry's `Kind:` carried on `Work`, which the offer reads from the ledger): for an entry whose `Kind:` is `live-check`, whatever brief the stage picks, say that this replaces any building the brief asks for, that the live copy is read and never pressed, the four endings and each one's outcome, and that the cadence's fact-check comment is posted before `check-waits`.
- **The outcome** (`stage_end`): `check-waits`, taken on a design or build stage for a live check alone, with the facts of its row, the entry's `Blocked by` and any board item read from the forge at the pull request's head (for a node's session too). It is written by no flow, so `flow3.OUTCOMES` and the flow check do not list it, and `stage_end.destination` answers it with its fixed move: `merge`, a refused merge back to this stage at most three times, on the stage's one `refused` count (`stage_merge`).
- **The record** (`stage_acts`, `stage_make`): no new wait. A merged pull request whose record's last outcome is `check-waits` closes the record, whatever it waited on, including a hand merge and a crash before the write. Clearing the home's own question on that close leaves a `decision` whose Ask the pull request wrote. The existing first offer of a closed record's open entry brings it back once pickable (`stage_read` already reads it so).

**Done when:** Tests on fixtures show: a live check's session is told the check's rules under a standard brief and under a person's own, and a build entry's is not; `check-waits` is refused on a build entry, on a pull request that archives the entry, changes a file outside the ledger and board, or carries a review stage's verdict, and where the head adds no blocker that holds (an archived id, a reached `until`, an `event` with no section, a `decision` with no board item); accepted, it merges past a review stage; the merge closes the record, including by hand after a person-only refusal and after a crash before the write, and keeps a `decision` the pull request wrote; while blocked the entry is offered to nobody; once pickable it gets a fresh session by the way in, on a new branch, with its stage renamed or its team moved meanwhile; a live check that holds ends by `work-pushed` on the flow's own route.
