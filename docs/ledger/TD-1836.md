**Why:** Grok Build 1.0.77 reads the person's `~/.claude/settings.json` for its permission mode, and a Claude Code `defaultMode` it reads wins over the launch's `--permission-mode` (TD-1835's probes, 2026-11-14). So on a machine whose file sets `auto`, every Grok session ShiftLead launches runs under the Claude classifier, `permission_prompts: all` included. TD-1835 designs the cure: the launch runs with `HOME` a launch home that mirrors the person's home by links, all but Claude Code's two user-level settings files.

**Location:** src/shiftlead/adapters/grok/; design §4.3 (The third adapter: Grok Build)

**Fix:** Build the launch home as design §4.3 *The third adapter: Grok Build* (*`launch`*, and the paragraph on what crosses with no switch) says, in `src/shiftlead/adapters/grok/`:
- `<config_dir>/launch-home/`, made or refreshed before every pane (create and resume): a symbolic link for each entry of the person's home, but `.claude`, a directory of its own holding a link for each of `~/.claude`'s entries but `settings.json` and `settings.local.json`;
- the refresh adds a link for each entry the home has gained and removes each link whose target is gone; an entry that is not a link is left and never deleted, and a link it finds is replaced only when it points elsewhere; it is safe with a second session of the profile running;
- the launch env's `HOME` is the launch home; a launch home that cannot be made or refreshed refuses the launch in words naming the path;
- `doctor_profiles`'s note for a profile under `permission_prompts: ask` on a machine whose `~/.claude/settings.json` sets a `defaultMode` (§4.3 *Reads*, §4.2a *permission_prompts*);
- unit tests: the note; the two settings files are absent and every other entry present at both levels; a refresh after the home gains and loses an entry; a regular file at the top of the launch home survives a refresh; the refusal.

Then TD-1637's walk on `grok-conformance` with the person's own `~/.claude/settings.json` in place (its `defaultMode: auto`). Since 2026-11-14 08:2x the walk's *first hook* step fails on kmaster for the person's home and the launch home alike (state `working` by hook after `SessionStart`, a *Help improve Grok* opt-in banner on the screen), so that step's cause is read first; it is TD-1637's, not this build's, and this build's walk waits for it if it is still failing.
