**Why:** Today, whether a model integration works and whether the model judges well are learned together, from a trial on live PRs, and the trial cannot tell them apart. Paul asked for an entry that separates the two (through `ao-led-tds-ledger`, m-5b1540d3e9be, 2026-11-10). The Gemini fact-check trial (TD-1214, TD-857) shows the cost:
- Of 72 `fact-check-trial:` lines on shiftlead's PRs since 2026-10-25, 63 are `none`. Most read `none · idle`, an ask the seat never read before the bound; a few read limited or no seat.
- The 4 verdicts it did give were all SHIP, with 0 defects caught and 9 missed.
- Since 2026-11-10 every reply has stopped on a Gemini CLI permission prompt (TD-1576).

Two weeks of live PRs were spent before anyone could say whether the failure was the plumbing or the model.

The design's checks do not cover either half:
- **The offline suite** (§4.3 *The conformance suite*, `tests/conformance/`) replays captured panes, hook payloads and transcripts through the adapter's methods. It never runs a seat's life end to end: a launch, an ask delivered and read, an `ao` command run, the reply landing, the seat ending.
- **The live walk**, `pdm run conformance <adapter> --profile <p>`, runs the real tool by hand. But it declares the profile with `permission_prompts: all`, the adapter's `asking_args`, and answers each permission as the person. So it never runs a seat the way an unattended one is launched (Gemini's `--approval-mode yolo`), and it could not have seen TD-1576's prompt, which only an unattended launch hits.
- **Nothing measures a model's fitness for a role** before it takes the role. TD-1214's ratios are read off live PRs after the fact.

**Design PR:** #3410

**Fix:** Design first (§4.3 *The conformance suite*; §4.9b *The fact-check*, *Who, and how long*; §4.2a profiles), then builds. Separate the plumbing from the judgment:

- **(a) A deterministic end-to-end conformance case per adapter, with no live model.** A stub CLI stands in for the tool's binary and replays a script: it launches, fires the hooks the adapter's captured fixtures say it fires, receives an ask and reads it with `ao inbox`, runs a fixed `ao` command (the reply), and ends. The case asserts the record's states, the reply landing on the asker's thread, and the seat closing. It runs in CI on a private tmux socket and a scratch home, as the offline suite does. Settle how far the stub mimics the tool (its hooks and composer from captured fixtures) and where the adapter's launch args are asserted instead of run.
- **(b) A live smoke check with a trivially checkable task**, such as *reply to this ask with the token `<nonce>`*. It runs on the real tool and profile **as an unattended seat is launched**: the adapter's unattended args, yolo included, and no person answering. It passes only if the nonce comes back on the thread with no NEEDS YOU, so it proves the real path end to end, permissions included, and would have caught TD-1576. Settle when it runs (a profile change, a CLI upgrade the home reads, an adapter change), what it spends, and where a failure is said.
- **(c) Quality measured apart from the merge path.** A fixed set of PRs with planted, known defects is given to a role's prompt and scored mechanically: caught, missed, false. A model's fitness for a role (fact-checker, reviewer) is then a number before it takes the role, not a trial run on live PRs. Settle where the set lives, how a planted defect is matched to a finding without a model judging it, and what score a role asks for. TD-1214's tally becomes this set's first baseline.

**Done when:** Done when the design names all three:
- the stub-CLI end-to-end case and what it asserts;
- the unattended live smoke, with its nonce, its triggers and where a failure is said;
- the planted-defect scoring set, with its mechanical match and each role's bar.
Builds land (a) in CI for Claude Code and Gemini CLI, and (b) would have caught TD-1576's prompt when replayed against Gemini CLI 0.66.0.
