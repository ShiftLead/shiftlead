## TD-2258: Nothing tests that a job starts from the set of logins and models its repo picked

**Why:** Audit of #4731 (TD-2068 slice 6), which has a job's session start on the first usable login of the built-in set its repo uses. `reach_for`'s `start` (`src/shiftlead/stage_job_tick.py`) names that set, `name = builtinstore.repo_set(sdoc, repo)`, takes the job's model from it and passes it on as `on_set=name`. Design §4.9d: "A repo uses one set"; `reach_for`'s docstring: the seat's model "from the built-in set the repo uses".

The one test of the call (`tests/test_stage_job_tick.py`, `test_the_reach_starts_a_review_stages_session_where_the_record_stands_at_one`) replaces `repo_set` with `lambda sdoc, repo: "s"`, which reads neither argument. With the call changed to `builtinstore.repo_set(sdoc, "")`, the 29 test modules naming the stores, stage starts or built-in seats passed at 368b1fefa (1162 passed). The line passed the repo before #4731, untested then too; #4731 makes the set's name choose the login as well. TD-2253 is the same gap for a built-in seat's fill, a different caller. With this change and those TD-2257 and TD-2259 name made together, the whole suite passed at f6882e354 (`pytest -n 8`: 10283 passed, 24 skipped).

Probe at 368b1fefa (a temporary test: settings with a set `night` whose board-answers model is haiku, `repos: {r: {builtins: night}}`, `reach_for` for repo `r`): unchanged, the job launches with model haiku on set `night`; with the change it launches with sonnet on `default`.

A break would start every repo's jobs on the default set's models and logins, whatever the person picked for the repo.
