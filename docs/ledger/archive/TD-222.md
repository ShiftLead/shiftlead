## TD-222: A board write-back is never pushed and the host agent never pulls

**Priority:** Medium
**Added:** 2026-09-28 (the designer, found in TD-208's round)
**Owner:** designer
**Kind:** design-first
**Blocked by:** TD-263, TD-264
**Status:** **Designed 2026-10-01** (the designer, PR #892; the steer to Paul on how a write-back reaches origin is `m-23539eb2dcc8`, bound 2026-10-02 05:31 MDT). Design: §6 *Pull* (the policy: every registered checkout, in the promote's pass, `--ff-only` when git allows — default branch, no git operation or promote run under way, the fast-forward accepted — and the anchor session is idle — every occupant of the root at rest, an external `claude` by its registry's `status`, one it cannot read taken as mid-turn; its `pulls` reading; the `repos.<repo>.pull` switch, on when absent), §4.4 *Board write-back* (the edit made on origin's head in a tree of the host agent's own and pushed; the checkout never written, the refusals for its state gone, *origin unreachable* and *the line is not on origin* in their place), §4.5 screen 6 (*the host agent does not pull* reversed; every row actionable; the read after a press a fetching one), §4.5a (the origin note's tail, the Repos card's **pull**, the Decide row), §5 (`pull`). **Paul's reply, 2026-10-01: *go with the default*.** The same night the anchor found the push itself refused by the repo's ruleset (*PR required*; `ALLOW_MAIN_PUSH=1` passes only the pre-push hook), so the road is now a branch of the host agent's own and a PR it opens and squash-merges at once (§4.4), steered to Paul as `m-9c19613f7220` (bound 2026-10-02 09:48 MDT) over a bypass on the ruleset for the pushing identity, which would let every session in the checkout push `main` under the override. **The steer's default is the third road, origin's head** — not the entry's (a), the checkout's own commit pushed, which leaves the checkout ahead on every press and needs a rebase the host agent must never make when origin moves first, nor (b), as it was. The two alternatives stay in the design-history. **Cadence §4.5's sentence** (*the tool commits in the main checkout … never pushes — the anchor's next push carries it*) is dev-cadence's: on the board for Paul, and TD-264 waits on it. The *Decided* and *Fix* below are the record of the round.
**Location:** design §4.4 *Board write-back* (*it never pushes*), `src/sessionorc/board.py` (its docstring: *the person's click is never turned into a dirty file under the anchor session's feet*), cadence §4.5 (the carve-out: the edit is committed in the main checkout and *never pushes — the anchor's next push carries it*), dev-cadence's reader (`_fetch_board`: *both sides changed — pull/push; showing local*)

**Why:** a Snooze, Done or Reply commits on the main checkout's default branch and stays there until the anchor pushes it. Until then the checkout has an edit origin lacks, and the next merged PR that touches the board makes the two differ on both sides; the reader then shows the local board, and what origin added is hidden until someone pulls and pushes by hand. The other way round, a row the Inbox reads from origin (TD-208) cannot be acted on until the checkout is pulled, because the host agent does not move the person's tree. TD-208's design says both on the page and cures neither.

**Fix:** decide, as one question or two: **how a write-back reaches origin** — (a) the host agent pushes its one commit, fast-forward only, which cadence §4.5 does not permit today (it names the anchor's push), so dev-cadence's rule changes first; (b) as today, the anchor's next push, with the page's warning as the reminder; (c) the edit is made on origin through the forge's API and the checkout catches up by a pull. And **whether the host agent may fast-forward the main checkout** (`--ff-only`, clean tracked files, on the default branch) so a row read from origin can be acted on, against *the tree is a person's* (design §6 *Promote*). The designer recommends (a) and no fast-forward: one commit of one line is the smallest thing that keeps every host's view the same, and a pull stays a person's or the anchor's act. Done when the choice is written in design §4.4 and its build entry exists.

**Decided, 2026-10-01 (Paul): the host agent fast-forwards the main checkout.** He asked after finding the anchor's `main` 19 commits behind origin with every board row read from origin disabled: *it seems like main on the anchor falls behind consistently — should we have our host agent pull it routinely if no session is running on the anchor?* The rule he chose: **when git allows and the anchor session is idle.** This reverses the designer's *no fast-forward* above and the design's *the host agent does not pull* (§4.5 screen 6 *Boards are read against origin*; §6 *Promote*: *the tree is a person's*), so the design changes first. For the round to settle:
- **When git allows:** the checkout is on its default branch and `git merge --ff-only origin/<default>` goes through. Git itself refuses a fast-forward that would touch a locally changed file, so a dirty file elsewhere (an unsaved memory note) does not stop it and nothing of the person's is overwritten. A checkout with a commit of its own is left alone and said on the page as it is today, which is every checkout holding an unpushed write-back commit, so this rule does little there until the first question is settled too.
- **The anchor session is idle:** no session in the checkout's root is mid-turn. The anchor is often a plain Claude Code session agentorc did not start, so the round says how the host agent knows and what it does when it cannot tell (the anchor's recommendation: no pull, and the origin note stays). No session at all counts as idle.
- **Where and how often:** a policy of the home's tick over the registry's checkouts, as the promote is; whether it is a setting (§5), and what the page says after a pull or a refused one.
- **The live copy is not moved by it:** a pull changes the checkout, and the promote stays its own press or policy (§6 *Promote*).
