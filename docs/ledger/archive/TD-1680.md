## TD-1680: Settings refuses every save for an account whose reading stopped reporting a window it still holds a reserve on

**Priority:** high
**Type:** debt
**Added:** 2026-11-11
**Owner:** grinder
**Kind:** build
**Status:** Resolved 2026-11-11
**Id take:** 8e6f227342d449468886449d558c022f

**Why:** The person cannot save any reserve for `claude-code:paul` from the Settings page (2026-11-11, screenshot `~/.shiftlead/attachments/draft-ad921cdc/paste-20261111-121115.png`). The account's reading now reports only a `week` window (its subscription no longer has a 5-hour session allowance), but `settings.yml`'s `usage_gate:` still holds `5h: 5` from before. `usage_cards` in `settings_page.py` draws a row for every reserve on a label no reading has shown (*no reading yet*), so the card shows a `5h reserve` field holding 5; its Save sends every row, and `set_settings` refuses the whole call because `5h` is a label the reading does not report: *account claude-code:paul reports no window 5h: its windows are week (design §4.7)*. The refusal counts a clear (`5h: null`) as an unknown label too, so emptying the field is refused as well, and so is `ao gate claude-code:paul 5h=`. The stale reserve does nothing (`settings.lines` reads only reported windows), yet it blocks every change to the account's real reserve: the only way out today is editing `settings.yml` by hand, though design §4.5 screen 8 says a setting is written only through `set_settings`. The row's *no reading yet* is also wrong: there is a reading, and it lacks that window. Any adapter that drops or renames a window will strand its account the same way.
