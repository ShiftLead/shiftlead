## TD-692: An open page can reload itself about once a second for hours, and only a hard refresh ends it

**Priority:** Medium
**Type:** debt
**Added:** 2026-10-14 (session `promote_check`, from Paul's report that ShiftLead had looked down for 30 minutes)
**Owner:** designer
**Kind:** design-first
**Status:** Designed 2026-10-14 (the designer; no mockup: one banner, drawn as the down banner is) — §4.5 *Browser mechanics* *A reconnect reloads once, never in a loop*. A stream is up at its first message that is not `error`, so a stream that fails each time it opens never reloads the page. Reloads on a reconnect are counted in `sessionStorage` by path; a fourth within 60 s is held back and the reload-loop banner (§4.5a, **Reload**) says why. The stream carries `?page=<hash>` (its `app.js`'s `v=`); the UI logs one warning for a client opening `/events` from one path more than 20 times in 60 s, naming the page's hash and its own, and logs the exception behind the `error` the `events` handler sends itself, at most once a minute (the subscriber's already is). `connectEvents` toasts an `error` on every page. The reproduction on a scratch home is the build's first step. Built by TD-694. Was: Open — Owner was `grinder` until 2026-10-14, which put a `design-first` entry in no lane (the design lane is `[design-first, owner:designer]`, design §4.9c); the design round is the designer's.
**Blocked by:** TD-694
**Location:** `src/shiftlead/ui/static/app.js` `connectEvents` (*a reconnect reloads the snapshot once*); design §4.5 *Browser mechanics*

**Why:** On 2026-10-14 Paul's laptop showed ShiftLead as down for at least 30 minutes, though Tailscale was connected. On kmaster both units were up and answering 200s, and the route port refused nothing from the laptop. In the UI's journal, three open tabs (`/repo/shiftlead`, Focus `ao-shiftlead-ao-connect`, Focus `ao-shiftlead-ao-dc-decouple`) each loaded the page, opened `/events`, and loaded the page again a second or two later. Together that was about 90 `/events` opens a minute, from 16:28:31 until Paul's hard refresh at 18:22:56. The loop lasted through five restarts (16:33, 16:59, 17:26, 17:57 and 18:18), each one an `auto` promote. Nothing in the journal flags it, and no error was logged. It began with no restart or promote at 16:28. After the hard refresh it fell to 0–14 opens a minute.

**Suspect, not proven:** `ws.onmessage` reloads when `reconnected` is set, and `onclose` sets it. If a socket closes before its first message and the next one gets a message, each fresh page reloads once more. The comment above `onopen` names that shape for a down agent. A plain reload kept the loop going and a hard refresh ended it, so a cached subresource (`app.js`, or the HTML that names it) is part of it.

**Fix:** design first (§4.5 *Browser mechanics*).
- **Reproduce** the loop on a scratch home: open Focus and the repo page in headless Chromium, restart the UI and the agent in each order, and promote. Record what closes the socket before its first message.
- **Bound it.** A page that has reloaded on reconnect more than N times in M seconds stops reloading. It shows the down banner with a **Reload** button and says why. A `sessionStorage` count keyed by path does it.
- **Make it visible.** The UI logs one warning when the same client reloads in a loop. A promote's restart is the usual trigger, so the warning names the build the page came from (`this page: <sha7>`, §4.5a build chip).
- **Tests:** the bound (a page stops after N reloads in M seconds) and the warning.
