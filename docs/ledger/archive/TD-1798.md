## TD-1798: A session idle before a usage cap reads stalled? when the cap lifts after a host agent restart

**Priority:** medium
**Type:** debt
**Added:** 2026-11-13
**Owner:** grinder
**Kind:** build
**Status:** Resolved 2026-11-13
**Id take:** 9af98572c99e49abbdd5eb8da3907c96

**Why:** On 2026-11-13, after TD-1797 (#3735) was promoted and the week cap lifted, four interactive Claude sessions that had been idle at their composer (`ao-paul`, `queue`, `security`, `td-704`) read `stalled?` instead of `idle`. The state a session had before a poll's `limited` is kept only in the host agent's memory (`_pre_limited`, `agent.py`), and the promote restarted the host agent while they were `limited`. On the lift `_usage_limits` found no saved state and fell back to `working` (`self._pre_limited.pop(s.id, "working")`); no hook comes from a session waiting at its composer to correct it, so the tick then read a `working` session with no output as `stalled?`. The harm is a false alarm on each such session, on the Queue and the Org, after any host agent restart inside a limited spell, which is exactly when a fix for a limit is promoted.

**Location:** src/sessionorc/agent_tick.py (_usage_limits); src/sessionorc/agent.py (_pre_limited); design §4.2 the limited rule

**Resolved:** 2026-11-13 (PR #3744)

**Done when:** Done when a session that was idle before a poll's `limited` reads `idle` after the cap lifts across a host agent restart, one that was working reads `working`, the design says where the earlier state is kept, and a test pins both.
