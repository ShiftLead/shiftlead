**Why:** Audit of #4767 (TD-2266). The test it added, `test_a_create_passes_over_a_login_whose_old_reading_projects_past_its_line` (`tests/test_launch_on_login.py`), fails now and then on unchanged code. It writes a usage reading into `agent._usage_acct` and then creates a session, while the `agent` fixture's tick loop is still running (`tests/conftest.py`); the tick keeps `_usage_acct` itself.

At d70555bf3 plus the ledger-only head of PR #4779, no source changed:

- The module run alone twelve times failed once: `assert 'hookstub:grind' == 'hookstub:spare'`, *the projection puts the first past its line*. An independent reader saw it fail in 2 of 4 runs of three modules together. Twelve runs of the one test alone all passed.
- With `await agent.tick()` added after the reading is set, the test failed 3 of 3.
- With `await park_ticks(agent)` added before the reading is set, it passed 3 of 3 alone, and the module then passed 30 runs of 30.

Which step of the tick undoes the reading I did not establish: after the added tick the `acct-1` key was gone in one run of three and still there in two.

A test that fails by timing reds a precheck for a pull request that changed nothing it reads.

**Location:** tests/test_launch_on_login.py test_a_create_passes_over_a_login_whose_old_reading_projects_past_its_line; tests/conftest.py park_ticks

**Fix:** Call `await park_ticks(agent)` in that test, or in `_real_rows`, before the reading is set (`tests/conftest.py` `park_ticks`).
