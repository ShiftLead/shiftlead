## TD-2037: Test workers crash in the UI page tests under load, so a precheck goes red for no reason in the PR

**Priority:** Low
**Type:** debt
**Added:** 2026-11-21
**Owner:** grinder
**Kind:** build
**Status:** Resolved 2026-11-21
**Id take:** 3dcb67c9c51745788ed24abdbceaea34

**Why:** On 2026-11-21 three runs of the full suite on PR #4298 (two prechecks and one local run) failed because pytest-xdist workers crashed. The tests they were running were UI page tests (tests/test_ui.py, test_settle_pages.py, test_sweep_switch.py, test_ui_build_chip_pages.py, test_ui_focus_rail.py, test_ui_inbox.py, test_no_agent_pages.py), and the set changed every run. Each one passed when run alone, and a fourth precheck on the same head passed (254s). kmaster's load average was 13 to 19 at the time, with 14 GB available. A crash like this turns a precheck red for a reason that has nothing to do with the PR, and the author pays for another full run. TD-1446 (archived) saw the same symptom once, in one test of tests/test_ui.py, on 2026-11-06.

**Location:** tests/test_ui*.py, tests/test_settle_pages.py, tests/test_sweep_switch.py, tests/test_no_agent_pages.py; pyproject's pytest/xdist options

**Resolved:** 2026-11-21 (PR #4306)

**Done when:** Two full suites run at once on kmaster finish with no worker crash, or the entry names the cause and why it cannot be helped.

**Log:**
- 2026-11-21: looked: on 2026-11-21, three pairs of runs at once on kmaster (the UI files twice, the full suite twice, then the full suite twice shaped as the precheck: TERM=xterm-256color, synced venv), load average up to 59: no worker crashed. The kernel log since 2026-11-20 12:00 holds no OOM kill and no segfault, and nothing in src/ or tests/ ends a worker. What does end one is pytest-timeout's thread method: a test past 120 s has its stacks dumped and the worker os._exit'd, which under xdist reads exactly as *worker 'gwN' crashed while running …* with the dump lost (checked with a 3 s timeout on a sleeping test) — TD-1446's cause, a hang under load. So these crashes are most likely hangs whose stacks the suite threw away.
- 2026-11-21: fix: pyproject sets faulthandler_timeout = 110, so pytest's faulthandler writes every thread's stack to the worker's stderr, which the controller prints, ten seconds before the kill: the next such crash in a precheck's output carries the stacks of its hang, and is filed as its own entry with them. Done when holds: two full suites at once finished with no worker crash, twice.
- 2026-11-21: archived: Resolved — Resolved — six runs at once crashed no worker and the kernel shows no OOM or segfault; the crashes read as pytest-timeout's os._exit on a hang, whose stacks xdist drops, so faulthandler_timeout = 110 now prints them before the kill
