   **The checkout must be mounted at the same absolute path inside the container.** contractmatch's devcontainer declares no `workspaceMount`, so the checkout is `/home/kmaster/contractmatch` outside and `/workspaces/contractmatch` inside (the Dockerfile's `WORKDIR`, `setup_scripts/postCreate.sh`, the repo's `.claude/settings.json` and `workers-api/assets/gen_og.py` all hardcode the inside path). Two things the earlier drafts parked as design questions are consequences of that and of nothing else:
   - **git worktrees break across the boundary.** `git worktree add` writes absolute paths both ways, and a team puts its lead and every grinder in a worktree. A worktree made inside points at `/workspaces/…` and is broken on the host; worse, `git worktree prune` on the host — which the cadence's own sweep runs — deletes the container's worktree metadata *while a grinder is in it*.
   - **Invariant 2's "identity that survives a mount namespace" is mostly just the path.** `occupants()` compares `Path(dir).resolve()`, and it never reads `repos.txt` (that registry feeds the New-session list and dev-cadence's `/attention`), so "register the repo on one host" — an earlier draft — was wrong in mechanism. Mount the checkout at the identical path and the home can check occupancy over its own records and the container's, because it knows from the `container:` entry that the paths are the same directory. What no agent can see is the person's own `claude` in the person's own VS Code container: `external_sessions()` reads a profile's config dir and tests liveness by pid, which means nothing across pid namespaces. That case is the person's, as a terminal on another machine is today, and the design says so.
   The home's generated definition sets `workspaceMount` and `workspaceFolder` (§4.4a); the repo's part is re-pointing the four files above (and the `safe.directory` lines the Dockerfile and `postCreate.sh` bake for the old path — harmless today only because the uids match) and pinning the user (`useradd --uid 1000`: Debian hands `developer` 1000 today because it is the image's first user, which is luck, not a contract).

   **The link. A container is a node like any other and dials out; `docker exec` is backwards for it** — `link:` is read only by a node dialling out (`_dial_home`, gated on `mode == "node"`) and `bridge()` connects to `paths.socket_path()`, its own namespace's socket, so the command would re-enter the same container and connect to itself: a loop, not a link. (True of *the link only*: `docker exec` is the right verb host→container, and it is how the terminal reaches a container.) The shape is **a per-node link socket at the home**: `serve` binds, for each `nodes:` entry, `~/.agentorc/links/<name>/link.sock` (`0600`, its directory `0700`), speaking only the link protocol, and a connection on it *is* that node, so `_serve_link` runs with the name from the home's config and never from the node's argv — §4.4a's rule kept, with no sshd in the image, no key, no network, and §4.5b intact. **The container gets the directory bind-mounted, never the socket file**: `serve` unlinks and re-binds its socket on every start (`agent.py`, `serve`), a bind mount of a file keeps the old inode, so a mounted socket file is dead after the first restart of the home — which every TD-062 promote is. Code at **both** ends: on the home, the listeners in `serve` and a connection handler that enters `_serve_link` with the configured name; on the node, `link: {socket: <path>}` in `hosts.py` and a branch in `link._dial_once` that opens a unix connection instead of a subprocess, with *ssh failed* worded *cannot connect*. Two shapes considered and not taken: `link: {ssh: <home>}` from inside the container (zero code, but an sshd reachable from a bridge network and a key in the image — the shape for a container on *another* machine, which is a plain ssh node); and ~~the home's whole `~/.agentorc` bind-mounted in~~, **struck** — it hands the container the home's `agent.sock`, where an unqualified caller is *a person at the home*: kill any session, `create`, set grants, plus the store, run logs and the person inbox. Not a weaker trust boundary — no boundary.

   **Who installs the agent — the home does (Paul's question, 2026-09-17).** Not the person by hand (`pipx install agentorc` inside drifts from the home's version until the link refuses it, and dies with the next image rebuild) and not the repo's Dockerfile (couples the project's devcontainer to agentorc and rebuilds the image at every promote). The home generates the node's devcontainer definition from the repo's — `build` paths re-anchored to absolute, since the file lives under `~/.agentorc/nodes/<name>/` — with the person's `mounts`, `customizations` and `containerEnv` dropped — contractmatch's `/mounted/stuff_for_containers_home` carries `.netrc`, `.kube` and `.modal.toml`, the person's whole credential set (Sonnet review, 2026-09-17: the earlier draft saw only `.netrc`) — and each dropped mount replaced by an empty tmpfs at its target, because a repo's lifecycle script may assume the path (contractmatch's `postCreate.sh` runs `mkdir -p /mounted/dev/…` under `set -e`, second Sonnet round: it would have died there), brings it up under its own id label as a second container from the project's image, installs its own wheel into a venv on the node's volume, writes the node's `hosts.yml`, and supervises the agent from its tick. The node's `AGENTORC_HOME` is on that volume: lose it on a rebuild and the run logs (invariant 3) and the waits go with it, and the node reconnects with an empty snapshot the home takes as the truth about that host. A worker's secrets are the node's `env` file — a fine-grained PAT scoped to contractmatch as `GH_TOKEN` (without it the first grinder pushes a branch and cannot open its PR, since the image's `gh` has no `~/.config/gh` and `git push` reads `.netrc`, which `gh` does not), the author name and email, a Doppler service token — never the person's.
