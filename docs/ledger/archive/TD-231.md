## TD-231: The usage endpoint answers 429 for hours though agentorc polls once per account

**Priority:** High
**Added:** 2026-09-28 (Paul: *investigate the 429s — we may need to research anthropic's best practices for retrieving usage programmatically*)
**Owner:** designer
**Kind:** design-first
**Blocked by:** TD-233
**Status:** Designed 2026-09-28 (the designer, PR #734), on the research below and its recommendation: design §4.4 *Usage, reported first and asked for last* and §4.3 `usage_report`. The Fix's step (2), measuring whose calls spend the endpoint's allowance, is not done and is no longer needed to choose: the design stops depending on the endpoint. Closes with TD-233. **Research done 2026-09-28** (the anchor's Sonnet pass, read-only, the endpoint not called; Claude Code 2.1.284). Findings: (1) **no documented way to read a Pro/Max subscription's limits.** The Usage & Cost Admin API needs an admin key, is *unavailable for individual accounts* and reports tokens and cost for API orgs (platform.claude.com/docs/en/manage-claude/usage-cost-api); `/api/oauth/usage` is undocumented. (2) **The statusline gets them, documented**: its stdin JSON carries `rate_limits.five_hour` and `rate_limits.seven_day`, each `{used_percentage, resets_at}`, for Pro/Max only, after the session's first API response, any window possibly absent (code.claude.com/docs/en/statusline). OpenTelemetry has no rate-limit metric; hooks were not found to carry it. (3) **The 429s are widely reported** for Max accounts even at five-minute polling, lasting hours, with `Retry-After` 0 or absent and no Anthropic reply (anthropics/claude-code #30930, #31637 closed *not planned*, #31021). So agentorc's doubling back-off can't learn the window. (4) Model responses carry `anthropic-ratelimit-unified-5h-utilization`, `-7d-utilization` and their resets, named only in the client binary (undocumented). (5) **The installed client calls the same endpoint itself** (`fetchUtilization`, with `?at_wall=1&skip_spend=1` variants; the trigger was not found), so the sessions on the account plausibly share its allowance with agentorc. **The recommendation, for the design round:** stop polling on a timer. The primary source is an agentorc-managed statusline command in each session it launches, set in the adapter's `--settings` layer and chained so a person's own statusline still runs. It writes the `rate_limits` it receives, with a timestamp, to a per-profile file under the home, and the host agent takes the freshest per account and shows its age (TD-230). That is zero extra traffic, fresh whenever any session is active, which is when the gate matters. The endpoint stays only as a fallback on demand: at most once per 15 minutes per account, a fixed hour's cool-off after a 429 and nothing during it. Caveats: an idle account gives a stale reading (TD-230's rule covers it), and the statusline fields need a client version that has them (v2.1.80 and later, per #31637), a window is dropped once its `resets_at` passes, and nothing is there before a session's first API response. The per-token-not-per-account reading of the limit in #30930 and #31637 is community speculation. **Next:** designed; the build is TD-233.
**Location:** `src/agentorc/adapters/claude_code/__init__.py` (`USAGE_URL = https://api.anthropic.com/api/oauth/usage`, the `anthropic-beta: oauth-2025-04-20` header, `usage_for`, `UsageRefused`, `_retry_after`), `src/sessionorc/agent_tick.py` (`_refresh_usage`: one poll per account, `USAGE_EVERY` 300 s, the doubling back-off to `USAGE_BACKOFF_MAX` 3600 s), design §4.2 (*usage*)

**Why:** TD-122 (built 2026-09-23, #517) cut the polls to one per account, because four profiles on one login had been refused. The refusals are back. The agent's log on 2026-09-28 reads *rate_limited (was ok)* at 16:26 MDT and *rate_limited (was no reading yet)* at 21:26 after a restart, with the last good reading at 22:21Z. The endpoint then refused every poll for six hours or more. agentorc asks at most every five minutes, less once backed off. So either the endpoint's allowance is far tighter than that, or something else on the account spends it: every Claude Code client may read the same endpoint for its own `/usage` and status, and on this account a dozen sessions run at once. The endpoint is not a documented API: agentorc reads it as Claude Code does, with the user's OAuth token and a beta header.

**Fix:** (1) **research** (Sonnet, read-only, with sources): whether Anthropic documents a supported way to read a Pro/Max subscription's usage programmatically (and if not, what the supported surfaces are: the Claude Code `/usage` command, the statusline's input JSON if it carries rate-limit fields, response headers such as `anthropic-ratelimit-*` on the model calls a session already makes); the endpoint's limits if stated anywhere; what the Claude Code client polls and how often; whether a `Retry-After` is sent (the agent's log records only the reason's transitions, so this needs the headers logged). (2) Measure here: count this account's calls to the endpoint across the sessions (is it us, or them?) and log the response headers of a refusal. (3) Then choose, in the design round the research makes needed: read usage from a supported surface (e.g. the headers or statusline data the sessions already receive, reported through the hook), poll less and share the reading, or stop polling while any session can report it. Done when the chip holds a reading under an hour old through a busy evening, and the source is one Anthropic supports or tolerates.

**Related:** TD-230 (the age on the chip, the gate on a stale reading), TD-122 (one poll per account), TD-087 (the reason), TD-073 (the reading), design §4.2, §4.2a.

**Resolved:** 2026-10-08 (designed and researched; built as TD-233, archived the same day) — see TD-233: the reading is reported first, and the endpoint is asked only as a fallback.
