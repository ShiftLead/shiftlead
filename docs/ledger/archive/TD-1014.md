**Why:** TD-1009 (ADR 2026-10-25, *Decision* 3): under dev-cadence TD-129 a repo carries a pin, not the files, so no reader can read a path in the checkout.

**Fix:** as §5 says — the resolver calls the launcher from the host agent's own venv (`sys.prefix`, never a login `PATH`), returns argv and env with `CADENCE_REPO_ROOT`; a pin it cannot resolve, or one needing a newer launcher interface, is an unserved lack by name; the readers move onto it one by one, the copy's paths read while a repo still has a lock; `ao host up` copies the pinned trees the node's repos name into `~/.shiftlead/nodes/<name>/cadence/<commit>/` and the container's cache. The exact launcher interface is TD-129's and is read from its build when this is picked. TD-1016's layer listing moves onto the resolver in whichever of the two lands second.

**Fix, the pin era's detections** (the copy's readers keyed on the lock, all moved here):
- `seams.reading`'s `cadence` lack: a repo holds dev-cadence when it has the pin (`docs/cadence.toml`'s `source` and `ref`) or, while it still has one, the lock; words *unserved: no dev-cadence (no pin in docs/cadence.toml, no docs/cadence-sync.lock) — `ao repo add <path> --adopt`*; `ao repo add` reads a pinned repo as adopted.
- `OLDEST` (TD-1012) is checked against the pin's `ref` as against a lock's `files_commit`, by the same ancestry read.
- A console script `dev-cadence` (`[project.scripts]`, a thin entry calling `sessionorc.dev_cadence.main(sys.argv[1:])`) puts the vendored launcher in the venv's `bin`, and the generated node Dockerfile links `/usr/local/bin/dev-cadence` to it beside `/usr/local/bin/ao`, by the same guarded rule (§4.4a, TD-1022), so dev-cadence's SessionStart line and shims find it on `PATH` in a node; a test holds the line as TD-1004's holds `ao`'s.
- TD-1013's release is read from the pinned tree's `ledgerboard.py` through the resolver; a repo with a pin and no copy never warns for the absent file.
