**Why:** Grok Build 1.0.77 reads the person's own Claude Code settings for its permission rules and mode: `~/.claude/settings.json` and `settings.local.json`, a project's `.claude/settings.json` and `settings.local.json` up to the repo root, and in a worktree the main checkout's `settings.local.json` deny and ask rules (its guide, *Permissions and safety* §3; `grok inspect --json` on kmaster lists `/home/kmaster/.claude/settings.json` as its one permissions source, 4 rules). No `compat.claude` key covers permissions (`compat.claude.*` covers agents, hooks, MCPs, rules and skills, and `GROK_CLAUDE_RULES_ENABLED=false` leaves the source in place); whether `auto_mode.enabled`, `default_auto_mode` or `ui.permission_mode` in the profile home's `config.toml` or `requirements.toml` wins over it was untried when this was filed; TD-1835's probes tried each in `config.toml` (none in `requirements.toml`), and none wins (docs/history/TD-1835.md). On kmaster that file sets `defaultMode: "auto"` (and four `git diff`/`git log` allow rules, none covering `cp`). TD-1637's live walk on `grok-conformance` saw no permission prompt: `cp /dev/null conformance-permission.txt` ran unasked, though the launch passed `--permission-mode default` (§4.3 `asking_args`) and the guide says a CLI flag overrides config. The same walk with `HOME` a scratch directory, the binary linked into it, passed all seven steps (2026-11-14, session 63a38041). That run hid the whole of `$HOME`, so `defaultMode` is the likely key (the one permissions source `inspect` lists) but not yet isolated: a walk with a scratch `HOME` holding only `{"permissions": {"defaultMode": "auto"}}` settles it. So every Grok session ShiftLead launches runs under the person's Claude Code permission mode and rules: a seat under `permission_prompts: all` is not asked as §4.2a says, and the person's Claude allow rules widen what a Grok seat runs unasked. §4.3 says nothing of it beyond the note slice 17 added.
