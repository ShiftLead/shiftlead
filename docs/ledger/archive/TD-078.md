**Status:** Resolved — Partly done — **the first sighting is reproduced and fixed** (PR #264, 2026-09-20): the file in a loop under two concurrent full suites failed once in 25 at the migration assertion (`assert 'exited' == 'idle'`), because the test stored a **paneless** record and ran under a one-second `CREATE_GRACE` with 0.3 s ticks — a tick between `start()` and the assertion judged it `exited`, correctly. The grace is now long while the migration is asserted and zero for the half that is about the grace passing, so each line bounds on its own rule; 40 runs under the same load, no failure. **The second sighting below is open** and is the same family, in a different test — 25 runs of `tests/test_agent.py -k send` in a loop under two concurrent full suites did not reproduce it on kmaster (2026-09-20), so it stands on its CI sighting alone. **A third sighting, 2026-09-27 (grinder-ao-1, a local full run on the TD-151 slice 1 branch, which touches no `src/sessionorc`):** `test_send_wait_three_outcomes` failed at `tests/test_agent.py:435` — the case *busy, and the whole queued turn runs between two polls (idle, working, idle back to back): settled, never a false prompt-stalled* — with `prompt-stalled: … showed no activity within 0.6 s`, which is exactly the false stall the case exists to exclude; alone it passes. So the watch ends with a live one, and a fourth followed in CI the same day (PR #670, 3.13, the same line). **Both are fixed (2026-09-27, grinder-ao-1, PR #672): the test's race, not the agent's.** The test gave each send a fixed 0.2 s before firing the hooks that stand in for the tool; under load the paste itself (`_type`, which confirms the prompt left the composer) took longer, so the hooks landed while the prompt was still being typed — before `rpc_send` took its `rev` baseline — and the wait then watched an idle that never moved. Reproduced by slowing `_type` by 0.4 s: the old test fails with the CI's exact `prompt-stalled … within 0.6 s`, and the new one passes. Each send now waits for its own paste (`_typed`: its `sends` entry written and the pane's typing lock free) instead of a sleep. In the real system the tool's hooks follow the typed prompt, so the agent's order holds. **Seen again 2026-10-01 00:46Z (grinder-ao-2):** `tests/test_agent.py::test_send_wait_three_outcomes` hit the suite's timeout on the 3.13 runner of PR #815 (run 36797544062, a change to the page and the CLI only) and passed on the re-run. **Seen again 2026-09-30 (grinder-ao-1):** `tests/test_agent.py::test_send_wait_three_outcomes` hung to the suite's timeout on CI's 3.12 job for PR #831, a diff with no `sessionorc` change (run 36807134632, attempt 1); 3.13 passed beside it and the rerun passed. The next run on 3.12 hung in the same test at the same point — PR #835, a doc-only diff (run 36807992641, attempt 1) — so on CI's 3.12 it is no longer rare: two of two runs within the hour. **Next:** the sightings are fixed; the anchor archives it after a clean week.

**A second one, seen in CI 2026-09-20 on a ledger-only PR (#262, Python 3.13 only; 3.12 passed the same commit):** `tests/test_agent.py::test_send_wait_three_outcomes` — `TmuxError: tmux paste-buffer -p -d -b ao-paste-… -t =ao-test-send-wait-three-outcomes0-w:: no current target`: the send raced the pane (the target session was not there, or not yet, when the paste ran). The job was re-run. Same family as the first: a wait that assumes a pane is up. Both belong to whoever takes this entry.

**What the second one actually was, 2026-09-20 (`tdgrind-ao-1`, PR #286) — the error is what a send to a record that has *exited* looks like.** It is reproduced on demand, in one line: kill a session, wait for `exited`, `send` to it, and the suite prints that exact string, buffer name and all. `send` and `keys` refused a **closed** record and not an exited one, so the paste went to tmux and tmux answered about a target it could not resolve — a tmux error for a question about a record, naming neither the session that had gone nor when. Under a loaded 3.13 runner the record reaching `exited` before the send is the only extra ingredient the CI sighting needed (the first sighting in this entry is the same tick judging a record `exited`, from the other side). **Fixed:** the host agent refuses it in words, with the exit code (`_refuse_gone`, design §4.5a *Focus composer*), and `tests/test_agent.py::test_send_to_an_exited_record_is_refused_in_words` holds it. That does not *prove* the CI run went that way — the runner's log is gone — so the test itself is unchanged and the sighting is not called fixed: what changed is that a repeat now names its cause instead of naming tmux. **If it recurs, the message will say which session exited and with what code.** And if it **hangs** rather than fails — which is what `tdgrind-ao-2` saw on 2026-09-20, 14 minutes of nothing on a branch that touches none of this code — the suite's per-test bound now stops the run with every thread's stack (TD-063, PR #314) instead of leaving a job-level cancel whose last line is the test *before* the one that stopped. Re-check on 2026-09-27; if a week of CI and local full runs is clean, close the entry.

**A third one, and the same shape — 2026-09-20, seen by `tdgrind-ao-2` in a full local run and reported to `tdgrind-ao-1`; fixed in the same PR.** `tests/test_identity.py::test_enforce_against_real_panes` died in the JSON decoder and passed on its own immediately after. The cause is in the test, and it is the family's own: **`_probe` waited for the answer file to *exist*, and the probe's `open(out, "w")` creates it empty.** Every run has that window; load widens it, and the read then parses nothing. The probe now writes `out.part` and `os.replace`s it onto `out` — a rename within one directory is atomic, so the path appears only when the answer is whole and the waiter's signal is the right one again. Nothing in `src/` is involved. It is recorded here rather than in a new entry because the entry *is* this family: a wait bounded on something other than the thing it is waiting for.

**Done when** the failure is reproduced (run the file in a loop under load — the full suite beside it) and its wait or ordering assumption is fixed, or a week of CI and local full runs passes without it and the entry is closed as not reproduced.
