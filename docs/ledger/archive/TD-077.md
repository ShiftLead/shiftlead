**Location:** `src/agentorc/cli.py` (`caller=os.environ.get("AGENTORC_SESSION")`), `src/sessionorc/client.py` (`req["caller"]`), `src/sessionorc/mail.py` (`is_person`: *the field absent from the envelope is the only thing that reads as a person*), `src/sessionorc/agent.py` (the socket, mode `0600`; every gate that reads `caller`)

**Why:** it does not. **Across hosts** identity is sound: §4.4a takes a request's host *from the channel it arrived on, never from a field*, and a link is bound to its key. **On one host** the caller is whatever the client puts in the envelope — the CLI copies `AGENTORC_SESSION` from its environment — and the socket, mode `0600`, accepts raw JSON from any process running as the same user, which every session on the host is. So a session can send as **another session** (`AGENTORC_SESSION=<id> ao msg …`) and as **the person** by sending no caller at all (`env -u AGENTORC_SESSION ao msg …`, or the person-only RPCs — `inbox_delete`, and from TD-069 `inbox_snooze` and `inbox_pause` — called directly). `mail.py` already says so in a comment (*the socket takes raw JSON from any local process*), and §4.8 says it of the control gate (*a guard against a confused worker, not a security boundary*); until §4.8a nothing said it of mail's marks or of the person, or what to do about it. The gates were built against **mistakes** — a worker acting on a session it does not control — and they hold against those. They do not hold against a model that decides to lie, and **the `[person]` mark is the most valuable thing to forge**: instructions come from controllers and people (§4.10), and TD-075 puts a cheap model beside a high-trust one that weighs mail by exactly that mark.

**What bounds it today:** anything that can reach the socket already runs as the person's user — it can type into any pane with `tmux send-keys`, edit `~/.agentorc`, or delete the checkout — so this is not a new privilege so much as a quiet, deniable one: forged mail looks legitimate in the record, where `send-keys` does not.

**Options, cheapest first (the anchor recommends 1 and 2 together now, 3 as the real boundary):**
1. **A per-session secret.** The host agent mints a token at launch, puts it in the session's environment beside `AGENTORC_SESSION`, and refuses a `caller` that does not present its own. The person's requests present one the UI and a person's shell hold (a `0600` file). A same-user process can still read another's environment or that file, so this stops the accidental and the casual, not the determined — but it turns *absent caller = person* from a default into a claim that must be backed.
2. **Identity from the channel, as §4.4a already does between hosts.** `SO_PEERCRED` gives the peer's pid; its ancestry names the tmux pane it runs under, and so the session. A `caller` that disagrees with the channel is **refused and shown** — a mark on the card, a line in the person's Inbox — since a mismatch is never innocent. Escapable (a double fork, `tmux run-shell`), so *no ancestry* must read as **unknown**, never as the person.
3. **A real boundary is an OS one.** A session in a container node (TD-057) can reach the home only through its link, so it can only ever be a session of that node; an untrusted model belongs there, with one node per trust level. Tokens and ancestry inside one user account are tamper-evidence, not isolation.

**What option 3 still needs (2026-09-19). This is designed, reviewed and tested behaviour, not an oversight** — `modes.py` says *a person may still message anyone*, and `tests/test_link.py::test_a_persons_forwarded_act_reaches_only_the_nodes_own_records` asserts that a caller-less `msg` from a node reaches a home session and that the person inbox is the person's *from anywhere* (security read of #217, review of #219). It is right for a real person at a node. What it rests on is the thing TD-077 is about: **nothing on a node's socket tells the person from a session that leaves its `caller` out** — so the reach that was given to the person is given to every session on that node. A container node bounds *which session* a caller can be — the home qualifies it with the link's host — but **not whether it is the person**: a request forwarded from a node with no `caller` is dispatched at the home as the person (`_forwarded`, `agent.py`). The bound that exists, *a person at a node acts only on that node's records*, covers the RPCs that name an `id` (`PERSON_NODE_BOUND`); **`msg` is not among them and names no `id`**, so `env -u AGENTORC_SESSION ao msg <a home session> "…"` from inside a container would land in that session's inbox marked `[person]`. `inbox` and `inbox_delete` on the person inbox pass the same way, so a container session could read and delete the person's mail — and, once TD-069 step 0 lands, snooze, pause and *Go with it*. So the design round for option 3 has to add: **(a) a node may be declared to carry no person** — an agents-only container — and the home then **refuses every caller-less request from its link**, reads of that node's own records aside; **(b)** on a node that does carry a person, a caller-less `msg` is refused unless every addressee is on that node, and the person inbox is not reachable; **(c) one node per trust level**, since sessions inside one node can still claim each other's ids; **(d)** where the high-trust sessions and the person live — the home, which then runs no untrusted session at all. TD-057 (container nodes) is another session's work in flight: this is design for that round, not a patch to make beside it.

**The choices, restated (2026-09-19, after the finding above).** What each defends depends on one fact: every session on a host runs as the person's own user, so a *determined* rogue needs no forged mail — it can type into any pane with `tmux send-keys`, which a session reads as its person speaking, and it can call the UI's own API on localhost. Inside one account, identity checks are **tamper-evidence**, not a wall.
- **A. Accept and document.** Write the threat model into the design: the gates stop mistakes, not lies. No work; leaves forged mail looking legitimate in the record.
- **B. Identity from the channel on one host.** Peer credentials give the connecting pid; its ancestry names the tmux pane, so the session. A `caller` that disagrees is refused **and shown** (the card, the Inbox); a caller-less request is the person only from the UI's process or from a process under no agentorc pane, and *unknown* is never the person. Stops the accidental and the casual — an agent talked into `env -u AGENTORC_SESSION` by something it read — and makes a forgery visible. Does not stop `send-keys`. Small, and needs nothing from TD-057.
- **C. A per-session secret.** Weaker than B (a same-user process can read it) and redundant beside it. Not recommended.
- **D. A secret only the person holds** (a passphrase behind person-only acts). Closes forged *mail* from the person, and is walked around by `send-keys` into the pane. Not recommended on its own.
- **E. An OS boundary.** Untrusted sessions in agents-only container nodes, one per trust level, **declared to carry no person** so the home refuses every caller-less request from that link; the person and the high-trust sessions on the home, which then runs nothing untrusted. The only choice that stops a determined rogue — forged mail, `send-keys` and the UI's API alike, since none is reachable from inside the container. Depends on TD-057, plus the no-person rule above.
**The anchor's recommendation:** **B now** — cheap, and it turns a silent forgery into a visible one — and **E as the condition for TD-075's trial**: a cheap, less-trusted model is not put beside the tech lead on the same account. A is what is true until then, and the design should say so either way.
