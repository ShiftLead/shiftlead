**Location:** src/sessionorc/ (the repo reading: per-entry synopsis, worktrees beside prs.open; held path, its PR waits for its reader); src/shiftlead/ui/common.py, queue.py, inbox.py, repo.py; src/shiftlead/ui/templates/inbox_row.html, queue_row.html, queue_card.html, repo_part.html; design §4.5 screen 6 A design links its synopsis, §4.5a Queue card: what needs the person, Queue page: card

**Why:** TD-1527's design (§4.5 screen 6 *A design links its synopsis*; §4.5a *Queue card: what needs the person* and *Queue page: card*): the person judges a design from its plain-words synopsis, `docs/synopses/TD-<design>.md`, and the Queue card and the Inbox must link it — through the person's editor link, with GitHub beside it for the phone.

**Fix:** Build §4.5 screen 6 *A design links its synopsis* and the two §4.5a sentences, on top of TD-1531's design-PR link. TD-1531's item carries only `design_pr`, a number; this build extends that same resolution so the item also carries the entry it resolved to (`<repo>#TD-n`, the item's entry or its one-hop `Part of` parent) and the source of the link (the open design PR's `prs.open` row, with its `branch` and `head`, or the `Design PR:` section), and adds the entry's own Queue line's lookup, by its own id alone, which TD-1531 does not do:
- **One resolution, in one place.** TD-1526's rule for an entry's own design link (its own section's last, else its own open *TD-n design: …* PR, one above the section's last winning, the lowest of two) is one function in `src/sessionorc/` that TD-1531's item side and this build's reading both call — this build moves TD-1531's into it if TD-1531 wrote it inline — so the reading answers per entry `{design_pr, source, synopsis}` and the item side takes the number and the synopsis from the same answer, never two implementations.
- **The reading answers per entry** (the held-path half, `src/sessionorc/`): the items are found on the page's side (`item_home`, `card_wants`, `_cut_item` in `src/shiftlead/ui/queue.py`), which the reading never sees, so the reading answers for every open or archived entry that carries a design link by its own id (its own `Design PR:` section, or its own open design PR by TD-1526's title rule) and carries the answer on that entry as `synopsis: {sha, exists, editor_path, branch}` (`editor_path` the file on the host's disk or None; `branch` the PR's or the default). The Queue, the Inbox (through TD-1531's map of open and archived entries) and the Repo page's board (its rows drawn by `src/shiftlead/ui/templates/repo_part.html`, which imports `queue_row.html`'s `row`; the code that hands each board row its entry carries `synopsis` there) all read this one per-entry `synopsis`. The UI side reads the `synopsis` of the entry the item's design link resolved to (the parent's where it took the parent's), the entry's own line its own; nothing about a synopsis asks git or the disk at render time.
- **Existence and copy.** For each such entry, the synopsis path is `docs/synopses/TD-<design>.md` in that entry's repo. Its ref is the open design PR's `head` where the link came from the open PR, else `origin/<default>`; it is drawn only where the file is in `git ls-tree --name-only <sha> docs/synopses/`, run in the repo's checkout on the repos registry's host, `origin/<default>` resolved to its commit first (the tick keeps the default branch's name), the answer cached per (commit sha, path) so a commit is asked once, one ls-tree per repo and commit answering every entry (never one process per entry). The ask runs in the repo reading in the host agent (`src/sessionorc/`), beside `prs.open`, never in a page request; the reading carries the answers. A head not in the checkout's objects reads as absent; a fork's PR (its row's `fork`) is never asked and draws none.
- **The editor target.** Before the merge: the worktree whose branch is the PR's `branch`, from `git worktree list --porcelain` in the repo's checkout, read once per repo reading beside `prs.open` (in the repo reading, `src/sessionorc/`, a held path), and the file on that worktree's disk; after it, the file in the repo's main checkout, on disk. The link is `editor_file_link(path)` (`src/shiftlead/ui/common.py`), drawn by the `file_link` macro, so its folder first is `checkout_of`'s — never a hand-built `vscode://` URL. No editor link under `open_in: none`, an `open_in` template with no `{path}` (`editor_file_link` answers None), or where the file is not on that disk. A worktree outside the main checkout's path is in no registry checkout, so its file is one launch.
- **The GitHub link.** `<base>/blob/<branch>/docs/synopses/TD-<design>.md`, `<base>` from `review.repo_web` on the entry's repo's root (the base `review.pr_url` builds on; GitHub's alone, so a repo on another forge draws no *GitHub* word), `<branch>` the PR's `branch` before the merge and the default branch after, percent-encoded with its `/` kept. A worktree outside the main checkout keeps both words (*synopsis* a one-launch editor link). With no editor link, *synopsis* itself carries this URL and no *GitHub* word is drawn; with no base and no editor link, nothing is drawn.
- **Drawing.** An item about a design (mail by `about`, board line by `Context:`, a `decision (…)` entry's own held row) ends its first line ` · design #n · synopsis · GitHub` on its Queue card and its Inbox row (`inbox_row.html`'s `head`, `board` and `ledger` macros; `queue_row.html` / `queue_card.html`), wherever it resolves a design entry — an item whose own `pr` is the design's last number (an `ask --pr`) drops the repeated `· design #n` but still draws `· synopsis · GitHub` after its own `#n`. Hover words (`file_link`'s `title`): *the design's synopsis, in your editor* and *the synopsis on GitHub* (*the design's synopsis, on GitHub* where *synopsis* links GitHub). A design entry's own line on the Queue — the card header's title where it is the top entry, its row under another — ends its title with `synopsis · GitHub` — and so does its row on the Repo page's board, drawn by the same macro — by its own id alone (its own section or open design PR, never its parent's), so a build's row draws none.
- **Tests:** a steer about TD-n whose section reads `#12`, with the file on `origin/<default>`, draws `· design #12 · synopsis · GitHub` on its card and Inbox row, *synopsis* a `data-file-link`; with the file absent from origin it draws `· design #12` alone; with an open *TD-n design: …* PR whose head holds the file and a worktree on its branch, *synopsis* opens the worktree's file and *GitHub* the PR branch's blob; with no worktree on that branch *synopsis* links GitHub and no *GitHub* word is drawn; under `open_in: none` the same; an item about a round entry `Part of` TD-n draws TD-n's synopsis; a build's row under a design draws none; the design entry's own card header draws `synopsis · GitHub`; the ls-tree is run once per (repo, sha) across two reads; the §4.6 file-link template test's set of file-link controls gains *synopsis*, so it must be drawn by `file_link`; an `ask --pr 12` about TD-n draws `#12 · synopsis · GitHub` and no `· design #12`; the Repo page's row of a design draws the words.

**Done when:** An item about a design whose synopsis file exists at the design link's ref draws `· synopsis` (the person's editor file link) and `· GitHub` (the forge blob) after `· design #n` on its Queue card and Inbox row, and the design entry's own Queue line ends its title with them; *synopsis* links GitHub where there is no editor link; the tests pass.
