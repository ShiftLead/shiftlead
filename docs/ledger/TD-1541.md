**Location:** src/sessionorc/queue.py (mail_repo, asker_repos, card_index's bare kept:/open/design: keys, kept_or_loose); src/sessionorc/agent_mail.py (_record_repo); design §4.5 screen 6 *A mail item's bare ref is its sender's repo's*, *Every item that needs the person draws on a card*; §4.10

**Why:** An item from another repo's session draws on an unrelated ShiftLead Queue card, so the person reads a contractmatch question as if it were about a finished ShiftLead entry, and does not see it on the open contractmatch card where it belongs. Reported by Paul through his session `ao-led-tds-ledger` (m-f78f8c6cc3c6), seen live since TD-1467 and TD-1468 shipped (2026-11-07 16:46Z).

Seen: ShiftLead's completed card `shiftlead#TD-064` (*Claude Code's peer messages…*, done #431) is kept in Recently completed with a Decide item. That item is contractmatch's ask m-60befff817b5 from grinder-cm-1 (team cm-grind, PR #214, `about: TD-064`, 11 days old), which is about `contractmatch#TD-064`, open on an open contractmatch card. Three more asks have the same shape and are likely misdrawn too: m-6b4af9902052 (about TD-063, from techlead-cm-1, whose record is gone), m-7d6cb34c756d and m-782632ab3229 (about TD-062).

How it happens: none of the four carries a `repo` stamp, since all were sent before TD-1467. Their senders are records on the contractmatch container node (`…@contractmatch`). `mail_repo`'s last step, the sender's record's repo, finds nothing this home can name: the record is gone (techlead-cm-1's), carries no `repo`, or holds a root on the node that this home's roots don't map and whose last path component (`asker_repos`' fallback) is not a name this home reads (a wrong name would draw a loose card, not this one). Which of these held is not established. So the bare `TD-064` stays bare, and `kept_or_loose` matches the bare `kept:TD-064` key, which `card_index` writes because only ShiftLead's completed cards hold that id. The send-side stamp already names a node's record against that node's own registry (`_record_repo`, TD-1467); the read side does not.

Design §4.5 screen 6 *A mail item's bare ref is its sender's repo's* says a ref stays bare only where the helper finds none, "as now", so the misdraw follows the design as written: the design must say what a bare ref with no known repo may match.

**Fix:** A design round on two questions, then a build:
1. **Name a node record's root against its own node.** The read side (`asker_repos`, `mail_repo` in `src/sessionorc/queue.py`) names an unstamped item's sender record by its node's registry, as the send-side stamp does (`_record_repo` in `src/sessionorc/agent_mail.py`, `test_a_nodes_record_is_named_against_its_own_hosts_registry`). The reading is synchronous and `_record_repo` asks the node, so the round settles where the name comes from: a roster the home keeps per node, or the record's own stamped repo name.
2. **What a bare ref with no known repo may match.** Either it never resolves through the bare `kept:` key (or the bare open-card and `design:` keys); or it never picks a card in a repo other than the one the sender's team serves (team cm-grind serves contractmatch); or, with neither known, it stays in the Inbox, which was the right fallback here. The round picks one and writes it in §4.5 screen 6.
Also: a one-time look at the open person-inbox items with no `repo`, to see how many draw on a card in a repo not their sender's. The four asks themselves are Paul's to close or answer; this entry is only about where they draw.

**Done when:** Tests: an ask with no `repo`, from a record on a node whose root this home's roots don't hold, `about: TD-064`, where only another repo's completed card holds TD-064, draws on the card of its sender's repo's TD-064 (open, kept or loose as that entry is), or in the Inbox where no repo is known, never on the other repo's card; the same for an open card's bare key; a stamped item is unchanged. Live: m-60befff817b5 no longer draws on `shiftlead#TD-064`.
