## TD-1719: Gemini CLI: a failed tool call's fixture, so its transcript entries carry error and marks_errors is True (TD-1491)

**Added:** 2026-11-11
**Owner:** grinder
**Kind:** build
**Status:** Open

**Blocked by:** TD-1716, decision (paul)
**Part of:** TD-1491

**Why:** §4.3 (TD-1491) gives a tool transcript entry an `error` flag, which `/shiftlead-feedback`'s digest uses to show a seat's failed calls. Gemini CLI's adapter cannot set it yet: no fixture or code shows how a failed call's record marks its status. Its fixtures hold only `"status":"success"`. Until it can, a Gemini seat's failed calls fold into the digest's call counts, and the index marks the seat `marks_errors: false`.

**Location:** design §4.3 read_transcript's error, marks_errors; src/shiftlead/adapters/gemini/transcript.py; tests/conformance/fixtures/gemini/transcripts/

**Ask:** Held with its design TD-1491 until Paul answers its end-of-rounds item (Go, One more round or Hold) on docs/user_attention.md.

**Fix:** Capture a Gemini CLI chat in which a tool call fails (a shell command that exits non-zero, and a refused tool call if the tool records one differently) as a conformance fixture under `tests/conformance/fixtures/gemini/transcripts/`, scrubbed as the others are. Read the failed call's status word from it, set `error` in the Gemini adapter's `read_transcript` from that word, and set the adapter's `marks_errors` True (§4.3). Capturing the chat runs Gemini CLI once on a scratch directory; it reads nothing of the person's.

**Done when:** The fixture is committed, and a test reads a failed call's entry as `error: True` and a successful one as False. The Gemini adapter's `marks_errors` is True, and §4.3's note on Gemini's `error` says how it is read rather than that it is not.
