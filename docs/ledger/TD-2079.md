## TD-2079: Find out whether A2UI would save tokens or improve ShiftLead's workflows

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-22 (Paul, through Add entry; drafted by the a2ui session)
**Owner:** designer
**Kind:** evaluation
**Status:** Open
**Id take:** ea08d101b54b4f72b1f378167b3dfcce

**Why:** A2UI (https://a2ui.org/, Apache 2.0, v1.0, its spec last updated June 2026) is a protocol that lets an agent describe a screen from a catalog of components, for a client to draw natively. It is said to use fewer tokens, and token spend is what limits how much work ShiftLead's sessions get done, so the claim is worth testing before anyone builds on it or dismisses it.

The claim is narrower than it sounds. The published saving (median input tokens 10,980 to 6,000, output 811 to 299 with thinking switched off, and 2,320 to 1,789 with it on; 54 samples, one Gemini model) is the project's own benchmark, and it compares A2UI's compact format with A2UI's own JSON. It says nothing about A2UI against what ShiftLead does now: its pages are drawn by the server from records, and an agent reaches the person with a sentence and labelled answers (an ask or a steer), a board line, a PR or report, or the tool's own permission dialog, which may cost fewer tokens than any generated screen. A saving would have to come from something ShiftLead's agents actually write today, and that has not been measured. The value may lie elsewhere, in richer answers on a Queue card or a Focus page, at the price of a client-side renderer and a new way for agent output to reach the person's browser.

**Location:** `docs/design/4.5-ui.md`, `docs/design/4.10-messages.md`, `docs/design/4.3-adapter-contract.md`, `src/shiftlead/ui/` (`queue.py`, `inbox.py`, `templates/`), `src/sessionorc/agent_mail.py`, `docs/decisions/2026-11-12-design-cost-model.md`

**Fix:** An evaluation, with no product change. Write a decision record under `docs/decisions/` that:

1. Measures, from real session transcripts, how many tokens ShiftLead's agents spend on output a person reads as UI (asks, steers, board lines, reports, mockups), beside total spend, so the largest possible saving is a number.
2. Reads the A2UI spec, its benchmark and its Python and web SDKs at first hand, and reruns a small sample on the Claude models the seats use if the measured share justifies it.
3. Names the workflows it could help, if any, and for each compares A2UI with the present server-drawn form on tokens, latency, what a person gains, and the work to build and keep it. It covers the security of drawing agent-authored UI in the person's browser, and whether it fits the adapter rule (design §4.3) and interactive sessions in tmux.
4. Ends in a recommendation: adopt for named workflows, run a bounded trial, or leave it. Any build is filed as its own entries.

**Done when:** The decision record is merged and linked from AGENTS.md's documentation map, it gives the measured share of tokens A2UI could affect, and it ends in one recommendation the person can accept or refuse.
