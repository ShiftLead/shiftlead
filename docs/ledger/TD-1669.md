## TD-1669: Put a member's brief in the system prompt at each fresh launch, the typed prompt saying so

**Priority:** medium
**Type:** feature
**Added:** 2026-11-11
**Owner:** grinder
**Kind:** live-check #3639
**Status:** Open
**Id take:** 29c5e62456e848f49a00e472ceb5c350
**Blocked by:** event (live)
**Part of:** TD-1551

**Why:** TD-1551's trial (design §4.3 *What a start reads from the prompt cache*): a start reads from the cache the tool definitions and the whole system prompt, the preface at its tail, and nothing after it. A member's brief is the same text for every member of one line whose definitions give the same lane and brief, and reaches the session in the typed first prompt, so every member start writes it fresh: a grinder's is about eight thousand tokens. In the context file, after the preface, it is read by every later member start of the same line, account and model within the hour. Split out of TD-1664 after review round 8 (Paul, 2026-11-11): the move touches every path a brief travels (create, replay, relaunch, resume, the typed line, Focus), and rounds 5–8 kept finding another one (F103–F142), while the capture script and the Add entry template stood.

**Fix:** Design §4.3 *The shared text goes in the system prompt, the per-start text after it*.

1. **A member's brief in the context file.** A member's brief, as composed with every slot filled and the Project `block` prefix, is the same text for every member of one line whose definition gives the same lane and brief (`{lane}` is a member's own `lane:` where set, `teams.py`; `{repo}` its own `brief:` supplement; `told` is per role; `{techlead}`, `{manager}`, `{flow}` and `{stage}` are per team; `{entry}` is filled per reader, step 3; only a seat's `{context}` is its own). Members of a scaled line share it; a member with its own lane or brief does not, and pays the system prompt's own text past Claude Code's opening line once more, roughly 2,200 to 3,000 tokens in the trial (§4.3).
   - **One place makes the move, and nothing it makes is stored.** The home's `rpc_create`, for a fresh create (never a resume, below) it launches itself (not one routed to a node, whose `create` has `prompt_from` stripped, `agent_remote.py`, and whose version may not know the move: a node member keeps its pasted brief), when the create carries a role's brief (`prompt_from` given), no `start_context`, no `argv` (`if argv: spec.argv = argv` replaces the adapter's argv, the flag with it), and an adapter declaring `start_context_system` (below). Every brief-composing path reaches it unchanged: a team launch (`teams.py`), `ao new --role` (`cli.py`), New session's preset (`ui/app.py`) and the tick's replay. The move works on copies, before the prompt's `ARG_LIMIT` check: the moved prompt and context are new locals handed to `ad.launch` only, and `prompt`, `start_context` and `prompt_from` are never rebound, since `launch_params(locals())`, `_schedule(locals(), …)` and `Session(start_context=…)` read them. It splits a trailing `\n\n{FILLED_FOR}` line off the prompt, hands the adapter's `launch` the brief (the Project block with it) as its start context, and makes the first prompt the moved-brief line (next item) with the `FILLED_FOR` line after it. The session record's `start_context` and the launch record (`LAUNCH_KEYS`, written by `launch_params`) keep the caller's own values, the pre-move `prompt` and `prompt_from` and no `start_context`, so every replay, relaunch and brief change (`_refill_prompt`, `RELAUNCH_KEYS`, `brief_changed`), each a fresh create, re-derives the move from them, never a stored copy, and the record's view and a node record's copy at the home are as today. The context file keeps a size bound, worded as one. Test the launch record's and the scheduled record's contents after a moved start, a moved start replayed after a brief change, a stored-prompt replay, a seat fill and a lost-brief replay.
   - **A resume keeps the conversation's context file.** A resume carries no `prompt_from` (a one-press Resume sends none, `ui/app.py`), so a resume never moves. Today `rpc_create` hands a resume `start_context_file_text(None)`, the preface alone, and the adapter writes it with `O_TRUNC`, which would wipe a moved brief. So in `rpc_create`: `keep = resume and start_context is None and ad.start_context_system and the conversation's context file exists` (`paths.context_file`, read through `asyncio.to_thread`); when `keep`, `ad.launch` is passed a new keyword `keep_context=True` and no text, and Claude Code's `launch` adds `--append-system-prompt-file` with the existing file and skips `write_context_file`. Only adapters declaring `start_context_system` take the keyword. A shared conversation is one file keyed by its id, and `_drop_context` runs only on Forget or a replacement by another conversation, so a same-conversation resume finds it.
   - **The launch record survives a resume.** A supervised resume writes the launch record wholesale from its own arguments (`_write_launch(s.id, s, launch_params(locals()))`), which have no `prompt`, `prompt_from` or `start_context`. On a resume, carry those three from the existing launch record (at `self._address(holder)`, or the newest record holding `resume` when the name differs) into `launch_params`, so a later replay still has its brief.
   - **A file gone.** Where a moved conversation's file is missing at a resume (a wiped launch dir, a reap), re-derive the move from the carried launch record: compose the brief from its `prompt`/`prompt_from` and write preface and brief, never the preface alone; where there is no launch record either, write the preface and log it (a `restarts` note naming the conversation). The resume's typed prompt is its own, never the moved line.
   - Say in §4.3 that a kept file keeps the preface it was written with, after `BRIEF_PREFACE` is reworded, and that a conversation started before the move keeps its pasted brief. Compaction needs nothing: the file is passed on every launch. Test: a moved start resumed twice (file bytes unchanged, typed prompt the resume's own, launch record's prompt kept), a resume with the file missing (brief re-derived), a resume with neither (preface, a note), a moved start with an `argv` (no move).
   - **Focus still shows what a member was told.** Focus calls `get`, and `rpc_get` is `_view(…, bookkeeping=True)`; the read goes there, with no new RPC method. In `rpc_get` only, where the adapter declares `start_context_system`, the record's `adapter_id` is set and its `start_context` is empty, read the conversation's context file through `asyncio.to_thread` under `suppress(OSError, ValueError)` (`paths.context_file` raises `ValueError` on an odd id), take the text after its first blank line (the preface holds none), and set it as `start_context` in the reply's copy only, never saved. Nothing after the preface means no row. `cards.py` computes `start_lines` from it as today; the list and stream views carry none, so check a live Focus refresh keeps the row from the `get`.
   - **The typed line.** `agent_wake` types `mail.BRIEF_LINE` as the lead of every first prompt, as literal keys, and pastes the rest; a card's Start session, `ao new --prompt`, a Gemini member, a node member and a Project-block-only start still paste theirs. So both lines stay live: `BRIEF_LINE` where a brief is pasted, a new `BRIEF_MOVED_LINE` (*My brief for this session is in your system prompt, after shiftlead's preface; act on it.*) where it moved. The waker tells them apart by `first_prompt.startswith(BRIEF_MOVED_LINE)`: then it types `BRIEF_MOVED_LINE` as the lead, the way it types `BRIEF_LINE`, and pastes only the remainder (a seat fill's `FILLED_FOR` line), skipping the paste when there is none; `_lead_typed` and `lead_in` apply to the moved line as to `BRIEF_LINE`, and the `(the brief)` send entry is still written. `mail.BRIEF_LINES` holds both, and every `startswith(mail.BRIEF_LINE)` reader (`agent_tick.py`'s `take_brief` and inbox read) becomes `startswith(mail.BRIEF_LINES)`.
   - **Add entry is not a moved brief**: it carries `start_context` and no `prompt_from` (TD-1664), so the move never applies. A create carrying both is left as given, its brief pasted, with a test.
   - **The adapter attribute** `start_context_system: bool` (default false), declared true by Claude Code's adapter: its start context is its tool's system prompt. Document it in `src/sessionorc/adapters.py`'s comment block and §4.3's contract block; the conformance suite asserts it implies `start_context`. Gemini CLI's start context is hook `additionalContext`, so it stays false and its briefs stay typed until its cache capture shows where its cache reads.
   - **The preface and the docs.** Reword `BRIEF_PREFACE` once: the brief after it, when there is one, is the person's instruction placed by shiftlead, as a typed brief is; the doorbell sentence stays. Note in §4.1 that a repo's `brief:` supplement and stage brief now sit in the system prompt. Reword every design and brief line that says a role's brief is pasted (`grep -rn "pasted\|first prompt" docs/design src/shiftlead/briefs`).
2. **A test** in `tests/test_start_context.py`: two members of one line with different names write context files of the same text (any paths), and two with different `lane:` do not; with the tests each bullet above names.
3. **The after measure.** Once promoted, run TD-1664's capture (`scripts/cache_capture.py`) on two grinder starts of one line, launched as members are, within the hour and of one commit, plus one subagent call in a grinder start (if a subagent's request carries the brief, stop and report it), and record the second start's first-request read in `docs/history/TD-1669.md` under `## §4.3` (the first start's write at the one-hour price is the pair's one-off), and reword §4.3's paragraph with it.

**Done when:** A member's start on an adapter whose start context is its system prompt, launched by the home itself, carries its brief in the context file and types the moved-brief line, the record and launch record keeping the caller's own values; a resume keeps the conversation's context file; Focus shows the brief; with the tests the Fix names. The after measure is in `docs/history/TD-1669.md` and §4.3.
