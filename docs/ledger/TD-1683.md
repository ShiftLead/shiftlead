## TD-1683: test: the stale-reserve row's Save-clears is pinned by substrings of app.js, never run

**Why:** **Why:** #3481 (TD-1680) changes what the Settings page's usage card does for a reserve on a window the account stopped reporting: `settings.html` draws a `setstale` row with no field, `app.js` sends that row as a clear (`"forms.usage"`), and the Save button stays enabled for a clean card holding one (`settle`). Its test, `test_a_reserve_on_a_window_the_reading_lacks_is_a_not_reported_row_the_save_clears` (tests/test_ui_settings.py), pins the two JS lines and the template by substring: `assert '$$(".setstale", f).map((r) => [r.dataset.label, ""])' in js` and `assert 'save.disabled = !dirty && !$(".setstale", f);' in js`. Its docstring says "the card's Save sends it as a clear", but nothing runs the JS: a rewrite that keeps the strings in a comment, or a change to the surrounding code (a `$$` that matches no row, a `dataset.label` the template stopped writing, a form builder that is no longer the one `usage` dispatches to) passes while the button does nothing. The server half is covered separately (`set_settings` with `None`, and `/api/settings/usage` with `""`), but nothing joins the row to the POST body.

**Fix:** Drive the card for real: the repo already drives pages in Playwright for screenshots (memory: headless-screenshots-on-kmaster), so a test marked for it (or the smoke's browser half) loads a Settings page whose fake agent reports `week` only with `5h` reserved, asserts Save is enabled on the untouched card, presses it, and asserts the POST to `/api/settings/usage` carries `{"5h": ""}` beside `week`. If a browser test is out of reach for the unit suite, extract the `usage` form builder into a function the test can call under node and assert its output instead of grepping its text.

**Done when:** A test runs the card's Save on a stale row and sees the clear in the request; deleting the `.setstale` mapping from `forms.usage` fails it.
