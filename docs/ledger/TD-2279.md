## TD-2279: A login's name is refused where another tool's login on the host already has it

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-26
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** 933817e93e2e40469b32ff9df98fda81
**Part of:** TD-2232

**Why:** TD-2232's design (§4.2b *Names are fixed*, §4.9e *A record's `profile`*): a login's name is unique on its host across every tool, a forgotten login's among them, so a stored record's `profile`, the login's bare name, goes on resolving to its login and account. Today `logins.name_taken` (`src/sessionorc/logins.py`) checks only the same tool, so `ao login add gemini --name grind` beside `claude-code:grind` is allowed; `profile_name` then reads both under their keys and every record written as `grind` resolves to no profile (TD-2232's probe at a5f15d01c: `get(grind) -> unknown profile 'grind'`), and `_account_key` (`src/sessionorc/agent_spend.py`) falls back to a key no reserve is kept under.

**Location:** src/sessionorc/logins.py, src/shiftlead/switchover.py; design §4.2b Names are fixed, §4.9e A record's profile

**Fix:** 1. `logins.name_taken` refuses a name any other login on the host has, of any tool, live (`data["logins"]`) or forgotten (`data["forgotten"]`) — the same tool's forgotten name stays `add_login`'s own refusal and take-back, as today — with the words §4.9e gives: *`<name>` is `<tool>:<name>`'s name on this host: a login's name is unique on its host*. Its docstring names §4.2b *Names are fixed* and TD-2232.
2. `add_login`'s suggested name (`suggest(suggested, taken)`, `src/sessionorc/logins.py`) takes as `taken` every bare name on the host, live and forgotten, of every tool, not its own tool's alone.
3. The switch-over's `_name_blockers` (`src/shiftlead/switchover.py`) blocks two logins of one host with one name whatever their tools (today it folds by `naming.tools_id(tool, name)`, one tool's alone), its cure *give one of them another name in the answers file* as today.
4. `logins.profile_name` and `profiles._from_logins` keep the key form for a file edited by hand to hold one name under two tools; their docstrings say that nothing shiftlead writes makes one (§4.9e).
5. Tests: in `tests/` beside `logins.py`'s own, a scratch `logins.yml` holding `claude-code:grind` (account `claude-code:acct-1`): adding `gemini:grind` is refused with the words of item 1 and the file is unchanged; adding a forgotten `gemini:old`'s name `old` as a `claude-code` login is refused; a suggested name skips another tool's; a record written as `grind` still reads `profiles.get("grind")` and its account `claude-code:acct-1` after a `gemini:reader` login is added. In the switch-over's tests, an answers file naming `claude-code:~/.claude` and `gemini:~/.gemini` both `paul` is a blocker.

**Done when:** No path shiftlead writes (`ao login add`, its suggested name, the switch-over's answers) gives two logins of one host one name, and a record written under a login's bare name still resolves to that login's account after another tool's login is added, with item 5's tests passing.
