## TD-2279: A login's name is refused where another tool's login on the host already has it

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-26
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** 933817e93e2e40469b32ff9df98fda81
**Part of:** TD-2232

**Why:** TD-2232's design (§4.2b *Names are fixed*, §4.9e *A record's `profile`*): a login's name is unique on its host across every tool, a forgotten login's among them, so a stored record's `profile`, the login's bare name, goes on resolving to its login and account while the login is live, and to no other login once it is forgotten. Today `logins.name_taken` (`src/sessionorc/logins.py`) checks only the same tool, so `ao login add gemini --name grind` beside `claude-code:grind` is allowed; `profile_name` then reads both under their keys and every record written as `grind` resolves to no profile (TD-2232's probe at a5f15d01c: `get(grind) -> unknown profile 'grind'`), and `_account_key` (`src/sessionorc/agent_spend.py`) falls back to a key no reserve is kept under.

**Location:** src/sessionorc/logins.py, src/shiftlead/profiles.py, src/shiftlead/switchover.py; design §4.2b Names are fixed, §4.9e A record's profile

**Fix:** The refusals' and blockers' words are §4.9e *A record's `profile`*'s; this entry points there.
1. A new helper in `src/sessionorc/logins.py`, `name_holder(data, tool, name, skip=None)`, gives the key of another tool's login on the host that has the bare name `name`, live (`data["logins"]`) first and then forgotten (`data["forgotten"]`), skipping `skip`, with whether it is forgotten; TD-2070's `ao host up` reuses it. `name_taken` checks, in this order: the same key live (today's *`<lk>` is a login on this host already*, kept), `name_holder` (§4.9e's live or forgotten words), then today's tools-shell fold (`naming.tools_id`). `add_login` passes the key it adds as `skip`, so a take-back (`back`) still passes; the same tool's forgotten name stays `add_login`'s own refusal with today's words. A take-back whose name another tool's login holds, live or forgotten (a hand-edited file only), is refused with the matching words. `name_taken`'s docstring, `add_login`'s (today *a forgotten login's name is refused any other folder*) and the module docstring (line 6, today *a name is unique per tool on a host*) say a name is unique on its host across every tool, citing §4.2b *Terms used below*, **Names are fixed**, and TD-2232.
2. `add_login`'s suggested name (`suggest(suggested, taken)`) takes as `taken` every bare name on the host, live and forgotten, of every tool, not its own tool's alone.
3. The switch-over check (`src/shiftlead/switchover.py`), three checks, each its cure *give one of them another name in the answers file*, as today:
   a. `_name_blockers(where, made)` keeps today's check, folded by `naming.tools_id(tool, name)` with its words, and adds one beside it over the same `made`: two logins whose `login.name` is the same string, whatever their tools.
   b. `host_logins` keeps its signature and return. Inside it, the profiles passed over at two of its `continue`s — `p.adapter == "shell"`, and the `except (KeyError, ValueError)` of an unregistered adapter — are kept as `(name, adapter)` pairs and handed to `_name_blockers` with `made`: a login whose `login.name` is one of them, of another adapter (the `shell` profile's adapter being the string `"shell"`), is a blocker. The other `continue`s (a folderless or not-here profile in `outside` mode, an adapter with no default home, a home that raises) are left out.
   c. A new function in `switchover.py`, called once in `cli.py`'s home check beside `switchover.teams(..., node_made=node_made)` (~5673), takes the home's `made`, each node's `made` and the answers file's `teams.<t>.logins`: a node's login of one tool named as a home login of another tool that a team on that node lists is a blocker. The `--answers` preview (~5645, `switchover.suggest`) is not changed: a name it suggests that collides is caught by the check.
4. A forgotten login's records resolve to no login while it is forgotten, as today; `profiles.get` and its readers are not changed for them (their read is TD-2280's). `logins.profile_name` and `_from_logins` keep the key form for a file edited by hand to hold one name under two tools; their docstrings say nothing shiftlead writes makes one (§4.9e).
5. Tests, beside `logins.py`'s own: a scratch `logins.yml` holding `claude-code:grind` (account `claude-code:acct-1`): adding `gemini:grind` is refused with §4.9e's live words and the file is unchanged; adding a forgotten `gemini:old`'s name `old` as a `claude-code` login is refused with the forgotten words; a take-back of a forgotten login on its folder still passes; a suggested name skips another tool's; a record written as `grind` still reads `profiles.get("grind")` and its account `acct-1` (`profiles.account_of("grind", "claude-code")`, the bare form a live login's account has today) after a `gemini:reader` login is added; after `claude-code:grind` is forgotten, adding `gemini:grind` is refused with the forgotten words, and after `ao login add --path` on its folder takes it back, the record written as `grind` reads its account `acct-1` again. `tests/test_login_verbs.py`'s assertion that `gemini:grind` is added beside a live `claude-code:grind` (`# per tool`, ~line 225) changes to expect item 1's refusal; `tests/test_launch_on_login.py::test_profile_name_is_the_bare_name_unless_two_tools_share_it` stays, as item 4's hand-edited file (its `LOGINS` fixture is written by hand). In the switch-over's tests: an answers file naming `claude-code:~/.claude` and `gemini:~/.gemini` both `paul` is a blocker; one naming two `claude-code` logins `Grind` and `grind` is still a blocker by today's fold; one naming a `gemini` login after a `shell` profile of that host is a blocker; one naming a node's `gemini` login after a home `claude-code` login a team on that node lists is a blocker.

**Done when:** No path shiftlead writes (`ao login add`, its suggested name, the switch-over's answers; `ao host up`'s provisioning is TD-2070's) gives two logins of one host one name, live or forgotten, and a record written under a login's bare name still resolves to that login's account after another tool's login is added, and again after the login is forgotten and taken back, with item 5's tests passing.
