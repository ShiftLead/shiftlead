## TD-1954: A flow names only its stages' roles: a Flows page lists the standard stages, says which seats a flow has and when each is used, names each seat's CLI and model, and copies a flow to vary it

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-18
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** 78f868e4658f49b09cdb4e9371413b3e
**Blocked by:** TD-1953, decision (paul)

**Why:** Paul, 2026-11-18, in TD-1153's conversation: a flows page "gives a set of standard actions (design, review, build, hunt, etc.) that can preferably be extended later. It seems like this would be the right place to set the model/cli used for each step." "The team page chooses the flow to use, and provides the other settings. If someone wants to have a different model do something, they copy/edit a new flow for it." "Seat count ranges belong on the team. The fact that a seat exists and when/how each is used belongs on the flow." And on the seats outside the stages: "It certainly makes sense for the models/subs to be defined per seat for these."

This reverses two rules of design §4.9c. Roles and flows are orthogonal and a flow names no model: the model is a profile on the role, the team or the member line. And a seat never sits out under a flow: the techlead, the auditors and the fact-checkers are the team's `seats:`, outside every flow, so no flow can drop one today. §4.9c *Made to be edited from a page, later* already shapes a flow as a directory of whole files for such a page. Built-in flows (`td`, `build-review`, `build`) cannot be redefined under their own names, so copy-then-edit is the road to a variant.

**Location:** src/shiftlead/flows/, src/shiftlead/org.py, src/shiftlead/repoconfig.py; design §4.9c, §4.9b, §4.8

**Ask:** Will you design the Flows page with a session: its standard stages, which seats each flow has, and each seat's CLI and model?

**Fix:** A Flows page listing the built-in flows, read-only with Copy, and the org's and each repo's flows, editable. A flow is built from a set of standard stages (design, build, review, hunt, ...) that can be extended later. It says which seats exist and when each is used: the lane stages, and the on-call seats (the reviewer, the auditors with their trigger, the fact-checkers, and possibly the manager), so a flow can leave one out. Each seat names the CLI and model it runs on, picked from what the Tools page (TD-1953) found. A different model for a step is a copied flow, whose stage briefs refer to the built-in's (`package:`) rather than copy them. Open question for the round: a repo's flow is shared through git while subscriptions are one machine's, so where a seat's subscription is bound (the flow on this install, or the team) is decided here.

**Done when:** the design round with Paul has written the Flows page and filed its builds.
