## TD-1954: A flow names only its stages' roles: a Flows page lists the standard stages, says which seats a flow has and when each is used, names each seat's model, and copies a flow to vary it

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-18
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** 78f868e4658f49b09cdb4e9371413b3e
**Blocked by:** TD-1953, decision (paul)

**Why:** Paul, 2026-11-18, in TD-1153's conversation: a flows page "gives a set of standard actions (design, review, build, hunt, etc.) that can preferably be extended later. It seems like this would be the right place to set the model/cli used for each step." "The team page chooses the flow to use, and provides the other settings. If someone wants to have a different model do something, they copy/edit a new flow for it." "Seat count ranges belong on the team. The fact that a seat exists and when/how each is used belongs on the flow." And on the seats outside the stages: "It certainly makes sense for the models/subs to be defined per seat for these."

This reverses two rules of design §4.9c. Roles and flows are orthogonal and a flow names no model: the model is a profile on the role, the team or the member line. And a seat never sits out under a flow: the techlead, the auditors and the fact-checkers are the team's `seats:`, outside every flow, so no flow can drop one today. §4.9c *Made to be edited from a page, later* already shapes a flow as a directory of whole files for such a page. Built-in flows (`td`, `build-review`, `build`) cannot be redefined under their own names, so copy-then-edit is the road to a variant.

**Location:** src/shiftlead/flows/, src/shiftlead/org.py, src/shiftlead/repoconfig.py; design §4.9c, §4.9b, §4.8

**Ask:** Will you design the Flows page with a session: its standard stages, which seats each flow has, and each seat's CLI and model?

**Fix:** A Flows page listing the built-in flows, read-only with Copy, and the org's and each repo's flows, editable. A flow is built from a set of standard stages (design, build, review, hunt, ...) that can be extended later. It says which seats exist and when each is used: the lane stages, and the on-call seats (the question seat, a review stage's reader, the auditors with their trigger, the fact-checkers), so a flow can leave one out; a flow that names no question seat leaves its members' questions to the person (the director's part is TD-1956), and the manager is every team's, the flow naming its model. Each seat names its model by family (the tool is the login's), with its `permission_prompts` and context bound, from what the Tools page (TD-1953) found. A different model for a step is a copied flow, whose stage briefs refer to the built-in's (`package:`) rather than copy them. Which login runs a seat is the team's (TD-1153), one ordered list across tools, decided in the frame.

Open for the round (moved from the frame, docs/decisions/2026-11-18-tools-flows-teams.md): how a flow is found once its directory name stops being its name, and what the org-over-repo-over-package shadowing means when two places hold one id; where the manager's and the question seat's other keys go (`lane`, `grants`, `unattended`, `on_call`, `context`), and whether the question seat and a review stage's reader stay one record as today; org flows cannot run on a node (§4.9c), so a node team's flows are its repo's; a flow switch never changes an interactive member's model (invariant 5), and a stage held only by an interactive member counts toward followability as today; followability drawn with its reason. The built-in flows are written as a person's are (Paul: dogfooding), each seat's model the package's choice from smoke and judge results (the manager on Sonnet once a manager smoke passes); until the known-passes list exists they name what their roles run on today (`org.yml`: hunter, auditor and manager on Sonnet, the rest on Opus). The migration: a team whose seats run another model today gets a flow of its own under a new name and id, its `flows:` list and `flow` setting re-pointed, each seat's role, trigger and model moved into it by key; for ao-grind (two fact-check seats on Gemini and Grok, grinder-ao-2's permission prompts) that is a PR rewriting `.shiftlead.yml` and adding `.shiftlead/flows/`. Review rounds: the four keys agent-cadence has today, by environment (recommended), with convergence and sticking-point keys filed against agent-cadence; agent-cadence's statistics read a design's cap from the repo's file, so a flow's cap by environment is read against it; a fact-checker seat's model and `CADENCE_FACT_CHECK_MODEL` are written from one field; a reviewer model the seat's login does not offer makes the flow unfollowable there; the person's cadence layer may order rounds (this install's: Sonnet, fix, Fable, fix), which a flow's `review-model` must agree with or override. The dual-read window for the six repos with teams, shiftlead's last, and `flow.yml`'s `format:` (the frame).
