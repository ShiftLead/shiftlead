**Why:** TD-1392's design: a wait is a gate in `Blocked by:`, never a `**Waits:**` line (cadence §2.14 at the pin ef7cf51). The briefs still tell each session to write the retired line: `src/shiftlead/briefs/grinder.md` (*Out of work*, and a live check that waits for an event), `designer.md` (*Out of work*), `entry.md` (`--field Waits=…`), `docs/briefs/test-audit.md` and `docs/briefs/docs-audit.md` (a finding's entry), and the ledger README's preamble describes it as this ledger's field. `grinder.md`, `designer.md` and the README also write `decision (paul) — <what they must do>`, the old form v2.4's `set` refuses (cadence §2.4).

**Ask:** Go once TD-1392's review rounds, which ended at the cap, are accepted? Answered on the board's 2026-11-05 decide item for TD-1392, which lists this build among its parts.

**Fix:** As design §4.4 *An entry says what it waits for* and §4.9b (a live check) now say, each place names the gate and its commands in place of the `Waits:` line:
1. **A date**: `agent-cadence run ledger.py set TD-n --blocked-by "<the ids it keeps>, until YYYY-MM-DD"` (a UTC day); a session that takes an entry whose reached date still stands drops it in its own PR (`set --blocked-by "<the rest>"`).
2. **An event a check can see**: write its section first, one line in plain words and one `check:` line (`agent-cadence run ledger.py edit TD-n --section "Event (<name>)" --from <file>`), then `set TD-n --blocked-by "<the ids>, event (<name>)"`; the typed checks are `pr-merged`, `file-contains`, `ref-includes`, and `host-log witnessed kind <kind> "<text>"` once TD-1388 is live; until the event runner (TD-1376) runs, `agent-cadence run gate_sweep.py --apply` lifts what passes.
3. **A wait no check can see**: a judgment entry blocked on by id, or `until` the day of the next look (at most 30 days out, ShiftLead's own cap, the briefs' guidance) — on the entry when it is itself the look (a live check naming its live build), else on a re-check entry the build is `Blocked by:` by id: a new entry, its id from `ao td reserve`, filed by `ledger.py new --id TD-n --kind build --blocked-by "until <date>"` with the look as its Fix, one for every entry waiting on the same occurrence; a look's note opens `looked:` (`ledger.py note TD-n "looked: …"`), and a look whose entry's Log holds one after its newest answered decision (or since it was filed; line order decides, not dates) is the second; both answers to the second lift, so the session that takes the re-check in its lane applies the answer first, read from the Log's newest `gate lifted: decision (paul)` line, its `answer "<label>"` matched against the item's two answers, never looking again; the decide already closed the board item, and one still open (a part still gated) is reported, not closed by hand — *keep watching* a new `until`, *drop it* each entry blocked on the re-check re-gated or dropped, then the re-check archived with `ledger.py archive --dropped`, in one PR, with what was read in a `note`; a second look that finds nothing gives it `decision (paul)` with an Ask.
4. **A forced claim** drops an `until` in its PR with `set TD-n --blocked-by "<the rest>"` (`lift` refuses an `until` before its day), and lifts an event gate: `ledger.py lift TD-n --gate "event (<name>)" --by <session id> --evidence <evidence>`, the evidence the check's own repo's `<repo>#<n>` (`pr-merged`) or `<repo>@<sha>` (the others).
5. `entry.md` drops `--field Waits=…` for a gate in `--blocked-by` (an event gate, whose section `set` and `new` need first, is added after `new` by `edit` then `set`); the ledger README's preamble sentence on **Waits** says the line is retired and what replaces it, keeping `Waits = until | event` on the `Fields:` line until ledgerboard v2.6's vendor (v2.5, tagged 2026-11-05, does not carry it).
6. **What waits on the person** is a bare `decision (paul)`, written in three steps in one PR: its Ask first (`ledger.py edit TD-n --section Ask --from <file>`, since `set` refuses a decision with no Ask), then the gate (`set TD-n --blocked-by "<the ids>, decision (paul)"`), and a `decide` item on this repo's board whose Context is exactly `TD-n decision (paul)`, by the full `board_edit.py add --kind decide` invocation design §4.4 *What waits on the person* gives (`--text`, `--due`, two `--answer`s or more, `--lift` for each answer that ends the wait, `--detail` with context, question and recommended), since the merge gate refuses a decision a PR adds with no board item (`uncovered_decisions`); never the old `decision (paul) — <what they must do>` (or `— <the mail's id>`), which v2.4's `set` refuses (cadence §2.4): `grinder.md` (twice), `designer.md` and the README's preamble.
7. `src/shiftlead/team_skill.md`'s line on a `**Waits:**` line naming a date or an event names the gate instead, and `agent_tick.py`'s docstring that names the line follows.

**Done when:** no brief under `src/shiftlead/briefs/` or `docs/briefs/`, no line of `src/shiftlead/team_skill.md`, and no line of `docs/ledger/README.md` but the `Fields:` declaration, tells a session to write a `Waits:` line or the old `decision (paul) — <text>` form; each names the gate commands above, a decision's three writes (Ask, gate, board `decide` item) among them, the printed `board_edit.py add` invocation accepted by the writer (a dry run on a scratch copy); and the briefs' doc-bound tests pass.
