## TD-2144: A session start that fails or is cancelled while its pane comes up can still leave a stray shell

**Priority:** Low
**Type:** debt
**Added:** 2026-11-24
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** c94e5d76dcb74d6e9d9f67025b207028

**Why:** The independent review of #4474 found two ways a create can still leave a pane up with no record, so the next tick adopts it as a nameless shell. `tmux.new_session` chains `new-session` with `set-option` and `pipe-pane` in one call, so a later step that fails raises `TmuxError` with the session already up. A create cancelled while it awaits `_start` leaves the start's thread running, and its pane comes up after the create has gone. Both were found by reading the code and neither has been reproduced.

**Location:** src/sessionorc/agent.py (create), src/sessionorc/tmux.py (new_session)

**Fix:** In `create` (`src/sessionorc/agent.py`), begin the guard TD-2125 added before `_start` rather than after it, keeping `DuplicateSession` out of it because that pane is another session's. On a `TmuxError`, kill the pane only if this call created it. On a cancel, wait for the start's thread to end before killing, and hold `_starting` until the kill has landed. This is a held path, so the pull request goes to the techlead.

**Done when:** Tests show that a start whose later tmux step fails, and a create cancelled during its start, each leave no pane and a following tick adopts nothing, and that a duplicate-session answer never kills the other session's pane.
