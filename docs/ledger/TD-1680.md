## TD-1680: Settings refuses every save for an account whose reading stopped reporting a window it still holds a reserve on

**Priority:** high
**Type:** debt
**Added:** 2026-11-11 (paul, through Add entry; drafted by ao-shiftlead-techlead-ao-1)
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** 8e6f227342d449468886449d558c022f
**Location:** src/sessionorc/agent_settings.py (set_settings, the reports-no-window check); src/shiftlead/ui/settings_page.py (usage_cards); src/shiftlead/ui/templates/settings.html (the Usage card); docs/design/4.7-cli.md (ao gate); docs/design/4.5-ui.md (screen 8), docs/design/4.5a-controls.md (Settings page: Usage)

**Why:** The person cannot save any reserve for `claude-code:paul` from the Settings page (2026-11-11, screenshot `~/.shiftlead/attachments/draft-ad921cdc/paste-20261111-121115.png`). The account's reading now reports only a `week` window (its subscription no longer has a 5-hour session allowance), but `settings.yml`'s `usage_gate:` still holds `5h: 5` from before. `usage_cards` in `settings_page.py` draws a row for every reserve on a label no reading has shown (*no reading yet*), so the card shows a `5h reserve` field holding 5; its Save sends every row, and `set_settings` refuses the whole call because `5h` is a label the reading does not report: *account claude-code:paul reports no window 5h: its windows are week (design §4.7)*. The refusal counts a clear (`5h: null`) as an unknown label too, so emptying the field is refused as well, and so is `ao gate claude-code:paul 5h=`. The stale reserve does nothing (`settings.lines` reads only reported windows), yet it blocks every change to the account's real reserve: the only way out today is editing `settings.yml` by hand, which design §4.5 screen 8 says a setting never needs. The row's *no reading yet* is also wrong: there is a reading, and it lacks that window. Any adapter that drops or renames a window will strand its account the same way.

**Fix:** 1. In `set_settings`' subscription path (`agent_settings.py`, the *reports no window* check), refuse only a reserve that sets a value on an unreported label; accept a clear (`null`) for any label, which removes it from `usage_gate:`. Then the page's empty field and `ao gate <account> <label>=` both clear a reserve on a window the account no longer reports.
2. In `usage_cards` (`settings_page.py`), when the account has a reading, draw a reserve on a label the reading lacks as a row that says so — *not reported: claude-code:paul reports week* — not *no reading yet*. Its Save sends that label as a clear, with or without the person emptying the field, so a Save of the reported windows succeeds and drops the stale reserve. Keep *no reading yet*, and the labels unchecked, for an account with no reading at all.
3. Write both behaviours into the design in the same PR: §4.7 `ao gate` (a clear is accepted on any label; only a value on an unreported label is refused) and §4.5 screen 8 / §4.5a *Settings page: Usage* (the not-reported row and what its Save sends).
4. Tests: `set_settings` accepts `{5h: null}` on an account whose reading reports only `week` and still refuses `{5h: 5}`; `usage_cards` draws the not-reported row; a Save of that card writes `week` and removes `5h`.

**Done when:** On an account whose reading reports only `week` but whose `usage_gate:` holds a `5h` reserve, the Settings page's Save changes the week reserve and removes the 5h reserve, `ao gate <account> 5h=` clears it, a new value on `5h` is still refused, the stale row says the window is not reported, and tests hold all four.
