**Why:** Part of TD-2104: the disk sweep deletes no branch, so a branch that never went through a session's close stays for good. Read on 2026-11-23 in shiftlead: of 406 local branches not checked out, the rule as designed deletes 190 on its first run. Another 99 moved within the 7-day age and 79 hold a commit only in their reflog, so those go later, as the age passes and git expires the entries. One has an expired reflog and is decided by the remaining steps. The rest stay: 21 track a live upstream, 4 are pushed and unmerged, and 12 hold commits no proof covers.

**Location:** src/sessionorc/branchsweep.py, src/sessionorc/agent_tick.py, design §4.6 *The disk sweep*

**Ask:** Should the grinders build the disk sweep rule that deletes local branches whose work has already landed?

**Answers:** Go (default) — the grinders build it | Not yet — nobody builds it until you say

**Lifts:** Go

**Fix:** Build §4.6 *The disk sweep*, *branches*, as written: a new module `branchsweep` run from `_prune_rules` beside `_sweep_worktrees`, under the same scope; the two proofs, the weigh's order and whys, the re-read of the tip, `git branch -D`, the INFO log line naming the commit, the once-a-day pace with its budget and in-memory cursor, the dry run; `disk.json`'s `branches` and `ao disk`'s lines (§4.6 *The sweep's reading*, §4.7). Tests use real git repos and a stubbed `gh`.

The help text of `worktree_keep_days` (`hosts.py`, the Settings page) says it also ages the branches rule.

**Done when:** In a test repo: a branch at the head of a PR merged into the default branch and one on the default branch are deleted and logged with their commit, and so is such a branch whose reflog git has expired, in a repo with ref logging on. Each of these is kept with its why: a branch with an unlanded commit, one pushed and unmerged, one at the head of a PR merged into another base, one at a squash-merged head with a commit only in its reflog, one tracking a live upstream, one merged whose own remote head still exists, one with no reflog in a repo with ref logging off and one in a bare repo with the setting unset, read from a linked worktree too, one checked out in a worktree, one moved within the age, one whose create lock is busy, one whose tip moves before the delete. A failed read of the logging setting keeps the branch. The counter branch and the default branch are never weighed. With `gh` failing, only the first proof deletes. A branch name with a slash takes no create lock. A run stopped by its budget carries on after its cursor and clears it at the end. A dry run deletes nothing and leaves the cursor. `ao disk` shows the counts and the kept list, at most 200 rows with the count past them.
