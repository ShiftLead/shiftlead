**Why:** TD-1551's trial (design §4.3 *What a start reads from the prompt cache*, 2026-11-11, a logging proxy between Claude Code 2.1.322 and the API): a start reads from the cache the tool definitions and the whole system prompt, the preface at its tail, wherever another start of the same account, model and system prompt wrote them within the hour (29,451 tokens), and nothing after it. The Add entry form's `entry.md` is the same for every Add entry start but has its four slots filled inside it and sits in the context file, so that start's system prompt is its own: it reads nothing past the tool definitions, and writes about 2,200 tokens of system prompt the other starts read. With its slots filled by constant phrases and the values in the composer, every Add entry start shares it (Paul, 2026-11-11: *the "add entry" should be taught to use the brief as-is and add its dynamic info after it to maximize cache as well*). Every adapter's cache layout is learnt the same way, by a capture: §4.3's conformance walk names this build's script. A member's brief moved the same way is TD-1669.

**Ask:** None now: Paul gave his go on 2026-11-11 after the confirming round (R20); this entry builds the cache-capture script and the Add entry template in the system prompt.

**Fix:** Design §4.3 *The shared text goes in the system prompt, the per-start text after it*. One PR does steps 1–3; step 4 is its follow-up.

1. **The cache capture tool.** Commit `scripts/cache_capture.py` (standard library only), loaded by path in its test as `tests/test_history.py` loads its script.
   - **The proxy** (`serve --port N --out DIR [--upstream URL]`, upstream default `https://api.anthropic.com`): a pass-through a tool's base URL is pointed at. It forwards each request and streams the response back as it comes (SSE included), passing `content-encoding` through, and writes each request body and the response body, decoded, to `DIR` — never a header.
   - **The reader** (`show FILE…`): a request's layout (tool count, each system and message block with its length and cache marker) and the first request's cache figures. It takes a small provider table saying where the system text, messages, cache markers and the usage's read and write fields are; Anthropic's is its first row, its usage read from a JSON response or from a streamed one's `message_start` and `message_delta` events. For a provider it has no row for, it prints block sizes and the raw `usage` only.
   - **Tests** in `tests/test_cache_capture.py`: the proxy against a local `http.server` stub upstream (a JSON and an SSE response, one gzip-encoded), asserting the client gets the bytes, the files hold the decoded bodies, and no header is written; the reader over a fixture request with a JSON and an SSE response.
   - Name the script in §4.3's conformance bullet *The cache capture, live, by hand*.
2. **The Add entry template in the system prompt.** `entry.md` is read two ways: by an Add entry start, and inside the techlead's brief through `{entry}`, filled from `HANDED_ENTRY` (`repoconfig.py`), which stays as it is. `entry_text` keeps its four-argument signature; a new dict `ADDED_ENTRY`, shaped as `HANDED_ENTRY`, holds the Add entry reader's constants (*the repo in your first message's values*, and so on), and the Add entry start (`ui/app.py`, `api_entry_session`) calls `entry_text(*(ADDED_ENTRY[s] for s in ENTRY_SLOTS))`, the same text for every Add entry start, as its `start_context`.
   - Reword the template's lines whose slot sits inside literal header text (`` `**Priority:** {priority}` ``, `` `**Type:** {type}` ``) so both readers' constants read as instructions (*`**Priority:**` with the Priority {priority}*), and keep `HANDED_ENTRY`'s phrases reading right there.
   - **The values block.** One function in `ui/app.py`, with a test, builds a labelled block — `Add entry values — repo: <repo>, Type: <type>, Priority: <priority>, ledger: <ledger>` — and `api_entry_session` returns as `text` that block, then a blank line and the person's words when there are any; it is the composer text even when the words are empty. Update the route's docstring. The person can still edit the composer before sending it.
   - **A value missing.** `entry.md` says: where the first message has no values block, or a value is missing or unreadable, ask the person for the repo, Type and Priority rather than guess; the ledger is the repo's (`.shiftlead.yml`'s `ledger:`).
   - Focus's *told at start* row for an Add entry session now shows the template with `ADDED_ENTRY`'s phrases, not the values; that is expected.
3. **Tests.** At the route, as `tests/test_ui_entry.py` posts to `/api/entry/session`: two POSTs with different repos, Types and Priorities hand `create` the same `start_context`, and each `text` holds its own values block (and the words after it, when given). Update `tests/test_ui_entry.py`'s `text` expectations (`text == words`, `text == ""`) and the `entry_text` ones there and in `tests/test_repoconfig.py`, whose `**Priority:** high` and `**Type:** feature` assertions move to the values block's test; the techlead's `HANDED_ENTRY` fill and its test stay.
