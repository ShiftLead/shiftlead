## TD-1835: A Grok session runs under the person's Claude Code permission mode and rules: ~/.claude/settings.json's defaultMode auto wins over asking_args

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-14
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** 95393914f0ff41e892d1df9c70a6ce03
**Part of:** TD-1550

**Why:** Grok Build 1.0.77 reads the person's own Claude Code settings for its permission rules and mode: `~/.claude/settings.json` and `settings.local.json`, a project's `.claude/settings.json` and `settings.local.json` up to the repo root, and in a worktree the main checkout's `settings.local.json` deny and ask rules (its guide, *Permissions and safety* §3; `grok inspect --json` on kmaster lists `/home/kmaster/.claude/settings.json` as its one permissions source, 4 rules). No `compat.claude` key covers permissions (`compat.claude.*` covers agents, hooks, MCPs, rules and skills, and `GROK_CLAUDE_RULES_ENABLED=false` leaves the source in place); whether `auto_mode.enabled`, `default_auto_mode` or `ui.permission_mode` in the profile home's `config.toml` or `requirements.toml` wins over it is untried. On kmaster that file sets `defaultMode: "auto"` (and four `git diff`/`git log` allow rules, none covering `cp`). TD-1637's live walk on `grok-conformance` saw no permission prompt: `cp /dev/null conformance-permission.txt` ran unasked, though the launch passed `--permission-mode default` (§4.3 `asking_args`) and the guide says a CLI flag overrides config. The same walk with `HOME` a scratch directory, the binary linked into it, passed all seven steps (2026-11-14, session 63a38041). That run hid the whole of `$HOME`, so `defaultMode` is the likely key (the one permissions source `inspect` lists) but not yet isolated: a walk with a scratch `HOME` holding only `{"permissions": {"defaultMode": "auto"}}` settles it. So every Grok session ShiftLead launches runs under the person's Claude Code permission mode and rules: a seat under `permission_prompts: all` is not asked as §4.2a says, and the person's Claude allow rules widen what a Grok seat runs unasked. §4.3 says nothing of it beyond the note slice 17 added.

**Location:** docs/design/4.3-adapter-contract.md (The third adapter: Grok Build); src/shiftlead/adapters/grok/

**Fix:** Design how a Grok launch keeps the person's Claude Code permission settings off its sessions, in §4.3 *The third adapter: Grok Build*. Candidates to read against the installed tool first: a launch `HOME` of the profile's own (what else the tool and its shell commands read from `HOME`: git and ssh config, the login shell's environment, `~/.grok/bin`); `[ui] permission_mode = "ask"` or `auto_mode.enabled = false` / `default_auto_mode = false` written into the profile home's own `config.toml` beside the hook file, and whether either wins over a Claude `defaultMode`; a `requirements.toml` in the profile home; or saying in §4.3 and the profile's doctor row that the person's Claude permissions apply to Grok. Then the build entry that does it, `Part of: TD-1550`.

**Done when:** §4.3 says how a Grok launch keeps the person's Claude Code permission mode and rules off its sessions, or that they apply and why. A build entry carries it, and TD-1637's walk on `grok-conformance` passes its *a permission* step with the person's `~/.claude/settings.json` in place.
