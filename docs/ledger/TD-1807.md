**Why:** On 2026-11-13 Paul saw the interactive session `queue` (`ao-shiftlead-queue`) marked **Working** on its Focus page for hours. It was waiting at its composer: its last turn ended at 07:09Z ("done 12:09 AM" on the pane), with no subagent, no shell and no pending prompt. A session that reads `working` when it is waiting misleads every reader: the person and the Queue think it is busy, and nothing tells them it is waiting on them. The screenshot is `~/.shiftlead/attachments/draft-0dbde902/paste-20261113-175530.png`.

The record read by the techlead at 2026-11-14T00:56Z:
- `state: working`, `confidence: tick`, `since: 2026-11-14T00:52:05Z`;
- `work_at`, `turn_at` and `seen_at` all at 2026-11-13T07:09:23Z, and `last_hook` none;
- `screen_at` 00:54:31Z;
- `ao explain` says *no screen rule matched*.

The likely cause has two halves:
1. **How it went wrong.** TD-1798 (#3744) records that `queue` was one of four idle sessions that read `stalled?` after a host agent restart inside a usage cap, because the lift fell back to `working`. #3744 fixes the lift for the future, but a record already set that way is not reset.
2. **Why it stays wrong.** Nothing brings a tick-set `working` back to `idle` while the tool sends no hook, and a session at its composer sends none. `_stall_check` (`agent_tick.py`) moves `stalled?` back to `working` whenever the masked screen hash moves, so the record likely cycles between `stalled?` and `working`, its `since` reset each time. That is how `since` came to be 00:52Z, after #3744 was live (merged 15:04 local; the screenshot's header reads *live 11-13 17:36*).

What still moves the masked screen of a pane at its composer is not yet known. The Claude Code adapter's `volatile_after` masks the rows after the last plain rule, and `volatile_rows` the spinner row. Candidates are the composer's labelled top rule (it carries the session's name, so it is not a plain rule and is not masked), the cursor, and the rows between the last turn's text and the composer. The footer rows, "Update installed" among them, sit below the lower plain rule and are already masked. `last_output` (00:54:27Z) falls 4 s before `screen_at` (00:54:31Z), so something repainted the pane just before the hash moved.

Mask them as the adapter's volatile rows (design §4.3 *An adapter names its volatile rows*).
2. **Give a tick-set state a way back.** A tick-read `stalled?` or `working` with no work-naming hook since `work_at`, whose pane shows the composer the adapter recognises as waiting, reads `idle`. Do this rather than letting movement alone read as work. Write the rule in design §4.2 first, beside the liveness cross-check.
3. **Check `queue` once it is live.** It should read `idle` without a prompt or a restart.

**Done when:** An idle Claude Code session at its composer, whose record was left `working` or `stalled?` by the tick, reads `idle` within a few ticks and stays there until its next hook. Design §4.2 says how, and a test pins both a moving footer that reads no work and the way back to `idle`.
