## TD-1508: Every write the home lands is read at once, and a press reads answered — applying until it lands

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-07
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** 1a489cf49d3a45379a9eec9043c7eff3
**Blocked by:** TD-1507
**Part of:** TD-1471
**Location:** src/sessionorc/agent_inbox.py (_reread_board, _answer_orphan_one, rpc_board_edit, rpc_ledger_decide, _ledger_road); src/sessionorc/agent_sync.py; src/sessionorc/agent_rank.py; src/sessionorc/queue.py; src/shiftlead/ui/inbox.py, src/shiftlead/ui/queue.py; design §4.4 Every write the home lands is read at once, The card's status

**Why:** Build TD-1471, slice 2 of 3 (design §4.4 *Every write the home lands is read at once*, *The card's status*; §4.5 screen 6). Only board presses re-read at once today: an orphaned question's answer (`_answer_orphan_one`) and a sync merge re-read nothing, and between a press and its landing (a fetch, a commit, a PR, a merge: seconds) every view shows the state the person just answered — *needs you* after the answer (TD-1364, TD-1368), an old answer on the line.

**Fix:** - **Every landed write re-reads at once** (`src/sessionorc/agent_inbox.py` `_reread_board`, which TD-1507 made read the ledger with the board): call it after an orphaned question's answer lands (`_answer_orphan_one`, after `board.add`) as the presses already do. A merge the home makes outside its board tree — a sync merge (`agent_sync.py` `_sync_merge_in`, once `sync.merge` lands) — re-reads with a fetch first (`_reread_board(root, fetch=True)`: a fetch of the default branch with the explicit refspec, then the board read from origin rather than the tree, whose head is as old as its last press), never the tree as it stood. A rank landing re-reads the same way as a press (it landed in the tree): `_rank_flush` runs off the loop (`agent_rank.py`), so `_rank_flush` returns the set of roots whose `board.land_rank` landed (a truthy return; the root is `repos[repo][0]`), and `_rank_run` awaits `_reread_board` on each once the thread returns. The design's table (§4.4 *Every write the home lands is read at once*) is the list: each row with *a PR the home merges* re-reads at once; a gate sweep's open PRs do not.
- **The `applying` mark**, kept apart from the reading: `self._applying` `{root: {key: {token: {act, answer, at}}}}` in memory, never in `self._repos` nor saved by `repos_store`; `key` is `board:<key>` for a board line's press (`rpc_board_edit`, `rpc_board_reply`) and `ledger:<repo>#TD-n` for a ledger decide or road (`rpc_ledger_decide`, `_ledger_road`), drawn on the entry's member. The press sets its mark and pushes `repos` before the write-back starts, and clears it in a `finally` when its call returns — landed and re-read, refused, failed, or `_reread_board` failing or returning early — pushing `repos` again; each press adds its own token with its own `act`, `answer` and `at`, a view drawing the newest standing token's, and a clear removes only its own token, the mark gone when the key holds none, so a second press on the same key, refused, restores the first's words and leaves the mark until the first returns. `_answer_orphan_one` marks nothing (its mail row closes with the answer). `_repo_view` and the Queue's pass (`_queue_pass`, `sessionorc.queue`) lay the marks over the board items and the entry rows they build from, so a tick's read in the meantime keeps the mark (it is not in the reading the tick replaces), and a restart starts with none.
- **The views**: the Inbox row (`src/shiftlead/ui/inbox.py`) and the Queue member line (`src/sessionorc/queue.py`, `src/shiftlead/ui/queue.py`) read `applying`: *answered — applying* for `act: decide`, *applying <act>* for the rest, in the place *answered — waiting on <asker>* takes (design §4.4 *The Queue*'s member order), and a member under a mark is no need (*The card's status*: no *needs you*, no amber, not counted).
- Tests:
  - A decide press on a `decision (paul)` member: before the write-back returns (a write-back stub that blocks), the `repos` push carries the mark, the card reads *answered — applying* with no *needs you*, the counts drop it, and a tick's read in that window keeps it; after it lands, the lifted entry and no mark.
  - A write-back that fails, and one whose re-read fails: the mark is gone, the row as the reading has it, the press's error returned.
  - Two presses on one line, the second refused: the row reads the first's words again and the mark stands until the first returns, then clears.
  - A landed `queue:` rank PR, the checkout stale: the card's `key` reads from origin in the `repos` push the flush ends with, before any tick.
  - An orphaned question's answer, the checkout stale: the new board line is in the next `repos` push.
  - A sync merge, the board tree last reset before an unrelated merge: the re-read reads origin's new head, never the tree's older one (no regression of board or ledger).
  - A restart mid-press: no mark after it; `repos_store`'s saved reading never carries one.

**Done when:** Every write the home lands on origin (design §4.4's table) re-reads board and ledger at once, and a press's row reads *answered — applying* (or *applying <act>*) from the press to its landing, never *needs you*; tests pin each view against a just-landed write with a stale checkout.
