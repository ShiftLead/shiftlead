**Why:** Build TD-1471, slice 2 of 3 (design §4.4 *Every write the home lands is read at once*, *The card's status*; §4.5 screen 6). Only board presses re-read at once today: an orphaned question's answer (`_answer_orphan_one`) and a sync merge re-read nothing, and between a press and its landing (a fetch, a commit, a PR, a merge: seconds) every view shows the state the person just answered — *needs you* after the answer (TD-1364, TD-1368), an old answer on the line.

**Fix:** - **Every landed write re-reads at once** (`src/sessionorc/agent_inbox.py` `_reread_board`, which slice 1 made read the ledger with the board): call it after an orphaned question's answer lands (`_answer_orphan_one`, after `board.add`), and after a sync merge (`agent_sync.py` `_sync_merge_in`, once `sync.merge` lands, after a fetch of the repo's default branch), as the presses already do; a rank landing (`agent_rank.py` `_rank_flush`, after `board.land_rank`) re-reads the ledger against origin the same way. The design's table (§4.4) is the list: each row with *a PR the home merges* re-reads at once; a gate sweep's open PRs do not.
- **The `applying` mark**: `rpc_board_edit`, `rpc_board_reply`, `rpc_ledger_decide` and `_ledger_road` (and `_answer_orphan_one` for its line) set `applying {act, answer, at}` on the board reading's item (by its `board:<key>`; for a ledger decide, the entry's row through its decided line once added) in `self._repos[root]["boards"]`, push `repos`, then run the write-back; the re-read replaces the item; a failed write-back drops the mark and pushes `repos` again before raising its error. In memory alone: never saved in `repos_store`, so a restart drops it. A tick's board read that lands mid-press keeps the mark on the item (the press is marked as `_boards_pressed` already marks it).
- **The views**: the Inbox row (`src/shiftlead/ui/inbox.py`) and the Queue member line (`src/sessionorc/queue.py`, `src/shiftlead/ui/queue.py`) read `applying`: *answered — applying* for `act: decide`, *applying <act>* for the rest, in the place *answered — waiting on <asker>* takes (design §4.4 *The Queue*'s member order), and a member under a mark is no need (*The card's status*: no *needs you*, no amber, not counted).
- Tests:
  - A decide press on a `decision (paul)` member: before the write-back returns (a write-back stub that blocks), the `repos` push carries `applying`, the card reads *answered — applying* with no *needs you*, the counts drop it; after it lands, the lifted entry, no mark.
  - A write-back that fails: the mark is gone, the row as before, the press's error returned.
  - An orphaned question's answer and a sync merge, the checkout stale: the new board line, and the merged change, are in the next `repos` push.
  - A restart mid-press: no mark in the saved reading.

**Done when:** Every write the home lands on origin (design §4.4's table) re-reads board and ledger at once, and a press's row reads *answered — applying* (or *applying <act>*) from the press to its landing, never *needs you*; tests pin each view against a just-landed write with a stale checkout.
