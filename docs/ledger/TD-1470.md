## TD-1470: No check asks whether open work has a live session able to act on it; a send to a down home is dropped silently

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-06 (Paul, through ao-led-tds-ledger and the techlead seat; drafted by ao-shiftlead-techlead-ao-1)
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** 78351797b3454c1fa863a725bd05518c
**Location:** src/sessionorc/agent_tick.py (the tick's policies); src/sessionorc/queue.py and src/shiftlead/ui/queue.py (the card's status); src/shiftlead/cli.py (`ao msg`, `ao td add`, `ao progress` against a stopped home); design §6, §4.4 *The card's status*, §4.10

**Why:** Asked by Paul through the person's session `ao-led-tds-ledger` (m-247dff0b7a94), from a review of that session's 28 incidents. Nothing in ShiftLead asks *is there open work that no live session can act on?* Each cause seen so far got its own entry:
- TD-1435: an idle seat with read, unworked asks;
- TD-1434: a seat switched to interactive;
- TD-1443: a limited or hung model;
- TD-1441: a team held by its daily start cap.

Other causes have no entry at all:
- the techlead seat parked at its fill ceiling for about 7 h (2026-11-05 15:04–22:22) with 8 asks waiting;
- the host agent down and then `ao` missing, so three filings from a session were lost with no one noticing (2026-11-06, about 01:00);
- agent-cadence's team stalled while TD-1360 waited on an event that had already passed (2026-11-05).

An outside session's poll loop has been doing this job all week.

**Fix:** Design first (§6, the tick's policies; §4.4 *The card's status*; §4.10). Paul's suggestion: one home-side check, run every tick. It finds any open ask, decide item or ready PR that no live session has been able to act on for more than N minutes, and raises a *needs you* on its card that names why:
- limited;
- interactive;
- capped;
- parked at its ceiling;
- released;
- home down.

The per-cause entries (TD-1434, TD-1435, TD-1441, TD-1443) become the reasons it reports, rather than each building its own alarm. Also in scope: a send never goes missing. `ao msg`, `ao td add` and `ao progress` already fail loudly against a stopped home: `main` catches `AgentUnavailable` and exits 3 with an error line (`src/shiftlead/cli.py`, `_unavailable`; design §4.7). The three filings lost on 2026-11-06 came from `ao` itself missing, so the shell said *command not found* and no CLI code ran, or from a session that did not act on the failed send. Say how a session learns its send did not land and sends it again: the brief's rule to read the exit, a spool the next `ao` drains, or the check above seeing the session's work stalled. Say where the check lives so it still runs when one seat is the stuck one, and what N is per kind.

**Done when:** The design names the check, its N per kind, the reasons it reports and where the card shows them, and how a send to a down home fails. Builds carrying `Part of: TD-1470` make it so. A test: an open ask whose only able seat is limited for more than N minutes makes its card read *needs you* with the reason *limited*. The design also says how a send that did not land, with the home down or `ao` missing, is noticed and sent again.
