## TD-2219: After the rename to builder, a person's old grinder brief addition is said to be unread rather than silently dropped

**Priority:** Low
**Type:** feature
**Added:** 2026-11-25
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** 70c220f00fe54484a87b3ae3258ef958
**Blocked by:** TD-2056
**Part of:** TD-2215

**Why:** TD-2215 (design 4.9c *The person's own rules under a flow*): once the removal build (TD-2056) renames `grinder` to `builder`, every session in the builder role reads the person's layer file `shiftlead/briefs/builder.md`, so a layer still holding `grinder.md` would add nothing and say nothing. The design keeps no fallback to the old name; the session's *Your own rules* says the file was not read.

**Location:** src/shiftlead/layers.py

**Fix:** Design 4.9c *The person's own rules under a flow*. In `shiftlead/layers.py`, a map of retired role names, `RETIRED = {"builder": "grinder"}`. Where `brief_parts(role, …)` finds, in a layer, no `shiftlead/briefs/<role>.md` but the retired name's file, that layer's part is the line *shiftlead/briefs/grinder.md in <layer root> is read by nothing: grinder is now builder, so rename it builder.md*, its source the old file (path and sha, so the *told at start* row heads it); nothing else of the file is read. A layer holding both files reads `builder.md` alone and says nothing of the old one. Every reader of `layers.person` gets it with no change of its own (a member's start, `ao new`, the New session form, and a stage's, an audit's and a job's session). This lands in TD-2056's pull request or after it, never before, since before the rename `grinder.md` is the file read.

**Done when:** A test with a temp own layer holding only `shiftlead/briefs/grinder.md`: a `builder` brief's *Your own rules* is that one line, naming the layer, with the file in `sources`; with `builder.md` beside it, `builder.md`'s text alone; with neither, *none*. The same through a stage session's launch (`stage_start.launch`).
