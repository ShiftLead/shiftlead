## TD-2033: Several orgs on one repo: claims on a branch beside the step state, so two homes can work the same ledger

**Priority:** Low
**Type:** feature
**Added:** 2026-11-21
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** 271f497a24ef4ce58692e5c6c43492e2
**Blocked by:** TD-1954, decision (paul)

**Why:** Paul, 2026-11-20, in TD-1954's conversation: if claims moved to a branch in the repo as step state does, then in theory different orgs could work on the same repo, and it might be worth a design to consider. Today a claim is a 12-hour lease in the session record at one home (design §4.4a, §4.8), so only sessions that report to that home are kept from taking the same entry. TD-1954 proposes keeping each entry's step on a dedicated branch written by compare-and-swap push, as `cadence/ledger-ids` already is, which any machine can read and write.

**Ask:** Once the Flows design (TD-1954) has settled where an entry's step is stored, will you run the design round on several orgs working one repo?

**Fix:** Design whether two homes can work one repo. The questions the round answers: whether the claim moves to the state branch beside the step, and how it lapses there when no home can see the other's sessions (a lease by time); which flow definitions both homes can read (a repo's flows are shared, an install's are not); how a step's key stays unique when two orgs' teams run flows on one repo; who gates and merges, and which home promotes; and what a session does when it finds an entry claimed by a home it cannot ask.

**Done when:** A design round with Paul says whether shiftlead supports several homes on one repo, and either writes the design and files its builds or records why not.
