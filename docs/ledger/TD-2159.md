## TD-2159: A review stage gives its counts of findings and of those it would not ship with, and the posted review comment carries them

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-24
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** e4f0ddc027854ca48fea4addbc94bcbc
**Blocked by:** TD-2158, decision (paul)
**Part of:** TD-2077

**Why:** Part of TD-2077 (design §4.9c *What a run records, for comparing flows*, §4.7 `ao stage end`). The home's `cadence-review:` comment for a review stage writes 0 findings for a ship and 1 for changes wanted, since the session gives no count, so a pull request's findings cannot be compared between flows.

**Ask:** Should the grinders build the design that records what each flow's run leaves behind, or run one more review round first?

**Location:** src/shiftlead/stage_end.py, src/shiftlead/cli.py, src/sessionorc/agent_stage.py, src/shiftlead/stage_start.py, src/shiftlead/briefs/standard/review.md, design §4.9c

**Fix:** Add `--findings <n>` and `--blocking <m>` to `ao stage end`: the argparse and docstring in `src/shiftlead/cli.py` (`cmd_stage_end`), the `stage_end` RPC's parameters (`src/sessionorc/agent_stage.py`) and the call in `src/shiftlead/stage_end.py`. Check the options in `call`, before the lock and before a job's reference is routed to `end_job`, so an entry's, a job's and an audit's call are checked alike, and a well-formed repeat is then answered as the first. Taken with `ship` and `changes-wanted` alone, refused on any other outcome; `changes-wanted` refused without both or with `m` at 0, `ship` refused with `m` above 0 and reading 0 for both without them, `ship --findings <n>` alone reading `m` as 0, `--blocking` without `--findings` refused, `m` above `n` refused. Write `findings: {all: n, blocking: m}` on the review row and post `n` as the comment's count in place of today's 0 or 1; on a job's record (a pull request's or a board answer's, §4.9c *What a run records, for comparing flows*) no row carries `findings`, the count still posted on the comment: `stage_job_end.end_job` takes no review verdict yet (§4.9d *Its pull request is reviewed and merged by the team's flow* designs it, still to be built), so nothing here writes a job's row. The `ship` row an `only-when` stage's pass writes (`_pass`, its reason `passed: …`) carries no `findings`. Tell a review stage's session to give them: the command's form and facts in `src/shiftlead/stage_start.py` (the text a stage's session is told) and `src/shiftlead/briefs/standard/review.md`. A build stage that posts its own `cadence-review:` comment keeps doing so with its real count, and both options are refused on its `work-pushed`.

**Done when:** Tests show the options refused on a non-review outcome (`other` among them, and a job's `work-pushed`), `changes-wanted` refused without a blocking count above 0, `ship` refused with one and reading 0 for both without them, `m` above `n` refused, `--blocking` without `--findings` refused, `ship --findings <n>` alone reading `m` as 0, every refusal made before the review comment is posted, a repeated call answered as the first with any changed counts ignored, the row's `findings` and the posted comment's count both matching, the `ship` row of an `only-when` stage's pass carrying no `findings`, and the review stage's told text and brief naming the options.
