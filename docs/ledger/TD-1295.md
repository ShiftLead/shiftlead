## TD-1295: The home keeps a log of the events it witnesses and answers "at least N of this kind, matching this text, since this date", so an entry waiting on such an event can be checked mechanically

**Priority:** medium
**Type:** feature
**Added:** 2026-10-31 (ao-led-tds-ledger, through `ao td add --repo`, for ledgerboard's planned `host-log` event check; drafted by ao-shiftlead-techlead-ao-1)
**Owner:** designer
**Kind:** design-first
**Status:** Open: filed held until Paul agrees the event model of ledgerboard's target design
**Blocked by:** decision (paul) — is the event model in ledgerboard's target design (`docs/plans/target-design.md` §3 and §4, still under your review) agreed? Say go, and the design round runs
**Location:** design §4.4 *An entry says what it waits for* (the `**Waits:** event` line, read by `ledger.waits_of` and marked by `settle.mark_waits`, which today ends only when someone edits the line away); `src/sessionorc/modes.py` (home-owned RPCs: a new log and its query are home writes and reads, and a missing row there is the bug made twice already); `src/sessionorc/store.py` and `paths.py` (the existing append-only logs, `doing.jsonl` and the per-session `events/`, the shape to follow); the places where the home witnesses the first kinds: a recorded precheck result (`cadence.py`), a person's press such as a team's **Apply** (§4.5a *flow changed — Apply*), and mail (`mail.py`, `agent_mail.py`); ledgerboard's `docs/plans/target-design.md` §4.2 (*Later: `host-log`*) and §4.4 (*Who runs what*)

**Ask:** Is the event model in ledgerboard's target design agreed (event gates checked only by machine, `host-log` among the checks), so this design can run? Go.

**Why:** an entry that waits on an event the home itself sees ("the test fails again in a precheck", "Paul's next Apply of dc-grind", "a session's `ao msg`") is written today as a `**Waits:** event — …` line and is never resolved. Nothing records whether the event happened, so the entry waits until a session happens to notice and edit the line, and in practice it waits for good. Ledgerboard's target design makes every event gate a mechanical check that the host runs (§4); it names three checks against the forge and files (`pr-merged`, `file-contains`, `ref-includes`) and leaves a fourth, `host-log <kind> "<text>" [times N]`, for later because ShiftLead keeps no such log. By that design's count about 3 of its 23 current waits need it. Without the log those waits become an `until <date>` plus a re-check entry, which is a guess on a date in place of the event.

**Fix:** design first, once Paul says go, for the long-term shape (the gate and check of ledgerboard's design), not for how waits are written today:
- **The log:** the home appends `{at, kind, text}` records of what it witnesses, append-only, home-owned and replicated or forwarded as §4.4a says for home state. The kinds are ShiftLead's vocabulary (to start: `precheck-fail`, `press`, `msg`), declared in one place, with what `text` carries for each. The round also decides retention.
- **The query:** an RPC and an `ao` read that answer whether there are at least N records of a kind whose text matches, since a date (`times` default 1; `since` given by the caller).
- **The consumer half:** where ShiftLead runs a ledger's event checks (ledgerboard's §4.4: every sweep, `events` passed to `pickable()`, a tool PR that lifts the gate with a `gate lifted` Log line citing the record), `check: host-log <kind> "<text>" [times N]` is answered from the query, with `since` the date the gate was added. The check's syntax is ledgerboard's (its TD-012, part of TD-010), so the build that wires it waits on that release.
- Done when the design says all of this, a build entry is filed for each part with `Part of: TD-1295`, and the log, the query and the check run on the live install.
