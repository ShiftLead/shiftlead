## TD-2315: A login question raised by a subagent that died stays on the card after the person logs in

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-26
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** 0084d86d28be43faa0cb72ef3457403a

**Why:** On 2026-11-26 the Claude login ran out at 17:30Z. In designer-ao-1 a background subagent (a2795c9cf9acaf0c8) died on it, and its `StopFailure` reached the hook with the subagent's `agent_id`, so the record took the question "Claude Code wants a login: Login reached its time limit" as that subagent's own open prompt. The person logged in and typed "continue" at 18:01Z; the session then ran for forty minutes (prompts, tools, three more subagents, a push), and its card still read *needs you* with the login question, since 17:30:33Z. Only an event of the asking thread ends a subagent's question, and a subagent that died on an API error sends none: no `SubagentStop` came either, so the record still counts it (`subagents: 1`, its id listed) and its count never reaches zero. The main thread's states went beneath the prompt (`kept`), as designed. The two grinders, whose main turns ended on the same error, cleared at their next prompt.

**Location:** design 4.2; adapters/claude_code/hook.py _stop_failure; agent_tick.py _apply_event

**Fix:** Design 4.2 first, in the same PR (the `StopFailure` row, the `SubagentStart`/`SubagentStop` row and *A subagent's prompt can end in three ways*). A subagent's `StopFailure` never writes the main thread's state: today any code of it does (an account's error a question tagged to the subagent, `rate_limit` the whole record `limited`, any other code `idle`). An account's error (a login, a billing stop) is the whole session's question whichever thread reports it, since the login is the session's: file it as the main thread's question, so the next main-thread prompt or tool ends it as it does today for a main turn. And a subagent whose turn ended on a `StopFailure` is over: count it down as a `SubagentStop` does, so the record does not hold a dead subagent's id until the next start. The event's one `subagent` field cannot both be left off the question and name the subagent to count down, so the adapter hands the id on in a field of its own that the core reads as the count-down's, a neutral name and no tool's (design 4.3).

**Done when:** A test feeds a `StopFailure` with `error: authentication_failed` and an `agent_id`, then a main-thread `UserPromptSubmit`: the record reads working with no open prompt, and the subagent is no longer counted. With a second subagent still counted, the first one's `StopFailure` counts down only itself and ends no prompt of the other. A subagent's `StopFailure` with `rate_limit`, and with another code, leaves the main thread's state as it was. The same events with no `agent_id` read as today.
