**Why:** Every session ShiftLead starts pays to read its opening context: Claude Code's system prompt, the repo's CLAUDE.md and AGENTS.md, the session-start hook's output, the member's brief and primer, and the mail it is handed. The API's prompt cache is keyed by content, not by session: a request whose opening bytes match an entry already written in the same workspace reads it at a tenth of the input price or less (Opus 5.5: $0.20 per MTok against $4), and every read keeps it alive (5 minutes by default, 1 hour on the longer TTL). The match stops at the first byte that differs, so one volatile item early in the context — a date, a time, an overdue count (*(5d overdue)*), a session's own name or worktree path, a git status snapshot — makes everything after it a fresh write for every session, every day. TD-1529 (td-max) starts more sessions of the same line or seat from the same brief, and each one pays this cold read; the more of that context two members share byte for byte, the less an extra costs (Paul, 2026-11-07: *if a date or other frequently changing item is used, list it as late as possible in the prompts*).

**Ask:** Will you let TD-1551's design, which files no reorder of what a started member reads, since no first request reads past Claude Code's static opening, and files one build (TD-1651, a measuring script, a print-mode trial of Claude Code's dynamic-sections flag, adoption at launch only on a rise, and a re-check that can take it out), go to its build after four review rounds ended at the cap with every build-changing fix read, or buy one more round, or hold it with a note?

**Design PR:** #3418

**Fix:** Examine first, then file builds. Inventory, in the order a member's model receives it, everything ShiftLead and agent-cadence put in front of a session it starts: the start prompt and brief (`sessionorc/brief.py`, `docs/briefs/`, the flow's brief), the primer (`docs/briefs/techlead-context.md`), the session-start hook's output (`agent-cadence hook session-start`: due items with their overdue counts, the cadence layer), the mail envelope a seat is handed (`ao inbox`), and the adapter's launch flags (`adapters/claude_code`). For each part, say:
- whether it is the same for every member of a line or seat, the same for every session in the repo, or different per session or per day, and what makes it differ (a date, a relative age, a name, a path, a count, an unsorted list);
- where in the context it lands, and so which shared parts it puts after itself.

Then propose the order and the wording that keep the largest shared opening first and every volatile item last (or out: a relative age can be a date the session computes, a list can be sorted), and how to measure it — the `cache_read_input_tokens` a member's first turns report, before and after, from the session's transcript usage. What Claude Code itself puts first (its system prompt's environment section: cwd, git status, date) is outside ShiftLead's reach; say how much of the opening it decides and whether a launch option changes it. Changes to agent-cadence's hook go upstream as an agent-cadence entry (filed with `ao td add --repo agent-cadence`, design §4.7 *Entries*, TD-1544). File each change as a build with `Part of:` this entry.
