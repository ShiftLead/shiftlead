## TD-1346: Build the Settings page's Teams **schedule** field — a switch, a profile pick and a window pick, the *starts* line beside them

**Priority:** Low
**Type:** feature
**Added:** 2026-11-03 (the designer, from TD-1344's design)
**Owner:** grinder
**Kind:** build
**Status:** Open
**Part of:** TD-1344
**Location:** `src/shiftlead/ui/templates/settings.html` (the team card's **schedule** row, and `info_teams`), `src/shiftlead/ui/settings_page.py` (`team_cards`: the rule, the `starts` line, the profile and window choices from the usage readings `usage_cards` already reads), `src/sessionorc/agent_settings.py` (`rpc_settings`: the optional `profiles` argument and its `labels` answer — a held path, read by the techlead seat), `src/shiftlead/ui/app.py` (the Settings page's `read("settings")`, which passes the profile names — the `profiles.yml` load moves ahead of the view's `asyncio.gather`, its malformed-file note still reaching the page's notes, the rest of `settings_files` staying on its thread, so the six RPCs still go together (§4.5 *Page loads*, TD-884); the team card's Save route, its body docstring and its 400 text *send until, reserve, on_work, balance or flow*, which gains `schedule`), `src/shiftlead/ui/static/app.js` (the switch, the window pick redrawn on a profile pick), `src/shiftlead/ui/help.py` and design §4.5a's help list.

**Why:** a person sets a team's schedule only from a terminal (`ao schedule`); the Settings page draws the field disabled (*not built — TD-133*).

**Fix:** as design §4.5a row *Settings page: Teams* (**schedule**) and §4.5 screen 8 say, mockup `docs/mockups/Settings.dc.html` (shot `docs/mockups/reviews/2026-11-03-td1344-settings-schedule.png`):
1. The row: a switch *start at a reset*, a **profile** pick (every profile `profiles.yml` defines) and a **window** pick: the labels of `_gate_reading(profile)` — its own reading, else its account's (TD-456), the windows `set_settings` checks a label against — in the reading's order, never the Usage card's reserve-only rows. A metered profile is drawn in the profile pick disabled, with the row's reason as its title (`_gate_reading` gives a metered profile only its own spend reading, never an account's, and the spend pass keeps it only while a session runs under it); a standing rule on one keeps it selected until moved. The page holds them for **every** profile `profiles.yml` defines through the `settings` read: it takes an optional `profiles` argument, the profile names the client read from `profiles.yml` (the host agent reads no profile list, `agent_common._usage_key`), and answers a `labels` map, each name to the labels of `_gate_reading(name)` — the very check `_schedule_window_known` makes — leaving the `gate` read the Usage card consumes as it is. Whether a profile is metered is the client's own `p.billing`, not the map's, and `labels` is never consulted for a metered profile: a standing metered rule's window is drawn as its own label in a fixed option. `profiles` absent answers no `labels` key; a value that is not a list of strings is ignored, as absent. The default profile is the one `profile_cards(profiles, default)` is given; where every profile is metered the switch is disabled with the reason; off, both picks disabled; turned on with no rule, `profiles.yml`'s default (else, that one metered, the first offered profile) and its reading's first label. A profile pick redraws the window pick client-side from the readings the page holds, keeping the label where the new profile reports it, else the first. A profile with no labels takes the label in a text field, noted *no reading of <profile> yet — the label is not checked*, drawn from those labels (after the reload the reply's `unchecked` is gone); an empty field is the RPC's *window is needed*, in place. A standing rule whose profile is no longer defined is drawn with that profile as its own option marked *(not reported)* and the text field; one whose label a defined profile's reading lacks keeps that label as its own option, marked the same; either is kept until moved. While off, the picks keep their values. *Moved* compares the whole rule — `{start, profile, window}` or null — with a `data-was` JSON of the drawn one, as **balance** does (`app.js`), so an unmoved Save, or off with no rule standing, writes nothing. Name the window control `schedule_window` in both its forms.
2. Beside it, the team card's *starts* words from the `settings` read's `starts` (`uiconf.team_starts`, server-side, shared, not copied): *starts at the reset · Thu 07:00*, *· held for a node's link*, *· no reading yet*; *no schedule* while off.
3. Save writes `set_settings {teams: {<team>: {schedule: {start: reset, profile, window}}}}` only when the row moved, and `schedule: null` when the switch went off; a refusal (a label the profile does not report) is drawn in place in the RPC's words; a successful Save reloads the page, as the Teams card's other fields do (`app.js`), so the line is drawn again from the `settings` read. Cancel puts the drawn values back (§4.5a *Save / Cancel on a card*): `form.reset()` does not rebuild a redrawn window control, so the redraw runs again on the form's `reset` event, and the dirty test sees the same element set. Until the next tick the line reads the reset from the reading, not `schedule_next` (`_schedule_starts`).
4. The disabled field and its *not built — TD-133* note go; `info_teams` keeps naming the schedule. §4.5a's row loses its *until then drawn disabled* clause, §4.5 screen 8 its *drawn disabled* clause, and §6 *Schedule*'s two *not yet built* notes say built, with a history line under §4.5a.
5. The help list (design §4.5a and `help.py`, together — `tests/test_help.py` holds them word for word) gains, after **balance** — the paragraph and its slug `schedule` in `help.py`'s Settings topics tuple, in the same order — : **schedule** (Settings page: Teams) — Starts this team again when a usage window resets: pick the profile and the window, such as grind's week, and at that reset the home starts the members a person last started, with the briefs they last read. A team that is running, or that you stopped, is left alone, and a reset found more than an hour late starts nothing. Turn it off and the team waits for Start, or for its work if you set that. ao schedule sets the same rule.

**Done when** the Settings page's Teams card sets and clears a team's schedule — refused and confirmed as `ao schedule` is, the *starts* line beside it matching `ao schedule`'s listing — tests cover the `settings` read's `labels` (given, absent, malformed) and the write (set, clear, unmoved Save writes nothing, a refused label shown in place) and the profile pick's window redraw, Cancel after a profile pick, a standing *(not reported)* rule surviving an unmoved Save, and a scratch-home look (`scripts/look_home.py`) shows the card, its shot in the PR.
