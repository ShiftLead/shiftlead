## TD-2053: Audits on a clock, and board answers and pull requests nobody holds as built-in seats

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-22
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** 039acbf17e084b7f8c7d5027904011fc
**Blocked by:** TD-2050, TD-2051, TD-2052, TD-2066
**Part of:** TD-1954

**Why:** The design replaces the auditor seats with audits a flow lists, each started on a clock with its own brief, and turns two free-pick work orders, a decided board line and a pull request nobody holds, into built-in seats, since a format-3 flow has no lane.

**Ask:** Should the builders start on audits that run on a clock and the two new built-in seats?

**Fix:** Build design §4.9c *Audits start on a clock* and *Two of the five are not seats today*: an audit's run record, its lease and its count from a merge commit, its three outcomes, the plain board line for an audit's other; a job for each decided board line and each unheld pull request, as design §4.9d *How each one runs* gives it: a job record on `shiftlead/state` keyed `board-<item id>` or `pr-<number>`, offered oldest first with one session at a time for each of the two seats in a repo, on the seat's model and the built-in set's login, its holder lost, silent and offered again as an entry's is; `ao stage end` from a job's session takes `work-pushed` (checked as a build stage's but with no entry archived, and for a board answer that the pull request closes the decided line, for an unheld pull request that it is the one given) and `other`; after `work-pushed` the record stands in its team's flow as a record of the stage that takes `other` entries would, so the flow's review stages read the pull request and the home merges, a move back to that stage starting a fresh job session, and a move the flow sends to any other build or design stage sending the job to the person; each seat runs one job session at a time in a repo, records already begun before new objects; a job that goes to the person puts one plain line on the board, keeps its id as `person_line` and waits, Reconcile clearing the wait and the counts once that line is closed; a job's holder holds a lease on its record as an audit's run does; an object that comes back after its record closed is a new job; a merge only the person can cure goes to the person, who merges by hand or closes the line; and a board answer's pull request closed unmerged sends the job to the person; policy rule 13 reads a decided board line against its job record, as design §4.9e *What decides which shape runs* gives it; Reconcile closes a job whose object is gone and gives a record whose team is no longer started to the repo's first started team. This entry also owns the tick's sixth act, start an audit, the checks `ao stage end` makes on an audit's outcomes (`findings-filed`, `nothing-found`, `other`), and the holder of an audit's run. The store for audit run records is TD-2048's; this entry builds what uses it: the run record's writes, its lease and its count. Once an audit's run records exist, the team page's *Beside the path* also draws each audit's next clock, when it next comes round (design §4.9d *The page*; TD-2061 drew the audits with their clocks and left this to the run records).

**Done when:** An audit starts when its clock comes round and never while its last run holds its lease; a lost run is offered again once. The board-answers seat never takes a decided line whose Context is an entry whose record waits on the person; held, for a pull request, means any record names it. Both seats start only while one of the repo's teams is started, on the model and the logins of the built-in set the repo uses (design §4.9d *The built-in seats and their page*), and wait where no login of that set is usable. `ao stage end` from an audit's session takes `findings-filed` only when it names at least one entry filed in the run, and `nothing-found` and `other` only with a reason; an `other` puts one plain line on the board, of the form the gate's append class accepts, naming the audit and the run. A decided board line gets one job record and one session; a second decided line, and a first job sent back by a review, each wait while a job session of the seat is live, the job sent back going first; a lost job session is offered again once and the second loss puts one plain line on the board naming the seat, the line and the reason; closing that line offers the job afresh. A job's `work-pushed` is refused while its pull request does not close the decided line; accepted, the record moves to the destination the team's flow gives `work-pushed` from the stage that takes `other` entries, a review stage's `changes-wanted` back to that stage starts a fresh job session on the seat's model, and `ship` to `merge` has the home merge. A job whose board line is closed by hand, or whose pull request merges or closes, has its record closed and its session ended. A pull request a job record names is not offered to the other seat and is no entry's work. A job whose flow sends `work-pushed` to a second build stage goes to the person. A job's `work-pushed` is accepted with no entry archived. A board answer whose pull request was closed by hand, its line still decided, goes to the person and is not offered again until that line of the home's is closed; a line decided again after its job closed gets a new job. The stuck-work pass reports a decided board line with no job record past its wait, naming why, and none that a job's holder is working.
