The person asked for a new entry (shiftlead's design §4.9 *Add an entry to the ledger*): its repo is {repo}, its ledger {ledger}, its Type {type} and its Priority {priority}. Their first message holds their words for it. In an Add entry session, whose first message opens with these values, where it has no values block, or a value is missing or unreadable, ask the person for the repo, the Type and the Priority rather than guess, and take the ledger from that repo's `.shiftlead.yml` (`ledger:`). Turn them into one entry, asking the person only for what the words and the repo do not settle: which of two readings is meant, what *done* is.

- **Read before you write**: the ledger's preamble and template (its first entry), and its three newest entries, for the shape and the header lines the file asks for — **Priority**, **Type**, **Added**, the preamble's own lines (an owner, a kind, where it declares them; what blocks it as `**Blocked by:**`, never a written *pickable*; the one parent it is a part of — a design's build, a feature's subtask — as `**Part of:** TD-n`, after **Kind**, the parent in this same ledger), **Status**, **Location**, **Why**, **Fix** — and the code and the design the words touch, so **Location** names files and sections and **Why** says the harm or the value, not only the symptom (cadence §2.3).
- **Priority**: `**Priority:**` followed by {priority} — the person's pick, unless their words name another in so many words (*Low priority.*): then the words', and your outcome says you followed them over the pick. Never ask the person a priority they picked.
- **Type**: `**Type:**` followed by {type}, after **Priority** (cadence §2.11). A feature's entry is the short one: its design round does the fleshing out.
- **Text the person reads is checked at its writer** (design §4.10 *Text a person reads is checked at its writer*): an `ask` or a `steer` to the person, a question passed up to them, a board `decide` or `act` line, and an entry's `**Ask:**`, `**Answers:**` and title catch the person up first, and their writers refuse what breaks the rules a check can read, so meet them before you send. The sentence (a message's first paragraph, a board line's bold head, an `**Ask:**`) is one plain sentence of at most 25 words with no code — no path, file name, call, option, commit or `snake_case` name — and a question ends in `?`. Every answer, and a `steer`'s `--default`, is `<label> — <consequence>` and says who acts in its consequence (*I'll…*, *you…*, *a session…*): *Pinned, run it again* is refused, *Pinned — a session runs it again* passes; the recommended answer comes first, marked `(default)`. The second paragraph on is the context, in plain words — what the named thing is for and why it matters, a coined term explained or left out, files and functions behind the link — and it need not name the larger work, which the Queue card's head already shows. An entry's title is its plain-words summary, with no code, no id and no internal label (*B4*, *slice*, *F123*), which belong in its body. A gate's answers are *Yes — a session lifts the gate and the entry can be picked | Not yet — nobody picks the entry until you say*, and the end-of-rounds item's *Go — the grinders build it | One more round — a session runs one more review round, then asks again | Hold: <note> — a session revises the design as your note says*. **Not clear**, the person's answer on any of these but a look or a question rerouted to them, sends the item back to its writer to rewrite (design §4.10 *Text a person reads is checked at its writer*, rule 6): a question is closed and its asker noted to rewrite it and ask again; a board line or an entry is decided *Not clear*, a work order to rewrite it; and each press is counted in the feedback review.
- **The number** is `ao td reserve`'s: the home takes the next free id, over main, its archive and every open PR, from the counter on origin and records it, so nobody else is given it (design §4.4 *A ledger entry's id is handed out by the home*). Where `ao` is not there or refuses, run `ledger.py new` below without `--id`: it takes one from the same counter itself (cadence §2.10). Never number by hand. If you are an interactive session filing an entry the person is still deciding, file it with `ledger.py new` as below, giving the block and an `**Ask:**` saying what lets it go in the same write (`--blocked-by "decision (<person>)" --ask <file>`, the Ask file is one line, the question alone, and any context goes in `--context <file>`, which writes a `**Context:**` section right after it), and a `decide` item on the repo's board whose Context is exactly `TD-n decision (<person>)` (`agent-cadence run board_edit.py add --kind decide --context … --answer … --lift …`, as design §4.4 *What waits on the person* gives it; the merge gate refuses a decision with no board item), all in the same PR — `new` refuses a `decision` block with no `**Ask:**`, and an `**Ask:**` with no `decision` block (`<person>` is the ledger's `Fields:` person word): no lane takes it until they answer (design §4.4 *An entry can land held*).
- **Team**: where the ledger's `Fields:` line names two or more teams in its `Team` vocabulary, give `--field Team=<team>`, which writes `**Team:** <team>` — never where it names fewer, since an undeclared field fails `ledger.py --check --since` (design §4.4 *An entry names its team*). The team is your own unless the work is plainly another's; a designer's builds take the designed entry's; a handed entry the `entry.team` it carries; else the team the words and the location point to. **Filled `by: tag`** (your fill's line reads *you are filled for: tag — TD-801, TD-802*): tag every listed id in one ledger PR (`agent-cadence run ledger.py set TD-n --field Team=<team>` on each), landed as below; where two readings stand, open the PR with your choice and `steer` the person with it as `--default`.
- **Added** names both hands: `--added "<date> (<the person>, through Add entry; drafted by <your session>)"`, the date from `date`, never guessed.
- **File it with the helper**, never a file typed (design §4.4 *A session writes the ledger and the board only through the helpers*): `agent-cadence run ledger.py new --id TD-n` under the id `ao td reserve` gave, the header fields as its flags — `--title`, `--priority`, `--type`, `--added`, `--owner` and `--kind` where the preamble declares them, `--part-of`, `--blocked-by` (a wait on a date as a gate there, `until YYYY-MM-DD`, never a `Waits:` line, which is retired), `--location`, `--field Team=…` where the `Fields:` line declares it, `--status` only when not Open — and `--why`, `--fix` and `--done-when` from files you write in your scratch directory (`$SHIFTLEAD_SCRATCH`) (`-` reads one from standard input, at most one). It writes the take's `**Id take:**` itself, judges the entry as the cadence check's `ledger` row will and writes nothing it refuses; it commits nothing, so commit the path it prints in your PR. A wait on an event a check can see is added after `new`, since `set` and `new` refuse an event gate with no section: its section first (`ledger.py edit TD-n --section "Event (<name>)" --from <file>`, one line saying it in plain words and one `check:` line), then the gate (`ledger.py set TD-n --blocked-by "<the ids>, event (<name>)"`). A later change to it is `ledger.py set|note|edit`, never typed.
- **How it lands**, as every ledger change does (cadence §4): a branch off `origin/<default>`, a PR, the docs fact-check against the repo, the gate, a squash merge through cadence step 5's line, typed whole as one command, so its squash ends in `Merged-by:`. The person does not approve the entry before it is filed: an entry that reads wrong is a line's edit afterwards. A filing PR you mean to leave open past a day is a draft, or a lane takes it (design §4.4 *A filing PR nobody holds is a work order*).
