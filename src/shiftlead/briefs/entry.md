The person asked for a new entry in the ledger of {repo}: {ledger}, with Type {type} and Priority {priority} (shiftlead's design §4.9 *Add an entry to the ledger*). Their first message is their words for it. Turn them into one entry, asking the person only for what the words and the repo do not settle: which of two readings is meant, what *done* is.

- **Read before you write**: the ledger's preamble and template (its first entry), and its three newest entries, for the shape and the header lines the file asks for — **Priority**, **Type**, **Added**, the preamble's own lines (an owner, a kind, where it declares them; what blocks it as `**Blocked by:**`, never a written *pickable*; the one parent it is a part of — a design's build, a feature's subtask — as `**Part of:** TD-n`, after **Kind**, the parent in this same ledger), **Status**, **Location**, **Why**, **Fix** — and the code and the design the words touch, so **Location** names files and sections and **Why** says the harm or the value, not only the symptom (cadence §2.3).
- **Priority**: `**Priority:** {priority}` — the person's pick, unless their words name another in so many words (*Low priority.*): then the words', and your outcome says you followed them over the pick. Never ask the person a priority.
- **Type**: `**Type:** {type}` after **Priority** (cadence §2.11). A feature's entry is the short one: its design round does the fleshing out.
- **The number** is `ao td reserve`'s: the home takes the next free id, over main, its archive and every open PR, from the counter on origin and records it, so nobody else is given it (design §4.4 *A ledger entry's id is handed out by the home*). Where `ao` is not there or refuses, run `ledger.py new` below without `--id`: it takes one from the same counter itself (cadence §2.10). Never number by hand. If you are an interactive session filing an entry the person is still deciding, file it with `ledger.py new` as below, then add an `**Ask:**` saying what lets it go (`ledger.py edit TD-n --section Ask --from <file>`) then the block (`ledger.py set TD-n --blocked-by "decision (<person>)"`), and a `decide` item on the repo's board whose Context is exactly `TD-n decision (<person>)` (`agent-cadence run board_edit.py add --kind decide --context … --answer … --lift …`, as design §4.4 *What waits on the person* gives it; the merge gate refuses a decision with no board item), all in the same PR — `new` refuses a `decision` block with no `**Ask:**`, and takes none (`<person>` is the ledger's `Fields:` person word): no lane takes it until they answer (design §4.4 *An entry can land held*).
- **Team**: where the ledger's `Fields:` line names two or more teams in its `Team` vocabulary, give `--field Team=<team>`, which writes `**Team:** <team>` — never where it names fewer, since an undeclared field fails `ledger.py --check --since` (design §4.4 *An entry names its team*). The team is your own unless the work is plainly another's; a designer's builds take the designed entry's; a handed entry the `entry.team` it carries; else the team the words and the location point to. **Filled `by: tag`** (your fill's line reads *you are filled for: tag — TD-801, TD-802*): tag every listed id in one ledger PR (`agent-cadence run ledger.py set TD-n --field Team=<team>` on each), landed as below; where two readings stand, open the PR with your choice and `steer` the person with it as `--default`.
- **Added** names both hands: `--added "<date> (<the person>, through Add entry; drafted by <your session>)"`, the date from `date`, never guessed.
- **File it with the helper**, never a file typed (design §4.4 *A session writes the ledger and the board only through the helpers*): `agent-cadence run ledger.py new --id TD-n` under the id `ao td reserve` gave, the header fields as its flags — `--title`, `--priority`, `--type`, `--added`, `--owner` and `--kind` where the preamble declares them, `--part-of`, `--blocked-by` (a wait on a date as a gate there, `until YYYY-MM-DD`, never a `Waits:` line, which is retired), `--location`, `--field Team=…` where the `Fields:` line declares it, `--status` only when not Open — and `--why`, `--fix` and `--done-when` from files you write in your scratch directory (`-` reads one from standard input, at most one). It writes the take's `**Id take:**` itself, judges the entry as the cadence check's `ledger` row will and writes nothing it refuses; it commits nothing, so commit the path it prints in your PR. A wait on an event a check can see is added after `new`, since `set` and `new` refuse an event gate with no section: its section first (`ledger.py edit TD-n --section "Event (<name>)" --from <file>`, one line saying it in plain words and one `check:` line), then the gate (`ledger.py set TD-n --blocked-by "<the ids>, event (<name>)"`). A later change to it is `ledger.py set|note|edit`, never typed.
- **How it lands**, as every ledger change does (cadence §4): a branch off `origin/<default>`, a PR, the docs fact-check against the repo, the gate, a squash merge. The person does not approve the entry before it is filed: an entry that reads wrong is a line's edit afterwards.
